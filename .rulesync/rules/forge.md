# Forge

Forge's design and procedures live in `nvim/contributing/forge/`, and this rule holds only the obligations those documents cannot enforce. Before changing Forge, find the task's row in the index at `nvim/contributing/forge/README.md` and read the procedure and architecture chapter it names. The README's "Keep documentation current" section defines which documents a change must update, and those updates belong to the same change.

- **Validation:** Inside Harness, run builds, tests, formatters, and linters only through configured checks, and configure missing coverage through the `harness-checks` skill. Outside Harness, follow `nvim/contributing/forge/building-and-testing.md`. Either way, finish every Forge code change, including Lua-only changes, with a passing `rust-build` after the final edits, because `cargo check` and test runs do not update the executable Neovim launches.
- **Interaction bugs:** Reproduce an interaction regression in an integration test that drives the Forge host with `MockProvider`, and confirm the failing assertion before fixing it.
- **No real-time waits:** Never make a test wait on the real clock for a timeout, deadline, or expiry to elapse. Such tests are slow and flaky. Test timeouts deterministically through a paused Tokio clock (`start_paused` with `advance`) or a mock at an existing production boundary, such as a mock provider that never answers. When neither reaches the timeout path, leave that path untested rather than adding a hook for it. Outer guards that bound a hung test remain allowed.
- **Bad states come from mocks:** Reach a failure state such as lock contention, SQLite busy, an expired deadline, channel saturation, or a slow or stuck process by pushing it directly through a mock or a paused clock at an existing boundary. Never create the real condition, because a test that manufactures real contention or volume is slow and its timing varies with machine load.
- **Lua tests jump to the behavior:** A Lua test reaches the state it verifies directly through mocks, then exercises only the behavior under test. Answer `forge.client` requests through `tests/support/mock_client.lua`, stub the module's collaborators with `stub.lua`, and replace external converters, processes, and clocks with a mock that returns fixed output, instead of driving the real host, a full planner turn, or an installed tool to get there. Launch the real Forge host or real Git only when their behavior is what the test verifies, and keep each such case to the one flow it checks; a case that spends most of its five seconds on setup belongs on mocks. A test covers its own module, so it never depends on the user's Neovim configuration: start a child with `-u NONE`, put only the module's dependencies on `runtimepath` with their default options, and send built-in keys such as `gk` rather than personal mappings. A test that passes only with someone's personal setup is a bad test.
- **No processes in Rust tests:** Rust tests never launch a shell, and launch `git` or another program only when that process is what the test verifies, such as process ownership, real Git object identity, or the `forge` binary over stdio. `CheckSupervisor` launches every check command as a real process, so Rust tests never run check commands; test check configuration, selection, and gating with no commands. Prepare fixture repositories without launching Git.
- **No test hooks in production types:** Never add `#[cfg(test)]` fields, methods, enum variants, or branches to production types to steer tests, such as forced expiry, scripted runners, injected failures, held barriers, instrumentation counters, or replaced capacities. Each one gives the test build a code path production never runs, so a test exercising it proves nothing about the shipped behavior. Any such hook requires the user's specific approval before it is added, and asking is the right move when a high-value behavior has no other way in. Inline `#[cfg(test)]` test modules and test-only fixture constructors that build ordinary production state are not hooks.
- **Test runner and duration:** Run Rust tests with `cargo nextest run --cargo-profile dev --locked`, never `cargo test`, except `cargo test --doc` for doctests. Each Rust test must finish in well under a second; nextest terminates any test at five seconds. Run Lua tests only with `nu .forge/checks/lua-tests.nu`, never a hand-written `nvim -l` command; the Neovim rule describes the unit and integration test layout and how to select tests, and `--lua` supplies setup for parameterized fixtures. The runner kills any test's process tree at five seconds. Fix or remove a slow test. A Rust suite may get a timeout exception in `nvim/rust/forge/.config/nextest.toml`, matched by binary or module, only when its shared slow cost is what it verifies, such as the real `forge` executable or a real Git view of the worktree, or when its tests guard high-value invariants that no faster test covers; the exception must state that reason, and a slow test that meets neither bar is deleted. Lua tests get no exceptions.
- **Flaky tests:** Fix or remove a flaky test. Never rerun it to measure or work around its flakiness.
- **Fixture directories:** Fixtures never create workspaces, data, or evidence inside the checkout, because a nested fixture repository surfaces in every later status, checkpoint, and Harness session of that checkout. Use `vim.fn.tempname()` for disposable state. Take retained evidence from `nvim/lua/forge/tests/support/evidence_directory.lua`, which places it under the OS temporary directory's `forge` subdirectory and removes it after a passing run. See "Place fixture workspaces" in `nvim/contributing/forge/editor-tests.md`.
- **Rust-to-Lua fixtures:** A Rust test never writes a file that a Lua test reads. Lua tests replay host payloads from recordings committed under `nvim/lua/forge/tests/fixtures/protocol/`, and the Rust test that produces a payload compares its output with the recording through `forge_recorded_fixtures::assert_matches_recording`. Any change to a payload the host sends to Lua must re-record and review the affected recordings, then rerun the Lua tests that read them, in the same change; see "Replay recorded host payloads" in `nvim/contributing/forge/editor-tests.md`.
- **Startup:** Forge startup launches the built executable and reports a missing one. Never add compilation, freshness checks, automatic rebuilds, or fallback executables to startup.
- **State compatibility:** Bump `storage::state::VERSION` for incompatible schema, session, or disposable-file contracts. Route all dependent state through `state/vN/`; never migrate sessions or require old editors to close before a new version starts. Keep user settings, configuration, permissions, and model preferences outside `state/`, and try to migrate settings gracefully with explicit failure reporting. `ForgeHistoryClear` stops its host and attempts every version under `state/`, deleting unlocked versions while preserving and reporting whole locked versions. Every state owner must retain a version lease; lock files live outside deletable directories.
- **Shared controls:** Reuse the existing control, picker field, or status command spec before adding a view-specific one, and extend the shared component when it lacks a capability. Derive mappings, hints, and `?` help from the shared command spec in `init.lua`, never from hardcoded key text.
- **Diff hunks:** Actions that write state or call Git, such as staging, comments, and viewed state, use raw zero-context hunks. Merged display hunks are presentation only, so expand `raw_hunks` before any such action.
- **`init.lua` locals:** `init.lua` sits at Lua's limit of 200 locals per chunk. Attach new file-scope helpers to the module table instead of declaring them `local`.
- **Cleanup:** Delete any `nvim.log` that headless Neovim creates before finishing a task.
