# Project checks

Tool-started checks report completion through a Rust-owned internal inbox. `CheckOwnerRuns` retains each admitted run's original invocation receipt; `CheckResults` groups successful results for the same exchange until every outstanding run has been collected, then admits one delivery containing those typed `check_result` elements. Collected failures bypass this wait. A failed command in an unfinished run is reported once with `complete="false"`; the final result follows after collection. The delivery carries command outcomes, captured source identities when available, diagnostic locations and severities, test counts, and a reference to complete logs. Evidence from one source snapshot does not validate later edits.

Check finalization retains a command's completed result even if later bookkeeping fails. The supervisor catches unexpected worker panics and includes their text in the execution error, so a passing test result cannot conceal the cause of a failed run. Synchronous Git commands used by checkpoint verification cross the runtime-safe command boundary described in [Git repositories](git-repositories.md#commands).

Compact check status uses the retained run-level execution error when no failed command supplies a cause. This keeps post-command checkpoint or persistence failures visible even when every command exited successfully.

The operation `check-result:<run-id>` and its immutable admission receipt live in the separate `check_inbox_*` tables. Admission and its receipt commit together; restart recovery retains accepted and uncertain provider-delivery evidence and retries only proven unsent work. The exchange event loop advances delivery directly, independently of the editor and user-queue suspension, edits, or ordering. Completed results require process collection even if a terminal result was saved earlier. Results can be delivered while another check runs; approvals, lifecycle transitions, and provider availability still gate dispatch. Cancelled or retired exchanges do not resume. Native steering targets only the original exchange; otherwise delivery waits for an idle provider and continues that exchange through the existing provider submission journal. Automatic completion and plan verification retain their own completion gates and do not emit a second tool-result message.

Pending result delivery remains internal, with no status section or entry in the editable user queue or user-steering section. Info-level events `check_result.collected`, `admitted`, `deferred`, `dispatched`, `accepted`, `delivery_changed`, `settled`, `recovered`, and `retired` identify the session and available exchange, run, input, and submission identities. Deferral logs occur when the input or reason changes, not on every event-loop pass. Diagnostic contents are excluded. Delivery errors have their own error-level events.

Agents normally start a check and continue independent work or end their turn while waiting. `check_status` remains available for explicit inspection, recovery, and cancellation confirmation; `check_detail` supplies logs and further result pages. A check's saved output holds what its command printed on standard output and standard error. When a command printed nothing, every surface that reports the failure says so instead of naming an empty log, which the model read as output Harness had lost: plan findings (`CommandCheck::findings`) state the exit status and `The command printed nothing on standard output or standard error.`, a repair turn's `CheckFailure` carries no `log`, and `check_detail` adds a `note` beside the command's exit status. A script adapter that consumes its tool's output, as a formatter adapter turning a file list into `file` events does, reports that outcome through its structured result, which findings list per file. The fixed Harness instructions classify check output as evidence rather than execution authority.

A check result that no longer matches the code, or a gate that passes because nothing ran, gives false confidence that a change works. Harness therefore records what ran against which inputs, reuses a result only when those inputs are unchanged, and reports skipped checks as Not run rather than Passed.

[Extending project checks](../extending-project-checks.md) covers adding adapters and custom inputs, and [Timeline](timeline.md#check-results) covers how results appear.

## Definitions

Checks live in the `checks` section of `.forge.json` and are edited through `check_definition_edit` with the `harness-checks` skill. Each definition has an identity, an automatic `trigger`, a required category (`typecheck`, `test`, `format`, `lint`, `build`, or `custom`), a directory, a runner, and prerequisites. A runner is either a command with typed named inputs or a structured adapter. The former `check` category is rejected with an error naming its replacement; configuration is never rewritten on load. An absent section blocks plan submission, and an explicitly empty one is valid.

Test adapters discover item IDs and report planned cases, progress, output, and terminal results through the common test contract. The compiled-in adapter catalog states which adapters and categories this build supports. Typecheck, test, format, lint, and build checks require an adapter; only `custom` permits a plain command. Invalid combinations name the check and direct callers to `check_definition_list`. Both saved configuration and internally assembled configuration pass this validation.

The Lua adapter injects a five-second deadline through its shared runner. An outer watchdog observes bootstrap case-start records independently of Neovim's event loop and terminates an expired process tree. Crashed processes receive terminal case failures from the adapter. Completed worker jobs retire themselves: synchronous `job kill` holds Nushell's global jobs mutex while invoking process termination, so using it for routine cleanup can block every worker's watchdog. Windows timeout cleanup uses a narrow native process-termination adapter instead of `taskkill`.

Check configuration approval compares parsed definitions with normalized defaults. Each changed check has a field-level diff; argument arrays retain their boundaries and order, and nested adapter options and custom inputs remain fully qualified. Added and removed checks show their complete definitions. The review retains the exact raw configuration diff and each captured helper diff in separate sections. Markdown fences exceed backtick runs in their contents so helper source cannot terminate a section. Approval still binds to the original configuration revision and helper digests, and publication revalidates those identities.

The approval picker opens changed checks and initially collapses raw configuration and helper sections. Its section rows expand without selecting an approval decision. The shared picker renders styled child content through its existing wrapping and viewport projection; `check_review.lua` supplies rows from the shared `diff_component` renderer. The retained approval detail remains a string, so the disposable-state format does not change. Earlier plain-text reviews remain readable.

The Lua script adapter partitions cases by the `-- requires-forge-host` marker immediately above a top-level case declaration. `lua-test` selects unmarked cases without a build prerequisite; `lua-host-test` selects marked cases and depends on `rust-build`. Static and exact discovery expose disjoint case inventories with unchanged case IDs, including mixed integration files. The unpartitioned manual runner retains the complete inventory. The `lua-adapter-test` check verifies partitioning and protocol behavior without building Forge.

The built-in `rust_nextest` adapter owns Cargo metadata, Rust module discovery, filter compilation, and native nextest event translation. An optional `nextest_command` routes the version probe, exact listing, and execution through a repository launcher. Static discovery uses Cargo directly. Exact discovery and execution share Cargo and nextest profile options. Native event names that collide across target kinds require separate binary runs. Metadata and source indexes live only for one operation. Like script adapters, nextest results currently remain excluded from automatic evidence reuse until their complete toolchain and dependency identity is implemented.

Nextest list and run commands forward Cargo JSON alongside their native output. The adapter consumes Cargo records before decoding inventories or test events and publishes `Built <package>` for non-cached artifacts through the test phase message. Compiler diagnostics retain Cargo's stderr rendering. Cached artifacts and build-script records do not replace the latest compiled package; artifact completion does not claim which compilation is currently active. The first test event changes the phase to Run and clears the build message. Phase messages are optional in saved progress, so existing check records remain readable without migrating disposable state.

Typecheck, lint, and build adapters use the diagnostic contract. Format adapters use per-file outcomes and distinguish verification from source-changing apply operations. The supervisor retains each category's result and progress in tagged enums, so one category cannot be mistaken for another after restoration. Diagnostic severity, target or file coverage, protocol completion, and process exit independently determine success. Error counts include diagnostics omitted by retention limits. Source locations, build artifacts, and formatting diffs remain available in result pages and the timeline.

The repository's Cargo adapter captures stdout, stderr, and the process exit code together before translating Cargo JSON into diagnostic and artifact events. An ambient shell exit code can belong to a different pipeline, so it never determines Cargo success. This adapter publishes its events after process completion.

Explicit `check_run` requests with `apply: true` dispatch format apply or lint fix. Ordinary chat permits both operations; plan Verify permits read-only checks and Resolve permits fixes. Apply preflight validates every named category and rejects implicit source-changing prerequisites. Commands run serially, and a failed selected prerequisite or fix stops the batch. Before launching a fix, the supervisor durably records its source snapshot and whole-check verification requirement. Partial edits survive failure and cancellation. The current reservation excludes conflicting checks across session data roots and holds same-session delegated-agent admission; coordination with arbitrary provider writers and surviving-process recovery remain work in progress. The full mutation contract in `checks-overhaul.md` is not yet satisfied.

The verification ledger persists `prepared`, `pending`, and `satisfied` states separately from command history. Preparation returns an unlaunched handle; crossing the durable launch boundary consumes it and returns a launched handle. Cancellation before that boundary can retire the provisional requirement. After collection, a sole valid unsupported result can retire it only when before/after source identities match and the result has been saved. Retirement restores earlier verification states invalidated by this attempt; stale source identities still remain unresolved. Process or storage failures retain the requirement, and a crash without a live proof handle treats prepared state conservatively as pending work. Source identities compare working-content digests and file modes, so committing already verified bytes does not reopen an obligation. A real content change anywhere in the captured workspace still invalidates whole-workspace verification.

Verification compares the originating check's ID, category, directory, runner, prerequisite IDs, and helper content. Selection settings and display labels are excluded because required verification always selects the whole check. Purpose belongs to each admitted command; satisfaction additionally requires Verify purpose. Custom preparation policy is retained in `CheckOperation.prepare`, as part of runner identity. Configured or task disabling prevents satisfaction; after re-enabling, a fresh passing run can satisfy the original obligation. A changed execution field or helper keeps it unresolved. The ledger uses version 5 under disposable state version 45; earlier ledgers are rejected without modification.

Repository lock files live outside session state: `%LOCALAPPDATA%/forge/repository-reservations` on Windows and `$HOME/Library/Application Support/forge/repository-reservations` on macOS. `FORGE_REPOSITORY_RESERVATIONS_DIR` overrides that directory for isolated tests and must be absolute; all participating test hosts inherit the same value. Keys use filesystem-canonical repository paths, with Windows case normalization. Independent clones have separate locks. Lock files remain in place after release, because deleting them could let two owners lock different files for the same repository. Hosts built before this shared namespace do not participate in it.

`repository_access/owner.rs` separates retained repository ownership from its execution slot. Admission takes a short exclusive gate before trying the shared or exclusive source lock; neither waits for another owner. An opaque scope may lend one slot to a descendant while its parent is idle. A read borrower cannot become a writer, context clones cannot admit concurrent borrowers, and retiring an ancestor revokes descendants without releasing their retained source lock. Scopes hold weak references, so an unused context cannot keep a completed owner alive. Named contention, expired-scope, wrong-repository, and read-only failures remain distinct from filesystem failures.

The gate validates `repository_access/journal.rs` records before granting access. Journal version 1 lives in `<repository-key>.operations/` beside the stable source and admission locks, outside disposable session state. Each operation records a unique owner nonce, PID for diagnostics, access mode, lifecycle phase, and last admitted borrower chain. A separate kernel-held lease identifies a live owner; PID equality or an age threshold does not establish liveness. Matching-version records with missing or contradictory fields, unknown versions, and abandoned started operations reject admission with their actual cause and record path. An abandoned prepared operation can be retired under exclusive source access; a collected record is pruned only after its owner releases the lease. Terminal publication failures retain the source lock and lease in memory, and a subsequent admission retries that publication before continuing.

The journal currently records possible execution before granting its execution slot, but does not yet register individual child identities or provide a gated process launcher. Consequently, an abandoned started operation reports `repository_recovery_required` instead of automatically collecting its descendants. This prevents an OS-released lock from silently admitting conflicting work, but does not complete process-death recovery. Provider and delegated-agent lifetimes remain to be connected to the ownership protocol.

Forge uses a local `process-wrap` patch for cancellation-safe Tokio collection. One retained collector owns descendant waiting across cancelled or repeated calls; a cached root exit cannot bypass collection. On Windows, it queries the job's active-process count instead of interpreting any completion-port notification as completion. Collection errors remain errors on subsequent waits. The job reference retained by its collector is released when collection finishes or its child wrapper is abandoned, preserving kill-on-close behavior. The Unix collector still has upstream `waitpid` scope and does not prove that reparented or escaped descendants have exited. This normal-lifetime collection fix does not establish durable child registration or recovery after host death.

Windows shell and Git launchers create their kill-on-close job before spawning and pass it through `PROC_THREAD_ATTRIBUTE_JOB_LIST`. The job handle is not inheritable. This removes their separate suspended-spawn/assignment interval; it does not register the job in the repository journal. Abrupt-launcher-death coverage checks that a child exits after its launcher is forcibly terminated, separately from normal cancellation.

Owned Git checkpoint and revision reads disable fsmonitor for each invocation, as repository writes already do. A background monitor would otherwise remain in the owned process tree after Git exits and prevent collection. These command arguments leave saved Git configuration unchanged.

Exact discovery retains shared source access. Static discovery reserves only its session's check-operation slot, so another session's source writer does not prevent it from starting. It still captures and compares configuration, helpers, preferences, and source snapshots before returning; an intervening edit invalidates the result. Both modes exclude other check operations in the same session and retain process ownership through collection.

Completion captures retain shared repository access until the owning state transition commits. Plan Check finalization keeps the reservation through report generation and atomically stores its result, report reference, execution, and task retirement. Native phase settlement reacquires access for its final snapshot, and ordinary Goal completion checks required verification under the same protection. A Goal completion whose verification is pending, or whose capture finds the reservation held by another owner, is refused and the goal continues; only progress evidence is captured without protection. The [planning architecture](planning.md) describes these completion paths. External writes and nonparticipating hosts remain outside the reservation protocol.

Host-owned LSP rename transactions acquire exclusive repository access after edit validation and before becoming committable. The blocking worker retains access through commit, then shares its reservation with the retained physical-change record. The broker acknowledges that reservation after saving the root exchange, managed child completion, or observed child record. Every retained copy shares the same acknowledgment; serialization preserves the change facts without serializing the live lock. A failed save leaves the reservation held by retained copies, and the root completion fallback saves a candidate before changing its in-memory record. Cancellation of the tool waiter cannot release a running worker's guard. Disk freshness is checked again at commit, since editor preparation precedes reservation acquisition. Reservation failures preserve their cause and leave source untouched. Abrupt host loss leaves a started journal record that blocks new source access; automated reconciliation of its mutations and child processes remains outstanding.

When an internal control context supplies a repository scope, LSP preparation borrows that scope instead of acquiring a conflicting lock. An expired or foreign scope is rejected without falling back to independent access. Commit checks revocation before writing, and the parent remains suspended through physical-change recording. Provider and managed-agent admission do not yet install these scopes; connecting their full execution and cleanup lifetimes remains required by the overhaul plan.

Diagnostic timeline rows preserve one-based UTF-8 byte columns in file actions. A result with located diagnostics adds a quickfix action containing the retained file locations, messages, codes, and severities. The editor loads it through the configured timeline-open action, without rereading logs. Missing positions remain unspecified in quickfix; source navigation clamps stale positions to valid coordinates in the current file. Actions are rebuilt from saved results, so this presentation change does not alter the stored result format.

`CheckRun::findings` combines declaration-conformance problems, unsatisfied planned-test obligations, and failed-command findings. Each diagnostic command keeps its original failure and log reference, includes unlocated errors and truncation counts there, and emits fully located error diagnostics as separate repair findings. The plan check finalizer stores that list before entering Resolve; the existing `plan:findings.md` reader renders it without parsing compiler output.

Custom commands receive closed stdin and are judged by their process exit status. `checks::invocation::resolve` substitutes declared scalar values or arrays of scalars into complete argv elements, never through shell interpolation. The removed `input: true` mode fails with a named migration error; selection receipts and generic file reports have no readers. Structured adapters report selected items and outcomes through the category contract, which Harness validates. Planned tests resolve through adapter IDs; custom commands cannot consume a `planned_cases` input source.

Task coverage uses `All`, `Paths`, or `Tests`. Test adapters accept `Tests`; path adapters and custom commands accept `Paths`. Removed scope spellings fail with migration instructions. An empty implicit task selection skips execution, while explicitly empty adapter selectors request whole coverage. A restored run reapplies its captured task scopes to the decoded configuration because authored definitions store no task scope.

Plan submission collects static inventories through the existing check-owner queue, sharing one deadline and checking the configuration, task overrides, helper content, and workspace again before returning warnings. The resolver qualifies each candidate with its check ID, prefers file-owned matches across all participating adapters, and reports ambiguity, duplicate entries, missing tests, and discovery failures at their authored lines. A case's optional target names the test check that owns it: `CheckConfig::test_target` matches a test check's ID, or else its label, ignoring case, when exactly one check matches, and restricts the case's candidates to that check. Submission refuses an unknown or ambiguous target at its line in `plan:tests.md` and lists the valid targets, for every change kind including new tests; a run that meets one anyway reports `InvalidTarget` as its finding. A planned name matches an adapter's qualified name at a `::` boundary; within the planned file it also matches a case's own label or its trailing group labels joined by ` > `, a space, or `::`, so `splits evenly` and `money > splits evenly` both find a Vitest case whose full name is `money splits evenly`. Several matching cases stay ambiguous. New entries are deferred until implementation, because a test that does not exist yet cannot be matched; their names are first checked by the exact discovery that Check runs. Submission never upgrades to exact discovery or treats static absence as verified removal.

`DeclarationDesign.submission_warnings` retains the submitted document version, test-artifact and reviewer-selection fingerprint, source snapshot, complete discovery configuration and task preferences, and each warning's file, name, change kind, and authored line. The Tests section and review metadata expose the retained report. Plan Review displays the warnings recorded at submission. It reads their saved source identity without acquiring a new checkpoint or querying current check settings. Later artifact or selection edits remove the warning's current-line attribution, and every resubmission replaces the report, including clearing it when no existing tests remain. The retained report is advisory and has no path to test evidence or completion gates.

The Check phase collects unscoped exact inventories under the admitted run's existing ownership. It resolves new, modified, and reused entries to case IDs across all participating checks, and proves removal only when every inventory succeeded and no candidate remains. Each test check receives its resolved IDs; checks owning no required-present entries are excluded. A missing or ambiguous entry prevents execution. `CheckRun.planned_tests`, retained inside `PlanExecutionRecord.check_runs`, stores the authored inventory, complete discovered inventories, snapshot-bound resolution, and each required case's observed status. Restoration recomputes every resolution from those inventories and rejects changed case identities, source locations, duplicates, or absence claims. Every required-present case must pass even when its enclosing check accepts skipped cases. Source, helper, or configuration changes invalidate the attempt. Git workspaces and ordinary folders both supply content snapshots.

If an exact inventory has locationless cases, the same owner requests static discovery within the remaining deadline. Supplementation joins only matching `(check ID, item ID)` cases, preserves any exact location (including an omitted line), and never adds static-only entries. Resolved locations retain exact or static provenance; unmatched cases remain source-unverified. Unavailable supplementation retains a diagnostic without invalidating a successful exact inventory. Changes during supplementation invalidate the full attempt. The plan review's execution report displays resolved check/case ownership, provenance, per-case outcomes, verified removals, and supplementary diagnostics for each retained attempt.

Planned Check runs capture one absolute tool deadline at admission. Source capture, exact discovery across participating checks, prerequisites, custom commands, adapter execution, and final validation consume that budget. Expiration stops further launches and fails the run; owned processes are collected before the reservation is released. Completed case results remain available. Cleanup and in-flight filesystem operations may finish after the deadline, so it is an execution budget rather than a fixed return-time guarantee. Ordinary runs retain their per-command budgets.

Discovery captures configuration and all task preferences before admission, applies task enable/disable overrides to configured enablement, and rejects results when either changes. Planned runs retain `CheckRunContext.task_overrides` separately from the merged reviewer selections and revalidate them before commands and final validation. Reviewer-disabled checks do not participate in planned-test ownership; mandatory post-mutation verification ignores those reviewer exclusions while still rejecting configured or task-disabled definitions. Authored check definitions accept `enabled: false`; omitted enablement defaults to true and explicit disabling survives serialization.

`DesignDocument.test_scopes` stores each reviewer's Planned or Whole suite choice. Scope updates share the version/digest-checked check-edit path, survive artifact regeneration, and reject keys that no longer identify test adapters. `PlannedTestExecution` retains the chosen scopes and compares them when considering prior evidence. Enabled Whole-suite checks run even without planned entries; disabled checks stay excluded. Per-case plan obligations still apply to whole-suite results. The plan picker exposes the Tests field and its help through shared command descriptions.

Each observed planned-case status references its selected test-verification command in the same attempt. Loading a complete run checks the command identity, check owner, case ID, and status; missing or inconsistent command evidence rejects the record. Reused outcomes from earlier runs cannot supply planned-case results. Unfinished entries stay unsatisfied, and invalidated attempts retain their evidence validation without satisfying the gate.

Before exact discovery, `PlannedTestExecution.inputs` freezes the source identity, base discovery configuration, managed helpers, task namespace and preferences, merged reviewer exclusions, test scopes, and verification ledger. Discovery uses the participating checks derived from that input. Restored inventories must contain exactly those checks, and the saved run context and source identity must agree with the input. Mandatory verification derives its pending set from the captured ledger. New mutations or changed obligation identities invalidate the attempt; this run may still satisfy its own captured obligations. Each plan retry starts a new run and new resolution instead of resuming an interrupted run's results.

Plan previews identify empty and removal-only test inventories without promising execution. Required-present tests defer ownership to Check, and whole-suite choices select their prerequisites even when triggers do not match. Full writer coordination, surviving-process recovery, atomic completion, configuration publication, and cross-platform acceptance remain tracked in `checks-overhaul.validation.md`.

## Setup before planning

`/plan` validates project checks before generating a plan. Missing or invalid configuration keeps the request in a `ConfiguringChecks` plan, run as a separate setup exchange that needs an explicit user answer before publishing configuration. A matching saved configuration then starts one planning exchange with the original request. An intentionally empty configuration skips setup, and submission still validates the saved configuration.

The setup exchange runs in Chat mode, so its admission still captures a `PlanningContext`, marked `configures_checks` while the plan waits in `configuring_checks`. Owner finalization of a normally completed setup turn calls `advance_configured_plan_now` before observing the response. That call advances the plan only when the check runner recorded a `ConfigurationSaved` event for the current configuration digest after the plan was created. A saved configuration therefore reserves the planning continuation as soon as setup settles. The observation counts progress as exactly that advance. A turn that leaves the plan in `configuring_checks` spends one setup turn of the plan's continuation budget, even if the workspace file changed without a recorded save. A cancelled, refused, or limit-terminated setup turn neither advances nor counts.

## Selection

Triggers select checks independently of execution scope:

| Trigger | Selects a check when |
| --- | --- |
| `any_change` | The task made a change. |
| `paths` or `files_changed` | Changed files match the include and exclude globs. |
| `manual` | A user requests it, or a dependent needs it. |

Required prerequisites always join the selection. The change set compares the current checkpoint with the owning task's first checkpoint, so files that were already dirty never trigger checks. Without a baseline, applicability is unknown, and scoped coverage blocks completion instead of being guessed. `enabled` permits execution, and `auto` controls trigger selection. A plan's `checks` list adds checks, and `disabled_checks` suppresses them for that plan without changing repository defaults.

## Execution

One Rust runner serves the automatic gate and `check_run`. Ordinary completion and successful goal completion enter the gate, while intermediate goal turns, questions, approvals, cancellation, and active children do not. The gate defaults to `after_queue`, which checks the entire queued batch, and `/config` can select `between_work`. Automatic completion checks are off until the user enables them. The broker checks that setting before capture, admission, revalidation, and result-driven retries. Pending format or lint verification cannot override it: the ledger retains those requirements for explicit verification or plan Checking. A check already running may finish, but disabling automatic checks prevents another run or repair from being scheduled.

Checks run serially. Command checks use the shell selected in `/config`; script adapters use their fixed argv and receive a protocol request on stdin. Admission derives command purpose from the custom runner's `prepare` flag or the explicitly requested adapter operation. `CheckConfig::order_preparing` runs that request's preparation commands and their prerequisites first, then orders typecheck, test, read-only format, lint, build, and custom, breaking ties by check ID. Explicit dependencies take precedence. Dependency-only adapters remain read-only, and an apply batch rejects implicit custom preparation. Independent checks continue after a verification failure; dependents of a failed prerequisite are skipped, and an apply batch stops after a selected prerequisite or fix fails.

`CheckEvidence` lets the gate reuse a command result only when context, resolved inputs, execution contract, helper content, and workspace are all unchanged. Script-adapter results do not reuse earlier runs: their fixed argv does not identify downstream tools invoked inside the script. They still satisfy the gate for the snapshot they actually checked. Cancellation suppression compares captured inputs separately, so unchanged cancelled work remains blocked instead of automatically restarting. Explicit runs always execute.

## Failure and repair

Ordinary completion-check failures go to a repair exchange owned by the original request. Repeated failures with unchanged inputs stop repair, and cancelled work with unchanged inputs becomes Blocked instead of retrying. Source changes during the gate invalidate it. A direct prompt uses normal steering or starts a foreground turn while the session check owner collects the run. Prompt preparation collects the prior provider invocation independently of check processes. Queued drafts and task continuations wait for checks. The session owner admits `check_cancel` from the current invocation against the active run ID, including a run requested by an earlier turn. Task verification retains its task permit and revalidates the evidence when it commits. Automatic completion hands its captured exchange and check work to the session owner so foreground settlement can finish.

Accepted plan execution owns a separate Check phase. Verify instructions derive from `PlanExecutionRecord::passed_check_commands`, the selected commands of the revision's passing run, which is also the source of citable `Harness check` evidence. When no configured check runs automatically, as with manual-only triggers, that list is empty: the prompt says that Harness ran no automated check commands and directs the model to `check_definition_list` and `check_run`, and the completed run reads `No automatic checks ran` instead of a vacuous `0/0 passed`. A failed or blocked run that started no command names its cause instead, such as `Checks · failed · planned test resolution has not completed`, and lists its selected checks as skipped under that heading. The attempt published before the initial scan holds `ChangeInventory::Pending`, so its commands read as queued rather than as configuration errors, and an interrupt during the scan retains them unstarted. The run belongs to the exchange whose turn requested Check, so a chat exchange sent while Check waits never receives its results, and a run that completes the plan leaves one `◇ Plan complete` row in that exchange: the execution's `Completed` lifecycle event, which `ExchangeLayout` places after the exchange's response. The run record carries no completion row of its own. A plan revision accepted while the execution runs keeps the Execute task, so its acceptance commits no `Approved plan entered execution` row; the revision's lifecycle rows record it inside the exchange. The model may request read-only checks in Verify and explicit fixes in Resolve. `checks::model_check_operations` rejects both during Implement, Check, check setup, and while delegated agents run; the repository reservation supplies exclusion at launch. Actionable command, configuration, and execution errors retain their individual diagnostics and enter Resolve, and a failed formatter's finding names each unformatted or failed file from its adapter result, since an adapter's saved command output is often empty; they do not leave an otherwise runnable task suspended in Check. Its durable local reservation survives newer chat exchanges, and explicit resume in Check schedules local work without a provider prompt. Goal retains only its Work phase; this execution state machine adds no Goal check phase.

## Agent tools

`CheckSupervisor` owns publication. A `check_run` admitted by the session owner outlives the provider turn that requested it, so the owner replaces that turn's update sink with an owner-lifetime publication stream before launch. Progress, results, and configuration errors therefore reach Neovim after the turn ends. The check request and the turn's observation travel on separate channels, so admission accepts a request whose scope matches either the foreground transaction's dispatched invocation or the observed steering scope.

Agents use `check_status` (with `wait_ms` up to 60 seconds), `check_list`, paged `check_detail`, `check_definition_list`, and `check_definition_details`. Task-level overrides from `/checks` persist per task without editing project defaults.

`ProviderBridge::prepare_dispatch` binds check tools to each dispatched invocation, including successors that continue the same exchange. Each binding keeps its own immutable invocation identity and authorization event sink. The bindings share the foreground owner's revocation lease and lifecycle publication destination, so retiring the foreground revokes every binding while delayed predecessor callbacks retain their original identity and remain subject to stale-scope rejection.

Check history and plan documents load only at their current versions, `CHECK_HISTORY_VERSION` in `checks/supervisor.rs` and `PLAN_SCHEMA_VERSION` in `plan/document.rs`.

A torn run record would otherwise block resume, preview, and fork of its whole session, because `CheckSupervisor::open` runs during broker initialization. `write_record` therefore syncs each replacement before renaming it into place, and `saved_history` skips a record it cannot read or decode, logs `checks.history_skipped` with its path, and leaves the file for inspection. The persistence worker in `checks/publication.rs` keeps writing after a failed progress write, because every write replaces the whole record; only a failure of the terminal snapshot turns the run into `ExecutionError`, and `run_admitted` saves that snapshot before publishing the terminal state, so the editor sees one outcome.
