# Harness permissions

A model that can write outside its workspace, or bypass a saved denial by rephrasing a shell command, cannot be left to run unattended. Harness therefore evaluates every reported operation against saved rules and access scopes before the provider receives an answer. Saved denials, protected targets, and write-off always win, whichever approval mode is selected.

## Limits of these controls

These scopes authorize the operations a provider reports. They do not sandbox everything a provider, shell, or MCP server does, and only Codex adds operating-system isolation, through `CodexSecurity`. Provider-local hooks and command policies can also reject a tool that Harness allowed.

## Access and approval

`HarnessSession` keeps two independent settings. `AccessPolicy` holds the read scope (Workspace or Full), the write scope (Off, Workspace, or Full), and extra directory lists. `ApprovalMode` is Ask, Deny, or Allow. New interactive sessions use full reads, workspace writes, and Ask. Resumption restores the stored selections, Background generation disables writes, and forks copy the source's access.

Filesystem planning adds an invocation-only `effective_write_roots` restriction for its authoring directory, without changing saved user access preferences. Directory evaluation rejects reported writes outside that root even under Full or Allow, and write-off still rejects capture and ordinary file writes. Baselines and host snapshots remain outside the writable root; read access does not make them editable.

`PermissionChange` resolves the permission commands through the task transition coordinator. `/yolo` selects full reads and writes, Allow, and sandbox off together, and repeating it switches back to Ask and re-enables the sandbox where the provider supports it.

## Evaluation order

Each operation passes through these stages in order:

1. `CompiledPermissionDocument` evaluates saved rules, without seeing the approval mode.
2. `DirectoryPolicy` evaluates canonical paths, grants, and scope.
3. `PermissionCoordinator` resolves anything still undecided: a popup under Ask, a one-time rejection under Deny, or a one-time approval under Allow.

Write-off denies every write, including writes to unknown paths, regardless of rules or grants. Explicit denials and protected targets always win, and providers can never write the permission document itself. Automatic decisions never persist rules.

A child agent's write scope is the stricter of its admitted selection and the current root, and a subagent profile with `write_access: "off"` produces a write-off selection. A write-off child holds a shared repository reservation instead of the exclusive writer reservation, so several can run at once. That reservation admits concurrency, not denial: this policy denies the child's reported writes, and the shared reservation is not an operating-system sandbox. See "Repository reservations" in [child-agents.md](child-agents.md).

Before any of these stages, `ProviderPermissionContext` rejects a command containing a PowerShell file writer (`Set-Content`, `Add-Content`, or `Out-File`, found by `command::shell_file_writer` in any pipeline, sequence, or nested launcher) and gives a reason that directs the author to a file-editing tool. Every refusal is a typed `Denial` that names its actor: Harness policy, the user, the approval timeout, or the approval mode, so a policy refusal never reads as the user's. The shell-writer denial says the command did not run, not to write files from the shell, and to make the edit now with "your file-editing tool", naming no provider's tool; it omits "do not retry or bypass", which would contradict that route. Writes-off is checked first and treats a shell writer as a write, so with writes off the refusal says writes are off and that the user can enable them with `/write`. A user's **Deny once** tells the model not to repeat the call in this turn unless the user asks, and that it may request it again then; only a saved deny rule carries the standing "do not retry or bypass". `PermissionCoordinator::record_policy_denial` publishes each refusal made before the coordinator as a `SavedPolicy` resolution on the request's item, with a short reason that includes the next step, so the tool row shows Harness's reason for every provider, ahead of a provider's generic text such as Copilot's fixed "Provider denied this operation". Claude, Copilot, and ACP return that reason to the model with the denial. Codex's decline reply carries no reason and Codex reports the declined call to its model as "rejected by user", so the Codex adapter queues the reason into the running turn as a developer message before it declines; see "Approvals and sandboxing" in [providers.md](providers.md). A shell write reaches the approval layer only as an opaque command, so it can never be matched against write roots or path rules; a file-editing tool reports a concrete path that directory evaluation can authorize, including planning's authoring root. Saved allow rules and Allow mode do not lift this rejection.

`PermissionStore` loads one validated document from `stdpath("config")/forge/permissions.json`, edited through `:ForgePermissions`, and compiles its matchers once.

Several editors share that file, so a save from one host's in-memory snapshot would erase another host's "always allow" or resurrect a rule it tightened. Every write therefore holds an exclusive lock on `permissions.json.lock` beside the document, re-reads the document under it, and applies only its own exact rules to what it read; `:ForgePermissions` saves remain whole-document replacements. The merged document replaces the file with one synced rename, so a concurrent reader sees the old or new document and never a missing one. An invalid document on disk fails the write instead of being overwritten. An approved allow keeps the revocation epoch only when the disk document equals the policy the store already enforced; any foreign change revokes captured callbacks, because the merged policy may be stricter.

Built-in host tools default to Allow at the tool-approval layer. Explicit saved tool rules still apply, including Ask and Deny. Resource permissions, directory scopes, write-off, protected paths, and tool-specific admission remain independent. External provider and MCP tools continue to require approval when no saved rule matches.

## Reported paths

Adapters reconstruct the affected paths before the coordinator sees a request. Codex resolves item approvals from the matching file proposal, and ACP combines partial callbacks with its tool snapshot. Missing targets stay unresolved, and a malformed target list fails as a whole.

Path authorization resolves relative paths from the execution workspace, follows symlinks before later `..` components, and compares path components rather than string prefixes. Comparing components stops `/repo-other` from matching a grant for `/repo`. The approval popup can add a reported file's directory to the global readable or writable lists. A write grant uses the containing Git worktree root, and accepted grants persist before the provider receives approval.

## Shell command analysis

A rule that matches `git status` is worthless if `git status; rm -rf .` also passes. Harness parses shell commands with pinned PowerShell, Bash, Zsh, and Nushell grammars, without running them, and splits compound commands into separate targets, each with its own approval decision. Targets that are already allowed are skipped. Callback builtins such as `ForEach-Object`, `Where-Object`, and Nushell's `each` and `where` pass only if every nested command passes.

Analysis fails closed, with a distinct error for each cause:

| Cause | Error |
| --- | --- |
| Dynamic command names, code evaluation, definitions, or redirections | `shell_command_unsupported` |
| Invalid syntax | `shell_command_parse_error` |
| Exhausted analysis budget (8,192 nodes, 64 tree levels, 16 nested shells, or a 25 ms parse deadline) | `shell_command_analysis_failed` |

Failed analysis never opens approval or authorizes part of a command, even under YOLO. `ProviderPermissionContext` turns the analysis error into a Harness-policy `Denial` (`Denial::command_analysis`) and records it on the tool row like any refusal made before approval. The error text states only the cause, such as `shell_command_unsupported: Harness cannot analyze method invocation in PowerShell commands`, and the refusal adds the permitted routes: the same work with commands Harness can analyze, or file changes through the model's file-editing tool. It carries no "do not retry or bypass", because asking for a rewrite while forbidding any retry or other tool once left a model unable to write a file at all; the next command is analyzed like any other, so the route widens nothing. Codex command text uses POSIX `shlex` quoting on every platform. In `permission.bash`, `"*"` is the lowest-priority decision.

Permission evaluation errors return through the denied tool's reason, without a separate error notification. Expanding the denied tool shows that reason through the existing rejection renderer, which prefers a recorded host decision and otherwise uses the provider's terminal denial. Ordinary policy and user rejections use the same tool detail surface.

Before an interactive Ask prompt, `forge-shell::resolution` also checks literal PowerShell command names in a clean, noninteractive PowerShell process. Discovery recognizes built-in aliases such as `%`, executable paths, and installed module exports without running the submitted command or initializing user modules. Missing names produce `shell_command_not_found`, including a reminder to quote literal pipes in Git format arguments. The five-second probe uses the policy workspace and host environment; profile-only definitions and environment changes made earlier in the submitted command are not available. This preflight does not run for saved allow/deny decisions, Allow or Deny mode, or other shell languages. A probe that cannot launch, times out, exits unsuccessfully, or answers unreadably reports `ResolutionFailure::DiscoveryUnavailable` rather than a command failure, because it says nothing about the command; the approval still opens and its reason says Harness could not pre-check the command's names. Denying instead told the model never to retry a command nobody had examined. `process::spawn_owned` falls back from the job-list creation attribute to a suspended launch assigned before it runs when Windows refuses the attribute with `ERROR_ACCESS_DENIED`, which it does for concurrent launches of a packaged app's execution alias such as the Store build of `pwsh`.

The approval and the tool row hide a launcher such as `bash -lc '...'` only when it is the whole command, using the same `shell_script` test that unwraps it for analysis. Codex reports a command item's argv joined with POSIX quoting on every platform, so a PowerShell script containing `$false` arrives as `"…pwsh.exe" -Command "…"'$false)'`; the Codex adapter reads the item through `provider_command`, the function its approval uses, and names the row by the launched script with that script's shell. An unquoted control operator after the script, as in `nu -c "sleep 45sec"; "exit code: $LASTEXITCODE"`, belongs to the outer shell, so neither the display nor the analysis treats the rest as the launched script.

## CLI adapters for command rules

`permissions/command_adapter.rs` owns command-rule matching. It first applies the existing literal token-prefix matcher, then asks a known CLI adapter for an additional match. Both paths retain the original rule's specificity score, so explicit rules still outrank broader rules. Tools without an adapter and invocations with unsupported global options keep literal matching.

The initial adapter lives in `permissions/command_adapter/git.rs`. It parses only the exact global options `-C <directory>` and `--no-pager`, before the first subcommand. For example, a `git ls-files` rule also matches `git -C D:\config --no-pager ls-files`. It preserves every token from the subcommand onward: a rule for `git branch --list` does not cover `git branch --delete`. Other global options, including `-c`, `--config-env`, `--git-dir`, `--work-tree`, `--exec-path`, `--paginate`, and attached `-Cpath`, disable the adapter match; explicit literal rules can still match them.

The matching projection retains `-C` operands in their original order and records `--no-pager`. A rule with explicit `-C` operands requires the same sequence, and a rule containing `--no-pager` requires that option on the invocation. A rule without these constraints remains unscoped. This is command authorization, not a new filesystem scope check: directory operands are not canonicalized or interpreted as directory grants. Git resolves repeated relative `-C` operands during execution, as described in the [Git options reference](https://git-scm.com/docs/git).

Adapters never rewrite `CommandInvocation`, its source spans, the command shown in approval, or the text sent for execution. Add another CLI by adding a sibling adapter and an explicit dispatch case. Keep token comparison and specificity in the shared matcher; keep option arity, supported spellings, context constraints, and subcommand boundaries in the adapter. Preserve unsupported syntax for literal matching, and add regression tests for equivalent forms, restrictive rules, context differences, malformed options, and original-source retention. An adapter must not turn an unfamiliar flag into permission by dropping it.

## Approval decisions

The approval picker stages one offered choice per independently identified target and submits them together when the last is confirmed. Checked request, target, and choice IDs bind that selection to the original `ApprovalScope` (item, turn, thread, or operation). Each choice contains its concrete decision, saved-rule effects, and directory grants. The coordinator validates those effects rather than inferring authority from a display label or a provider-specific choice string. Any denial rejects the whole operation, and rules persist atomically before the provider request is released. Each target's page opens with no choice selected (picker page `selected_index = 0`), because the popup can take focus from a composer in Insert mode and the host lists allow choices first: an Enter already in flight confirms nothing. A popup that takes focus mid-sentence still receives the next letters as decisions, which once saved an "always allow" rule after a one-second pause, so no key timing decides that typing has stopped: at the single opening point of the approval, the plan question, and the question picker, `controller.hold_while_typing` tests the editor mode synchronously, and in Insert, Replace, or Command-line mode in any buffer it leaves the request pending as if the user had dismissed it, adds it to one controller-owned list, and notifies the reopen key. One global `InsertLeave` and `CmdlineLeave` hook opens the held popups in order (approval, plan question, questions) when the session's view is in the current tab; held popups for another tab wait for the reopen key. Each held entry records the window and mode the request interrupted, and both the release hook and `oe` open the popup through `Picker.present_from`, so the picker returns there when it closes rather than to the Normal mode the user left to release it; `popup_window.restore_origin` keeps an Insert-mode origin in Insert mode when the picker closes from one of its own Insert-mode mappings, because `:startinsert` does nothing in Insert mode while `:stopinsert` would end it after the mapping. Closing the picker first enters whichever window Neovim chooses, often the transcript, and both the transcript and the composer end Insert mode whenever focus enters them; `popup_window.close` and `restore_origin` therefore set `popup_window.returning_to_insert` for the whole return, and that entry guard in `views/harness/layout.lua` keeps Insert mode while it is set. Keys a terminal delivers in one burst with the submit key are already queued when the popup closes and run before anything scheduled, so the mode must survive the close itself; a later `:startinsert` would come too late. The question picker closes as soon as the last answer is submitted, before the host replies, so keys typed after the submit key reach the restored window; a failed save is reported with the reopen key and shown beside the kept drafts. The approval and question pickers also set the shared picker's `input_settle_ms` to `Picker.focus_taking_settle_ms` (350 ms): one `vim.on_key` observer in `views/picker/init.lua` arms the guard on every open of such a picker, and the picker discards every typed key except its close keys, `Ctrl-C`, and actions marked `interrupt`. The observer discards after mappings resolve, so neither picker nor global mappings run. Each discarded key restarts the interval, only the release timer ends the settling, and it redraws the footer, which reads **Waiting for typing to stop** exactly while keys are discarded. A guarded picker that closes for any reason other than the user's confirmation or close key, as on expiry or a host resolution, discards keys for the same interval, so they do not land in the composer; an owner that closes it after the user's decision passes the `"user"` reason. Outside the guard, the same observer drops every key in a picker list that is not one of the list buffer's own mappings, the command line, or a special key, because a built-in editing command or a global mapping such as `Y` to `P` would raise E21 in its unmodifiable buffer; the keys a dropped mapping's right-hand side produces after its first key arrive with no typed keys and are dropped with it until the next typed key or main-loop turn. A plan question can arrive while the session's activity reads busy, as the execution settings that automatic plan acceptance asks for while its command applies; the presentation then waits, and the controller's `activity_changed` handler presents the question once the session settles, holding it like any other popup while the user types. The controller marks an approval presented only after the picker opens, skips presentation while the view has no window, and records a dismissal only for the user's own close key; a popup displaced by another picker is presented again through `Picker.when_idle`.

`PermissionApprovalEvent::{Requested, Resolved, Cancelled}` is host-owned. Resolution retains each target's decision and source, committed rules/grants, and timestamp. Cancellation retains its own reason and never fabricates a user denial. Timeout is an explicit one-time decision. An automatic denial by saved policy or by the approval mode records the policy's reason, whether the request arrived under that mode or a mode change decided it while pending; `automatic_decision` supplies both, so no row reads a generic "Permission denied". `DirectoryAccessGranted` describes a persisted grant under that same original scope; a late grant or resolution cannot authorize another pending request. Native adapter writers cannot publish any of these host events. Approval presentation carries an explicit execution kind: `Managed` or `NativeObserved`. A native child request inherits policy only through its trusted original association and a positively registered child owner. Resolving or dismissing it operates on that approval; it never invokes a managed `AgentTask` cancellation path.

Every `PermissionRequest` names its `PermissionSubject`: `Tool(item_id)` for the host tool item the approval gates, or `Unattached` when no admitted item exists, as for Harness's own host-tool approvals or a request that arrives before its item is admitted. Each adapter owns the mapping from its native call identity to the host item. The coordinator publishes an attached request under `ApprovalScope::Item` within its turn, and an unattached one under the turn or thread scope. The item scope lets the tool watchdog relate the wait to the tool, as described in [Tool execution deadlines](harness.md#tool-execution-deadlines).

`/config` sets the approval and answer timeouts, ten minutes each by default, and zero disables expiry. The waiting provider future owns the approval deadline, so closing the picker cannot pause it. Expiry returns a one-time denial recorded as `resolution_source: timeout`, whose text says nobody answered rather than that the user rejected it, and forbids only repeating the call unprompted: when the user asks for the operation again, the model requests it again. It leaves rejection feedback for the request's execution owner. The provider receives the denial inside the running turn, so when that turn then completes normally the model has already answered it: `HarnessBroker::discard_answered_timeout_feedback` drops feedback for the exchange's turns at successful settlement, for every provider, and no continuation starts. Feedback survives when the turn was interrupted or failed, or when the approval expired after its turn settled; the session's approval-timeout watcher then delivers it in a permission-timeout continuation turn once the owner is idle, so the model continues the requested work instead of waiting for the user. The guidance names each operation and states that it did not run, is not approved, and must not be performed through another shell, terminal or MCP tool, or script unless the user approves a new request; the model continues the independent parts of the request and reports that the operation still needs approval. Either way, `TimelineRenderer::approval_timeouts` draws an **An approval timed out** row directly beneath the Tools group holding the request's item, not after the model's answer. The continuation is root work like any other turn: the driver acquires the root execution permit before staging it and keeps the expiry pending while queued input holds that permit, in which case the input's own turn carries the feedback as a notice. A follow-up queued during the approval therefore never starts a second foreground delivery beside the continuation; it steers into the running continuation where the provider accepts steering, or waits for it to finish. The timeline expansion shows the original approval request and actions followed by the automatic timeout outcome, while the provider receives only the continuation guidance. Multiple expirations retain each request. An expired question set answers each open question with its recommended or first option. Plan acceptance never times out.

Adapters receive only a semantic `PermissionResponse` (`Allow`, `Deny`, or `Cancelled`) and the configured `ApprovalMode`, so they cannot depend on picker layout or Harness timing. Harness owns the presentation types in `forge-harness/src/provider/approval_view.rs`, including `ApprovalRequestView`, `ApprovalItem`, `ApprovalChoice`, `ApprovalCommand`, and `ApprovalAnswer`. It also owns the decision deadlines in `forge-harness/src/session/timeout.rs`, including `InputTimeout`, `InputDeadline`, and `ResolutionSource`. Each adapter maps the semantic response to its native wire answer. Codex, for example, sends accept, decline, or cancel.

## Check editing

`session.check.editing.set` controls the per-session `check_editing` permission, which is off by default. Every `check_definition_edit` call goes through the approval coordinator in Ask mode, regardless of saved allow rules, and write-off still rejects it. The `harness-checks` skill owns the configuration instructions. `check_definition_list` reports the live value as `check_editing`, and the interaction contract points the model there instead of stating the value. The value can change during a turn, after the contract was delivered, so the contract never embeds it. The contract's tool approval, access configuration, and purpose do reach a Codex model at every change: Codex replaces per-turn collaboration-mode instructions with its model catalog's preset, so the adapter injects the contract into thread history before `turn/start` whenever it differs from the last injection, as [Providers](providers.md#sessions) describes.
