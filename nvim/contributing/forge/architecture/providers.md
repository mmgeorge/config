# Providers

Each provider reports identities, phases, tools, and failures differently, and a consumer that decoded those differences itself would show one provider's quirks as another's behavior. Provider adapters therefore normalize every transport into one typed Harness contract, and shared settings record real capability differences instead of simulating unsupported operations.

[Harness](harness.md) covers the session lifecycle, [Permissions](permissions.md) covers approvals, and [Provider configuration](provider-configuration.md) covers settings, resources, and models. Input delivery is in [Provider submissions](../provider-submissions.md).

## Instruction reads

Adapters disable provider-managed memory on native session creation and resumption: Claude receives `autoMemoryEnabled: false`, Copilot receives `MemoryConfiguration::disabled()`, and Codex receives both `memories.use_memories = false` and `memories.generate_memories = false` through its shared thread policy. Existing stored memories remain on disk or in the provider service, and ordinary file tools can still read a memory file when explicitly requested.

`TurnMetadataEvent::InstructionRead` carries a full source path and filename under the native turn that read it. Adapters collect one initial snapshot per binding and publish it only after positive native start, so opening a conversation alone creates no transcript activity. Claude queries `get_context_usage.memoryFiles`, Copilot queries `session.instructions.getSources` and excludes conditional or default-disabled sources, and Codex retains `instructionSources` from thread open.

Claude registers an `InstructionsLoaded` SDK callback for later native loads. Copilot enables `enableOnDemandInstructionDiscovery` independently of ambient configuration discovery and consumes only successful, tool-correlated `model.tool_execution` messages tagged `instruction-discovery`; their runtime framing supplies the loaded paths. Its expanded startup source bodies also identify imported files. Successful explicit instruction-file reads use shared typed read semantics in all three adapters, including literal shell reads through `CommandInvocation::read_paths`, which skill attribution also uses. The tracker deduplicates a full path within its owning turn, permits another turn to report it again, and never infers reads from model commentary or tool output. Codex's unreported internal loads and ACP instruction tracking remain unsupported.

## Task completion and native outcomes

Adapters report native facts and collect their resources. Successful task tools do not request interruption: there is no `tool_finished` or task handoff callback. Copilot continues through the assistant's final output and ordinary native completion after `plan_phase_done`. Native interruption remains `ProviderError::Interrupted`; an explicit host stop carries its separate cancellation, reconfiguration, or shutdown provenance. A pending completion request cannot turn a failed or interrupted native turn into success.

Mediated native permission callbacks consult the invocation's shared mutation seal before evaluation and again after an approval wait. Copilot returns one-operation approvals; Claude's tool callback returns a scoped allow/deny result. Codex may grant native permissions for the remainder of a turn, and provider-owned caches or already-authorized processes can avoid another host callback. The seal therefore is not a filesystem lock. Direct Harness tools and check starts share the seal; final Execute evidence compares snapshots after collection and rejects workspace changes after the phase request. External editors and already-admitted writers remain possible and must be reflected in collected evidence. No adapter abort is used as a fallback.

## Provider contract and ownership

The provider boundary spans three crates. `forge-provider-api` defines the object-safe `Provider` interface, normalized requests, events, errors, models, and capabilities. `forge-providers` owns native protocol decoding, process runtimes, SDK handles, resource profiles, and session state; its native modules are private behind the registry. `forge-harness::provider::ProviderBridge` prepares host resources and binds normalized callbacks to tools, permissions, task authority, and durable submissions. The API and native implementation crates do not depend on Harness, and the interface has no Harness-associated types.

Providers address conversations only by `ThreadId`. `InvocationScope`, `EventScope`, `TurnAddress`, `SessionRequest`, `ForkTarget`, permission callbacks, and test controls carry the thread, never the Harness session and agent that own it. Harness defines `SessionId` and `ThreadOwner` in `provider/thread_owner.rs` and derives each root thread identity from its owner, keeping the persisted `thread:<session, agent>` form. An adapter mints an observed child's thread with `ThreadId::child`, which keeps the parent's host namespace and adds the child's `AgentId`; `register_observed_turn` rejects a child thread outside the binding's namespace. Harness therefore resolves the owner of any admitted thread through `ThreadOwner::from_thread_id` (exposed on scopes by `ScopeOwner::owner`) without a second table that could disagree with the adapter, and maps owners back to threads for cancellation, permissions, and per-owner event subscriptions. Adapter-private state keyed by owner, such as Copilot's trace correlation label and terminal inventory key, uses the thread identity.

Only `forge-providers` declares the Copilot SDK dependency; Harness has no direct SDK dependency, including in tests. Native wire, SDK ancestry, version, and permission conversion regressions live beside their private implementation. Harness integration tests implement the same normalized interface through `EventFixtureProvider` and the production bridge. Shared mocks exercise acceptance, completion, cancellation, permissions, and host effects without knowing a provider's wire format.

Every provider operation receives a host-issued `OperationContext` containing its identity, immutable deadline, and explicit cancellation observer. The host retains the matching cancellation source with the original worker; losing a result waiter never requests cancellation. Repeating the same context and typed request observes the original disposition, while changed identity/request combinations reject. Opening transfers the sole stream once; observing an already-taken open result cannot allocate another binding. Deadline and explicit cancellation failures retain their operation, phase, and effect disposition, and never imply that input was not consumed.

The bridge retains fork and compaction requests with their operation contexts before native dispatch. Retry observation uses that original request without reloading resources or resolving a replacement binding. A fork's operation identity includes the request's `attempt_id`, so a new attempt for the same child after a failure is a new operation and does not replay the retained failure. `ForkSource::Binding` copies an idle live conversation; `ForkSource::Checkpoint` reads a recorded position and does not require the source to be idle, which is how Harness forks a session whose turn is running. A compaction record also retains its original event reader; its watermark cannot be satisfied by a later binding for the same owner. Shutdown closes history-operation admission and signals retained cancellation before waiting for bridge admission guards. Cancellation interrupts an unfinished watermark wait, while already-consumed completion evidence remains valid. Claude compacts through a `/compact` user frame. The CLI reports the outcome in a `status` frame's `compact_result`; on failure that frame may carry the CLI's reason in `compact_error`, which the CLI omits in some sessions, and the command's `result` frame carries the CLI's printed answer, such as "Not enough messages to compact.". The adapter keeps the first of these as `provider_explanation`, so a declined compaction reads in the CLI's words rather than as an `Unknown` failure. When Claude reports that compaction failed, the conversation is unchanged, so `ClaudeProvider::compact_session` returns the failed compaction and keeps the binding; it invalidates the binding only when Claude reports neither completion nor failure. Invalidating on a reported failure closed the session's observation and left later queued prompts unadmitted.

`Provider::thread_open` returns an opaque binding, initial negotiated capabilities, and its sole ordered event stream. The bridge installs stream consumption before dispatching input. `turn_start` and `turn_steer` return direct input-acceptance evidence or a delivery error; an acceptance receipt does not establish native completion. Root, managed-child, and Background callers use the same retained execution owner while keeping their own presentation and result waits.

Open and configure results carry the negotiated capability manifest, and the bridge republishes each accepted one as host `HostEvent::CapabilitiesNegotiated` on the binding stream: before the native relay starts for an open, and after the operation watermark for a configuration. The broker applies only root-owned manifests whose binding is still active, using the same binding gate and monotonic `effective_revision` check as native `Provider.CapabilitiesChanged`, so a manifest queued by a retired generation cannot overwrite its replacement. Without this publication, adapters that never emit a native capability notification would leave persisted fork and compaction support stale, because turn completion no longer carries capabilities.

An eager startup open gave every unused chat a native conversation, and each pre-prompt settings change could then replace that empty conversation with a new provider ID. Interactive startup therefore never opens one. `SessionController::prepare_provider_initialization` attaches the session observation listener and registers the root execution owner, then reports `ProviderInitialization::Deferred`. The native conversation opens or resumes inside `ProviderBridge::turn_start`, through the per-owner `HostSession.initialized` cell that already serializes first-use admission, and it captures the configuration current at that admission. Before that point `ProviderBridge::thread_configure` returns `ConfigureReceipt::Deferred` and changes only local settings, and closing a never-used chat issues no native close. Codex, Copilot, and ACP report a new conversation's ID only in the open result, so `ProviderBridge::install_session` carries that ID as the `history` of the ordered `HostEvent::CapabilitiesNegotiated` publication, and `HarnessBroker::apply_negotiated_capabilities` commits it through `retain_session_identity` for an active root binding. A later replacement history still arrives as `Thread.IdentityResolved`. The open supplies only static instructions, `ProviderRequest::open_instructions`, because adapters retain open-time instructions for every later turn; each turn's purpose, task contract, and settings travel as tracked context sections, described in [Turn context](#turn-context). Missing established history now surfaces as the first input's turn failure. Manual compaction of a chat with neither native history nor exchanges fails locally instead of opening a conversation to compact, and background-terminal inventory for an unopened owner reports a supported, empty list without a native request. Load-time recovery still clears an unused saved identity, and established history is never silently replaced. Until a binding opens, capability queries fall back to the descriptor's manifest, and catalog queries use the workspace context.

`forge-providers::turn_runner::RetainedTurn` retains one native `TurnResult`, collects the same provider-owned foreground resources, and then publishes the sole `Turn.Completed(CompletedTurn)`. That record contains the native outcome, completion timestamp, exact `CoveredInput` attempts, final accounting, and the separate collection timestamp. Collection cannot choose another outcome. Failed observation or collection fences the connection with `Provider.Unavailable` instead of publishing ordinary completion. A dropped waiter leaves the worker and unfinished collection owned.

Positive native child processing starts a separate retained child driver; lifecycle metadata alone does not manufacture a child turn. The child's original reader and callback group survive parent-turn collection. Parent `Turn.Completed` can publish while that child remains active and a successor root turn starts. Late child items retain their original identities, and the child's own `Turn.Completed` waits for its native terminal evidence and independent callback collection rather than borrowing the parent's certificate.

Harness consumes that collected result before its own commit ticket applies retained callback effects, child results, and checkpoint work. Provider collection and host commit remain separate barriers. `TurnInterruptResult` carries the original normalized turn identity and a stream watermark, with no second outcome field. Configuration and interruption callers consume through their returned watermarks before dependent transitions. The bridge relay advances a binding's published position only when it hands the event to the owner channel, after every fallible routing step. An owner that refuses a native event, for example one arriving after its execution was fenced, reports the position through `ProviderBridge::event_rejected`, which discards that event's binding metadata. A close waits for the published prefix to be consumed, refused, or orphaned by a dropped receiver, so it cannot hold provider admission forever behind a fenced owner; configuration, settlement, and compaction waits treat a refused or orphaned position as `Disconnected`, since they need proof of consumption. Root and Background brokers drain the retained inbox; managed children attach their scoped presentation stream.

`ProviderEvent` has five exhaustive families: `Provider`, `Thread`, `Turn`, `Item`, and `Agent`. Checked `ThreadId`, `TurnId`, `ItemId`, and `AgentId` values identify their registered objects; native session IDs remain separate opaque `ProviderSessionId` values. The binding registry resolves each event's original host owner before the host wraps it in a scoped `HarnessEvent::Native`. Late output never acquires the currently visible turn's ownership.

A valid late `Turn.Error` may append diagnostic metadata to its exact retained original turn after `Turn.Completed`. Identical observations deduplicate across reload. This exception admits no foreground execution and cannot change the collected native outcome, retry decision, completion record, or ownership; a diagnostic is not a new completion signal.

The first positive `ModelResolved` observation may likewise fill an unknown actual model on that original completed turn. It does not resolve a successor's model or change configured selection. Once the completed turn has a confirmed model, a conflicting late model change rejects; repeated confirmation remains idempotent.

Idle session presentation accepts that late confirmation only for the latest root exchange and turn under their original active binding. Historical and retired-binding observations remain in their original history and cannot replace a successor's displayed actual model.

Adapter decoders receive an `AdapterActivityWriter`, which accepts metadata and item activity but cannot publish turn start, final completion, provider unavailability, or host-policy events. A `NativeTurnStart` handle reports positive start evidence; the retained runner owns terminal publication. Host approvals, directory grants, retry presentation, child waits, and verified skill attribution travel separately as `HarnessEvent::Host`. Production providers expose neither `prompt` nor `prompt_stream`; output-oriented fixtures collect above the public acceptance and event contracts.

Native protocols keep adding notification types, while the normalized vocabulary stays closed, so a decoder that dropped every unrecognized type would hide lost content or lifecycle evidence behind an apparently healthy turn. Each decoder therefore admits an unmapped notification only through an explicit, tested policy. The Copilot decoder's `unmapped_disposition` names the SDK types that another retained observer consumes, such as idle, checklist, background-inventory, and permission events, and `session.snapshot_rewind`, which only echoes the history truncation that the adapter's own retraction request performed. It also names the types the pinned SDK defines as presentation, catalog, or configuration metadata. The ACP session decoder admits `current_mode_update` and `session_info_update`, plus an echoed `user_message_chunk` whose input Harness already retains. Every other type produces one `Provider.Warning` of kind `UnsupportedNativeEvent` per binding and type, scoped to the receiving thread; the warning changes no turn lifecycle or retry decision. Copilot builds a decoder for each turn, so the binding owns the reported types as `ReportedEventTypes` and lends them to every decoder; a decoder-owned set would repeat the warning on each turn. Codex child lifecycle decoding accepts only the exact `collabAgentToolCall` and `subAgentActivity` item shapes from `item/started` and `item/completed`. A malformed collaboration item is a protocol failure rather than an ignored observation.

`ProviderTools`, `ProviderPermissions`, `InputReceipt`, `ProviderTrace`, `TurnControl`, and `ProviderHostEffects` are callback boundaries into the host. Native code asks for a tool result, permission decision, or committed receipt without acquiring Harness storage or task state. Prompt requests carry full invocation configuration, the current tool allowlist, typed task commands, structured question replies, and ordered recovered input with its attachments. Harness owns goal scheduling and enqueues ordinary input for continuation; adapters never schedule native goal work. Initial tool registration remains stable; each invocation enforces its own allowlist. Where an adapter needs HTTP MCP transport, the request supplies a unique endpoint and retained lease for that invocation. Direct native tool callbacks use `ProviderTools`. `ProviderTools::call_reply` returns a `ToolReply` whose `ToolOutcome` says whether Harness refused or failed the call; adapters report a failure through the native failure field (Claude `isError`, Codex `success: false`, Copilot a `failure` result with its `error`), so the provider and the timeline show a failed call with its reason. A call that answered, even negatively, is a success; an admission refusal, such as a task that changed or stopped during the call, is a failure whose text names the cause. A retired endpoint cannot route delayed calls to a newer invocation. `forge-shell` separately owns shell parsing and process primitives used by the policy layer and native runtimes.

Provider errors expose typed operations and categories, never native response codes, messages, payloads, or source chains. Diagnostic display messages are deliberately sanitized by the producer. Provider tracing accepts normalized lifecycle records only. Forge has no setup or sign-in flow; users sign in through each provider's own CLI. An authentication failure, including an ACP login-required rejection at session open, keeps the `Authentication` category, and its display message tells the user to sign in through that CLI.

Native adapters additionally emit Rust `tracing` diagnostics before normalization discards their causes. The host subscriber sends redacted display errors and source chains to the existing JSONL writer, not to the provider contract or host stdout. Provider operations carry session and operation spans, and retained workers and cleanup inherit their dispatcher and span. Severity filtering controls diagnostic recording only; it cannot change delivery evidence, retry decisions, or cleanup ownership. See [Debugging](../debugging.md) for levels, storage, and inspection boundaries.

Codex classifies process-creation failures at the spawn boundary as
`ProviderError::RuntimeLaunch`, retaining the selected provider, configured
executable without arguments, and a normalized missing, permission-denied, or
unavailable cause. Catalog discovery, session opening, configuration replacement,
and input reconciliation preserve that evidence instead of replacing it with
`Transport`. The displayed error names the executable and suggests checking its
installation or provider settings; native operating-system details stay in JSONL.
Other connection failures retain their transport classification. The retained
catalog startup worker inherits its caller's diagnostic dispatcher and span.

Copilot's shared transport-error conversion records native display causes before
discarding them, including configuration, skill and MCP inspection, terminal
inventory, history reads, and disconnect failures. Interruption and runtime
collection retain their existing typed dispositions while also logging the native
cause. Catalog spans carry their host-issued operation IDs; Background requests
provide an explicit diagnostic destination independently of interactive sessions.

Terminal inventory protocol failures additionally retain a typed field failure: missing inventory, missing or invalid identity, or missing display command. `ProviderFailure` stores that optional detail without native values; records without it remain readable. Operation traces retain `kind`, `phase`, `disposition`, and `terminal_inventory_error` through both storage and inspection. Free-form `reason` text remains excluded by the trace policy. `ObservationCleanup` renders its retained original failure separately from fencing, cancellation, and collection failures, so a failed close does not replace the initiating cause in the displayed diagnostic.

`ProviderCapability.integration` declares optional operations, resource targets, isolation choices, and implementation limitations in each adapter. The compiled-in registry supplies identities, launch defaults, and declarations before a session starts; Lua does not maintain a duplicate provider catalog. `CapabilityManifest` records only provider facts: each provider operation's support, typed restrictions, and application boundary. Menu groups, labels, ownership, and explanations belong to `forge-harness::provider::capability_menu`, which also adds the Harness-owned workflows such as goals, queues, plans, and child agents, so an adapter never declares a host workflow. Steering policy is likewise Harness's: an active task of any kind accepts steering whenever the binding supports `native_steer`. Open and configuration results publish effective support; later changes arrive on the ordered binding stream. The bridge retains the snapshot consumed by the owner, and `/capabilities` reads that snapshot without calling native discovery. Schema and effective revisions have separate counters. Unsupported optional operations return a typed feature error. Cancellation identifies both the binding and exact invocation, so a repeated or delayed request cannot interrupt a successor. Terminal operations use a binding-scoped typed terminal identity.

## Sessions

Adapters suppress native workflow tools before model execution so questions, agent work, plans, and goals use Harness authority. Claude extends its launch-time denylist with plan transitions, task tracking, and agent discovery; Copilot applies source-qualified `builtin:` exclusions on create and resume, including `task_complete`, while preserving custom tools and selected MCP tools. Copilot inputs remain explicitly interactive, native autopilot continuation stays disabled, and root idle remains its turn-completion boundary. Native file, shell, and web tools remain available under the existing permission policy.

Codex applies one shared workflow configuration to open, resume, replacement, fork, and turn requests. It disables native structured questions, plan tracking, goals, and agent tools. It also disables the `send_message_to_user_async` feature flag, but Codex 0.164–0.169 independently enables that tool when model metadata advertises it; the public app-server configuration therefore cannot guarantee its removal. The adapter does not replace model metadata or claim complete suppression of native user messaging. Antigravity's tool policy is unchanged.

The same policy sets `features.multi_agent_v2.multi_agent_mode_hint_text` to an empty string. Codex 0.169 otherwise appends a prerequisite to read a hosted multi-agent skill when native agent tools are hidden, although Harness supplies its own `agent_*` tools without that skill. Codex treats the empty override as an instruction to omit its multi-agent mode block, leaving delegation guidance to Harness and the selected project instructions.

Codex turn requests explicitly set `summary: "concise"` so the status preview does
not depend on the model catalog's reasoning-summary default. The adapter maps
`item/reasoning/summaryTextDelta` to readable summaries and keeps raw reasoning
separate. The Harness `status_thoughts` setting controls display of those summaries.

Planning authoring uses ordinary native execution posture so file tools remain available; read-only review questions still request a native planning posture. Harness supplies invocation-only effective write roots independently of saved access preferences. Codex replaces its sticky `runtimeWorkspaceRoots` on every turn as well as `writableRoots`, so returning from a restricted authoring turn restores the ordinary project-root context.

Native initialization validates the selected runtime before opening or resuming its conversation. The current minimums are Codex 0.164.0, Copilot CLI 1.0.103, Claude Code 2.1.317, and Antigravity ACP 1.4.5. The Copilot SDK dependency is pinned separately to 1.0.26; its version does not prove that a configured CLI override is supported. Codex reads its initialization user agent, Copilot queries the connected runtime status, Claude Code runs `claude --version` before catalog discovery and each process launch, and ACP reads the adapter version from the initialization handshake. Missing, malformed, and below-minimum versions produce typed initialization errors. A replacement runtime must validate again. All adapters use the shared `RuntimeRequirement` and `ValidatedRuntime` contract, with one minimum per adapter and no maximum or exact-version capability gate. Codex shares its initialize, version validation, and initialized notification across discovery, session open, reconfiguration, and recovery. ACP prefers the configured executable; if the default executable is unavailable, it selects the newest locally installed managed copy and validates that copy through the same handshake.

Conversations open or resume their provider session asynchronously, without creating an exchange or sending model input. The controller releases its broker lock during network work and rejects stale results after configuration changes. The broker persists the root conversation ID when it accepts a provider turn-start boundary, so interrupting the first turn still keeps the conversation.

Saved sessions use the current `SESSION_FORMAT_VERSION` in `storage/mod.rs` (66 for this contract). Explicit resume rejects older or missing versions before decoding changed session state or opening native history, with a create-new-session diagnostic. Listing omits unsupported records while retaining their stored history. New-contract sessions remain resumable.

Harness defaults to the Codex app-server provider, and `harness.provider = "copilot"` selects the Copilot SDK. Broker initialization resumes the most recently updated session for the repository and provider. Switching providers requires choosing New chat or Resume session and never transfers context across providers. It stops the one host that serves every Harness tab, so it is unavailable while any connected tab has a running turn, queued or unsent input, or a finalization in progress. A failed switch restores the previous session.

Copilot's native session registry serializes preparation per execution owner. It retains repair notices, resource leases, terminal readers, and compaction subscriptions with the matching binding. The binding's `CompactionMonitor` is the only publisher of root-thread compaction: `CopilotEventDecoder` decodes only a native subagent's compaction, because the decoder a finished turn leaves retained also reads idle notifications and published each root compaction a second time under its native event identity. The monitor's `ManualCompactionMap` assigns the next native start to the oldest manual request no start has claimed, and a request gives its identity up only when the CLI never answered it, because the CLI emits its start and completion notifications before its answer but the monitor can read them after the answer arrives. `CopilotSession::compact` reports the owner's Harness thread, not the native session ID, since the host settles an attempt only for the conversation it addressed, and it maps the typed `session.history.compact` answer onto token and message counts. A JSON-RPC error answer is the CLI declining or failing the request, so it returns a failed compaction whose `provider_explanation` carries the CLI's reason without its `Request ... failed with message:` wrapper. A turn takes its workspace from the `SessionRequest` that opened the binding: the SDK session's own `workspace_path` is Copilot's session-state directory, and resolving reported file paths, instruction sources, or a restarted client's working directory against it left every reported path absolute. A selected MCP server's native startup waits for its handshake, which a hung server holds for the runtime's own startup bound; that bound matched the 30-second open deadline, so one hung Rulesync server failed every first prompt. Opening therefore disables unselected servers under the open deadline, where failure still rejects the session, and `McpStartup` starts the selected servers in a background task owned and aborted with the binding. Until startup settles, the MCP catalog reports each server's live native status, and settled failures then appear as startup errors. Copilot also holds queued turns until an in-flight MCP load settles, so a hung server would still stall the first prompt for the native bound. `McpStartup` therefore puts every start request on the wire before the binding is exposed, and while startup is unsettled each accepted prompt calls `session.mcp.moveLoadingToBackground`. That call releases only turns already waiting and reports `movedToBackground: false` otherwise, which is why it follows native acceptance of the input rather than startup; the released turn proceeds while servers join as they connect. An abort while input is still queued discards that input and emits only `abort`, with no `user.message` for it; whether an idle follows is not part of the native contract. A steer is queued this way until the next turn boundary, so a steer sent during a model call and an interrupt a few seconds later once left the prompt owner waiting for coverage the discarded steer could never get, until the ten-second grace force-stopped the client. `CopilotTurnEvent::observe_abort_terminal` therefore settles the execution on the first root event after the abort at which no root turn still runs and every send has settled, when some accepted input never reached a turn: each such input is covered as interrupted, so Harness settles its steering row as not confirmed read, and an abort before any turn started still settles as cancelled. An aborted idle covers discarded input the same way. Copilot can also hold steering until the current model call ends; when its `user.message` arrives inside the running root turn, `EventDecoder::consumed_input` publishes a completed user item carrying the steering submission, which is Copilot's consumption report: Harness keeps the acknowledged steering in the status area until then and places its row at that point, so the reply follows its prompt. The adapter classifies `model.*` telemetry, `agent.interrupted`, `session.usage_record`, and `prompt_cache_break` as carrying no normalized meaning, and `external_tool.requested` and `external_tool.completed` as owned by the SDK tool handler, so they raise no unsupported-event warning. Replacing submitted history disconnects its old SDK router before resuming the same ID; replacing a provisional session keeps the old binding until preparation succeeds. The host marks a specific binding as submitted before input can reach the provider, so an output-free cancellation cannot accidentally publish a new history boundary.

The published Copilot SDK still has internal unbounded queues and can hide router-level event loss. Forge-owned queue bounds do not remove that upstream limitation. The accepted scope and possible future SDK patch are documented in [limitations.md](../../../../limitations.md).

Copilot keeps an accepted `user.message` even when Harness interrupted its turn before the model answered, so after a resume the next prompt's turn once carried out the interrupted request alongside the new one. Every resume of retained Copilot history, including the replacement binding an access change installs, therefore runs `history_repair::repair`. Besides an incomplete trailing tool-call suffix, it truncates a trailing request followed only by turn opening, hooks, and the resume's own `session.model_change`, through the same `session.history.truncate` call, then rereads the history to verify the cut. `repair_cut` chooses one cut for both cases: when the turn that left a pending call never answered its request, removing only the call would leave that request as the history's last word, so the cut moves back to the request's `user.message`. A two-step repair once removed the call, then failed verification on the request it left behind and refused the provider open. The next prompt reports the repair as the `HistoryRepaired` notice; the removed request never reappears as a prompt or steer. Repair reads every agent's events, not only the main agent's, because Copilot chains each persisted event to the one appended before it, whichever agent wrote it. A call whose turn an abort closed is settled history although Copilot records no completion for it, and repair proves the abort by walking the turn end's ancestry back to the call's declaration; when the interrupted call was a delegated search and its agent had begun, the abort's parent is that agent's event, so a main-agent-only read broke the chain, left the call pending, and refused the open on every later prompt. When the incomplete suffix holds later answers, results, or requests, repair refuses the open as `HistoryConflict` rather than discard them, and the failure tells the user to continue in a new session. A Copilot access change is a detach and resume, so it takes about a second to show.

## Turn context

A model that acted on the permissions and task from conversation open would approve, write, or plan under settings the user has since changed, while repeating the whole Harness context on every turn costs about 1,000 tokens per message. Every adapter supplies its system or developer instructions only when it opens, resumes, or reconnects a conversation, so text that can change during a live binding cannot live there. Harness therefore sends that text as two typed standing sections (`forge_provider_api::forge::Permissions` and `Task`), each only when its value changes or the conversation may have lost it, in this order:

| Section | Contents |
| --- | --- |
| `permissions` | Tool approval, reject-all guidance under Deny, read and write access with their directory lists, and the `Toolsets` line. `"."` names the workspace; an invocation-only write root such as the planning directory shows as `Write access: planning directory only.` with that root as the only write directory. |
| `aside` | Present only in an aside session. Its `origin_session_id` and `origin_session_name` attributes name the origin, and its text states the aside's role and the tools that inspect and message the origin. |
| `agent` | Present only in a child agent's conversation, from `ProviderRequest::child_agent`. It carries the child's `path` and `parent` attributes, a sentence stating that each task arrives as an `<agent_message type="new_task">` and that Harness delivers the child's final response to its parent, and the profile's instructions in `<profile_instructions>`. The profile stands here rather than travelling with each task so that compaction, which clears the delivery record, sends it again instead of summarizing it away. |
| `task` | The active task, identified by its `kind` attribute. `plan` carries a `plan_id` attribute and holds the planning directory and authoring-guide path from `PlanAuthoringScope`, a sentence stating that each user message during the task is input to the plan, the user's original `<request>`, and the planning contract, during planning and plan discussion. `execute` carries execution, plan, phase, and revision attributes and holds `<phase_instructions>`, `<findings>`, `<approval_comments>`, and the accepted `<design>`. `goal` holds the `<objective>` and completion rule. `none` states that no task is active and replaces any earlier task. The task comes last because it is usually the longest section and the one the turn acts on. |

Every Harness-authored text after the open-time instructions is a typed value from `forge_provider_api::forge`, rendered into `<forge>` blocks by one writer. A turn's input is a `TurnInput` whose `TurnKind` states why the turn happens: a user message, plan discussion, check setup, a chat reply while questions are pending, a plan review question, a question response, recorded planning answers, a plan review decision, a check repair, a collected check result, child results, a parent's task for a child agent, a message from another session, an approval timeout, a Harness task step, or a Background request. The kind decides the data elements (`<question_response>`, `<recorded_answers>`, `<pending_questions>`, `<plan_review>` with its `<plan_edits>`, `<check_failures>`, `<check_result>`, `<agent_message>`, `<session_message>`) and the fixed `<instructions>` text, which `forge/instructions.rs` owns; callers never write instruction text, and `Notice` values add side conditions such as an approval timeout, a task start, a resume with a user message, or a repaired Copilot history. User text exists only in the kinds where the user typed something, and Harness never wraps it, because a model gives text quoted inside another message less authority than the user's own message. Text another model wrote is always wrapped, for the same reason: it must not arrive with the user's authority. A child's task and the messages its parent queued before the task started travel as `<agent_message type="new_task">` and `type="message"` elements, a child's report reaches its parent as `type="final_answer"`, and an aside's message reaches its origin as `<session_message>`. Each element names its sender, by agent path or session ID, and its kind's fixed instructions decide what the receiver does with it. Constructors reject empty failure lists, empty answer sets, empty review feedback, and child continuations without results.

No section lists host tools, because adapters receive each turn's tool definitions natively. `tools/toolsets.rs` names the toolsets that can change during a conversation by the prefix their tools share, or by their single tool: `lsp_*`, `harness_session_*`, `agent_*`, and `check_definition_edit`. Each tool family declares its name next to its catalog (`lsp::TOOLSET`, `session::TOOLSET`, `agents::TOOLSET`, and `checks::DEFINITION_EDIT`), and a test checks every tool in a family against it. `toolsets::requirement` states when each toolset or task tool is available; `ControlToolRegistry` appends that sentence to the advertised description, and `toolsets::unavailable_reason` returns the same sentence when a call is rejected. The control endpoint, check editing, planning's `plan_read` and `plan_edit` guard, and Codex all use that reason: Codex registers its catalog once per thread, so it asks `ProviderTools::unavailable_reason` when the model calls a tool the invocation does not allow.

`ProviderRequest::open_instructions` supplies the text that stays true for the whole conversation: `plan/prompts/system.md`, which holds the check, permission, and Harness inspection policy, the check shell name, `prompts/lsp.md`, which tells the model to prefer LSP tools when they are available, and `forge::overview`, which states that the system instructions always apply, that a newer standing section replaces only the earlier copy of that section, what a turn is, that agents address each other by path from `/root` (`forge::ROOT_AGENT_PATH`), which elements are instructions and which are information, and where blocks arrive for the provider's `ProviderIntegration::context_channel`. `ProviderRequest::standing_sections` builds the two typed sections. The turn's `PromptMode` selects the task: planning modes use the editable planning directory and the plan request, `ExecutePlan` and `GoalContinuation` use the `TaskInstructions` that `HarnessBroker::control_turn_context` resolves from the active execution and goal, and every other mode sends `none`. A paused task overrides that choice in every mode: `HarnessBroker::paused_task_instructions` resolves `TaskInstructions::Paused`, and the turn carries `<task kind="..." state="paused">` with the goal's objective, the plan's request, or the execution's title and a rule not to work on the task until `/task resume`, so a message sent while a task is paused never reads `none` on any provider. A user message during an Execute task is dispatched in `ExecutePlan` whatever the execution's state, so the turn always carries `<task kind="execute">` and the plan tools; plan reads stay available, and plan edits, revision submissions, and phase completion refuse with the execution's state and `/task resume` while the execution is paused, blocked, or not yet started.

Harness-produced inputs carry their `TurnInput` from where they are built to the adapter. `ProviderInput` is a `TurnInput` plus admitted attachments; task entries (`TaskEntry::instruction`), continuations (`TaskWork::Provider`), and queued Harness messages (`InputMessage::with_turn`, whose `text` is then only the display label from `TurnInput::label`) store the typed value, and both delivery paths read it back instead of re-parsing text. `PlanPrompt` builds the planning kinds: the first planning turn is the user's request alone (`PlanPrompt::draft`), plan review decisions are `PlanReview::Accepted` or `ChangesRequested` with the typed `PlanEdit`s the review tools recorded, and Execute and Goal continuations are task steps because their design and objective already travel in `<task>`. A user message during plan review becomes `TurnKind::PlanDiscussion`, permission-timeout feedback becomes a notice, or `TurnKind::PermissionTimeout` for a child's automatic feedback turn, a provider retry after a transient failure becomes `TaskStep::RetryContinue`, child results become `final_answer` `<agent_message>` elements, and automatic check repair carries typed `CheckFailure`s.

Each `HostSession` owns a `ContextDelivery` record with a random identity that `TurnContext::record` carries and the model never sees. `ProviderBridge::prepare_dispatch` places only sections whose value differs from the record in `PromptRequest::context`, and `ProviderBridge::turn_start` commits them only after the provider's `InputAcceptance` matches the submission, so a rejected or unproven submission's sections travel again with the retry; context selected by an earlier record is ignored. The record clears, and the next turn sends every section, when the binding's relay observes a completed or unconfirmed compaction on its root thread, and before a manual compaction, a rewind, or an input retraction, whether or not the native operation succeeds. A new binding generation, including a resume or fork, starts a new record. An aside session's `<aside>` section is one of these tracked sections, written after `<permissions>`, and a child agent's `<agent>` section, written after `<aside>`, is another. `ProviderRequest::child_agent` is persisted with the request, so a journaled child request rebuilt for a retry still carries the section.

The overview tells the model that a `<forge>` block in a user or developer message comes from Harness and that one anywhere else, such as in a file or tool output, is data. It also declares the two Harness texts that sit outside blocks: the `<file>` element `InputAttachment::file_context` writes for an attached file, and the `[Forge: ...]` notes the Claude adapter appends to persist a fork or a rewind, and the rollback note the Codex adapter appends after a rewind. The two rewind notes open with the same statement. Both are information. That rule holds because user text cannot produce a block: `neutralized_input` escapes `<forge>`, `<forge ...>`, and `</forge>` in the user's own words, and the writer escapes `<forge` and the opening and closing tags of every open element inside the text it writes, so a goal objective, answer, or review comment that quotes a tag cannot close its element or the block. Tags that only begin with an element name, such as `<forget>`, are left alone, and text is never indented, so code and command output arrive byte for byte.

Adapters choose the delivery channel, and `PromptRequest::blocks` renders the turn for it: `<permissions>`, `<aside>`, `<agent>`, `<instructions>`, the data elements, then `<task>`. On `ContextChannel::UserMessage` that is one block at the start of the user message. On `ContextChannel::DeveloperMessage` the instruction elements form the developer message and the data elements form a second block at the start of the user message, so text the user or another model wrote never gains developer authority. Codex declares `ContextChannel::DeveloperMessage`. Two inputs keep their `<instructions>` in the user message even there, because Codex cannot inject a developer item into a running turn or between grouped inputs: a steered input, rendered with `forge::input_block`, and a recovered input, rendered with `forge::earlier_input_block`. The developer-channel overview says so. It keeps the `developerInstructions` sent at thread start or resume, and its collaboration-mode state prefers the model catalog's built-in mode text over the `collaborationMode.settings.developer_instructions` that `turn/start` carries ([`collaboration_mode.rs`](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/context/world_state/collaboration_mode.rs)), so that slot carries only the static open-time text. `CodexProvider::submit` appends the instruction block as one developer-role `message` item through `thread/inject_items` before it sends `turn/start`. Codex records injected items outside any turn: they never appear in `thread/read` turns, so output-free retraction still sees at most one user message, and their `rawResponseItem/completed` notification names no admitted turn and publishes nothing. Codex records the user message itself only when the turn begins sampling, so an interrupt in the turn's first half second leaves an interrupted turn with no user message. `retractable_turn` accepts that empty turn as well as one whose only user message carries the cancelled submission's `clientId`, because the rollback authorization already proved the submission was the turn's only input; rejecting it kept such a prompt in history as `Cancelled 0s`. For the same reason `thread/revert`, which cuts history where its `beforeTurnId` turn starts (`ForkBoundary::BeforeTurn` in `codex-rs/thread-store/src/local/paginated_fork.rs`), keeps the developer item injected before the first removed turn. A rollback of a goal's start exchange therefore leaves the goal's `<instructions>` and `<task>` block in Codex's history even though the revert removes the start turn and every continuation, and `thread/revert` accepts no other boundary. Harness cannot remove that item, so `rewind_binding` voids it: once a revert that removed at least one turn passes its verification read, the adapter appends `turn_context::ROLLBACK_NOTE` as one developer item through `TurnContextDelivery::deliver`. The note is a `[Forge: ...]` history note that says the user rolled the conversation back to that point and that a `<forge>` developer message above it that follows the last completed turn belongs to the rolled-back interaction, whose `<task>` and `<instructions>` the model must not continue, quote as the user's instruction, or count as messages; the next turn's own block states the current task. A rewind that removed nothing sends no note, a runtime recorded as `Unsupported` skips it because its context traveled inside the reverted turns, and a failed note is traced as `provider.rewind.note_failed` without failing the completed rewind. A runtime without the method rejects it with an id-less `-32600` "unknown variant" error, which the RPC reader hands to the sole pending waiter. `NativeRpc::method_request` reports that rejection as `MethodReply::UnknownMethod`, `TurnContextDelivery` records `Unsupported`, and later turns place the block at the start of the user input without probing again. Any other injection failure fails turn preparation before `turn/start`, because a turn that starts without its current permissions is the failure this mechanism prevents. Every runtime request that `submit` makes before `turn/start` (`model/list`, skill paths, and the injection) races the input's cancellation through `unless_cancelled`. `cancel_invocation` waits for the preparing input to finish, and a loaded runtime once took about ten seconds to answer `thread/inject_items` while it reached its plugin service, which held a cancelled child, and its parent's stop, at `Stopping` for that long. No `turn/start` has been written when the wait is abandoned, so no native turn exists; the late reply finds no waiter, and an injection that may still land has already marked the thread's history as established.

Claude, Copilot, and ACP have no mid-conversation developer channel and keep the default `ContextChannel::UserMessage`, so their adapters place the block at the start of the user message, before the user's text. ACP agents without a native system prompt receive the open-time text wrapped as `<system_instructions>` (`forge::system_instructions_block`). Each recovered input is preceded by `RecoveredInput::block`, an `<earlier_input index="n"/>` marker with that input's own elements, and its words follow unwrapped. A steered input renders with `forge::input_block` and no standing sections. Background and isolated generation use `TurnKind::Background`, which renders no block. Adapters read the user's words with `TurnInput::user_input` and never inspect other kinds; the mock provider reads the plan ID from the typed task or the planning directory's last path component.

## Messages

Copilot reads `assistant.message_start` metadata before deltas and reconciles the matching `assistant.message` snapshot by message identity. Recognized phases are `commentary` and `final_answer`, and missing or unknown phases stay unclassified. If a successful invocation ends with commentary and no explicit final answer, the adapter emits that text again as a response with a new identity. An explicit empty final answer suppresses this, and failure or cancellation never produces a response. Root `assistant.idle` or `session.idle` supplies a terminal candidate. The former ends the main processing loop even when background terminals keep the native session busy. The candidate finishes execution only after in-flight sends settle and every accepted steering message is covered by native input observed before that idle boundary. An older idle cannot cover a later input, and a child idle cannot finish the root execution. Background terminal inventory remains observable after foreground completion.

Copilot correlates each accepted message ID with a root-envelope `user.message`, its native turn, and the event ancestry leading to completion. Root inputs can carry `parentAgentTaskId`; that field does not identify a child subscription. Events with an `agentId` cannot supply root input coverage. Ephemeral streaming and idle events refer to durable ancestry without becoming the parent of subsequent durable events.

A Copilot subagent's events carry its `agentId`, and the decoder publishes them through the child turn's own writer, which accepts only the child's thread and turn. Copilot also reports the subagent's context window as a `session.usage_info` under that `agentId`. Harness shows one context figure, the root conversation's, so the decoder drops a child's report: addressed to the root thread on the child's writer, it once failed the writer's scope check, and that ownership conflict failed the whole delegating turn.

Copilot's pre-tool hook names no tool call, so `permission::checkpoint_hooks` routes it by actor instead. A subagent's hook carries the subagent's `agentId` in its actor metadata and reports the subagent's own `sessionId`, which differs from the hook context's root session; `CallbackRouter::before_tool_native` then waits on that child's own host barrier, through the native IDs `observe_native_child` registered for it. A hook that names no subagent fences the root invocations, and is refused while a child is live because its owner is then ambiguous. Treating every hook as ambiguous once denied each read-only tool of the built-in Search Subagent before it ran, so the subagent returned an empty answer and the parent reported that nothing matched. A finished child's ID stays retired, so its late hooks are refused rather than left waiting. A refusal names its actor on the tool row: the decoder reads Copilot's `Denied by preToolUse hook:` prefix and reports Harness's own barrier apart from another hook and from a refusal the provider reports without an actor.

The decoder publishes a subagent as `running` once its own turn starts. A synchronous subagent runs inside its delegating tool call, and Copilot's `abort` ends the root turn while leaving the subagent's turn open; it reports the subagent's cancellation only when the session shuts down. `CopilotEventDecoder::interrupt_synchronous_children` therefore ends every live synchronous child at the root `abort`: it interrupts the child's open items, finishes the child as `Interrupted`, which the transcript shows as `cancelled`, completes its turn, and retires its callback authority, so the child runs no further tools. Later events of such a child are discarded. The host ends the same children at the user's cancel request, before Copilot's `abort` arrives, and discards whatever they report afterwards; "Child ownership" in [child-agents.md](child-agents.md) describes that fence, which also covers a subagent that finished before the stop reached Copilot. A subagent Copilot runs with `executionMode: "background"` outlives its delegating turn and is not ended this way. A native child's exchange records no checkpoints of its own, because the delegating exchange's checkpoints cover its edits, so it shows no edits notice.

Codex keeps the phase from `item/started` for matching deltas and snapshots. ACP assigns message identities within its execution. Consecutive chunks of the same kind join one message only while their optional native `messageId` matches, so two adjacent API messages stay separate items; agents that omit `messageId` join on kind alone. ACP carries no phase, so `AcpSession` leaves prose unclassified until the first `tool_call` or `tool_call_update` for a tool-call ID it has not seen before. That event marks all pending prose as commentary, and the end of the turn marks the last unclassified message as the response. The end of the turn settles that role whatever the outcome: Harness hides an interrupted response and keeps other prose, so a reply left unclassified at an interruption stayed in the transcript while Codex and Copilot replies, which carry their phase from the start, left it. Updates to tools that are already known do not classify anything, because an agent can report a terminal status for an earlier, abandoned tool after it has written the final answer. Claude Code classifies prose from richer evidence, described under [Claude Code](#claude-code). Adapters never assign tools or checks to commentary, because `Exchange` captures each activity's owner at admission.

## Tools

`ItemStart` fixes each item's family: user message, assistant prose, full or summarized reasoning, command execution, file change, or another tool call. Message classification distinguishes unclassified prose from positively identified commentary or response text; reasoning uses `ReasoningKind` independently. `MessageCompletion` replaces accumulated deltas with final or interrupted text.

Tool descriptors, argument fragments, positive execution evidence, output, native file observations, and outcomes are typed item events under the original identity. `ToolItemEvent::DescriptorUpdated` preserves later validated metadata without creating another item. `ToolCompletion` retains its outcome and any final descriptor/output snapshots; an omitted snapshot preserves previously observed content. Conflicting type, owner, or final-snapshot replay fails atomically. Committed LSP edits are separate `HostFileChange` effects, identified by the original authenticated callback scope and host call ID. They never fabricate a native `Item.Tool.Changes` event or modify a native final snapshot. A native item is attached only after positive correlation. Each adapter also supplies `ToolSemantics`: a command with its shell and working directory, explicit read targets, or an unclassified operation. Skill attribution consumes that metadata and waits for successful completion. The broker and renderer never infer an operation from a native tool name or argument schema.

Codex classifies activity by top-level item type. Before titles enter durable state, the transport replaces values under credential-like keys, such as `token`, `api_key`, `password`, and `authorization`, with `[REDACTED]`. Shell headings summarize simple reads and searches after decoding the launcher, and the durable command never changes. ACP tool updates merge by tool-call identity, and structured diff content becomes a `ProviderChangeSet` without reading the workspace. Antigravity edits can complete without diff content, so `/capabilities` marks its file diffs as limited. A commentary's **Edits** section lists reported operations; the exchange's **Edits** summary uses checkpoint comparisons.

For the Codex event mapping verified against 0.164.0, background lifetime needs positive evidence: an empty-stdin `terminalInteraction` reports a still-live session, or a started `CommandExecution` has `unifiedExecStartup`, `InProgress`, a nonempty process ID, and no reported exit when the root ends normally. A process ID, pending status, or nonempty terminal input alone is insufficient. This retention rule follows the [process manager](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/unified_exec/process_manager.rs), [exit watcher](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/unified_exec/async_watcher.rs), and [normal task completion](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/tasks/mod.rs): process startup precedes the startup event, exit/drain ends the command, and normal task completion retains the session process manager. The adapter does not issue an optional inventory RPC to infer lifetime at root completion.

Interrupted or failed foreground work without positive yield/exit evidence cannot use that normal-completion retention rule. Missing collection evidence produces an explicit observation/collection failure while retaining the native outcome and resource ownership; it cannot manufacture successful cleanup or authorize killing an independent terminal. Raw-event availability differs between cold thread creation and resumed listeners, so absence of a raw yield event is not proof of native exit.

`ControlToolRegistry` assembles family catalogs under `tools/`. Each tool has its own file containing its description, schema, and handler. Shared schemas and services stay within their family; provider adapters use the same catalog and invocation boundary. `ControlToolExecutor` owns the shared lifecycle for every adapter's control callbacks. It serializes runtime mutations, and cancellation interrupts tool waits and lock waiters. A new turn gets a fresh executor, so late results from an earlier generation are rejected.

Tool families are organized by purpose:

```text
tools/
  agents/       child-agent tools
  checks/       check definitions and execution
  goals/        goal status and completion
  lsp/          editor source queries
  plan/         semantic file edits and the plan overview
  questions/    asynchronous questions and answers
  repository/   Git status and diffs
  session/      session history and inspection
  config.rs     Harness configuration inspection
```

The plan overview owns its check selection alongside planned tests and manual verification. Tool descriptions use multiline literals, and detailed field guidance belongs to the tool schema rather than the planning prompt. Domain modules such as `plan/`, `checks/`, and `agent/` retain their state and business operations.

Tool handlers return `ToolResult` with explicit `ToolError` variants and conversions from lower-level errors. One response renderer preserves structured failure details and retry information across providers. Turn admission and cancellation remain transport errors so adapters can stop stale work before publishing a tool response.

## Attachments

Attachments resolve against the Harness data root at admission and stay separate from prompt text. Images get each provider's native form: `localImage` items for Codex, the file attachment list for Copilot, and base64 content for ACP when the agent advertises `promptCapabilities.image`. Unsupported image input fails before the prompt activates. PDFs and other files are passed as retained-file context, never as silently extracted text.

## Execution and cancellation

Harness workflow intent never crosses the provider boundary. `PromptRequest` carries a provider-neutral `ExecutionMode`, which is `Planning` for plan drafting, discussion, and review questions and `Default` otherwise; ACP maps `Planning` to a native plan mode when the agent offers one. Task starts arrive as host-prepared text: Harness renders the "Goal started", "Plan started", or "Execution started" heading ahead of the task's own input before the request reaches any adapter, so every provider receives the same announcement and none inspects task kinds.

Native adapters signal stop before collecting local callbacks. Codex sends `turn/interrupt`, Copilot sends abort and repeats it to cover a pending send, and ACP revokes callback authority and stops its process tree.

Copilot acknowledges `session.send` before it begins the message's turn, and an abort in that moment does not prevent the turn: Copilot reports the abort and then runs the message anyway. The adapter had already settled the message as discarded by the abort, so the late `assistant.turn_start` had no owner, the event intake rejected it as unexpected execution, the client generation failed under the pending abort ("request cancelled"), and Harness restarted the provider for a `Ctrl+C` sent a fraction of a second after submitting. `BindingState::interrupt` therefore first waits, for at most two seconds, in `CopilotTurnEvent::wait_native_start` until an accepted input's root turn starts, the invocation reaches its terminal boundary, or its observer leaves; the abort then interrupts a running turn. A turn that has not started within the grace, as one held by a slow MCP load, is aborted while still queued and settles as discarded. Copilot allows ten seconds for that wait, abort, pending sends, and the native prompt task to settle. An abort acknowledgement alone does not prove termination. If that grace expires, or interruption fails while the native task remains active, `BindingState::interrupt` fails the shared SDK generation and force-stops its client. Every session on that generation loses observation; recovery must collect it before admitting replacement work. Host restart retires the owner through `thread_close` first, and closing a binding on the force-stopped client once failed with the generation's observation failure, because terminal and session teardown are native RPCs the dead client cannot answer; the restart then failed and the session stayed unavailable. `close_binding` therefore first collects any failed generation with all its bindings, so the close succeeds and the replacement opens on a new client. The grace excludes host callback collection, which retains ownership independently. Neither timeout nor client termination fabricates a successful `Turn.Completed`.

Cancellation before native dispatch keeps its typed cancellation result at every journal and host-admission gate. The execution owner captures the prevented submission and attempt identities before starting asynchronous collection. Completion may remove the live attempt while collection runs; the collection result retains that proof so a matching configuration replacement remains authorized. A newer cancellation fence still rejects an older replacement.

Codex callbacks run outside the socket reader, so an LSP lookup or approval cannot block steering or cancellation. Steering targets the exact active invocation. Codex reports a steer's consumption as a `userMessage` item whose `clientId` matches the `clientUserMessageId` sent on `turn/steer`; [`record_pending_input` in Codex 0.164.0](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/hook_runtime.rs#L673) passes that ID into the recorded user prompt, and `codex/normalization.rs` publishes the item with its submission ID. Shared Harness owns continuation after child completion and submits separately journaled ordinary input with a fresh invocation identity after native settlement and host commit. Adapters never schedule autonomous continuation or reopen settled work.

Codex socket intake and notification dispatch retain incoming frames without an aggregate byte ceiling. Control replies can reach their waiters while tool notifications await consumption. Shared host queues and the Copilot adapter use the explicitly selected 4096-frame capacity; the Copilot SDK subscription is configured to the same capacity for both new and resumed sessions. Observation failures retain their normalized category through execution failure and stream closure.

Copilot intake and shared Harness observation queues grow in memory while their consumers are delayed; they neither truncate valid output nor cancel a conversation because a fixed event count was reached. The encoded transport uses bounded frames and waits for byte capacity; larger events cross it in ordered chunks. Copilot's SDK retains its own finite broadcast buffer, so Forge drains that subscription independently of presentation. SDK lag remains observation loss rather than proof of native completion. Sustained backlog can increase memory use.

Copilot creation, resume, and model changes request concise reasoning summaries. The decoder
therefore classifies `assistant.reasoning_delta` and `assistant.reasoning` as
`ReasoningKind::Summary`, including a completed snapshot without preceding deltas. The status
renderer selects that classification; full reasoning and assistant commentary remain distinct.

Copilot intake closes its foreground sender before acquiring the decoder context to report failure, allowing a prompt that holds that context to finish. The session task drops its adapter future before terminal publication, releasing execution guards during cancellation. A force-stopped client marks its shared runtime generation unavailable; recovery collects that generation before starting or attaching a replacement. Recovery resumes the saved native conversation and never replays an uncertain prompt automatically. `turn_interrupt` awaits collection of the exact invocation while preserving session reuse. `thread_close` immediately revokes admission and callback authority, then collects readers, terminals, profiles, and callbacks. Failed close retains its first failure and unfinished ownership for retry. Normal completion passes through the retained runner, which collects foreground resources before publishing `Turn.Completed`. An execution start after that boundary invalidates admission rather than reopening committed work; a delayed cancellation still names its original invocation.

A Copilot shell command runs as a task of the binding's private helper session, where `session.abort` on the model session cannot reach it, so an interrupted turn once left its command running as a background terminal until the command ended by itself. `ShellSession::execute_owned` owns each launch's foreground wait, and `ShellSession::cancel_waits` publishes the invocation's revocation before it wakes that wait. A launch released while its invocation is revoked stops its own native task through `ShellSession::stop_task`, which cancels the task and publishes the refreshed inventory, and returns `Cancelled` without reading output for the stopped model turn. Copilot runs each command through its own wrapper process (`pwsh -NoProfile -NonInteractive -Command` on Windows, a child of `copilot-runtime --server --stdio`), and `session.tasks.cancel` stops only that wrapper: the command's own processes, such as `nu.exe` under `nu -c "sleep 60sec"`, kept running with a dead parent until they exited by themselves. Before cancelling, the launch therefore reads the wrapper's id from `session.tasks.getProgress` and captures the wrapper's descendants with `forge_shell::process_tree`, and after cancelling it stops those that survive, deepest first. Each captured identity pairs the process id with its creation time, so a reused id is never stopped, and `command_descendants` selects nothing unless the wrapper is a grandchild of the Forge process through the runtime it launched, which rejects both a reused wrapper id and a provider that reports its runtime's own id. The wrapper itself is left to Copilot's cancellation. A failure to read the tree leaves the command to Copilot's cancellation alone. `Driver::collect` awaits `ShellSession::settle_revoked_launches` before the turn reports completion, so the inventory update precedes `Turn.Completed`. Steering calls only `interrupt_waits`, which releases the wait and leaves the command running. A launch in `async` mode, a launch with a zero wait, and a command that outlived its wait are background terminals: they survive interruption and stop only through the terminal picker or binding close. Copilot may run a long command that looks like a foreground command as an `async` launch followed by a `read_powershell` or `read_bash` call with a long delay; an interrupt then releases only the read, and the command stays listed under `1 terminal running` until it exits or the user stops it from the terminal picker.

Copilot cancellation reads native task identities independently of terminal presentation, in both the model session and its private shell helper. Both paths use the same live-background-shell selection as display, but only display requires a command label. Missing or invalid identities still reject collection explicitly. The helper re-reads the task inventory after cancellation and retains ownership until no matching tasks or unsettled launches remain; missing display metadata cannot prevent that absence check or substitute for it. Only a lost `session.tools.execute` reply leaves a launch uncertain; any reply settles it, including a rejection the adapter cannot classify. An uncertain launch stays retained for that collection but does not refuse later launches, which carry their own identities. A rejected permission returns the native result kind `denied` (with feedback, such as the reason Harness gives for a denial or an expired approval) or `rejected` (without feedback), and `NativeToolResult::into_sdk` hands the model that kind and text unchanged, so the model reads the reason and the event decoder records the call as denied.

Provider shutdown collects bound and provisional session intake before stopping the SDK client. Otherwise SDK detach closes a still-observed subscription, and intake mistakes orderly shutdown for observation loss and force-stops the transport while shutdown RPCs are pending. Successful SDK collection marks every shared session handle stopped, preventing later cleanup from issuing detach or abort RPCs against the closed transport. SDK stop errors remain explicit and retryable.

[Provider retries](../provider-retries.md) defines when a failed request is retried.

## Claude Code

The Claude ACP adapter hid the CLI's command lifecycle, so Forge could not tell a folded steer from a lost one, and it could neither rewind nor fork at a checkpoint. `ClaudeProvider` in `forge-providers/src/claude/` therefore drives `claude -p` directly over its stream-json protocol, the protocol the Claude Agent SDKs use. `ClaudeTransport` owns one process: it writes newline-delimited user frames and control requests to stdin, decodes every stdout line into a typed `StdoutFrame`, delivers ordinary frames in order, and answers each inbound control request on its own task so a pending permission never blocks the stream. Unknown frame kinds decode to `Unknown` rather than failing, and `ClaudeSessionState` reports each kind once as `UnsupportedNativeEvent`.

Launch arguments pin the CLI to Forge's authority. `--permission-prompt-tool=stdio` with a session-level `permissions.ask: ["*"]` setting routes every tool through a `can_use_tool` control request, which `ClaudeSessionState::authorize` resolves through the invocation's `ProviderPermissions`. `--setting-sources=project,local` keeps user-level settings from granting tools outside Harness, and `--strict-mcp-config` admits only the MCP servers Harness selected. Selected servers can carry credentials such as bearer headers, and any local process can read another process's command line, so `launch_spec` writes the server configuration to `forge-mcp-config.json` in the session's private profile and passes that path to `--mcp-config`. Harness control tools reach the CLI as an in-process SDK MCP server named `forge-harness-control`: the CLI sends `mcp_message` control requests, and `host_tools::handle` answers `initialize` and `tools/list` from the invocation's tool list and routes `tools/call` to `ProviderTools` with the CLI's tool-use ID. `--disallowedTools` removes native agents, background tasks, schedulers, worktrees, and questions, because Harness owns those workflows. Skills arrive through a per-session `--plugin-dir` profile.

Each turn applies its model, effort, and plan mode with `set_model`, `apply_flag_settings`, and `set_permission_mode` control requests before writing the prompt, so a `/model` or `/plan` change takes effect at the next prompt without restarting the process. A change to MCP servers or skills restarts the process with `--resume`, which keeps history.

The turn boundary comes from the CLI's own evidence. Every user frame carries a Forge-minted `uuid`, and `command_lifecycle` frames report it `queued`, `started`, and `completed`. A steer that reaches the model mid-turn completes before the turn's `result`; a steer that arrives too late is still queued at that `result` and starts another CLI turn. `ClaudeSessionState` decides the Forge turn's end under its active-turn lock: a `result` ends it only when no tracked command is queued or unseen, and an interrupt always ends it. Once the end is decided, `track_command` refuses further steers, so Harness resubmits them as prompts. `interrupt{cancel_queued: true}` stops the turn and drops queued steers, and the CLI's `aborted_streaming` or `aborted_tools` terminal reason maps to `Interrupted`. An interrupt that reaches an input the CLI has not started, as while the CLI is still starting after a resume or a fork, cancels that input instead: the CLI reports it `cancelled` in `command_lifecycle` and prints no `result`, because no CLI turn ran for it. `ClaudeSessionState::command_lifecycle` therefore ends the Forge turn as `Interrupted` from that cancellation once no CLI turn is running and no tracked input is waiting to start one, and the binding stays usable for the next prompt. A CLI that neither ends its turn nor cancels its input within `INTERRUPT_GRACE` of an interrupt is wedged, so the provider invalidates the binding, which ends the turn and lets Harness restart the provider. The same bound covers a CLI that never acknowledges the prompt at all. `deliver_input` waits for `command_lifecycle queued` before it reports the prompt accepted, and a turn start has no deadline of its own, so a frozen CLI once held that wait, and every cancel behind it, forever. A cancellation that arrives during that wait now gives the CLI `INTERRUPT_GRACE` to acknowledge the written prompt and then fails the delivery, which invalidates the binding the same way. A steer's acknowledgement wait takes the same bound from its turn's cancellation, because the turn ends only after every steer's delivery settles. After the `result`, the adapter classifies the reply and closes the turn's items before it asks `get_context_usage` for the status-line context figure. That query, like the startup query for instruction sources, races the turn's cancellation and `CONTEXT_USAGE_DEADLINE`, three seconds, and goes without the answer when either fires: a CLI once left it unanswered for ten minutes after a finished turn, which kept the turn `Working`, its reply in the Thinking fold, and its interrupt `Stopping` until the answer came. An interrupt that arrives after the `result` therefore ends the turn at once, without an `interrupt` request, since the CLI already ended its turn. `ClaudeProvider::cancel_invocation` waits at most `INTERRUPT_SETTLEMENT_GRACE`, twenty seconds and under the 30-second stop response deadline, for the turn to settle; a turn still unsettled then invalidates the binding, so the stop fails and Harness restarts the provider instead of leaving the session `Stopping`.

A cancel can also arrive before the prompt is written. `run_prompt` waits in `TurnControl::before_send` while Harness captures the turn's baseline checkpoint, and `submit` has installed the turn's settlement record by then, so the interrupt finds a turn to collect. That turn settles as a pre-dispatch rejection: `PreparationFailed`, or `PreparationCleanup` when Harness has already retired the journal entry that `reject_before_dispatch` then tries to reject. Nothing reached the CLI in either case, so `turn_runner::interrupt_outcome` reports the interrupt collected, as it does for a turn that completed or ended `Cancelled`. A cleanup failure that invalidates the binding, a preparation that failed for another reason, and a native failure remain interrupt failures. `cancel_invocation` once accepted only a bare `Cancelled`, so every cancel inside the checkpoint window failed its stop and made Harness restart a healthy provider. The ACP adapter installs its settlement before the same wait, and `AcpProvider::cancel_invocation` uses the same classification.

Claude declares no `native_turn_rollback`. Dropping a turn requires `rewind_session`, which restarts the process, so `retract_input` answers `NeverConsumed` only for an input in `rejected_inputs` and `Unsupported` for an interrupted turn the CLI accepted. Harness therefore returns a cancelled prompt to the composer on Claude Code only on proof that the CLI never accepted it, which in practice is a cancel that lands before `run_prompt` writes the prompt. Once the CLI reports the input `queued`, an interrupted exchange stays in history as cancelled even when it produced no output.

The CLI's own history needs repair after such an exchange. An interrupt that lands before the CLI records any assistant or tool-result entry for the turn leaves the prompt and a `[Request interrupted by user]` marker as consecutive user entries, and the API joins consecutive user entries into one message, so the next prompt reached the model in the same message as the cancelled request. A trace of the pinned 2.1.317 CLI after a steer and a stop shows the CLI discarding the queued steer (`cleared_on_cancel`) and the model then writing the cancelled prompt's essay as its answer to a one-word request. The adapter therefore marks such a turn `unanswered` in the binding's ledger, together with the chain entry its prompt `follows`, which `history_tip` knows only while `fork_point` does, because a compaction or a turn without a checkpoint appends entries the adapter cannot name. Before the next prompt, compaction, or fork, `withdraw_unanswered_request` restarts the CLI with `--resume-session-at` at that entry, unguarded because the marker is a user entry, appends a note that makes the truncation durable, and closes that process to publish the kept branch before resuming. When the entry is unknown, as for the first prompt of a resumed binding, or the CLI refuses the resume, a note written with `shouldQuery: false` withdraws the request instead and tells the model to answer only what follows. A stop can also leave an unanswered request behind an answered checkpoint. A steer still queued at a CLI turn's `result` starts a follow-up CLI turn after the answer, and the CLI records the steer as a user entry of its own; a stop before the follow-up answers leaves that entry and the marker after the turn's checkpoint. A steer that Harness resubmitted as a prompt, because it arrived after the turn ended, leaves them after the previous turn even though its turn reports no execution and settles as `Cancelled`. `ClaudeSessionState` sets `unanswered_input` when the CLI starts an input of the turn and clears it at each assistant entry, `TurnEnd::unanswered` reports it, and `run_prompt` records every such turn in the ledger, the cancelled one included; `withdraw_unanswered_request` then resumes at the turn's own checkpoint when it has one. The removal also keeps the ledger's positions true. The guarded resume of a later rewind refuses a discarded range that does not start with the dropped turn's prompt, and the steer's entry and marker once made the rollback of the exchange after such a stop fail twice with `ThreadRewind failed: Rejected`. Harness still shows the cancelled exchange and lists any steer it carried as not confirmed read.

The same lifecycle supplies steering's consumption evidence. A trace of the pinned 2.1.317 CLI, steered with `haiku` in stream-json mode, shows `command_lifecycle started` for a steer at the moment it joins the next model request, in both of its paths. A steer written while a tool runs is `queued` at once and `started` right after that tool's result, immediately before the `requesting` status of the call that reads it. A steer written while the model streams pure text stays `queued` through that CLI turn's `result`; the CLI then reports the prompt `completed`, the steer `started`, opens a follow-up CLI turn with a new `system init`, and streams the output that uses it. The CLI never echoes a steer as a `user` frame, so `started` is the only boundary. `steer_session` records each journaled steer through `ClaudeSessionState::record_steering` before it writes the frame, keyed by the frame `uuid` and holding the submission ID, the steering invocation, and the user's text from `user_text`. `ClaudeSessionState::command_lifecycle` moves the record to `started_steering` on `started`, and the first stream event or assistant frame that produces output publishes, before that output, a completed user item carrying the text and submission ID on the active turn's address, but only while that turn still belongs to the recorded invocation. A stop that ends the request before any output leaves the steer unreported, so Harness lists it as not confirmed read, which holds, because the adapter withdraws the request from the CLI history. A report at `started` drew such a steer in prompt styling directly below the cancelled heading with nothing after it, which read as an exchange without an outcome. `cancelled`, and `completed` without a preceding `started`, remove the record without publishing; `forget_command` removes it when the write failed, `finish` drops started and unstarted records of the retiring invocation, and `invalidate_binding` clears them all. The turn's own prompt and context-only steering (`SteeringDelivery::Context`) are never recorded, because an echo without a submission ID would become an ordinary transcript row. The deferred follow-up CLI turn stays inside the same Forge turn, so its consumption report precedes its output within one Harness turn.

Stream events carry the API message ID and content-block index, so text and thinking deltas build separate items keyed by both, and thinking becomes a reasoning summary because the CLI runs with `--thinking-display=summarized`. A `message_delta` whose stop reason is `tool_use` marks pending prose as commentary before the tool starts, and the end of the turn, completed or interrupted, marks the last pending prose as the response, for the reason given under [Messages](#messages). Complete assistant frames reconcile any text the stream missed. A turn's token usage comes from its `result`. Its duration is the sum of the `duration_ms` of the CLI turns whose `result` reported usage, because Harness divides the reported output by it: a steered turn whose follow-up CLI turn a stop ended before any message once reported only that follow-up's 53 ms, and the heading read 18,358 tokens per second for a three-second answer. A result the client aborted mid-stream reports zero usage although its API message already consumed the prompt, so `ClaudeSessionState` retains each API message's latest usage from `message_start`, assistant frames, and `message_delta`, and reports their sum for an interrupted result that counts nothing; with nothing retained it reports no usage, and the heading shows no token figures. An output count is final only in a `message_delta` that names a stop reason: the CLI copies the `message_start` count into the message's assistant frames, and when a stream is abandoned the CLI closes it with its own `message_delta` that copies the partial message's null stop reason and that same start count. Interrupted long answers reported such start counts, five and eight tokens, as their output, and a rate of 1 token per second over the whole turn. For a result that did not succeed, whether the adapter interrupted the turn or the CLI ended it for a reason the adapter does not recognize, the report carries an output figure only when at least one message was retained and every retained message has its final count; otherwise the heading shows the input figures without output or throughput. The adapter records the decision as a `provider.usage.settled` trace event naming the result's subtype and terminal reason, each retained message's `final` or `provisional` count, and the branch taken, because the stream frames themselves are not retained. Tool results carry structured `tool_use_result` payloads, and Write and Edit results become `ProviderChangeSet` diffs of their original and new contents. When the client interrupts a turn, the CLI closes each running tool with an error `tool_result`; that result reports the interruption rather than a failure of the tool, so an error result that arrives while the turn is being interrupted completes its tool as `ToolOutcome::Interrupted`, as the tools the CLI leaves without any result do.

Conversation rollback keeps the active CLI when the binding's ledger can identify the first prompt after the retained transcript entry. The `rewind_conversation` control receives that prompt's UUID and the most recent observed input UUID. It cuts before the prompt, persists the kept branch, and confirms the removed prompt's identity. The adapter truncates its ledger only after that confirmation. A refusal that protects later history leaves the binding in place and reports the reason. A failed persistence attempt or an uncertain reply invalidates the binding before it can admit more input.

When the binding cannot identify the first discarded prompt or Claude cannot locate it, rollback resumes at the retained entry with `--resume-session-at`. The adapter adds `--resume-drops-turn` when it can verify that one turn owns the discarded suffix, appends a `shouldQuery: false` note to persist the truncation, and calls `commit_truncation` to publish the kept branch and reopen it. `ClaudeConversation::restart` retires the old transport before closing it so that deliberate replacement preserves binding admission. A CLI process records its newest entry as the transcript's leaf checkpoint (a `last-prompt` record) only when it exits, and a later resume or fork loads the chain of the newest checkpoint unless the transcript's newest entry follows it, finding `--resume-session-at` only in that chain. The process a truncation replaces records the discarded branch as it exits, so until the truncating process exited too, every other process loaded the discarded branch: a checkpoint fork at an answer given after a stopped request was withdrawn failed with `No message found with message.uuid`, and a plain resume would have brought the withdrawn request back. The truncating process's exit records the note, which every later entry follows. This costs one additional CLI launch for a truncation that uses a launch flag. The CLI refuses a `--resume-drops-turn` resume, and exits before its initialize answer, when the discarded range does not start with the declared prompt or holds another user entry, and a rewind note is such an entry. The binding's `LedgerTurn` therefore remembers the note written after the turn a rewind kept: a later rewind that keeps that turn again resumes at the note, so the next turn's prompt opens the discarded range, and a rewind that drops a turn followed by a note runs unguarded. The guard also refuses a range holding absorbed queued content: the CLI records each steer a running turn absorbed, a Harness check-result delivery included, as a `queued_command` attachment, and the guard reported `range contains absorbed queued content` for the start of a goal whose first turn had received its check results. `LedgerTurn::absorbed_steering` records whether the CLI turn consumed any input after its prompt, and a rewind that drops such a turn runs unguarded, because the steer belongs to the dropped Harness exchange. The CLI prints the reason for a refused launch as an error `result` before it exits, and `ProcessFrames` keeps the errors of a `result` that arrives before the handshake, so `launch` logs the reason as the `error` field of `provider.startup.refused`, the one free-text field the host log keeps, and returns the failure as `ProviderError::Explained`, whose display appends the CLI's words to the normalized cause, so a refused fork's notice states the reason. The closed output alone once left the host log with only "Claude Code closed its output" and the notice with "provider ThreadFork failed: Initialization". A refused rewind resumes the original history and reports `Rejected` without changing it, and rewinding before the first turn has no transcript entry to resume at and is rejected. A compaction writes a boundary entry with no parent, so the chain the CLI loads begins there and `--resume-session-at` names no earlier entry; the CLI exits with `No message found with message.uuid`, which the adapter reports as `Rejected`. The registry therefore declares `conversation_rewind_stops_at_compaction`, and Harness refuses such a rollback before confirmation. Fork starts a short-lived process with `--resume`, `--fork-session`, and a Forge-minted `--session-id`, writes a note that runs no model turn, and waits for its completion, so the target history exists before the result returns. A rewind leaves the discarded turns in the transcript beside the kept history, and an unpositioned `--fork-session` copied the discarded branch, so a fork that followed an `/undo` gave the model the rolled-back prompts. `ClaudeBinding::fork_point` therefore holds the last entry of the kept history, the newest turn's checkpoint or the checkpoint a rewind kept, and a binding fork passes it as `--resume-session-at`; a checkpoint fork passes its checkpoint. A turn without a checkpoint and a compaction append entries the adapter cannot name, so they clear the point, and the fork then takes the CLI's own leaf. The note is the fork target's newest entry, and a plain resume of a trailing user entry makes the CLI add a synthetic "No response requested." reply that the model reads. `UnstartedSessions` therefore records each target forked at a named point until its first turn ends, and `launch_conversation` resumes such a target at that point, which discards the note when the first prompt is appended. The record lives in the provider, so a target first opened after an editor restart resumes plainly and shows the note. Workspace model discovery uses a process with `--no-session-persistence`.

The CLI writes a conversation to disk when its first turn runs, so the session id `thread_open` mints names nothing until then: `--resume` of that id prints "No conversation found" and the CLI exits before its handshake. Two operations once resumed it anyway. The provider restart that follows a failed stop reopened the session and failed every later prompt with a `ThreadOpen` initialization failure, and a change to MCP servers or skills before the first prompt invalidated the binding. `UnstartedSessions` therefore records each minted id until a turn the CLI started ends, and `launch_conversation` starts such a conversation again under `--session-id` when its resume fails initialization. It attempts the resume first because only the CLI knows whether a prompt it received before it froze reached disk. An id that ran a turn is never started again, since that would replace history Harness still shows. `ProcessFrames` withholds a process's exit from `ClaudeSessionState` until its initialize handshake completes, so the failed resume cannot invalidate the state the second launch serves; `launch` returns the failure to its caller instead. The record lives in the provider, so it does not survive an editor restart: there Harness clears a provider session id that its submission journal proves unconsumed. Harness requests no native fork of a session that holds no provider turn, so `fork_session` never receives one.

## ACP

`AcpConversation` in `forge-providers` owns each ACP v1 connection, handshake, model configuration, and native event state for Antigravity's standalone ACP server. The shared bridge owns the control endpoint and permission context; the native owner retains the resource lease with its binding. Harness control tools reach ACP agents through a private loopback MCP endpoint of at most 16 connections.

Provider restart reloads the same native conversation, and failing to load it fails configuration instead of creating replacement history. Initialization rejects agents that cannot load conversations. Advertised child sessions enter the shared agent registry, at most 256 per prompt, and become interrupted when the root prompt returns. `AcpRuntime` resolves configured adapters and never installs provider runtimes.

An agent notice glued to the answer misreports a startup failure as model speech, so the handshake advertises `session.notices`, and `AcpSession::notice` publishes a `sessionUpdate: "notice"` title and description as a thread-scoped `NativeNotice` warning. The same session publishes `ModelResolved` when a turn's native execution first starts, reading the session's current model from `/models/currentModelId` or the `model` configuration option, because ACP turns carry no per-turn model evidence. An agent can re-send an unchanged notice, such as an MCP server startup failure, with every turn, so `AcpSession` remembers the notice text it has published and drops exact repeats for the session's lifetime.

A tool update reports its execution start when the native status is `in_progress`, or when it reaches `completed` or `failed` without an `in_progress` update in between. An agent can report quick tools straight from `pending` to `completed`, and without a start the transcript rendered the row with an empty duration slot. A cancelled tool never ran and records no start.

An agent can route approval of its own native tools through `session/request_permission` without file or command targets. An untargeted request would normalize to `Unknown`, which the Harness matcher denies without a prompt, so `native_tool_targets` names the request by its title. A tool search that selects only `mcp__forge-harness-control__*` tools inherits Harness control-tool authority as `HostTool`; every other named tool becomes an askable `Tool` target, and only a nameless request stays `Unknown`. ACP model, skill, and MCP catalogs require an open binding: a workspace query before the first lazy open reports `ModelSelection` as unsupported.

## Approvals and sandboxing

All three approval modes keep identical native callback setup, and Harness applies Ask, Deny, or Allow after saved rules and reported-file checks. Native operations without callbacks stay outside that boundary. Changing the approval mode therefore never reconfigures a provider; the new mode applies to callbacks already bound to the running turn. Access and shell changes still reconfigure the provider natively.

Each adapter names the host tool item its approval gates in `PermissionRequest::subject`, because only the adapter holds the native-to-host identity mapping. Codex looks up the host item for the request's `itemId` or `callId` in its normalization state, Claude reads the decoder's admitted tool by `tool_use_id`, ACP reads its admitted tool by `(session_id, toolCallId)`, and Copilot records each native call's host item when its event decoder starts the tool, then resolves the callback's call ID through that record. A request whose item is not yet admitted is `Unattached`. Harness uses the subject to suspend that tool's deadline while the approval waits. Antigravity enterprise terminal policy can run commands without a callback, so its approval capability is limited. After a Copilot denial, completion requires a later final answer or Harness handoff, and provider idle without either fails the exchange. Codex's decline reply has no reason field and the declined item it then reports names none, so the adapter records the host's answer in `CodexNormalization` by host turn and native item when it answers the approval (`ApprovalRefusal`), and the declined item completes as `ToolOutcome::Denied` with that reason. Codex also reports the item declined after a `cancel` reply, which the adapter sends for an approval that Harness cancelled because it stopped the turn, such as for `/compact`, a configuration change, or an interrupt. Codex's approval decisions offer no answer that means "interrupted": `decline` lets the turn continue, `cancel` interrupts it, and a JSON-RPC error reads as a failed approval (`on_command_execution_request_approval_response` in `codex-rs/app-server/src/bespoke_event_handling.rs`). The adapter therefore keeps sending `cancel` and records the cancellation, and the declined item completes as `ToolOutcome::Cancelled`. Recorded as a denial, the call once read `denied` in the session tools, and the turn that a compaction ran again told the user that the command "was denied before it ran". Codex app-server 0.170.0 also maps a decline to "rejected by user" in its own tool output, so a Harness policy denial would read to the Codex model as a user rejection, and the model would never see the permitted route the reason names, such as the file-editing tool for a refused shell write. Before it sends a decline that carries a reason, the adapter therefore appends a developer message with `thread/inject_items` on the requesting thread; it says that Codex reports the call as rejected by user and quotes Harness's typed reason. During an active turn Codex queues an injected item as pending input of that turn (`Session::inject_client_response_items` in `codex-rs/core/src/session/inject.rs`), so the model reads it on its next request, after the declined call's output. Delivery is best effort: a runtime that refuses the message leaves the decline and the row's reason unchanged. Claude, Copilot, and ACP return the typed Harness reason with the denial itself.

OS isolation is enabled only by an adapter's explicit `os_sandbox` declaration. Codex declares support and advertises Windows isolation modes only on Windows; the shared access policy retains an optional opaque `isolation_mode`. Inherited settings resolve against capabilities. Explicit unsupported choices reject before commit, including unknown isolation IDs with sandboxing off. Adapters reject known unsupported shapes before allocating resources or changing history. Native-agent suppression is a separate capability: integrations that cannot enforce it report that limitation.

## Catalog and accounting normalization

Observed context capacity is display-only metadata and never creates a selectable context-window option. Configuration accepts only options in the provider's catalog, including rejecting overrides when the choice list is empty. No synthetic default-window alias is sent to adapters.

The bridge's `SessionOpening` owns each open request together with its operation identity, deadline, and cancellation handle. Dropping a waiter retains that exact transaction. A definite admission or preparation rejection with unchanged effects permits a new attempt; uncertain work retains its original identity. Closing the transaction permanently prevents another open through that owner. Once provider-wide shutdown has collected every native resource, `SessionOpening::collect` releases an open that is still uncertain, because no process remains that could hold what it may have created. Codex answers an open interrupted after its `thread/start` request was written with an uncertain observation and repeats it to every later collector, so before this release a child agent cancelled at that moment failed every cleanup with `provider ThreadOpen failed: Cancelled`, stayed `Closing`, and failed its parent's stop.

Adapters publish reasoning choices in ascending effort order and supply model catalog order. The picker only applies user pins; shared text generation selects the first advertised effort without recognizing native names. Generation resolves model, reasoning, and service tier from the normalized catalog before opening `SessionHistory::Temporary`. This creates a fresh conversation without resuming or appending to the interactive conversation. The existing `isolated_generation` wire capability names this separate-conversation workflow; it does not certify complete native tool or instruction suppression.

The shared helper supplies no host tools, selected skills, or MCP endpoints, denies permission callbacks, disables writes, and requests read-only sandboxing where the adapter supports it. Adapters suppress inherited resources, native tools, and hooks through supported controls. Unsupported suppression does not reject generation: native defaults can remain, subject to access and approval policy. The result collector selects final answer text and ignores native activity; host tools and host workflows remain unavailable. Validation, cancellation, and cleanup use the ordinary retained provider lifecycle.

Codex uses normal CLI authentication and a fresh ephemeral thread, documented base instructions, read-only sandboxing, denied approvals, and disabled web search. It does not fabricate model metadata, export credentials, substitute `CODEX_HOME`, or gate generation by an audited CLI version. Claude and Copilot retain their supported temporary/no-tool controls. ACP opens a fresh session without assuming an unsupported native history-deletion operation. Persistent Background sessions retain their own resources and conversation lifecycle.


The helper creates independent input and attempt identities with temporary receipt storage, submits ordinary input, and collects final response messages through invocation settlement. It excludes reasoning, commentary, and tool output, limits collected message content to 1 MiB, and applies a 120-second generation deadline. Host validation runs before close. A deadline explicitly cancels the current provider operation; utility shutdown also explicitly cancels active utility work. A retained worker owns close even if the result waiter disappears. Close receives a fresh cleanup context and drains the sole reader while collection runs; its deadline is independent of generation cancellation. Provider shutdown joins utility work before collecting the native runtime.

`Turn.Usage` carries checked `UsageReportId` values and optional `ModelCallId` correlation. Complementary reports with one identity merge; conflicting measurements reject, and duplicate reports cannot charge tokens twice. Per-call counts and cumulative snapshots retain unavailable categories rather than treating them as zero. Context occupancy arrives separately as `Thread.ContextUsage`, including post-compaction changes, and never becomes a model-call charge. The provider reports `used`, `size`, and any `reserved` tokens the runtime withholds from the window, such as Codex's fixed reserve; Harness derives the remaining percentage from those facts. Reports retain explicit duration and independently available native call endpoints. A timing-only report is valid, but an empty report is rejected. The constructor never infers `reported_duration_ms`; host turn timestamps and provider collection time never replace missing native call evidence. Compaction decoding converts native fields and billing categories to normalized fields and labeled measurements with explicit units; presentation does not assume a billing currency.

Native attachment encoders and resource-profile recipes live in `forge-providers`. Harness resolves retained objects into normalized file content and selects portable resources. `thread_configure` applies complete model, access, approval, and resource settings only to a settled binding. Private adapter replacement preserves the logical binding and event stream; results include effective capabilities and an event watermark the owner consumes before dependent work. Fork requests carry the target owner, workspace, configuration, resources, and system instructions; `thread_fork` returns persisted history without opening the target, and the host opens that history separately. Discovery uses explicit workspace or exact-binding contexts. `mcp_list(Configured)` supplies prompt definitions without starting servers; `mcp_list(Observed)` reads readiness and tools without changing live configuration. A retained picker observation keeps the fast initial rows usable while readiness resolves.

### Event-driven terminal inventory

Adapters publish `Thread.TerminalsUpdated` with an opaque, binding-scoped `TerminalInventory` on the same stream as other observations. The inventory holds the observed terminals and a `complete` flag, which is false while the native runtime is still opening and has not yet listed its tasks. Support and startup presentation are host facts: `forge-harness::provider::terminal_status::BackgroundTerminalStatus` derives `supported` and `starting` for the editor. The host forwards `terminals_changed`; the UI fetches one attachment snapshot and then consumes these updates. Native protocols and terminal handles remain adapter-owned. Codex watches native item/process lifecycle notifications and dispatcher replacement. Copilot subscribes before its initial refresh, then lists tasks only after `session.background_tasks_changed`; it never refreshes in response to its own refresh notification.

These publications are edges, and an adapter publishes one only when a native notification prompts it to re-read its list. A terminal that ends without such a notification stays in the last published inventory, and the status row once kept counting it while the picker, which reads the live list, showed none. `forge.views.harness.terminals` therefore reads the level at two points: it re-reads `background_terminals` each time `activity_changed` reports the `idle` phase, and it adopts the inventory the terminal picker fetched. A push bumps the observer's revision, so a read that started before a newer push is discarded. Whether a published inventory can also be lost or reordered between the adapter and the editor during cancellation has not been established; these reads bound how long either fault stays visible.

Codex writer release subscribes to `thread/closed` before requesting unsubscribe. One paginated loaded-thread snapshot handles an already-unloaded writer; a still-loaded writer completes from its matching close notification. Close evidence is per occurrence, so a previous close of the same native identity cannot authorize a later release. No periodic loaded-thread request remains.

Copilot marks history as resumable only after the input collector observes possible native dispatch. Cancelling preparation leaves the native session unused. Configuration may replace that unused session, publishing the new durable identity after committing its local configuration and retiring old terminal handles. A possibly dispatched input still requires resuming the existing history.

Codex retains its complete private stderr stream instead of a truncated diagnostic tail. Normal shutdown and replacement collect both the process and its diagnostic reader; dropping a shutdown waiter leaves that same reader owned for the next collection attempt. The only startup retry here follows a failed WebSocket connection while the newly launched server is not yet listening. It does not poll an established session. The socket owner records every remote close and failed socket operation before it closes its data queue, so a connection whose owner ended without a recorded failure was closed or dropped by Forge itself and reports `CodexConnectionError::Released`. Its readers and waiters still fail as a transport loss, but the release is traced at debug level as `provider.connection_released` rather than as a `provider.failure`, which every binding close previously logged as a failed `TurnStart`.
