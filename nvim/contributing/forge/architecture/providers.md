# Providers

Each provider reports identities, phases, tools, and failures differently, and a consumer that decoded those differences itself would show one provider's quirks as another's behavior. Provider adapters therefore normalize every transport into one typed Harness contract, and shared settings record real capability differences instead of simulating unsupported operations.

[Harness](harness.md) covers the session lifecycle, [Permissions](permissions.md) covers approvals, and [Provider configuration](provider-configuration.md) covers settings, resources, and models. Input delivery is in [Provider submissions](../provider-submissions.md).

## Provider contract and ownership

The provider boundary spans three crates. `forge-provider-api` defines the object-safe `Provider` interface, normalized requests, events, errors, models, and capabilities. `forge-providers` owns native protocol decoding, process runtimes, SDK handles, resource profiles, and session state; its native modules are private behind the registry. `forge-harness::provider::ProviderBridge` prepares host resources and binds normalized callbacks to tools, permissions, task authority, and durable submissions. The API and native implementation crates do not depend on Harness, and the interface has no Harness-associated types.

Providers address conversations only by `ThreadId`. `InvocationScope`, `EventScope`, `TurnAddress`, `SessionRequest`, `ForkTarget`, permission callbacks, and test controls carry the thread, never the Harness session and agent that own it. Harness defines `SessionId` and `ThreadOwner` in `provider/thread_owner.rs` and derives each root thread identity from its owner, keeping the persisted `thread:<session, agent>` form. An adapter mints an observed child's thread with `ThreadId::child`, which keeps the parent's host namespace and adds the child's `AgentId`; `register_observed_turn` rejects a child thread outside the binding's namespace. Harness therefore resolves the owner of any admitted thread through `ThreadOwner::from_thread_id` (exposed on scopes by `ScopeOwner::owner`) without a second table that could disagree with the adapter, and maps owners back to threads for cancellation, permissions, and per-owner event subscriptions. Adapter-private state keyed by owner, such as Copilot's trace correlation label and terminal inventory key, uses the thread identity.

Only `forge-providers` declares the Copilot SDK dependency; Harness has no direct SDK dependency, including in tests. Native wire, SDK ancestry, version, and permission conversion regressions live beside their private implementation. Harness integration tests implement the same normalized interface through `EventFixtureProvider` and the production bridge. Shared mocks exercise acceptance, completion, cancellation, permissions, and host effects without knowing a provider's wire format.

Every provider operation receives a host-issued `OperationContext` containing its identity, immutable deadline, and explicit cancellation observer. The host retains the matching cancellation source with the original worker; losing a result waiter never requests cancellation. Repeating the same context and typed request observes the original disposition, while changed identity/request combinations reject. Opening transfers the sole stream once; observing an already-taken open result cannot allocate another binding. Deadline and explicit cancellation failures retain their operation, phase, and effect disposition, and never imply that input was not consumed.

The bridge retains fork and compaction requests with their operation contexts before native dispatch. Retry observation uses that original request without reloading resources or resolving a replacement binding. A fork's operation identity includes the request's `attempt_id`, so a new attempt for the same child after a failure is a new operation and does not replay the retained failure. `ForkSource::Binding` copies an idle live conversation; `ForkSource::Checkpoint` reads a recorded position and does not require the source to be idle, which is how Harness forks a session whose turn is running. A compaction record also retains its original event reader; its watermark cannot be satisfied by a later binding for the same owner. Shutdown closes history-operation admission and signals retained cancellation before waiting for bridge admission guards. Cancellation interrupts an unfinished watermark wait, while already-consumed completion evidence remains valid. Claude compacts through a `/compact` user frame. When Claude reports that compaction failed, the conversation is unchanged, so `ClaudeProvider::compact_session` returns the failed compaction and keeps the binding; it invalidates the binding only when Claude reports neither completion nor failure. Invalidating on a reported failure closed the session's observation and left later queued prompts unadmitted.

`Provider::thread_open` returns an opaque binding, initial negotiated capabilities, and its sole ordered event stream. The bridge installs stream consumption before dispatching input. `turn_start` and `turn_steer` return direct input-acceptance evidence or a delivery error; an acceptance receipt does not establish native completion. Root, managed-child, and Background callers use the same retained execution owner while keeping their own presentation and result waits.

Open and configure results carry the negotiated capability manifest, and the bridge republishes each accepted one as host `HostEvent::CapabilitiesNegotiated` on the binding stream: before the native relay starts for an open, and after the operation watermark for a configuration. The broker applies only root-owned manifests whose binding is still active, using the same binding gate and monotonic `effective_revision` check as native `Provider.CapabilitiesChanged`, so a manifest queued by a retired generation cannot overwrite its replacement. Without this publication, adapters that never emit a native capability notification would leave persisted fork and compaction support stale, because turn completion no longer carries capabilities.

An eager startup open gave every unused chat a native conversation, and each pre-prompt settings change could then replace that empty conversation with a new provider ID. Interactive startup therefore never opens one. `SessionController::prepare_provider_initialization` attaches the session observation listener and registers the root execution owner, then reports `ProviderInitialization::Deferred`. The native conversation opens or resumes inside `ProviderBridge::turn_start`, through the per-owner `HostSession.initialized` cell that already serializes first-use admission, and it captures the configuration current at that admission. Before that point `ProviderBridge::thread_configure` returns `ConfigureReceipt::Deferred` and changes only local settings, and closing a never-used chat issues no native close. Codex, Copilot, and ACP report a new conversation's ID only in the open result, so `ProviderBridge::install_session` carries that ID as the `history` of the ordered `HostEvent::CapabilitiesNegotiated` publication, and `HarnessBroker::apply_negotiated_capabilities` commits it through `retain_session_identity` for an active root binding. A later replacement history still arrives as `Thread.IdentityResolved`. The open supplies only static instructions, `ProviderRequest::open_instructions`, because adapters retain open-time instructions for every later turn; each turn's purpose, task contract, and settings travel as tracked context sections, described in [Turn context](#turn-context). Missing established history now surfaces as the first input's turn failure. Manual compaction of a chat with neither native history nor exchanges fails locally instead of opening a conversation to compact, and background-terminal inventory for an unopened owner reports a supported, empty list without a native request. Load-time recovery still clears an unused saved identity, and established history is never silently replaced. Until a binding opens, capability queries fall back to the descriptor's manifest, and catalog queries use the workspace context.

`forge-providers::turn_runner::RetainedTurn` retains one native `TurnResult`, collects the same provider-owned foreground resources, and then publishes the sole `Turn.Completed(CompletedTurn)`. That record contains the native outcome, completion timestamp, exact `CoveredInput` attempts, final accounting, and the separate collection timestamp. Collection cannot choose another outcome. Failed observation or collection fences the connection with `Provider.Unavailable` instead of publishing ordinary completion. A dropped waiter leaves the worker and unfinished collection owned.

Positive native child processing starts a separate retained child driver; lifecycle metadata alone does not manufacture a child turn. The child's original reader and callback group survive parent-turn collection. Parent `Turn.Completed` can publish while that child remains active and a successor root turn starts. Late child items retain their original identities, and the child's own `Turn.Completed` waits for its native terminal evidence and independent callback collection rather than borrowing the parent's certificate.

Harness consumes that collected result before its own commit ticket applies retained callback effects, child results, and checkpoint work. Provider collection and host commit remain separate barriers. `TurnInterruptResult` carries the original normalized turn identity and a stream watermark, with no second outcome field. Configuration and interruption callers consume through their returned watermarks before dependent transitions. The bridge relay advances a binding's published position only when it hands the event to the owner channel, after every fallible routing step. An owner that refuses a native event, for example one arriving after its execution was fenced, reports the position through `ProviderBridge::event_rejected`, which discards that event's binding metadata. A close waits for the published prefix to be consumed, refused, or orphaned by a dropped receiver, so it cannot hold provider admission forever behind a fenced owner; configuration, settlement, and compaction waits treat a refused or orphaned position as `Disconnected`, since they need proof of consumption. Root and Background brokers drain the retained inbox; managed children attach their scoped presentation stream.

`ProviderEvent` has five exhaustive families: `Provider`, `Thread`, `Turn`, `Item`, and `Agent`. Checked `ThreadId`, `TurnId`, `ItemId`, and `AgentId` values identify their registered objects; native session IDs remain separate opaque `ProviderSessionId` values. The binding registry resolves each event's original host owner before the host wraps it in a scoped `HarnessEvent::Native`. Late output never acquires the currently visible turn's ownership.

A valid late `Turn.Error` may append diagnostic metadata to its exact retained original turn after `Turn.Completed`. Identical observations deduplicate across reload. This exception admits no foreground execution and cannot change the collected native outcome, retry decision, completion record, or ownership; a diagnostic is not a new completion signal.

The first positive `ModelResolved` observation may likewise fill an unknown actual model on that original completed turn. It does not resolve a successor's model or change configured selection. Once the completed turn has a confirmed model, a conflicting late model change rejects; repeated confirmation remains idempotent.

Idle session presentation accepts that late confirmation only for the latest root exchange and turn under their original active binding. Historical and retired-binding observations remain in their original history and cannot replace a successor's displayed actual model.

Adapter decoders receive an `AdapterActivityWriter`, which accepts metadata and item activity but cannot publish turn start, final completion, provider unavailability, or host-policy events. A `NativeTurnStart` handle reports positive start evidence; the retained runner owns terminal publication. Host approvals, directory grants, retry presentation, child waits, and verified skill attribution travel separately as `HarnessEvent::Host`. Production providers expose neither `prompt` nor `prompt_stream`; output-oriented fixtures collect above the public acceptance and event contracts.

Native protocols keep adding notification types, while the normalized vocabulary stays closed, so a decoder that dropped every unrecognized type would hide lost content or lifecycle evidence behind an apparently healthy turn. Each decoder therefore admits an unmapped notification only through an explicit, tested policy. The Copilot decoder's `unmapped_disposition` names the SDK types that another retained observer consumes, such as idle, checklist, background-inventory, and permission events. It also names the types the pinned SDK defines as presentation, catalog, or configuration metadata. The ACP session decoder admits `current_mode_update` and `session_info_update`, plus an echoed `user_message_chunk` whose input Harness already retains. Every other type produces one `Provider.Warning` of kind `UnsupportedNativeEvent` per binding and type, scoped to the receiving thread; the warning changes no turn lifecycle or retry decision. Codex child lifecycle decoding accepts only the exact `collabAgentToolCall` and `subAgentActivity` item shapes from `item/started` and `item/completed`. A malformed collaboration item is a protocol failure rather than an ignored observation.

`ProviderTools`, `ProviderPermissions`, `InputReceipt`, `ProviderTrace`, `TurnControl`, and `ProviderHostEffects` are callback boundaries into the host. Native code asks for a tool result, permission decision, or committed receipt without acquiring Harness storage or task state. Prompt requests carry full invocation configuration, the current tool allowlist, typed task commands, structured question replies, and ordered recovered input with its attachments. Harness owns goal scheduling and enqueues ordinary input for continuation; adapters never schedule native goal work. Initial tool registration remains stable; each invocation enforces its own allowlist. Where an adapter needs HTTP MCP transport, the request supplies a unique endpoint and retained lease for that invocation. Direct native tool callbacks use `ProviderTools`. A retired endpoint cannot route delayed calls to a newer invocation. `forge-shell` separately owns shell parsing and process primitives used by the policy layer and native runtimes.

Provider errors expose typed operations and categories, never native response codes, messages, payloads, or source chains. Diagnostic display messages are deliberately sanitized by the producer. Provider tracing accepts normalized lifecycle records only. Forge has no setup or sign-in flow; users sign in through each provider's own CLI. An authentication failure, including an ACP login-required rejection at session open, keeps the `Authentication` category, and its display message tells the user to sign in through that CLI.

Native adapters additionally emit Rust `tracing` diagnostics before normalization discards their causes. The host subscriber sends redacted display errors and source chains to the existing JSONL writer, not to the provider contract or host stdout. Provider operations carry session and operation spans, and retained workers and cleanup inherit their dispatcher and span. Severity filtering controls diagnostic recording only; it cannot change delivery evidence, retry decisions, or cleanup ownership. See [Debugging](../debugging.md) for levels, storage, and inspection boundaries.

Codex classifies process-creation failures at the spawn boundary as
`ProviderError::RuntimeLaunch`, retaining the selected provider, configured
executable without arguments, and a normalized missing, permission-denied, or
unavailable cause. Catalog discovery, session opening, configuration replacement,
and input reconciliation preserve that evidence instead of replacing it with
`Transport`. The displayed error names the executable and suggests checking its
installation or provider settings; native operating-system details stay in JSONL.
Other connection failures retain their transport classification. The retained
catalog startup worker inherits its caller's diagnostic dispatcher and span.

Copilot's shared transport-error conversion records native display causes before
discarding them, including configuration, skill and MCP inspection, terminal
inventory, history reads, and disconnect failures. Interruption and runtime
collection retain their existing typed dispositions while also logging the native
cause. Catalog spans carry their host-issued operation IDs; Background requests
provide an explicit diagnostic destination independently of interactive sessions.

Terminal inventory protocol failures additionally retain a typed field failure: missing inventory, missing or invalid identity, or missing display command. `ProviderFailure` stores that optional detail without native values; records without it remain readable. Operation traces retain `kind`, `phase`, `disposition`, and `terminal_inventory_error` through both storage and inspection. Free-form `reason` text remains excluded by the trace policy. `ObservationCleanup` renders its retained original failure separately from fencing, cancellation, and collection failures, so a failed close does not replace the initiating cause in the displayed diagnostic.

`ProviderCapability.integration` declares optional operations, resource targets, isolation choices, and implementation limitations in each adapter. The compiled-in registry supplies identities, launch defaults, and declarations before a session starts; Lua does not maintain a duplicate provider catalog. `CapabilityManifest` records only provider facts: each provider operation's support, typed restrictions, and application boundary. Menu groups, labels, ownership, and explanations belong to `forge-harness::provider::capability_menu`, which also adds the Harness-owned workflows such as goals, queues, plans, and child agents, so an adapter never declares a host workflow. Steering policy is likewise Harness's: an active task of any kind accepts steering whenever the binding supports `native_steer`. Open and configuration results publish effective support; later changes arrive on the ordered binding stream. The bridge retains the snapshot consumed by the owner, and `/capabilities` reads that snapshot without calling native discovery. Schema and effective revisions have separate counters. Unsupported optional operations return a typed feature error. Cancellation identifies both the binding and exact invocation, so a repeated or delayed request cannot interrupt a successor. Terminal operations use a binding-scoped typed terminal identity.

## Sessions

Codex turn requests explicitly set `summary: "concise"` so the status preview does
not depend on the model catalog's reasoning-summary default. The adapter maps
`item/reasoning/summaryTextDelta` to readable summaries and keeps raw reasoning
separate. The Harness `status_thoughts` setting controls display of those summaries.

Planning authoring uses ordinary native execution posture so file tools remain available; read-only review questions still request a native planning posture. Harness supplies invocation-only effective write roots independently of saved access preferences. Codex replaces its sticky `runtimeWorkspaceRoots` on every turn as well as `writableRoots`, so returning from a restricted authoring turn restores the ordinary project-root context.

Native initialization validates the selected runtime before opening or resuming its conversation. The current minimums are Codex 0.164.0, Copilot CLI 1.0.103, Claude Code 2.1.317, and Antigravity ACP 1.4.5. The Copilot SDK dependency is pinned separately to 1.0.26; its version does not prove that a configured CLI override is supported. Codex reads its initialization user agent, Copilot queries the connected runtime status, Claude Code runs `claude --version` before catalog discovery and each process launch, and ACP reads the adapter version from the initialization handshake. Missing, malformed, and below-minimum versions produce typed initialization errors. A replacement runtime must validate again. All adapters use the shared `RuntimeRequirement` and `ValidatedRuntime` contract, with one minimum per adapter and no maximum or exact-version capability gate. Codex shares its initialize, version validation, and initialized notification across discovery, session open, reconfiguration, and recovery. ACP prefers the configured executable; if the default executable is unavailable, it selects the newest locally installed managed copy and validates that copy through the same handshake.

Conversations open or resume their provider session asynchronously, without creating an exchange or sending model input. The controller releases its broker lock during network work and rejects stale results after configuration changes. The broker persists the root conversation ID when it accepts a provider turn-start boundary, so interrupting the first turn still keeps the conversation.

Saved sessions use the current `SESSION_FORMAT_VERSION` in `storage/mod.rs` (66 for this contract). Explicit resume rejects older or missing versions before decoding changed session state or opening native history, with a create-new-session diagnostic. Listing omits unsupported records while retaining their stored history. New-contract sessions remain resumable.

Harness defaults to the Codex app-server provider, and `harness.provider = "copilot"` selects the Copilot SDK. Broker initialization resumes the most recently updated session for the repository and provider. Switching providers requires choosing New chat or Resume session and never transfers context across providers. It stops the one host that serves every Harness tab, so it is unavailable while any connected tab has a running turn, queued or unsent input, or a finalization in progress. A failed switch restores the previous session.

Copilot's native session registry serializes preparation per execution owner. It retains repair notices, resource leases, terminal readers, and compaction subscriptions with the matching binding. A selected MCP server's native startup waits for its handshake, which a hung server holds for the runtime's own startup bound; that bound matched the 30-second open deadline, so one hung Rulesync server failed every first prompt. Opening therefore disables unselected servers under the open deadline, where failure still rejects the session, and `McpStartup` starts the selected servers in a background task owned and aborted with the binding. Until startup settles, the MCP catalog reports each server's live native status, and settled failures then appear as startup errors. Copilot also holds queued turns until an in-flight MCP load settles, so a hung server would still stall the first prompt for the native bound. `McpStartup` therefore puts every start request on the wire before the binding is exposed, and while startup is unsettled each accepted prompt calls `session.mcp.moveLoadingToBackground`. That call releases only turns already waiting and reports `movedToBackground: false` otherwise, which is why it follows native acceptance of the input rather than startup; the released turn proceeds while servers join as they connect. An abort while input is still queued discards that input and emits only `abort`, with no `user.message` or idle, so the prompt owner settles such a turn as cancelled on the abort itself. Copilot can also hold steering until the current model call ends; when its `user.message` arrives inside the running root turn, the decoder publishes a completed user item carrying the steering submission, and Harness moves the acknowledged steering row to that point so the reply follows its prompt. The adapter classifies `model.*` telemetry, `agent.interrupted`, `session.usage_record` as carrying no normalized meaning, and `external_tool.requested` and `external_tool.completed` as owned by the SDK tool handler, so they raise no unsupported-event warning. Replacing submitted history disconnects its old SDK router before resuming the same ID; replacing a provisional session keeps the old binding until preparation succeeds. The host marks a specific binding as submitted before input can reach the provider, so an output-free cancellation cannot accidentally publish a new history boundary.

The published Copilot SDK still has internal unbounded queues and can hide router-level event loss. Forge-owned queue bounds do not remove that upstream limitation. The accepted scope and possible future SDK patch are documented in [limitations.md](../../../../limitations.md).

## Turn context

A model that acted on the permissions and task from conversation open would approve, write, or plan under settings the user has since changed, while repeating the whole Harness context on every turn costs about 1,000 tokens per message. Every adapter supplies its system or developer instructions only when it opens, resumes, or reconnects a conversation, so text that can change during a live binding cannot live there. Harness therefore sends that text as two typed standing sections (`forge_provider_api::forge::Permissions` and `Task`), each only when its value changes or the conversation may have lost it, in this order:

| Section | Contents |
| --- | --- |
| `permissions` | Tool approval, reject-all guidance under Deny, read and write access with their directory lists, and the `Toolsets` line. `"."` names the workspace; an invocation-only write root such as the planning directory shows as `Write access: planning directory only.` with that root as the only write directory. |
| `aside` | Present only in an aside session. Its `origin_session_id` and `origin_session_name` attributes name the origin, and its text states the aside's role and the tools that inspect and message the origin. |
| `agent` | Present only in a child agent's conversation, from `ProviderRequest::child_agent`. It carries the child's `path` and `parent` attributes, a sentence stating that each task arrives as an `<agent_message type="new_task">` and that Harness delivers the child's final response to its parent, and the profile's instructions in `<profile_instructions>`. The profile stands here rather than travelling with each task so that compaction, which clears the delivery record, sends it again instead of summarizing it away. |
| `task` | The active task, identified by its `kind` attribute. `plan` carries a `plan_id` attribute and holds the planning directory and authoring-guide path from `PlanAuthoringScope`, a sentence stating that each user message during the task is input to the plan, the user's original `<request>`, and the planning contract, during planning and plan discussion. `execute` carries execution, plan, phase, and revision attributes and holds `<phase_instructions>`, `<findings>`, `<approval_comments>`, and the accepted `<design>`. `goal` holds the `<objective>` and completion rule. `none` states that no task is active and replaces any earlier task. The task comes last because it is usually the longest section and the one the turn acts on. |

Every Harness-authored text after the open-time instructions is a typed value from `forge_provider_api::forge`, rendered into `<forge>` blocks by one writer. A turn's input is a `TurnInput` whose `TurnKind` states why the turn happens: a user message, plan discussion, check setup, a chat reply while questions are pending, a plan review question, a question response, recorded planning answers, a plan review decision, a check repair, child results, a parent's task for a child agent, a message from another session, an approval timeout, a Harness task step, or a Background request. The kind decides the data elements (`<question_response>`, `<recorded_answers>`, `<pending_questions>`, `<plan_review>` with its `<plan_edits>`, `<check_failures>`, `<agent_message>`, `<session_message>`) and the fixed `<instructions>` text, which `forge/instructions.rs` owns; callers never write instruction text, and `Notice` values add side conditions such as an approval timeout, a task start, a resume with a user message, or a repaired Copilot history. User text exists only in the kinds where the user typed something, and Harness never wraps it, because a model gives text quoted inside another message less authority than the user's own message. Text another model wrote is always wrapped, for the same reason: it must not arrive with the user's authority. A child's task and the messages its parent queued before the task started travel as `<agent_message type="new_task">` and `type="message"` elements, a child's report reaches its parent as `type="final_answer"`, and an aside's message reaches its origin as `<session_message>`. Each element names its sender, by agent path or session ID, and its kind's fixed instructions decide what the receiver does with it. Constructors reject empty failure lists, empty answer sets, empty review feedback, and child continuations without results.

No section lists host tools, because adapters receive each turn's tool definitions natively. `tools/toolsets.rs` names the toolsets that can change during a conversation by the prefix their tools share, or by their single tool: `lsp_*`, `harness_session_*`, `agent_*`, and `check_definition_edit`. Each tool family declares its name next to its catalog (`lsp::TOOLSET`, `session::TOOLSET`, `agents::TOOLSET`, and `checks::DEFINITION_EDIT`), and a test checks every tool in a family against it. `toolsets::requirement` states when each toolset or task tool is available; `ControlToolRegistry` appends that sentence to the advertised description, and `toolsets::unavailable_reason` returns the same sentence when a call is rejected. The control endpoint, check editing, planning's `plan_read` and `plan_edit` guard, and Codex all use that reason: Codex registers its catalog once per thread, so it asks `ProviderTools::unavailable_reason` when the model calls a tool the invocation does not allow.

`ProviderRequest::open_instructions` supplies the text that stays true for the whole conversation: `plan/prompts/system.md`, which holds the check, permission, and Harness inspection policy, the check shell name, `prompts/lsp.md`, which tells the model to prefer LSP tools when they are available, and `forge::overview`, which states that the system instructions always apply, that a newer standing section replaces only the earlier copy of that section, what a turn is, that agents address each other by path from `/root` (`forge::ROOT_AGENT_PATH`), which elements are instructions and which are information, and where blocks arrive for the provider's `ProviderIntegration::context_channel`. `ProviderRequest::standing_sections` builds the two typed sections. The turn's `PromptMode` selects the task: planning modes use the editable planning directory and the plan request, `ExecutePlan` and `GoalContinuation` use the `TaskInstructions` that `HarnessBroker::control_turn_context` resolves from the active execution and goal, and every other mode sends `none`.

Harness-produced inputs carry their `TurnInput` from where they are built to the adapter. `ProviderInput` is a `TurnInput` plus admitted attachments; task entries (`TaskEntry::instruction`), continuations (`TaskWork::Provider`), and queued Harness messages (`InputMessage::with_turn`, whose `text` is then only the display label from `TurnInput::label`) store the typed value, and both delivery paths read it back instead of re-parsing text. `PlanPrompt` builds the planning kinds: the first planning turn is the user's request alone (`PlanPrompt::draft`), plan review decisions are `PlanReview::Accepted` or `ChangesRequested` with the typed `PlanEdit`s the review tools recorded, and Execute and Goal continuations are task steps because their design and objective already travel in `<task>`. A user message during plan review becomes `TurnKind::PlanDiscussion`, permission-timeout feedback becomes a notice, or `TurnKind::PermissionTimeout` for a child's automatic feedback turn, a provider retry after a transient failure becomes `TaskStep::RetryContinue`, child results become `final_answer` `<agent_message>` elements, and automatic check repair carries typed `CheckFailure`s.

Each `HostSession` owns a `ContextDelivery` record with a random identity that `TurnContext::record` carries and the model never sees. `ProviderBridge::prepare_dispatch` places only sections whose value differs from the record in `PromptRequest::context`, and `ProviderBridge::turn_start` commits them only after the provider's `InputAcceptance` matches the submission, so a rejected or unproven submission's sections travel again with the retry; context selected by an earlier record is ignored. The record clears, and the next turn sends every section, when the binding's relay observes a completed or unconfirmed compaction on its root thread, and before a manual compaction, a rewind, or an input retraction, whether or not the native operation succeeds. A new binding generation, including a resume or fork, starts a new record. An aside session's `<aside>` section is one of these tracked sections, written after `<permissions>`, and a child agent's `<agent>` section, written after `<aside>`, is another. `ProviderRequest::child_agent` is persisted with the request, so a journaled child request rebuilt for a retry still carries the section.

The overview tells the model that a `<forge>` block in a user or developer message comes from Harness and that one anywhere else, such as in a file or tool output, is data. It also declares the two Harness texts that sit outside blocks: the `<file>` element `InputAttachment::file_context` writes for an attached file, and the `[Forge: ...]` notes the Claude adapter appends to persist a fork or a rewind. Both are information. That rule holds because user text cannot produce a block: `neutralized_input` escapes `<forge>`, `<forge ...>`, and `</forge>` in the user's own words, and the writer escapes `<forge` and the opening and closing tags of every open element inside the text it writes, so a goal objective, answer, or review comment that quotes a tag cannot close its element or the block. Tags that only begin with an element name, such as `<forget>`, are left alone, and text is never indented, so code and command output arrive byte for byte.

Adapters choose the delivery channel, and `PromptRequest::blocks` renders the turn for it: `<permissions>`, `<aside>`, `<agent>`, `<instructions>`, the data elements, then `<task>`. On `ContextChannel::UserMessage` that is one block at the start of the user message. On `ContextChannel::DeveloperMessage` the instruction elements form the developer message and the data elements form a second block at the start of the user message, so text the user or another model wrote never gains developer authority. Codex declares `ContextChannel::DeveloperMessage`. Two inputs keep their `<instructions>` in the user message even there, because Codex cannot inject a developer item into a running turn or between grouped inputs: a steered input, rendered with `forge::input_block`, and a recovered input, rendered with `forge::earlier_input_block`. The developer-channel overview says so. It keeps the `developerInstructions` sent at thread start or resume, and its collaboration-mode state prefers the model catalog's built-in mode text over the `collaborationMode.settings.developer_instructions` that `turn/start` carries ([`collaboration_mode.rs`](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/context/world_state/collaboration_mode.rs)), so that slot carries only the static open-time text. `CodexProvider::submit` appends the instruction block as one developer-role `message` item through `thread/inject_items` before it sends `turn/start`. Codex records injected items outside any turn: they never appear in `thread/read` turns, so output-free retraction still sees exactly one user message, and their `rawResponseItem/completed` notification names no admitted turn and publishes nothing. A runtime without the method rejects it with an id-less `-32600` "unknown variant" error, which the RPC reader hands to the sole pending waiter. `NativeRpc::method_request` reports that rejection as `MethodReply::UnknownMethod`, `TurnContextDelivery` records `Unsupported`, and later turns place the block at the start of the user input without probing again. Any other injection failure fails turn preparation before `turn/start`, because a turn that starts without its current permissions is the failure this mechanism prevents.

Claude, Copilot, and ACP have no mid-conversation developer channel and keep the default `ContextChannel::UserMessage`, so their adapters place the block at the start of the user message, before the user's text. ACP agents without a native system prompt receive the open-time text wrapped as `<system_instructions>` (`forge::system_instructions_block`). Each recovered input is preceded by `RecoveredInput::block`, an `<earlier_input index="n"/>` marker with that input's own elements, and its words follow unwrapped. A steered input renders with `forge::input_block` and no standing sections. Background and isolated generation use `TurnKind::Background`, which renders no block. Adapters read the user's words with `TurnInput::user_input` and never inspect other kinds; the mock provider reads the plan ID from the typed task or the planning directory's last path component.

## Messages

Copilot reads `assistant.message_start` metadata before deltas and reconciles the matching `assistant.message` snapshot by message identity. Recognized phases are `commentary` and `final_answer`, and missing or unknown phases stay unclassified. If a successful invocation ends with commentary and no explicit final answer, the adapter emits that text again as a response with a new identity. An explicit empty final answer suppresses this, and failure or cancellation never produces a response. Root `assistant.idle` or `session.idle` supplies a terminal candidate. The former ends the main processing loop even when background terminals keep the native session busy. The candidate finishes execution only after in-flight sends settle and every accepted steering message is covered by native input observed before that idle boundary. An older idle cannot cover a later input, and a child idle cannot finish the root execution. Background terminal inventory remains observable after foreground completion.

Copilot correlates each accepted message ID with a root-envelope `user.message`, its native turn, and the event ancestry leading to completion. Root inputs can carry `parentAgentTaskId`; that field does not identify a child subscription. Events with an `agentId` cannot supply root input coverage. Ephemeral streaming and idle events refer to durable ancestry without becoming the parent of subsequent durable events.

Codex keeps the phase from `item/started` for matching deltas and snapshots. ACP assigns message identities within its execution. Consecutive chunks of the same kind join one message only while their optional native `messageId` matches, so two adjacent API messages stay separate items; agents that omit `messageId` join on kind alone. ACP carries no phase, so `AcpSession` leaves prose unclassified until the first `tool_call` or `tool_call_update` for a tool-call ID it has not seen before. That event marks all pending prose as commentary, and normal turn completion marks the last unclassified message as the response. Updates to tools that are already known do not classify anything, because an agent can report a terminal status for an earlier, abandoned tool after it has written the final answer. Claude Code classifies prose from richer evidence, described under [Claude Code](#claude-code). Adapters never assign tools or checks to commentary, because `Exchange` captures each activity's owner at admission.

## Tools

`ItemStart` fixes each item's family: user message, assistant prose, full or summarized reasoning, command execution, file change, or another tool call. Message classification distinguishes unclassified prose from positively identified commentary or response text; reasoning uses `ReasoningKind` independently. `MessageCompletion` replaces accumulated deltas with final or interrupted text.

Tool descriptors, argument fragments, positive execution evidence, output, native file observations, and outcomes are typed item events under the original identity. `ToolItemEvent::DescriptorUpdated` preserves later validated metadata without creating another item. `ToolCompletion` retains its outcome and any final descriptor/output snapshots; an omitted snapshot preserves previously observed content. Conflicting type, owner, or final-snapshot replay fails atomically. Committed LSP edits are separate `HostFileChange` effects, identified by the original authenticated callback scope and host call ID. They never fabricate a native `Item.Tool.Changes` event or modify a native final snapshot. A native item is attached only after positive correlation. Each adapter also supplies `ToolSemantics`: a command with its shell and working directory, explicit read targets, or an unclassified operation. Skill attribution consumes that metadata and waits for successful completion. The broker and renderer never infer an operation from a native tool name or argument schema.

Codex classifies activity by top-level item type. Before titles enter durable state, the transport replaces values under credential-like keys, such as `token`, `api_key`, `password`, and `authorization`, with `[REDACTED]`. Shell headings summarize simple reads and searches after decoding the launcher, and the durable command never changes. ACP tool updates merge by tool-call identity, and structured diff content becomes a `ProviderChangeSet` without reading the workspace. Antigravity edits can complete without diff content, so `/capabilities` marks its file diffs as limited. Reported edits never replace checkpoint-based **Workspace changes**.

For the Codex event mapping verified against 0.164.0, background lifetime needs positive evidence: an empty-stdin `terminalInteraction` reports a still-live session, or a started `CommandExecution` has `unifiedExecStartup`, `InProgress`, a nonempty process ID, and no reported exit when the root ends normally. A process ID, pending status, or nonempty terminal input alone is insufficient. This retention rule follows the [process manager](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/unified_exec/process_manager.rs), [exit watcher](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/unified_exec/async_watcher.rs), and [normal task completion](https://github.com/openai/codex/blob/rust-v0.164.0/codex-rs/core/src/tasks/mod.rs): process startup precedes the startup event, exit/drain ends the command, and normal task completion retains the session process manager. The adapter does not issue an optional inventory RPC to infer lifetime at root completion.

Interrupted or failed foreground work without positive yield/exit evidence cannot use that normal-completion retention rule. Missing collection evidence produces an explicit observation/collection failure while retaining the native outcome and resource ownership; it cannot manufacture successful cleanup or authorize killing an independent terminal. Raw-event availability differs between cold thread creation and resumed listeners, so absence of a raw yield event is not proof of native exit.

`ControlToolRegistry` assembles family catalogs under `tools/`. Each tool has its own file containing its description, schema, and handler. Shared schemas and services stay within their family; provider adapters use the same catalog and invocation boundary. `ControlToolExecutor` owns the shared lifecycle for every adapter's control callbacks. It serializes runtime mutations, and cancellation interrupts tool waits and lock waiters. A new turn gets a fresh executor, so late results from an earlier generation are rejected.

Tool families are organized by purpose:

```text
tools/
  agents/       child-agent tools
  checks/       check definitions and execution
  goals/        goal status and completion
  lsp/          editor source queries
  plan/         semantic file edits and the plan overview
  questions/    asynchronous questions and answers
  repository/   Git status and diffs
  session/      session history and inspection
  config.rs     Harness configuration inspection
```

The plan overview owns its check selection alongside planned tests and manual verification. Tool descriptions use multiline literals, and detailed field guidance belongs to the tool schema rather than the planning prompt. Domain modules such as `plan/`, `checks/`, and `agent/` retain their state and business operations.

Tool handlers return `ToolResult` with explicit `ToolError` variants and conversions from lower-level errors. One response renderer preserves structured failure details and retry information across providers. Turn admission and cancellation remain transport errors so adapters can stop stale work before publishing a tool response.

## Attachments

Attachments resolve against the Harness data root at admission and stay separate from prompt text. Images get each provider's native form: `localImage` items for Codex, the file attachment list for Copilot, and base64 content for ACP when the agent advertises `promptCapabilities.image`. Unsupported image input fails before the prompt activates. PDFs and other files are passed as retained-file context, never as silently extracted text.

## Execution and cancellation

Harness workflow intent never crosses the provider boundary. `PromptRequest` carries a provider-neutral `ExecutionMode`, which is `Planning` for plan drafting, discussion, and review questions and `Default` otherwise; ACP maps `Planning` to a native plan mode when the agent offers one. Task starts arrive as host-prepared text: Harness renders the "Goal started", "Plan started", or "Execution started" heading ahead of the task's own input before the request reaches any adapter, so every provider receives the same announcement and none inspects task kinds.

Native adapters signal stop before collecting local callbacks. Codex sends `turn/interrupt`, Copilot sends abort and repeats it to cover a pending send, and ACP revokes callback authority and stops its process tree.

Cancellation before native dispatch keeps its typed cancellation result at every journal and host-admission gate. The execution owner captures the prevented submission and attempt identities before starting asynchronous collection. Completion may remove the live attempt while collection runs; the collection result retains that proof so a matching configuration replacement remains authorized. A newer cancellation fence still rejects an older replacement.

Codex callbacks run outside the socket reader, so an LSP lookup or approval cannot block steering or cancellation. Steering targets the exact active invocation. Shared Harness owns continuation after child completion and submits separately journaled ordinary input with a fresh invocation identity after native settlement and host commit. Adapters never schedule autonomous continuation or reopen settled work.

Codex socket intake and notification dispatch retain incoming frames without an aggregate byte ceiling. Control replies can reach their waiters while tool notifications await consumption. Shared host queues and the Copilot adapter use the explicitly selected 4096-frame capacity; the Copilot SDK subscription is configured to the same capacity for both new and resumed sessions. Observation failures retain their normalized category through execution failure and stream closure.

Copilot intake and shared Harness observation queues grow in memory while their consumers are delayed; they neither truncate valid output nor cancel a conversation because a fixed event count was reached. The encoded transport uses bounded frames and waits for byte capacity; larger events cross it in ordered chunks. Copilot's SDK retains its own finite broadcast buffer, so Forge drains that subscription independently of presentation. SDK lag remains observation loss rather than proof of native completion. Sustained backlog can increase memory use.

Copilot intake closes its foreground sender before acquiring the decoder context to report failure, allowing a prompt that holds that context to finish. The session task drops its adapter future before terminal publication, releasing execution guards during cancellation. A force-stopped client marks its shared runtime generation unavailable; recovery collects that generation before starting or attaching a replacement. Recovery resumes the saved native conversation and never replays an uncertain prompt automatically. `turn_interrupt` awaits collection of the exact invocation while preserving session reuse. `thread_close` immediately revokes admission and callback authority, then collects readers, terminals, profiles, and callbacks. Failed close retains its first failure and unfinished ownership for retry. Normal completion passes through the retained runner, which collects foreground resources before publishing `Turn.Completed`. An execution start after that boundary invalidates admission rather than reopening committed work; a delayed cancellation still names its original invocation.

Copilot cancellation reads native task identities independently of terminal presentation, in both the model session and its private shell helper. Both paths use the same live-background-shell selection as display, but only display requires a command label. Missing or invalid identities still reject collection explicitly. The helper re-reads the task inventory after cancellation and retains ownership until no matching tasks or unsettled launches remain; missing display metadata cannot prevent that absence check or substitute for it.

Provider shutdown collects bound and provisional session intake before stopping the SDK client. Otherwise SDK detach closes a still-observed subscription, and intake mistakes orderly shutdown for observation loss and force-stops the transport while shutdown RPCs are pending. Successful SDK collection marks every shared session handle stopped, preventing later cleanup from issuing detach or abort RPCs against the closed transport. SDK stop errors remain explicit and retryable.

[Provider retries](../provider-retries.md) defines when a failed request is retried.

## Claude Code

The Claude ACP adapter hid the CLI's command lifecycle, so Forge could not tell a folded steer from a lost one, and it could neither rewind nor fork at a checkpoint. `ClaudeProvider` in `forge-providers/src/claude/` therefore drives `claude -p` directly over its stream-json protocol, the protocol the Claude Agent SDKs use. `ClaudeTransport` owns one process: it writes newline-delimited user frames and control requests to stdin, decodes every stdout line into a typed `StdoutFrame`, delivers ordinary frames in order, and answers each inbound control request on its own task so a pending permission never blocks the stream. Unknown frame kinds decode to `Unknown` rather than failing, and `ClaudeSessionState` reports each kind once as `UnsupportedNativeEvent`.

Launch arguments pin the CLI to Forge's authority. `--permission-prompt-tool=stdio` with a session-level `permissions.ask: ["*"]` setting routes every tool through a `can_use_tool` control request, which `ClaudeSessionState::authorize` resolves through the invocation's `ProviderPermissions`. `--setting-sources=project,local` keeps user-level settings from granting tools outside Harness, and `--strict-mcp-config` admits only the MCP servers Harness selected. Selected servers can carry credentials such as bearer headers, and any local process can read another process's command line, so `launch_spec` writes the server configuration to `forge-mcp-config.json` in the session's private profile and passes that path to `--mcp-config`. Harness control tools reach the CLI as an in-process SDK MCP server named `forge-harness-control`: the CLI sends `mcp_message` control requests, and `host_tools::handle` answers `initialize` and `tools/list` from the invocation's tool list and routes `tools/call` to `ProviderTools` with the CLI's tool-use ID. `--disallowedTools` removes native agents, background tasks, schedulers, worktrees, and questions, because Harness owns those workflows. Skills arrive through a per-session `--plugin-dir` profile.

Each turn applies its model, effort, and plan mode with `set_model`, `apply_flag_settings`, and `set_permission_mode` control requests before writing the prompt, so a `/model` or `/plan` change takes effect at the next prompt without restarting the process. A change to MCP servers or skills restarts the process with `--resume`, which keeps history.

The turn boundary comes from the CLI's own evidence. Every user frame carries a Forge-minted `uuid`, and `command_lifecycle` frames report it `queued`, `started`, and `completed`. A steer that reaches the model mid-turn completes before the turn's `result`; a steer that arrives too late is still queued at that `result` and starts another CLI turn. `ClaudeSessionState` decides the Forge turn's end under its active-turn lock: a `result` ends it only when no tracked command is queued or unseen, and an interrupt always ends it. Once the end is decided, `track_command` refuses further steers, so Harness resubmits them as prompts. `interrupt{cancel_queued: true}` stops the turn and drops queued steers, and the CLI's `aborted_streaming` or `aborted_tools` terminal reason maps to `Interrupted`. An interrupt that reaches an input the CLI has not started, as while the CLI is still starting after a resume or a fork, cancels that input instead: the CLI reports it `cancelled` in `command_lifecycle` and prints no `result`, because no CLI turn ran for it. `ClaudeSessionState::command_lifecycle` therefore ends the Forge turn as `Interrupted` from that cancellation once no CLI turn is running and no tracked input is waiting to start one, and the binding stays usable for the next prompt. A CLI that neither ends its turn nor cancels its input within `INTERRUPT_GRACE` of an interrupt is wedged, so the provider invalidates the binding, which ends the turn and lets Harness restart the provider. The same bound covers a CLI that never acknowledges the prompt at all. `deliver_input` waits for `command_lifecycle queued` before it reports the prompt accepted, and a turn start has no deadline of its own, so a frozen CLI once held that wait, and every cancel behind it, forever. A cancellation that arrives during that wait now gives the CLI `INTERRUPT_GRACE` to acknowledge the written prompt and then fails the delivery, which invalidates the binding the same way.

Stream events carry the API message ID and content-block index, so text and thinking deltas build separate items keyed by both, and thinking becomes a reasoning summary because the CLI runs with `--thinking-display=summarized`. A `message_delta` whose stop reason is `tool_use` marks pending prose as commentary before the tool starts, and turn completion marks the last pending prose as the response. Complete assistant frames reconcile any text the stream missed. Tool results carry structured `tool_use_result` payloads, and Write and Edit results become `ProviderChangeSet` diffs of their original and new contents.

History operations restart the idle process. `ClaudeConversation::restart` retires the old transport before shutting it down: an unexpected process exit invalidates the binding, but a deliberate replacement must not, or the first prompt after a rewind or resource change fails admission. Rewind resumes at the requested checkpoint with `--resume-session-at`, adding `--resume-drops-turn` when exactly one turn is dropped so the CLI verifies the cut, then writes a `shouldQuery: false` note, because the CLI persists the truncation only when the next entry is appended. A refused rewind resumes the original history and reports `Rejected` without changing it, and rewinding before the first turn has no transcript entry to resume at and is rejected. Fork starts a short-lived process with `--resume`, `--fork-session`, and a Forge-minted `--session-id`, writes a note that runs no model turn, and waits for its completion, so the target history exists before the result returns. Workspace model discovery uses a process with `--no-session-persistence`.

The CLI writes a conversation to disk when its first turn runs, so the session id `thread_open` mints names nothing until then: `--resume` of that id prints "No conversation found" and the CLI exits before its handshake. Two operations once resumed it anyway. The provider restart that follows a failed stop reopened the session and failed every later prompt with a `ThreadOpen` initialization failure, and a change to MCP servers or skills before the first prompt invalidated the binding. `UnstartedSessions` therefore records each minted id until a turn the CLI started ends, and `launch_conversation` starts such a conversation again under `--session-id` when its resume fails initialization. It attempts the resume first because only the CLI knows whether a prompt it received before it froze reached disk. An id that ran a turn is never started again, since that would replace history Harness still shows. `ProcessFrames` withholds a process's exit from `ClaudeSessionState` until its initialize handshake completes, so the failed resume cannot invalidate the state the second launch serves; `launch` returns the failure to its caller instead. The record lives in the provider, so it does not survive an editor restart: there Harness clears a provider session id that its submission journal proves unconsumed. Harness requests no native fork of a session that holds no provider turn, so `fork_session` never receives one.

## ACP

`AcpConversation` in `forge-providers` owns each ACP v1 connection, handshake, model configuration, and native event state for Antigravity's standalone ACP server. The shared bridge owns the control endpoint and permission context; the native owner retains the resource lease with its binding. Harness control tools reach ACP agents through a private loopback MCP endpoint of at most 16 connections.

Provider restart reloads the same native conversation, and failing to load it fails configuration instead of creating replacement history. Initialization rejects agents that cannot load conversations. Advertised child sessions enter the shared agent registry, at most 256 per prompt, and become interrupted when the root prompt returns. `AcpRuntime` resolves configured adapters and never installs provider runtimes.

An agent notice glued to the answer misreports a startup failure as model speech, so the handshake advertises `session.notices`, and `AcpSession::notice` publishes a `sessionUpdate: "notice"` title and description as a thread-scoped `NativeNotice` warning. The same session publishes `ModelResolved` when a turn's native execution first starts, reading the session's current model from `/models/currentModelId` or the `model` configuration option, because ACP turns carry no per-turn model evidence. An agent can re-send an unchanged notice, such as an MCP server startup failure, with every turn, so `AcpSession` remembers the notice text it has published and drops exact repeats for the session's lifetime.

A tool update reports its execution start when the native status is `in_progress`, or when it reaches `completed` or `failed` without an `in_progress` update in between. An agent can report quick tools straight from `pending` to `completed`, and without a start the transcript rendered the row with an empty duration slot. A cancelled tool never ran and records no start.

An agent can route approval of its own native tools through `session/request_permission` without file or command targets. An untargeted request would normalize to `Unknown`, which the Harness matcher denies without a prompt, so `native_tool_targets` names the request by its title. A tool search that selects only `mcp__forge-harness-control__*` tools inherits Harness control-tool authority as `HostTool`; every other named tool becomes an askable `Tool` target, and only a nameless request stays `Unknown`. ACP model, skill, and MCP catalogs require an open binding: a workspace query before the first lazy open reports `ModelSelection` as unsupported.

## Approvals and sandboxing

All three approval modes keep identical native callback setup, and Harness applies Ask, Deny, or Allow after saved rules and reported-file checks. Native operations without callbacks stay outside that boundary. Antigravity enterprise terminal policy can run commands without a callback, so its approval capability is limited. After a Copilot denial, completion requires a later final answer or Harness handoff, and provider idle without either fails the exchange.

OS isolation is enabled only by an adapter's explicit `os_sandbox` declaration. Codex declares support and advertises Windows isolation modes only on Windows; the shared access policy retains an optional opaque `isolation_mode`. Inherited settings resolve against capabilities. Explicit unsupported choices reject before commit, including unknown isolation IDs with sandboxing off. Adapters reject known unsupported shapes before allocating resources or changing history. Native-agent suppression is a separate capability: integrations that cannot enforce it report that limitation.

The native mock implements normalized prompt scripts and session-scoped response holds through `ProviderTestControl`. `provider/mock_response.rs` translates the host test-control route into those typed commands. `session.provider.mock_response` works without the broker execution lock, so a test can control a response while its real turn owns that lock. ## Catalog and accounting normalization

Observed context capacity is display-only metadata and never creates a selectable context-window option. Configuration accepts only options in the provider's catalog, including rejecting overrides when the choice list is empty. No synthetic default-window alias is sent to adapters.

The bridge's `SessionOpening` owns each open request together with its operation identity, deadline, and cancellation handle. Dropping a waiter retains that exact transaction. A definite admission or preparation rejection with unchanged effects permits a new attempt; uncertain work retains its original identity. Closing the transaction permanently prevents another open through that owner.

Adapters publish reasoning choices in ascending effort order and supply model catalog order. The picker only applies user pins; shared text generation selects the first advertised effort without recognizing native names. Generation resolves model, reasoning, and service tier from the normalized catalog before opening `SessionHistory::Temporary`. This creates a fresh conversation without resuming or appending to the interactive conversation. The existing `isolated_generation` wire capability names this separate-conversation workflow; it does not certify complete native tool or instruction suppression.

The shared helper supplies no host tools, selected skills, or MCP endpoints, denies permission callbacks, disables writes, and requests read-only sandboxing where the adapter supports it. Adapters suppress inherited resources, native tools, and hooks through supported controls. Unsupported suppression does not reject generation: native defaults can remain, subject to access and approval policy. The result collector selects final answer text and ignores native activity; host tools and host workflows remain unavailable. Validation, cancellation, and cleanup use the ordinary retained provider lifecycle.

Codex uses normal CLI authentication and a fresh ephemeral thread, documented base instructions, read-only sandboxing, denied approvals, and disabled web search. It does not fabricate model metadata, export credentials, substitute `CODEX_HOME`, or gate generation by an audited CLI version. Claude and Copilot retain their supported temporary/no-tool controls. ACP opens a fresh session without assuming an unsupported native history-deletion operation. Persistent Background sessions retain their own resources and conversation lifecycle.


The helper creates independent input and attempt identities with temporary receipt storage, submits ordinary input, and collects final response messages through invocation settlement. It excludes reasoning, commentary, and tool output, limits collected message content to 1 MiB, and applies a 120-second generation deadline. Host validation runs before close. A deadline explicitly cancels the current provider operation; utility shutdown also explicitly cancels active utility work. A retained worker owns close even if the result waiter disappears. Close receives a fresh cleanup context and drains the sole reader while collection runs; its deadline is independent of generation cancellation. Provider shutdown joins utility work before collecting the native runtime.

`Turn.Usage` carries checked `UsageReportId` values and optional `ModelCallId` correlation. Complementary reports with one identity merge; conflicting measurements reject, and duplicate reports cannot charge tokens twice. Per-call counts and cumulative snapshots retain unavailable categories rather than treating them as zero. Context occupancy arrives separately as `Thread.ContextUsage`, including post-compaction changes, and never becomes a model-call charge. The provider reports `used`, `size`, and any `reserved` tokens the runtime withholds from the window, such as Codex's fixed reserve; Harness derives the remaining percentage from those facts. Reports retain explicit duration and independently available native call endpoints. A timing-only report is valid, but an empty report is rejected. The constructor never infers `reported_duration_ms`; host turn timestamps and provider collection time never replace missing native call evidence. Compaction decoding converts native fields and billing categories to normalized fields and labeled measurements with explicit units; presentation does not assume a billing currency.

Native attachment encoders and resource-profile recipes live in `forge-providers`. Harness resolves retained objects into normalized file content and selects portable resources. `thread_configure` applies complete model, access, approval, and resource settings only to a settled binding. Private adapter replacement preserves the logical binding and event stream; results include effective capabilities and an event watermark the owner consumes before dependent work. Fork requests carry the target owner, workspace, configuration, resources, and system instructions; `thread_fork` returns persisted history without opening the target, and the host opens that history separately. Discovery uses explicit workspace or exact-binding contexts. `mcp_list(Configured)` supplies prompt definitions without starting servers; `mcp_list(Observed)` reads readiness and tools without changing live configuration. A retained picker observation keeps the fast initial rows usable while readiness resolves.

### Event-driven terminal inventory

Adapters publish `Thread.TerminalsUpdated` with an opaque, binding-scoped `TerminalInventory` on the same stream as other observations. The inventory holds the observed terminals and a `complete` flag, which is false while the native runtime is still opening and has not yet listed its tasks. Support and startup presentation are host facts: `forge-harness::provider::terminal_status::BackgroundTerminalStatus` derives `supported` and `starting` for the editor. The host forwards `terminals_changed`; the UI fetches one attachment snapshot and then consumes these updates. Native protocols and terminal handles remain adapter-owned. Codex watches native item/process lifecycle notifications and dispatcher replacement. Copilot subscribes before its initial refresh, then lists tasks only after `session.background_tasks_changed`; it never refreshes in response to its own refresh notification.

Codex writer release subscribes to `thread/closed` before requesting unsubscribe. One paginated loaded-thread snapshot handles an already-unloaded writer; a still-loaded writer completes from its matching close notification. Close evidence is per occurrence, so a previous close of the same native identity cannot authorize a later release. No periodic loaded-thread request remains.

Copilot marks history as resumable only after the input collector observes possible native dispatch. Cancelling preparation leaves the native session unused. Configuration may replace that unused session, publishing the new durable identity after committing its local configuration and retiring old terminal handles. A possibly dispatched input still requires resuming the existing history.

Codex retains its complete private stderr stream instead of a truncated diagnostic tail. Normal shutdown and replacement collect both the process and its diagnostic reader; dropping a shutdown waiter leaves that same reader owned for the next collection attempt. The only startup retry here follows a failed WebSocket connection while the newly launched server is not yet listening. It does not poll an established session.
