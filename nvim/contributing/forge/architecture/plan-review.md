# Plan review

A review that drifts from the submitted revision, or loses comments when a request fails, cannot serve as the approval gate for implementation. PlanReview therefore shows one captured revision, checks that revision again on every edit and decision, and keeps unsaved feedback through failures.

[Planning](planning.md) covers how a plan is written and what happens after acceptance. Editable-region and draft-comment mechanics are in [Buffers and rendering](buffers-and-rendering.md).

## Document

PlanReview opens with one compact block snapshot. Modified files contribute changed chunks and enclosing declaration boundaries through the shared diff presentation, and later revisions send disjoint block patches compared by stable block identity. Sections appear in order: proposed declaration changes, Tests, Checks, and Verification. Rust test attributes and test-only `cfg` gates are masked in both views.

Every parser and projection splits plan text into rows on LF, and a decoration computed from text that kept a CR would extend one byte past its row. Authored artifact text therefore enters a plan with LF line endings: `design_artifact::lf_line_endings` converts CRLF and bare CR both when `plan_edit` stores an artifact and when `authoring_import` reads the planning directory, whose fingerprint still binds the raw bytes. Plans stored before that conversion still open, because the review renders the Flows section's Markdown from the same rows it displays.

Declaration comparisons first match unique Tree-sitter callable owners, then run the histogram matcher on the gaps between them. This follows Git's [patience](https://github.com/git/git/blob/c51408889c3b372814bc20b9431c3b74d0d268eb/xdiff/xpatience.c) approach, with callable identities as anchors. Removed-row navigation opens the previous proposal, or the source baseline on the first submission, and never the current worktree.

The plan's `working_path` still identifies the host-owned rendered review, not the agent's authoring directory. The native controller requests schema inspection through its captured document owner; `review_document::action` serializes that reviewed document into a read-only buffer rather than loading the current draft. Later edits under `plan-workspaces` therefore change neither the displayed declarations nor the inspected schema.

## Navigation

The PlanReview winbar shows review state, visibility, and only the `? help`
shortcut. Keep individual bindings such as `ov`, comment, save, and acceptance
commands in the help popup; do not add shortcut lists to the winbar or its status
text. The help popup reads the registered commands and configured bindings.

`.` and `open` resolve the selected token through saved Tree-sitter coordinates. A target inside the plan is revealed in PlanReview, opening folds and restoring omitted context. A target outside the plan opens its real source buffer.

Source-backed definitions use an already-running project language server on demand. Rust supplies the real path, digest, position, and filetype, Lua loads the file into a hidden buffer and requests `textDocument/definition` without autostarting a server, and Rust validates the document, revision, view, and digest before mapping the result. Requests have a five-second deadline, discard superseded results, and are never cached. No generated source, stub project, or dependency download is involved.

Inline-code identifiers in prose resolve against the complete proposed declaration index. Unique matches get their declaration-kind color, and ambiguous names open a chooser. An unmatched name may query `workspace/symbol` on at most four existing clients, with at most 256 results each and a five-second deadline. That query excludes captured files, so deleted declarations cannot reappear.

## Review edits

Reviewers can rename declarations and delete tests in place. A rename highlights every span it rewrites while the reviewer types the new name, and entering the name opens a confirmation with that preview still on screen, so nothing changes until the reviewer confirms. When no other proposed declaration shares the name, `references::narrative_mentions` rewrites every whole-identifier occurrence: inside any inline-code span, such as a signature or a qualified path, on every row of a fenced code block such as Usage, and anywhere in a test description, while a longer identifier that starts with the name stays. A name several declarations share is rewritten only in an inline-code span whose whole content resolves to the renamed declaration alone. `PlanReferenceIndex::resolve_planned_module_imports` binds a planned file's relative import or re-export, such as a TypeScript barrel's `export { name } from "./module"`, to the planned declaration it names, because the workspace resolver cannot read a file the plan only adds; the rename then rewrites that export too. A name that already exists in the scope is refused with only that reason. A saved comment keeps its rows across an edit: `review_annotation::relocate_row` matches each row by its navigation target, label, and rendered text nearest the old offset, and falls back to the same offset, because prose rows share their section's target and the section heading would otherwise capture the comment. `session.plan.test.delete` removes only the selected inventory entries, and `session.plan.check.update` changes the plan's check selection through the same versioned path. Planned tests feed the check preview, so a test deletion is a check-selection edit that removes only tests: `PlanFileStore::update_checks` recomputes the preview and persists the full render of the edited document, which the next review capture compares against. Each edit validates the captured view and source version and returns an updated projection, so the review never reloads. Confirmed deletions show immediately and restore on failure; an edit that commits but cannot refresh the open projection reloads the review from the committed plan.

For directory-authored plans, reviewer edits update authored files through the same recoverable artifact transaction. The editable directory and rendered review remain separate: ordinary agent edits never rewrite an existing submitted review, and a dirty directory requires resubmission before acceptance. Intervening draft edits reject a reviewer write rather than being overwritten.

A model can submit a newer revision while a review is open. The review is a snapshot of one revision, so its edits never rebase: a save or edit that reaches the host after the source changed is refused with the reason. Only a newer model revision is a new submission; review edits keep the model revision, and their own replies update the review. When the session's plan record names a newer model revision awaiting review, a review shown in a window reloads to it in that window, without a new tab or a focus change. A hidden or closed review stays hidden, one notice says `Plan revision N is ready · op`, and `op` reopens it the same way. Unsaved draft comments move to the new revision's line with the same text, nearest their old position; drafts the host already saved take the host's re-anchored lines, and any draft whose text no longer appears is reported with its text. Review edits queued for the replaced revision are discarded with a notice.

The editor keeps at most one `ov` visibility toggle in flight. Presses made while it waits are counted, and an odd count sends one more toggle after the reply, so rapid presses end in the state their parity selects. Every projection action applies its returned patch whenever the patch's base is still the replica's revision, even when a newer input made the capture stale, because the host has already applied the action; staleness suppresses only the cursor effect and callback.

The plan keeps an ordered `manual_changes` list of review edits no planner prompt has yet received in a revision that replaced them, which acceptance, revision feedback, and resumed execution show to the agent. Review edits reach that list only through the task command owner: the service turns `session.plan.entity.rename`, `session.plan.test.delete`, and `session.plan.check.update` into `TaskCommand::EditPlan`, `BrokerObserver::prepare_owner_plan_edit` appends the edit with `record_manual_changes`, and the broker refuses those methods, so no edit lands where the delivery record and retirement below cannot see it. A review shows exactly what acceptance executes, so every prompt to the planner while edits or saved comments are pending carries them. A change request carries them as `<plan_review decision="changes_requested">`, and a plan discussion carries them as `<plan_review decision="pending">` beside the user's message, with instructions to keep the edits and address the comments in any revision. The broker records what each prompt delivered in the plan directory's `review-delivery.json`, keyed by the model revision the prompt saw. When the next submission commits, `commit_plan_submission` retires the delivered edits and comments, keeps the undelivered ones in `manual_changes`, carries each undelivered comment to the new revision's annotation store when its rows still resolve there, and keeps the bodies of those it cannot place in `unplaced_review_comments`. The editor names the items that stay pending in one notice on the new revision, and the next prompt delivers the unplaced comments as text. Nothing is dropped silently, and no delivered edit is replayed at execution. Check selections and test scopes in it are the net difference from the submitted revision: an entry that restores the submitted choice removes the earlier one. The accepted-plan input leaves check-selection edits out, because Harness enforces the accepted selection itself; the revision's timeline entry still lists them. Each edit advances the review digest, while submitted snapshots stay unchanged. Accepting or requesting changes freezes one snapshot of the edited draft and records one revision.

## Annotations and questions

Annotations attach to a source line, and `Ctrl-S` saves feedback and submits unanswered questions. Revision requests carry structured comment anchors. Feedback formatting finishes before the broker changes plan state, so an invalid anchor cannot drop comments from a revision.

`session.plan.question.answer` forks the source session once per question. Each fork keeps conversation history and receives the saved design, plan ID, version, source digest, and exact selected text with canonical plan line numbers. Up to three lines before and after the complete selection are labeled separately as context. Semantic declaration excerpts retain their own file line numbers, distinct from plan line numbers. All excerpts come from the captured review snapshot, not current workspace files. The fork answers about the selected text without writing files or changing the plan. Answers persist in the annotation store. Editing a question invalidates its answer, so a late response cannot attach to different text. `/config` exposes a provider-local Ask model, thinking level, and speed.

## Decisions

Only one decision can be pending at a time. Submitting a decision checks that the plan and buffer still match the captured revision and keeps the review open until the host answers. An accepted decision hides the review and focuses the Harness composer. A refused one leaves the review and its unsaved feedback in place and reports the host's full reason in an error notice wrapped to the notifier's width, which the notification history keeps. The decision popup drains keys already in the typeahead when it opens and discards keys that arrive within the focus-taking settle interval, including keys a key-hint plugin feeds back rather than types, so a repeated `oY` does not become comment text or submit it. Harness never opens PlanReview automatically.

Accepting nonempty inline comments uses the same revision feedback as requesting changes. Each comment retains its saved source anchors and any associated question-and-answer thread. Question-only threads do not become revision instructions. `PlanAcceptance` retains the captured comments until execution choices are confirmed. Harness then revises the plan instead of entering implementation.

`TaskSnapshot.auto_accept_plan` controls acceptance independently of the plan lifecycle. `/plan accept on/off` changes it without replacing the task or invalidating an active provider turn. New Plan tasks start with it off. Accepting inline feedback and requesting changes preserve it; only `/plan accept on/off` changes it. Complete submissions consult the current flag, and accepting a submission does not consume it. Execution inherits the planning task's policy. Clearing or replacing the task discards it.

`TaskSnapshot.plan_execution` retains selected execution settings and review context separately from acceptance policy. Entering execution copies the chosen tool approval, executor, and compaction into the Execute task's `plan_execution`, where they last for the whole execution; the task entry that also carries them is replaced when a paused execution resumes. A revision accepted during execution reads them from there, so the tool-approval question is asked once per execution. The input coordinator rechecks the flag under control admission before promoting a current submitted document, including recovery after interrupted promotion. It is the only owner of automatic acceptance: planning finalization does not accept a submission itself, because a second acceptance started execution beside the coordinator's recorded one, which then failed as `Execution did not start` with an `Input delivery failed` warning. Drafts, stale submissions, and paused tasks cannot promote. Review entries retain their originating exchange ID; revision dispatch resumes that exchange and its checkpoint rather than displaying another task-start heading.

Once execution authorization is complete, approval is recorded separately from task installation. A running planning response finishes naturally while the owner retains the pending decision outside the command lane. The timeline shows the wait; cancellation and replacement remain available. The final commit rechecks the selected review digest and source guards. Failed or interrupted planning retains the approval evidence but cannot start Execute automatically. Repeating the same pending selection observes its original decision; a different revision requires a new approval.

After submission, a prompt for the selected waiting Plan task becomes a plan discussion. A successful edit there applies `ChangesRequested` and requires a new submission or question before completion.

## Question picker

A question-only turn saves `PlanElicitation` under an `AwaitingInput` plan and opens the shared picker across the bottom of the Harness surface. Provider choices default to the keys in `picker.choice_keys`. After the final answer, a review page lists every answer before the provider resumes.

Ordinary questions use the session question controller. Each confirmed answer commits independently and enters the input journal. Clarification remains pending and receives an attributed `question_reply`; `question_revise` changes only a pending question and fences stale choices. The model may withdraw a question with a reason, but cannot record a user answer. Plan acceptance retains its own explicit confirmation gate.
