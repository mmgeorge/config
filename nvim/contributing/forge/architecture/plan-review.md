# Plan review

A review that drifts from the submitted revision, or loses comments when a request fails, cannot serve as the approval gate for implementation. PlanReview therefore shows one captured revision, checks that revision again on every edit and decision, and keeps unsaved feedback through failures.

[Planning](planning.md) covers how a plan is written and what happens after acceptance. Editable-region and draft-comment mechanics are in [Buffers and rendering](buffers-and-rendering.md).

## Document

Submission validates the plan and saves its Markdown and navigation index. PlanReview loads these artifacts for the selected revision, verifies their identity, and projects the review into one compact block snapshot. Modified files contribute changed chunks and enclosing declaration boundaries through the shared diff presentation, and later revisions send disjoint block patches compared by stable block identity. Sections appear in order: proposed declaration changes, Tests, Checks, and Verification. Rust test declarations follow the visibility of the declaration and its enclosing module. All includes private tests and test-only modules.

Plan Review reads changed-file headings, counts, and canonical line offsets from the submitted plan. The navigation index records which visibility mode exposes a changed row in each file. Public skips files with only private changes or ordinary imports. All shows files with changes visible under full inspection. Explicit reference jumps can reveal hidden context. For older indexes the host derives visibility from the saved declaration diff when opening the review. The host renders complete change and test bodies on demand and reuses them across folds and section moves in the open document. Reopening requests the remembered expanded files with the initial projection.

Submission stores per-file declaration deltas in the revision's parsed design under `file_summary`, keyed by review path. Classification compares declaration tokens and saved behavior blocks, ignoring imports and comments. Folded and expanded file headings share the delta. Zero, unavailable, and missing deltas produce a bare file heading. When a submitted revision has a summary from the earlier counting rules, opening the review recalculates its delta from the saved sides and keeps it in the open file inventory.

The host marks file folds closed in the initial projection. The Lua review document keeps file fold choices in editor memory by Harness session, plan, and file fold ID. A reopened review applies those choices before rendering its first frame, including when a new revision moves a file heading.

When a clean review reopens, the controller keeps the loaded buffer's text and filetype while the winbar shows the loading state. The comment renderer compares the new projection with those rows and writes only changed ranges. An unchanged reopen therefore avoids triggering text-change and filetype callbacks.

PlanReview and batched pull-request review share the whole-file partition, section headings, and membership updates in `forge_diff::presentation::file_review`, plus the editor's viewed and unviewed command specs. PlanReview groups the projected file blocks after assigning canonical source anchors. Moving a file rebuilds the section folds from those blocks and carries local drafts through the shared comment editor. The host atomically saves the set of viewed file headings beside the plan as `review-viewed-<saved-digest>.json`. Working and historical reviews of the same revision load that set before projecting Changes. A revision without a saved set opens with every file unviewed.

Visual viewed-state commands capture the distinct file headings touched by the editor selection. The host validates them against one review revision, saves the set of viewed files once, and publishes one section update.

PlanReview identifies file blocks that cross the Viewed Changes heading during publication. The shared buffer view restores positions on those blocks by editor row and byte column, just as Status does when staging removes a block from its section. Each window captures its own position and scroll state at the commit boundary.

Every parser and projection splits plan text into rows on LF, and a decoration computed from text that kept a CR would extend one byte past its row. Authored artifact text therefore enters a plan with LF line endings: `design_artifact::lf_line_endings` converts CRLF and bare CR both when `plan_edit` stores an artifact and when `authoring_import` reads the planning directory, whose fingerprint still binds the raw bytes. Plans stored before that conversion still open, because the review renders the Flows section's Markdown from the same rows it displays.

Declaration comparisons first match unique Tree-sitter callable owners, then run the histogram matcher on the gaps between them. This follows Git's [patience](https://github.com/git/git/blob/c51408889c3b372814bc20b9431c3b74d0d268eb/xdiff/xpatience.c) approach, with callable identities as anchors. Removed-row navigation opens the previous proposal, or the source baseline on the first submission, and never the current worktree.

The plan's `working_path` still identifies the host-owned rendered review, not the agent's authoring directory. The native controller requests schema inspection through its captured document owner; `review_document::action` serializes that reviewed document into a read-only buffer rather than loading the current draft. Later edits under `plan-workspaces` therefore change neither the displayed declarations nor the inspected schema.

A review opened or reopened in a new tab draws no number, sign, fold, or status column of its own window (`open_review_tab` in `native_controller.lua`). `tabnew` copies the window it runs in, usually a Harness transcript or composer whose columns belong to that view, and showing the review buffer again restores the columns of the last window that showed it, so a review reopened with `op` once drew the transcript's two-cell sign column and sat two columns to the right of where it first opened.

## Navigation

The PlanReview winbar shows review state, visibility, and only the `? help`
shortcut. Keep individual bindings such as `ov`, comment, save, and acceptance
commands in the help popup; do not add shortcut lists to the winbar or its status
text. The help popup reads the registered commands and configured bindings.

`.` and `open` resolve the selected token through saved Tree-sitter coordinates. A target inside the plan is revealed in PlanReview, opening folds and restoring omitted context. A target outside the plan opens its real source buffer.

Source-backed definitions use an already-running project language server on demand. Rust supplies the real path, digest, position, and filetype, Lua loads the file into a hidden buffer and requests `textDocument/definition` without autostarting a server, and Rust validates the document, revision, view, and digest before mapping the result. Requests have a five-second deadline, discard superseded results, and are never cached. No generated source, stub project, or dependency download is involved.

Inline-code identifiers in prose resolve against the complete proposed declaration index. Unique matches get their declaration-kind color, and ambiguous names open a chooser. An unmatched name may query `workspace/symbol` on at most four existing clients, with at most 256 results each and a five-second deadline. That query excludes captured files, so deleted declarations cannot reappear.

## Review edits

When a matched callable gains a behavior block, Plan Review compares its complete plain
signature on both sides. An identical signature gets one modified row with both source
line numbers. The host retains the baseline row and its canonical offset. The editor omits
that row's text so the cursor skips it, and still renders comments anchored there.
File and hunk counts describe the raw diff.

Reviewers can rename declarations and delete tests in place. A rename highlights every span it rewrites while the reviewer types the new name, and entering the name opens a confirmation with that preview still on screen, so nothing changes until the reviewer confirms. When no other proposed declaration shares the name, `references::narrative_mentions` rewrites every whole-identifier occurrence: inside any inline-code span, such as a signature or a qualified path, on every row of a fenced code block such as Usage, and anywhere in a test description, while a longer identifier that starts with the name stays. A name several declarations share is rewritten only in an inline-code span whose whole content resolves to the renamed declaration alone. `PlanReferenceIndex::resolve_planned_module_imports` binds a planned file's relative import or re-export, such as a TypeScript barrel's `export { name } from "./module"`, to the planned declaration it names, because the workspace resolver cannot read a file the plan only adds; the rename then rewrites that export too. A name that already exists in the scope is refused with only that reason, before the confirmation opens: `references::names_in_scope` collects the declarations, local import aliases, and Lua function owners of the renamed symbol's scope from the proposed file, which holds the declarations the workspace file already has as well as those the plan adds, and the preview carries them as `existing_names`, so `entity_rename.proposed` refuses an entered name in that list without asking, and `PlanReferenceIndex::renamed` refuses the same names when a rename arrives anyway. The confirmation returns to the review in the mode the rename began in, rather than the Insert mode the name input is still ending when its submit key opens the confirmation. A saved comment keeps its rows across an edit: `review_annotation::relocate_row` matches each row by its navigation target, label, and rendered text nearest the old offset, and falls back to the same offset, because prose rows share their section's target and the section heading would otherwise capture the comment. `session.plan.test.delete` removes only the selected inventory entries, and `session.plan.check.update` changes the plan's check selection through the same versioned path. Planned tests feed the check preview, so a test deletion is a check-selection edit that removes only tests: `PlanFileStore::update_checks` recomputes the preview and persists the full render of the edited document, which the next review capture compares against. Each edit validates the captured view and source version and returns an updated projection, so the review never reloads. Confirmed deletions show immediately and restore on failure; an edit that commits but cannot refresh the open projection reloads the review from the committed plan.

For directory-authored plans, reviewer edits update authored files through the same recoverable artifact transaction. The editable directory and rendered review remain separate: ordinary agent edits never rewrite an existing submitted review, and a dirty directory requires resubmission before acceptance. Intervening draft edits reject a reviewer write rather than being overwritten.

A model can submit a newer revision while a review is open. The review is a snapshot of one revision, so its edits never rebase: a save or edit that reaches the host after the source changed is refused with the reason. Only a newer model revision is a new submission; review edits keep the model revision, and their own replies update the review. When the session's plan record names a newer model revision awaiting review, a review shown in a window reloads to it in that window, without a new tab or a focus change. A hidden or closed review stays hidden, one notice says `Plan revision N is ready · op`, and `op` reopens it the same way. A task that accepts plans automatically gets no such notice, because the host accepts the revision without the reviewer. Unsaved draft comments move to the new revision's line with the same text, nearest their old position; drafts the host already saved take the host's re-anchored lines, and any draft whose text no longer appears is reported with its text. Review edits queued for the replaced revision are discarded with a notice.

The editor keeps at most one `ov` visibility toggle in flight. Presses made while it waits are counted, and an odd count sends one more toggle after the reply, so rapid presses end in the state their parity selects. Every projection action applies its returned patch whenever the patch's base is still the replica's revision, even when a newer input made the capture stale, because the host has already applied the action; staleness suppresses only the cursor effect and callback.

The plan keeps an ordered `manual_changes` list of review edits no planner prompt has yet received in a revision that replaced them, which acceptance, revision feedback, and resumed execution show to the agent. Review edits reach that list only through the task command owner: the service turns `session.plan.entity.rename`, `session.plan.test.delete`, and `session.plan.check.update` into `TaskCommand::EditPlan`, `BrokerObserver::prepare_owner_plan_edit` appends the edit with `record_manual_changes`, and the broker refuses those methods, so no edit lands where the delivery record and retirement below cannot see it. A review shows exactly what acceptance executes, so every prompt to the planner while edits or saved comments are pending carries them. A change request carries them as `<plan_review decision="changes_requested">`, and a plan discussion carries them as `<plan_review decision="pending">` beside the user's message, with instructions to keep the edits and address the comments in any revision. The broker records what each prompt delivered in the plan directory's `review-delivery.json`, keyed by the model revision the prompt saw. When the next submission commits, `commit_plan_submission` retires the delivered edits and comments, keeps the undelivered ones in `manual_changes`, carries each undelivered comment to the new revision's annotation store when its rows still resolve there, and keeps the bodies of those it cannot place in `unplaced_review_comments`. The editor names the items that stay pending in one notice on the new revision, and the next prompt delivers the unplaced comments as text. Nothing is dropped silently, and no delivered edit is replayed at execution. Check selections and test scopes in it are the net difference from the submitted revision: an entry that restores the submitted choice removes the earlier one. The accepted-plan input leaves check-selection edits out, because Harness enforces the accepted selection itself; the revision's timeline entry still lists them. Each edit advances the review digest, while submitted snapshots stay unchanged. Accepting or requesting changes freezes one snapshot of the edited draft and records one revision.

## Annotations and questions

The annotation projection inserts comment and answer rows into the review buffer.
Consecutive Markdown source rows stay in one Tree-sitter region across those gaps.
Each compact comment and read-only answer has its own syntax region. The projection
includes its body bytes and newlines, so Tree-sitter omits box padding, borders,
headings, and reply dividers. Each message also owns its Markdown layout marks.
A plan fence that spans an inserted comment can only paint plan rows. In a comment,
fence labels and rules fit between the card borders, and Tree-sitter token colors take
precedence over the card's default text color. Fenced examples keep their authored spacing.

Plan Review stores the card bodies as buffer text. Extmarks draw the headings and footer
as virtual lines and the side borders as virtual text. When Markdown hides a closing
code fence at the end of an answer, the footer follows the last visible code line.
The follow-up popup uses that same display anchor. Native cursor movement and Visual
selection therefore operate directly on the bodies. The popup reads the selection before
leaving Visual mode and uses the timeline's quote formatter. `draft_comments.input_target`
captures the selected source range or the message under the cursor. For a follow-up it
uses that message as the parent and the thread's final footer as the popup anchor.
For an empty body row, the review positions the idle cursor after the virtual border
and restores the logical end of line before input so motions, yanks, and quotes use
the same bytes as an ordinary empty row.
Opening the review folds existing threads. While the review is open it keeps fold
choices by root message ID. A folded thread projects one
summary row counting its question and comment annotations, and incoming answers update
the underlying thread while it stays folded. The popup tracks the footer across redraws. Confirming a nonempty input appends a new
annotation to the review. Saving uses the existing annotation queue and submits unanswered
questions. Canceling discards the popup buffer.

A follow-up question or comment carries its ancestors, oldest first and each with its answer, as conversation context (`ReviewAnnotationStore::thread_context`); its own body follows that context once, and its siblings and its own follow-ups stay out, so every saved comment reaches the revising model exactly once as its own requested change. Revision requests carry structured comment anchors. Feedback formatting finishes before the broker changes plan state, so an invalid anchor cannot drop comments from a revision.

`session.plan.question.answer` assigns a fork of the source session on the first Ask in an annotation chain. Follow-ups reuse that chain’s provider conversation, including after reopening the review. The plan ID and root annotation identify the chain within the source session. New annotations get fresh IDs even when an earlier card at the same location was deleted. Questions in one chain run in order, and separate chains can answer concurrently. Saving a plain comment records revision feedback without starting a provider turn. Each Ask receives the saved design, plan ID, version, source digest, and exact selected text with canonical plan line numbers. Up to three lines before and after the complete selection are labeled separately as context. Semantic declaration excerpts retain their own file line numbers, distinct from plan line numbers. All excerpts come from the captured review snapshot, not current workspace files. The fork answers about the selected text without writing files or changing the plan. Answers persist in the annotation store. Editing a question invalidates its answer, so a late response cannot attach to different text. `/config` exposes a provider-local Ask model, thinking level, and speed. Forge reads these settings for each Ask. Changing them applies to the next request in the same provider conversation. Clearing the override restores the source session’s current model and tuning.

Opening an editable Plan Review starts one read-only standby fork per source session. The provider opens the conversation without submitting a prompt. At the first Ask in a new chain, Forge checks that the native binding is live and that the source history, provider generation, access, model, effort, context window, speed, and resource settings still match. A matching fork starts answering immediately and Forge prepares its replacement in parallel. A missing, stale, or still-opening standby sends the question through ordinary fork creation. Additional views of the source share its standby. Closing the last editable view retires its unused fork.

Within the source session’s disposable state directory, each standby has a marker under `review-forks/unused`. Claiming it atomically renames the marker to `review-forks/chains/<chain-id>`, so reopening the card reaches the same provider conversation. Chains created through ordinary fork creation use their deterministic session ID. On reopening a review after a host interruption, Forge collects marked unused forks after checking their parent, purpose, and empty exchange history.

## Decisions

Only one decision can be pending at a time. Submitting a decision checks that the plan and buffer still match the captured revision and keeps the review open until the host answers. An accepted decision hides the review and focuses the Harness composer. A refused one leaves the review and its unsaved feedback in place and reports the host's full reason in an error notice wrapped to the notifier's width, which the notification history keeps. The decision popup drains keys already in the typeahead when it opens and discards keys that arrive within the focus-taking settle interval, including keys a key-hint plugin feeds back rather than types, so a repeated `oY` does not become comment text or submit it. Harness never opens PlanReview automatically.

Accepting nonempty inline comments uses the same revision feedback as requesting changes. Each comment retains its saved source anchors and any associated question-and-answer thread. Question-only threads do not become revision instructions. `PlanAcceptance` retains the captured comments until execution choices are confirmed. Harness then revises the plan instead of entering implementation.

`TaskSnapshot.auto_accept_plan` controls acceptance independently of the plan lifecycle. `/plan accept on/off` changes it without replacing the task or invalidating an active provider turn. New Plan tasks start with it off. Accepting inline feedback and requesting changes preserve it; only `/plan accept on/off` changes it. Complete submissions consult the current flag, and accepting a submission does not consume it. Execution inherits the planning task's policy. Clearing or replacing the task discards it.

`TaskSnapshot.plan_execution` retains selected execution settings and review context separately from acceptance policy. Entering execution copies the chosen tool approval, executor, and compaction into the Execute task's `plan_execution`, where they last for the whole execution; the task entry that also carries them is replaced when a paused execution resumes. A revision accepted during execution reads them from there, so the tool-approval question is asked once per execution. The input coordinator rechecks the flag under control admission before promoting a current submitted document, including recovery after interrupted promotion. It is the only owner of automatic acceptance: planning finalization does not accept a submission itself, because a second acceptance started execution beside the coordinator's recorded one, which then failed as `Execution did not start` with an `Input delivery failed` warning. Drafts, stale submissions, and paused tasks cannot promote. The promotion's operation identity names the plan, its user and model revisions, and `TaskSnapshot.plan_acceptance_enablement`, which `SetPlanAcceptance` increments each time the flag turns on; an acceptance that `/plan accept off` withdrew therefore runs as a new operation after `/plan accept on`, rather than the command journal replaying the withdrawn reply. The coordinator never resubmits an identity the journal already holds: a finished one is reported once as `automatic_acceptance_stopped` and left for the user, because a replay changes nothing and resubmitting it turned input admission into a busy loop. Review entries retain their originating exchange ID; revision dispatch resumes that exchange and its checkpoint rather than displaying another task-start heading.

Once execution authorization is complete, approval is recorded separately from task installation. A running planning response finishes naturally while the owner retains the pending decision outside the command lane. The timeline shows the wait; cancellation and replacement remain available. The final commit rechecks the selected review digest and source guards. Failed or interrupted planning retains the approval evidence but cannot start Execute automatically. Repeating the same pending selection observes its original decision; a different revision requires a new approval.

After submission, a prompt for the selected waiting Plan task becomes a plan discussion. A successful edit there applies `ChangesRequested` and requires a new submission or question before completion.

## Question picker

A question-only turn saves `PlanElicitation` under an `AwaitingInput` plan and opens the shared picker across the bottom of the Harness surface. Provider choices default to the keys in `picker.choice_keys`. After the final answer, a review page lists every answer before the provider resumes.

Ordinary questions use the session question controller. Each confirmed answer commits independently and enters the input journal. Clarification remains pending and receives an attributed `question_reply`; `question_revise` changes only a pending question and fences stale choices. The model may withdraw a question with a reason, but cannot record a user answer. Plan acceptance retains its own explicit confirmation gate.
