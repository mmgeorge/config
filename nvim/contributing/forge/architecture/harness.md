# Harness sessions, tasks, and permissions

An agent session that loses a prompt, replays a write after a crash, or lets the editor guess its lifecycle state cannot be trusted with a repository. Harness therefore owns durable sessions, exchanges, tasks, goals, child agents, approvals, and recovery state in Rust. Lua presents that state and captures explicit user intent, but never infers lifecycle transitions on its own.

Provider transport behavior is described in [Providers](providers.md). Plan lifecycle and checking gates are described in [Planning](planning.md). Buffer publication is described in [Buffers and rendering](buffers-and-rendering.md).

## Process and session ownership

The broker runs once per Neovim process inside the shared Forge host. `client.lua` owns the persistent JSONL process, and every Harness request and event carries a durable session ID, so independent sessions run concurrently without a globally active session. `session.lua` keeps each live session's transcript buffer, composer, windows, queue, and subscriptions in `harness_by_id` inside one Neovim tab.

One process-wide provider runtime serves every session. Codex launches one app-server with a loopback WebSocket listener and gives each session its own JSON-RPC connection and thread. Copilot shares one SDK `Client`, with independent sessions per Harness slot. The Codex launcher and its descendants live in a Windows Job Object or Unix process group that is terminated on shutdown. Provider stderr keeps a 16 KiB tail for startup failures.

Each session owns a `SessionCoordinator`. Provider execution requires its `ExecutionPermit`, while control commands and input admission stay available, so one session never waits behind another's provider work. The permit is held from request preparation through finalization and response delivery, and cleanup holds a separate control permit that blocks new execution until it finishes. The host reserves four of its 64 request slots for control methods such as health, operation status, cancellation, and approvals.

`/new [name]`, `/fork`, and `:ForgeHarnessNew` open their tab before provider work finishes. A fork first persists a child with `provider_fork_state = preparing`, the source's last completed provider turn, and an immutable snapshot of the source's visible history behind a typed `Forked` event. Provider preparation then runs outside the parent's lock. A prompt sent early waits only on that child, and completion persists `ready` or `failed` before notifying. The child inherits history for display only, without tasks, questions, or live agents. Codex forks request `excludeTurns`, because Harness renders its own history.

## Commands and operations

`forge.command` gives each mutation an immutable command identity bound to the session, host epoch, method, and arguments. Duplicate requests return the recorded response, and the response is recorded before delivery, so a lost acknowledgement can be checked through `session.command.status.get`. `session.command.apply` persists an operation ID on the ordered input lane before dispatch, and a compare-and-set claim lets each intent run once. `session.command.operation.get` reports an uncertain outcome but never replays it, and a restarted host never authorizes replay. Locally rejected requests carry `not_admitted`, so the UI never reports an unknown outcome for a request that never left Neovim.

Settings, permission, model, resource, and compaction changes share one coordinator in admission order. It closes conflicting execution, collects the provider attempt, finishes checkpoint finalization, applies the latest intent, and resumes the same exchange when its task remains active. A later pause prevents an earlier change from restarting work, and superseded intents never start a provider attempt. Permission toggles resolve against the preceding pending selection, so rapid commands compose.

`forge.replica` keeps confirmed state, optimistic intents, and editor drafts separately. A reply removes only its matching intent and rebuilds the view over the newest confirmed state, and revision gaps keep the previous view until replacement state arrives. Snapshots are scoped to their conversation, host generation, runtime epoch, and revision, so an older snapshot never replaces newer state. Failed state reads stay visible and retry after one, two, and four seconds, and `/task refresh` requests a new snapshot.

## Durable storage

SQLite runs in WAL mode with FULL synchronization at `stdpath("data")/forge/harness/harness.sqlite3`. File content lives in a SHA-256 object store, and plans keep canonical JSON and Markdown under `plans/`. Mutating transactions acquire write admission before reading their baselines, and the five-second busy timeout waits for another writer. Exhausted waits fail visibly and never replay provider work. The Harness and settings databases keep independent versions in `PRAGMA user_version`, and newer unsupported schemas stay untouched.

Each live session owner holds an operating-system file lock for the controller's lifetime, released at process exit, so recovery needs no heartbeat. Owner-checked saves prevent a stale broker from overwriting its replacement. A lock collision returns structured lease metadata, and Neovim offers Retry and Start New Session, plus Fork Session when the backend supports native forks. Deleting a session acquires its lock, commits an intent before filesystem cleanup, and resumes interrupted cleanup at startup. Renames commit the name and its timeline event together, and an expected-name check stops a late generated title from replacing a user rename.

Each session uses one versioned envelope, and only the exact current format loads: session format 51 and preference format 41. Older records stay stored but invisible, without migration. Tool output is stored as ordered `tool_output_chunk` rows keyed by exchange, turn, call, and byte offset. Each append commits before publication, and completion commits metadata and output together. Observer connections are read-only, so session rename, exchange comments, declaration reads, and rollback previews work while a provider turn runs.

## Input delivery

`SessionCoordinator` owns accepted messages through an in-memory `SessionInputQueue`. `session.input.apply`, `session.input.get`, and `session.input.operation.get` work without the provider execution lock. Ctrl-S sends ordinary input, steering an active turn as soon as the provider allows, while Ctrl-Q queues an explicit follow-up, and each group keeps FIFO order. Steering never bypasses uncertain delivery, pending configuration, or a pause. Pause sets a revisioned delivery barrier that operations captured earlier cannot undo.

Provider acceptance and queue acknowledgement are distinct. `SubmissionStore` persists the `Prepared → Sending → Accepted` journal, and restart recovery never treats `Sending` as permission to replay. A turn that ends before dispatch keeps the message for the next eligible interaction. Failed messages stay visible in red with the retry shortcut and block later follow-ups until retried or removed. `storage::admission::SessionAdmission` keeps the compact task, operation, question, and exchange projection in memory, republished after every committed storage mutation, so submission never reopens SQLite.

Lua owns the complete unsent draft, and typing sends nothing to Rust. Ctrl-s captures the draft and sends one `session.prompt.submit` with text, typed attachments, and a monotonically increasing session token. Acceptance clears only the unchanged captured draft, rejection keeps it, and newer typing always survives. Rust publishes a durable running exchange before provider preparation, and `PreparedTurn` binds completed preparation to that one exchange. Queued prompts keep their entry, attachments, task, and configuration until acceptance. Queue editing reserves an entry, so the queue drains only up to it, and `[editing]` marks the reservation.

`views/harness/attachment.lua` imports pasted file paths through `session.attachment.import`, tracking the pasted range with extmarks. `attachment.rs` stores complete files in the object store, and the composer keeps the typed objects separately from text, so text never carries a hidden attachment URL. Command admission and queue classification share one leading-token parser in `completion/command_source.lua`. Unknown slash commands keep the draft and notify, and a filename extension marks a path prompt instead. Up and Down navigate prompt history, which persists across sessions and restarts.

## Exchanges and cancellation

An `Agent` owns a persistent provider identity, an `Exchange` owns one admitted request through resolution, and each provider invocation is a `Turn` inside it. `ExchangeNode` preserves the order of turn content, delegations, clarifications, steering, plan resolution, and artifact changes. Provider execution runs as a task in the broker's `JoinSet`, and every exit aborts and joins it before transport cleanup, so cancellation never detaches work.

`session.turn.cancel` bypasses the serialized request queue so Ctrl-C can interrupt an active turn. Cleanup keeps the provider reader until native execution is collected. A newly submitted prompt stays retractable while the provider has produced no message, tool activity, task update, or workspace change. Codex retracts through `thread/rollback`, and Copilot through `session.history.truncate` at the submission's first root `user.message`. The broker then deletes the provisional interaction and Lua restores the exact prompt. If cancellation arrives while the checkpoint barrier still denies tools, the exchange settles without workspace snapshots, because its tools never had mutation access. After visible activity, cancellation persists the partial exchange as cancelled.

Mode restart interrupts provider turns and pauses the exchange, which keeps its request, plan, goal, and initial checkpoint. A pending baseline is collected and stored first, and resumption reuses it. Copilot cleanup has an eight-second bound. A cleanup or checkpoint failure keeps the exchange finalizing and blocks new admission. Ctrl-C, new prompts, and goal resume retry finalization first. The terminal checkpoint and exchange outcome commit together. Host exit overlays a reconnect error on the retained transcript, and only reopening Harness reconnects.

## Tasks and recovery

`TaskRecord` identifies a conversation-scoped Plan, Execute, or Goal workflow with its saved access and approval, phase, status, generation, and attempt. `current_task_id` selects it, and the task owns its plan through `TaskRecord.plan_id`. `/task` lists tasks, `/task new` offers the three kinds, and `/task resume`, `/task pause`, and `/task clear` act on the selected task. `/execute` and `/execute last` transition a submitted plan's task into Execute, and terminal executions require an explicit fork. Read requests never settle tasks or clear waits.

Interrupting keeps the selected task, and the next ordinary message resumes a paused task with that message as added instructions. Permission-driven resumption tells the model the previous and effective approval modes and asks it to inspect interrupted operations before retrying, without widening access. Workflow changes never enable writing or expand filesystem scope. The default approval for new Goal tasks and accepted plans is Ask, and the Plan approval defaults to Keep current. A goal accepts controls only while active.

Restart recovery keeps committed phase and completion evidence, suspends unfinished attempts, marks unsettled operations outcome-unknown, and never starts a provider automatically. Pause operations recover as cancelled, and unfinished provider turns in a finalizing exchange become interrupted. Health requests use reserved admission, the UI sends at most one per conversation, and ten seconds without a response shows connection uncertainty. Failure, disconnect, and unknown outcomes suppress automatic queue draining.

## Plan generation

The broker owns plan generation as one bounded continuation loop for every backend. Each turn applies plan edits to the canonical document, and only three outcomes move forward: a submitted plan, a new unresolved question, or another bounded turn. `ContinuationBudget` provides the shared budget mechanics for goals and planning. `PlanGeneration` allows 20 turns and stops after two consecutive turns without document progress. `/plan retry` resets only that budget. Automatic retries and goal continuations admit new exchanges labeled `Planning continued` or `Goal continued` without synthetic user prompts, so each attempt keeps its own metrics.

`PlanStateMachine` validates question, feedback, submission, review, acceptance, cancellation, and failure transitions. `PlanQuestionLedger` records answers, skips, and withdrawals keyed by both provider ID and a content digest, so a resolved decision cannot reopen when a provider retries with a different ID. `SessionPhase` projects exactly one visible phase. `RetryingPlanGeneration` and `PlanningFailed` expose only `/plan retry` and `/plan cancel`. Manual plan review uses a bounded review channel through the broker that owns the running exchange, so decisions return to the same control runtime without a new exchange.

## Timeline

Each session controller owns one `TimelineStream`, which compares stable entry identities and emits ordered `insert`, `replace`, `remove`, `tool_output`, and `message` operations under a monotonic revision. Initial load, reconciliation, resume, and preview carry full snapshots, and streaming carries only changed items. Provider lifecycle events stay transport evidence and never mutate transcript records in Lua. Prompt submission creates no Lua-owned interaction: broker admission emits the first patch with the durable interaction and a `Working` status. Provider deltas for one owner coalesce for at most 16 ms or 64 KiB.

`TimelineProjector` combines interactions, plan lifecycle records, and executions into one ordered presentation, with plan events placed by their `ExchangeAnchor`. `ExchangeLayout` keeps provider activity inside the activity fold and renders artifacts, plan submissions, verification results, and checkpoint changes before the final response. Check runs and session events require a `TimelineOwner` at creation, either the session or an exchange position, and that owner never changes.

`NodeMap` owns the expansion choices, node incarnations, and output sources for one open presentation. `NodeState` travels inside block metadata, so one publication changes text, node state, and visible ranges together. Lua sends `set_expansion`, `load_more`, and `retry_loading` node actions with a view sequence and node generation, and every window showing the presentation shares the choice. Tool output materializes through 16 KiB source chunks with an initial 64 KiB formatted prefix. Expanded file and section bodies load two window heights at a time, with 64 KiB pages and at most eight section requests per viewport pass. A failed section reports once and waits for an explicit retry.

Prompts and responses longer than three rows can fold. Prompts start folded, and the two latest responses stay expanded. Prompts and final responses use `●`, thoughts `○`, lifecycle rows `◇`, and tool calls `•`, while only fold headings use `▸` and `▾`, one per heading. Tool timings use a fixed six-cell column, such as `439ms`, `2.5s`, or compact minutes. Reasoning stays in durable history but never renders as commentary. `W` selects complete display rows, gutters included, and `<Space>l` copies them as displayed.

`ToolOutputView` keeps the ANSI parser across deltas, and `ToolOutputSnapshot` shares output storage with separate output windows without copying or reparsing. `BufferText` shares immutable packed rows through `Arc`. Fenced code is published first and highlighted later by `TranscriptSyntax` jobs, each with a 10-second deadline. The timeline has no aggregate byte, row, or block limit. Pages and transport parts bound individual deliveries.

## Check results in the timeline

Active checks never become history entries. `TimelineStream::update_checks` replaces only the status during a run and removes it atomically when it inserts the final result. Completed results form one Checks root that groups runs by Formatting, Lint, Validation, Tests, and Builds, then by source file or target. Categories start collapsed with their latest passing ratio, maximum attempts, and total duration. The root counts each check's latest outcome, so an earlier failure stops counting after a successful retry, while Run rows keep every attempt. The supervisor reads an optional generic JSON report from callbacks and never parses runner output itself.

`CheckSupervisor` holds admission and records under one lock, and the active run owns the source-work permit until its processes are collected. Process cancellation runs in an independent task, so blocked output cannot delay termination. `CheckPublication` coalesces intermediate snapshots in a separate persistence worker and flushes the terminal snapshot before the result returns. Automatic repair reopens the owning exchange through a dedicated transition that keeps its prompt, usage, and checkpoint.

## Status presentation

`SessionPhase` combines with optional `CheckActivity` in `buffer/status.rs`. The primary label keeps its own row, check progress follows, and the latest reasoning preview follows when the portable `status_thoughts` preference is on. That preference defaults to on. Active labels are Working, Planning, Revising plan, Compacting, Implementing, Verifying, Resolving, Stopping, and Saving exchange. Completed headings are Planned, Implemented, Verified, and Resolved. An idle provider with running checks shows Checking. Rust derives elapsed time such as `Working · Ns` from its own start timestamp, and Lua supplies only the one-second sync cadence.

`WorkflowActivity` builds lifecycle text from `LifecycleAction`. Started enters a task or phase, Continued starts another automatic exchange, and Resumed restarts paused or interrupted work. The status row's `BlockMetadata.status` carries its row, animation flag, and hint context, and Lua reads it from committed metadata, never from label text. User decisions show a static `◷`, and failures and pauses do not animate. One timer per transcript updates only the spinner extmark.

## Context and compaction

Provider usage normalizes into durable `ContextUsage`, which the winbar shows as remaining percentage and total window. `AutoCompaction` is a per-session policy with an enabled flag and a token threshold. It is off by default for ordinary sessions, and Background sessions enable it at 128,000 tokens. It runs after completed provider work and never estimates bytes as tokens. `Compaction` is a separate lifecycle with operation identity, observed start and completion, outcome, and an optional `CompactionResult`. `native_compact` gates manual `/compact`, which uses Codex `thread/compact/start` or Copilot `session.history.compact` and never creates a user exchange.

Each automatic operation owns one `ExchangeNode::Compaction` at its first observed position. While it runs, the status shows `Compacting · Ns`. Completed headings show before and after token counts only when both readings exist, and the after reading is accepted only after the provider confirms completion. A turn that ends before confirmation records an unconfirmed outcome. Copilot keeps a `Backend::compaction_stream` subscription alive across turns for compaction it starts on its own.

## Usage and durations

Each `Turn` keeps native input, cached input, reasoning, and output counts. Codex cumulative snapshots and Copilot `assistant.usage` call identities are persisted in `ExchangeMetrics`, so replay counts each report once. `ExchangeMetrics.request_count` counts distinct usage reports. Headers share one layout, such as `Planning 120s │ 20/21 tools · 12 s │ 820.0k -> 7.0k · 65 tps`, followed by changed-file totals when nonzero.

The outer duration covers tools and delegated waits during active execution and freezes during user-input and permission waits. Tool time is the union of overlapping calls in that same clock. The pass count includes only successful calls. Throughput divides generated tokens by active time outside tool, approval, and delegated waits, and both values stay fixed until the next report. Each `ToolCall` keeps its first running and first terminal timestamps, and a call first seen at completion shows `—`.

## Permissions

New interactive sessions use full reads, workspace writes, and Ask. Resumption restores the stored selections, Background generation disables writes, and forks copy the source's access. `HarnessSession` owns `AccessPolicy` (read scope Workspace or Full, write scope Off, Workspace, or Full, plus extra directory lists) separately from `ApprovalMode` (Ask, Deny, or Allow). `PermissionChange` resolves `/read full`, `/write`, `/write full`, `/ask`, `/deny`, `/allow`, and `/yolo` through the task transition coordinator. `/yolo` selects full reads and writes, Allow, and sandbox off together. Repeating it switches to Ask and re-enables the sandbox where supported. Shift-Tab toggles writes Off and Workspace.

`PermissionStore` loads one validated Rulesync-shaped document from `stdpath("config")/forge/permissions.json`, edited through `:ForgePermissions`, and compiles its matchers once. `CompiledPermissionDocument` evaluates saved rules without seeing approval mode, and `DirectoryPolicy` evaluates canonical paths, grants, and scope. Write-off denies every write, known or unknown path, regardless of rules or grants. Explicit denies and protected targets always win, and the permission document itself is never writable by providers. `PermissionCoordinator` then resolves a remaining Ask with a popup under Ask, a one-time rejection under Deny, or a one-time allow under Allow. Automatic decisions never persist rules.

Adapters reconstruct the affected paths before the coordinator sees a request. Codex resolves item approvals from the matching file proposal, and ACP combines partial callbacks with its tool snapshot. Missing targets stay unresolved, and a malformed target list fails as a whole. Path authorization resolves relative paths from the execution workspace, follows symlinks before later `..` components, and compares path components rather than string prefixes. The approval popup can also add a reported file's directory to the global readable or writable lists. A write grant uses the containing Git worktree root, and accepted grants persist before the provider receives approval. These scopes authorize reported operations only. They do not sandbox everything a provider, shell, or MCP server does, and only Codex adds OS isolation through `CodexSecurity`.

Shell commands are analyzed with pinned PowerShell, Bash, Zsh, and Nushell grammars without execution. Compound commands split into separate targets, each with its own picker page and exact and broad choices, and targets already allowed are skipped. Callback builtins, such as `ForEach-Object`, `Where-Object`, and Nushell's `each` and `where`, require every nested command to pass. Dynamic command names, code evaluation, definitions, and redirections return `shell_command_unsupported`. Invalid syntax returns `shell_command_parse_error`, and exhausted analysis budgets (8,192 nodes, 64 tree levels, 16 nested shells, or a 25 ms parse deadline) return `shell_command_analysis_failed`. Failed analysis never opens approval or authorizes a partial command, even under YOLO. Codex command text uses POSIX `shlex` quoting on every platform. In `permission.bash`, `"*"` is the lowest-priority decision, and the category displays as `shell`.

The approval picker stages one decision per target and submits them all when the last one is confirmed. Any denial rejects the whole operation, and rules persist atomically before the provider request is released. `/config` sets approval and answer timeouts, ten minutes each by default, with zero disabling expiry. The waiting provider future owns the approval deadline, so closing the picker cannot pause it. Expiry returns a one-time denial recorded as `resolution_source: timeout` with continuation guidance. An expired question set answers each open question with its recommended or first option. Plan acceptance never times out. The winbar shows the access abbreviation with `dx` for Deny, `ax` for Allow, and `ce` when check editing is on, and adds a red `YOLO` prefix for full access with Allow and no sandbox.

`session.check.editing.set` controls the `check_editing` permission per session, off by default, through `/checks edit on` and `/checks edit off`. Every `check_definition_edit` call is reviewed through the approval coordinator in Ask mode regardless of saved allow rules, and write-off still rejects it. The `harness-checks` skill owns the configuration instructions.

## Child agents

`AgentCoordinator` owns child conversations per root session: unique `/root/<name>` paths, durable `AgentTask` records, inboxes, follow-up queues, and cancellation. Admission reserves one of eight active slots, then commits the agent, the parent `Delegation`, the queued child `Exchange`, and the task in one transaction. Each child runs one task at a time with at most 32 pending follow-ups and starts with fresh provider history in the shared workspace. Provider tool callbacks reach the coordinator through a 64-entry channel instead of the broker lock, and tool authority expires with the root turn.

The portable `subagent_tools` setting is off by default, and `/agents on` and `/agents off` change it. Enabling it exposes `agent_spawn`, `agent_send`, `agent_followup`, `agent_interrupt`, `agent_list`, `agent_activity`, and `agent_tool_output`, with no wait tool. When a root turn ends with unfinished delegated children, the exchange stays open, and Harness starts one continuation with their reports after they settle. New user input resumes the exchange immediately. `agent_activity` returns at most 20 recent entries, five by default, without tool output, and `agent_tool_output` reads at most 32,000 characters per call through ownership-validated references. Children never receive delegation or root planning tools.

`AgentProfileStore` owns the global `stdpath("config")/forge/subagents.json`. Profiles hold a purpose, instructions, enabled state, provider, model, thinking, speed, and permission mode. `inherit` copies the root's choice at admission, while `default` selects the provider default. Each child persists its resolved profile, so editing a profile never retunes existing children, and effective permissions are the stricter of the snapshot and the current root. `/agents spawn` and `/agents edit` drive the profile picker and full-page form, and saves are revision-checked atomic replacements.

Main nests each child's fold inside its owning thought, previewing the latest thought and tool while running and the full delegated timeline after completion. Enter on its heading opens the child timeline. Child approvals show `Agent <name> · <provider>` and cancel only that child's requests on interruption. Root cancellation and access changes collect child execution first, and cleanup has a 30-second bound. On reopen, unfinished child tasks become interrupted and never replay.

## Session navigation and configuration

Only the transcript window owns the winbar. It shows the confirmed access and approval code, a speed glyph (`󱐌` for Fast, a red `󱐋` for Ultrafast), the resolved runtime model and thinking level, remaining context, and `? help`. A single trailing `*` marks a model, thinking, or speed change that is waiting for current work to stop. Codex resolves the `default` model through `model/list` and persists it, and the winbar shows `resolving model` until then. `runtime_resolved` events update the model without waiting for turn completion.

`views/picker/` owns every compact Harness decision surface: one state and layout model, a renderer, and a float anchored to the bottom of the transcript and composer. Structured rows use stable field IDs. Tab moves focus, arrows change values, Space toggles, and Enter edits or opens. The picker hides the terminal cursor through a paired global `guicursor` transition and restores it afterward. Window-local highlighting cannot hide a focused terminal cursor, so do not replace this transition. `/config` groups controls into Models, Compaction, Checks, Planning, Execute, Permissions, Tools, Display, Provider, and Debug. `/fast` and `/ultrafast` select exclusive service tiers, and disabling sends `default` explicitly.

`/undo` lists settled interactions newest first and offers conversation-only rollback, or rollback with file restoration when a checkpoint exists. Rollback collects execution, pauses the task, replaces the provider conversation, and restores the reverted prompt to the composer. Rolled-back exchanges disappear from the timeline but keep their records. `/sessions` previews sessions in the transcript window without taking a lease, `C-j` deletes an inactive session, and Enter resumes it. `/rename` renames directly. Bare `/rename` generates a two-to-six-word name in an isolated provider conversation. Each visited session has its own transcript buffer, and `session_navigation.lua` resumes the session on `BufEnter`. Non-Git sessions that enable writing require confirmation and display `NO CHECKPOINT`.

## Agent inspection

The root interaction exposes `harness_config` and seven `harness_session_*` tools through `control_tools/harness`, and the `harness-sessions` skill documents them. The portable `session_tools` setting, on by default, removes the history tools when off. Inspection uses read-only SQLite connections without migrations or leases. Reading another session requires authorization against its workspace, and that session's saved permissions never authorize the caller. Results are written to a private temporary snapshot with opaque continuations, and page budgets bound delivery rather than total size. Log inspection exposes only allowlisted diagnostic metadata, never prompts, credentials, or private reasoning.

## Out of scope

Harness adds provider strategies only through the typed `Backend` contract and never scrapes PTYs. The broker runs per Neovim process, so cross-editor live control would require moving it to a shared daemon with stronger lease coordination. Provider-local hooks and command policies can still reject a tool under Harness Allow, because backend-native policy remains authoritative outside the Harness protocol.
