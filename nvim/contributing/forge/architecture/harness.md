# Harness sessions and tasks

An agent session that loses a prompt, replays a write after a crash, or lets the editor guess its lifecycle state cannot be trusted with a repository. Harness therefore keeps sessions, exchanges, tasks, goals, and recovery state in Rust. Lua presents that state and captures explicit user intent, and it never decides a lifecycle transition itself.

This chapter covers the session lifecycle, from process ownership through input delivery, cancellation, and recovery. Read the related chapters for neighboring concerns:

## Terms

A **session** is one durable conversation with its settings and history. An **exchange** covers one admitted request from admission to resolution. A **turn** is one host-admitted provider response cycle inside an exchange, identified before native acknowledgement, so an exchange can contain several turns. A **task** is the durable owner of a Plan, Execute, or Goal workflow in the session's `active_task` slot. Its `TaskId` survives Plan becoming Execute, while `TaskRevision` changes whenever control admission changes.

The exchange owner (`ExchangeDriver`) uses the following terms, each with one meaning. Code names and trace event names follow them, while stable failure codes such as `execution_collection_timeout` keep their original spellings, because the editor matches on them.

| Term | Meaning | Code |
| --- | --- | --- |
| Active turn | The turn that currently owns provider execution. | `ActiveTurn` |
| Queued turn | An admitted turn waiting for the active turn to finish. | `QueuedTurn` |
| Dispatch | Sending a turn's input to the provider. It ends when the provider reports the turn's native start after the adapter confirms the send, or is lost when the send ends without confirmation. | `TurnDispatch`, `DispatchStage` |
| Stop | Interrupting work and waiting until its native and host work has finished. | `ExchangeStop`, `StopIntent`, `running_stops` |
| Idle | No turn or stop is running. | `TurnStatus::Idle` |
| Restart | Replacing the provider session and initializing it again. | `ObservationRecovery` |
| Execution state | Whether the owner may start provider execution: ready, stopping, restarting, or failed. | `ExecutionState` |
| Delivery uncertain | The journal records `Sending`, so the provider may hold the input and it is never sent again. | `SubmissionState::Sending` |

`exchange/owner.rs` holds only the handle that callers use: `ExchangeOwner`, `QuestionEvents`, and the `OwnerEvent` messages they send. `exchange/driver.rs` holds `ExchangeDriver`, whose `run` loop is a fixed sequence of named phases in `exchange/driver/`: intake (`intake.rs`), publication, storage, and delivery bookkeeping (`step.rs`), the effect phase that starts admitted work (`step.rs`, `check_admission.rs`), and wake selection and application (`wake.rs`, with one handler file per wake family under `handlers/`). Every phase reads its decisions from `Admission::evaluate` and changes the execution state only through `ExecutionState`'s transition methods (`execution_state.rs`), so no phase keeps its own copy of a rule or pairs the execution fence by hand. `RunningTasks::is_idle` is the only definition of "no background job is running", which restarts, shutdown, and approval timeouts all wait on, and `ExchangeDriver::turn_status` is the only computation of the turn status that stops and steering read. One update step applies a bounded run of already ready wakes before its effect phase, so a burst of turn or child events does not interleave with half-applied commands. The run ends as soon as the owner inbox holds intent, and a step that received intent at its entry runs its effect phase before taking further ready events, so a command or status request waits for the event being applied rather than for the run; the inbox was once read only after the run, which held the agents picker's `Ctrl-X` for 742 ms of child events until the child had completed.

### Publication outbox

`SessionPublications` (`exchange/publication.rs`) commits every sequenced owner notification to `owner_publication` before any output, and offers rows strictly in sequence order, so a stale row offered out of turn would corrupt the editor's view of the epoch. Four rules keep the outbox from stalling, leaking, or pacing a stream by the disk:

- **Document wakes.** `document_changed` only tells the editor that a newer transcript revision exists, so it never enters `owner_publication` and carries no `_publication` sequence. `SessionPublications` keeps the newest wake in memory, overlaying each wake on the one it supersedes so a status field from the older wake survives. Delivery sends the wake once no unadmitted row and no reconnect response precedes it, and a direct sequenced send flushes it first. A wake lost with the process or a closed transport heals through the reconnect snapshot's `timeline_revision`. An in-memory flag records whether an unadmitted row can exist, so delivery opens no transaction while the outbox is drained.

- **Owner start.** `recover_interrupted_offers` reclassifies every unadmitted row from the earlier epoch, `pending` as well as `offering`, to `uncertain`. Live delivery never sends an uncertain row, so the previous epoch's timeline revisions cannot raise the editor's floor; the first reconnect page carries those rows and admits them.
- **Direct offers.** A direct send commits the row, hands it to the transport, and queues the `admitted` update as a write-behind command, so the send waits on one commit instead of three and writes no intermediate `offering` state. A crash before the queued update commits leaves the row `pending`, which the next owner start reclassifies as `uncertain` and the reconnect page then reconciles. An update that fails fences the session scope: `SessionPublications` refuses every later publication with `Unavailable` rather than send behind a row whose state it could not record.
- **Pruning.** Owner start and each confirmed reconnect page delete admitted history that no reader still needs. They keep every unadmitted row and everything after the first one, the highest sequence (sequence allocation and cursor validation read the maximum), rows after the confirmed page, and rows whose origin is a durable producer identity, which a retried producer finds instead of publishing again. A cursorless reconnect page starts after the admitted prefix, because a newly attached view adopts current state without replaying history; the response still echoes the caller's absent cursor as `after`.

## Terminal task requests

`goal_complete`, `goal_blocked`, and `plan_phase_done` acknowledge intent during the current invocation. They leave the workflow unchanged while the provider delivers its final response. A host-owned terminal receipt binds intent to the dispatched task revision and invocation. The shared mutation seal closes new task mutations, native permission requests, check starts, and child work; read-only inspection, exact retries, final output, collection, and explicit cancellation remain available.

The finalizer requires normal native completion, successful collection, reconciled callbacks, current task authority, and current workflow evidence. It records Goal workspace evidence, progress accounting, and terminal disposition in one task transaction. A Goal completion that Harness cannot certify is refused, not failed: when a format or lint fix still awaits whole-check verification, or another owner (typically a check run the model started and left collecting) holds the workspace reservation when the turn ends, the finalizer settles the request with an ordinary continuation decision. The goal stays active, the terminal receipt records that decision, and the continuation input carries a `GoalCompletionRefused` notice with the reason, so the model learns why on its next turn. For pending verification, `goal_verification_pending` names each check and the exact whole-check `check_run` request, because a request that names only the check ID selects the changed paths and never satisfies the obligation. A Harness continuation never preempts a running check (`InputMessage::preempts_checks`): the model may end a goal turn while its own `check_run` still runs, and a preempting continuation interrupted that run and every retry, so the goal looped on the refusal until it stalled. A Goal or Execute task that becomes blocked or stalls records a `TaskAdvancement` row naming the cause and the `/task resume` and `/task clear` commands. While it stays blocked, `SessionPhase::blocked_by` replaces the idle phase with `SessionPhase::Blocked`, whose reason comes from `Task::blocked_cause`; both texts use `SuspensionReason::blocked_cause`, so the status split and the row name the same cause. Only an idle phase yields, so a stopping turn or queued input handing off to its turn keeps its own status. `SessionPhase::paused` follows the same rule for a paused task: only a phase in which nothing runs becomes `Paused`, so a turn that runs while its task is paused, such as an ordinary prompt in a session whose plan a restart paused, keeps `Working` with its clock and interrupt hint, and running children keep `WaitingForAgent`. Both status projections, `HarnessBroker::live_interaction_status` and the observation snapshot, name running children before they apply the pause, so they agree. A busy workspace still yields unprotected progress evidence, so the check result that is about to arrive starts the next turn instead of being retired with a failed exchange. Execute settlement also commits its artifact and retires completed tasks in that transaction. A phase transition retains its decision before reserving dependent work; replay reconciles a missing reservation through the existing task-turn journal without creating another reservation. Goal receipts retain the committed projection so a lost publication acknowledgement can restore the effect ledger without replaying the task mutation.

Manual and automatic approval use the same Plan-to-Execute path. A ready approval records one reviewed revision and its execution choices, then waits outside the command lane for any planning response to settle. The timeline shows this wait. Cancellation, pause, replacement, and shutdown can supersede it. Idle approval uses the same commit path immediately. Approval never requests a provider stop. Source and review guards are checked again before installation; later edits require fresh approval.

A foreground that fails for any reason releases its host settlement fence once native cleanup and every publication job have joined. Nothing replays a failed foreground's host effects, and durable stores already hold whatever an interrupted effect committed, so a host effect left ambiguous or unpublished is reported as a secondary failure rather than retained. Retaining the fence would refuse every later prompt with "prior host settlement is still pending" until the editor restarted.

Uncommitted receipts recovered after an owner restart cannot stand in for collected native evidence. Recovery rejects their advancement and pauses only their original still-active task for explicit recovery. A committed receipt remains committed. Provider input whose delivery was uncertain is never resent to repair task state. Disposable state uses compatibility directory `v47`; older live owners keep their own directory. Opening a database checks its version and all required tables before session startup; an incomplete matching-version schema is rejected without repair. Owner startup failures retain their cause in unavailable activity and reject new prompts, and the UI displays that cause while preserving the draft. Leased cleanup skips and reports live owners and leaves persistent settings outside the cleanup scope.

## Process and session ownership

The broker runs once per Neovim process, inside the shared Forge host. `client.lua` owns the JSONL connection to that host. Every Harness request and event carries a session ID, so sessions run concurrently and there is no globally active session. On the Lua side, `session.lua` keeps each session's transcript buffer, composer, windows, and subscriptions in `harness_by_id`.

One host serves one provider: `BrokerRuntime` holds a single provider runtime, and resolving a session saved under another provider fails with "session uses a different configured provider". Opening such a session therefore replaces the host, and `switch_provider` in `views/harness/init.lua` is the only owner of that replacement. It refuses while any Harness tab has running, queued, or unsent work, because the stop interrupts every tab. While it runs, the switching view's status rows read `Switching Harness to <provider>`. It then stops the host, initializes a new one on the target provider with the chosen session or a new chat, and restores the previous provider and session when that initialization fails. The destination is built hidden behind the switching view and replaces it once rendered, as a same-provider `/sessions` switch is, so the view never shows a blank transcript; `provider_catalog.models` labels the destination's model from that provider's latest catalog while the session's own catalog loads, so the winbar never shows a raw model id the editor already has a label for. It returns whether the switch started, so a caller dismisses its own picker only for a started switch. A host restart unloads every session, so `mark_detached_views` gives every other view a `host_error` notice that names the provider the host now serves and the way back (`Harness now serves Codex CLI. Submit or run :ForgeHarness to return to Copilot CLI.`). `health.notice` marks it `outlives_host`, which keeps the status rows visible although that view's presentation is no longer live; a notice that fades would leave a view that looks alive while every submit fails. A submit, queue, or steer from such a view, or `:ForgeHarness` in it, calls `reconnect`: a host on another provider switches back through `switch_provider` under the same refusal rule and without saving the default, and a host on the same provider resumes the session in place. Either way the composer keeps its draft unsent and the tab stays open. A detached view keeps drawing the old host's presentation, decorations and gutter markers included, until its session returns. That presentation belongs to a host generation that no longer exists, and closing it in place cleared the transcript's decorations a host round trip before the new presentation drew, so one frame showed the raw rows shifted by the empty gutter. `session_navigation.activate` therefore rebuilds a view that returns to its own session on a new host behind its panes: `begin_rebuild` gives it a fresh transcript buffer in a hidden window over the transcript, where the new presentation renders without the composer (`pending_rebuild`), and `complete_rebuild` closes the old presentation, puts the hidden window in its place, deletes the old buffer, and binds the composer, all in one callback. `/sessions` lists a session that such a view still shows as **Inactive** with `(open, disconnected)`. `/provider` saves the new provider as the default for later editor starts. The session picker reaches the same switch when the chosen session belongs to another provider, and passes `persist_default = false`: choosing a session is not choosing a default, so startup keeps following the saved default provider.

Each session has a `SessionCoordinator`. Provider work needs its `ExecutionPermit`, while control commands and input admission do not, so one session never waits behind another's provider work and a busy session can still accept input. The permit lasts from request preparation through execution finalization and is released before the final response or input update publishes readiness. A delayed input snapshot must not leave the editor busy after native work has settled. The exchange owner serializes mutation commands and retains their asynchronous jobs, so dropping a request waiter cannot abandon cleanup or publish a later result out of order. Transport admission reserves capacity for control requests during saturation.

Controller construction resolves inherited model tuning against the provider's workspace catalog before publishing the controller or its initial snapshot. An unavailable model fails construction. Unavailable saved reasoning, context-window, and service-tier choices fall back to advertised defaults; absence of a context-window override stays absent. This applies equally to initial opening, new conversations, and resumed controllers, so an early prompt cannot race native initialization with unchecked preferences. Explicit configuration commands continue to reject unsupported choices before committing them.

`/new` and `:ForgeHarnessNew` open their tab before provider work finishes. `session_navigation.begin_new` binds the composer command set to that tab's composer at once, because creation can take seconds and keys typed there meanwhile would otherwise fall through to the user's own mappings; a submit before the session exists keeps the draft through `admit_composer_input`. The reply does not change the mode or focus of a composer the user is already in: `focus_state` leaves Insert mode only through the composer's entry guard when focus moves, and `/clear`, which keeps the focused composer, leaves Insert mode in `new_session` when it is submitted. A request the host refuses created no session, so `session_navigation.fail_pending` closes that tab with its buffers, mappings, and autocommands and reports the refusal in the view that issued the request. `/fork` and `/btw` open no tab until the host answers, because the host refuses a fork of a source with running children or of a fork still in its first turn, and a tab opened for that request was drawn for a frame before the refusal closed it. `controller.fork_session` takes the command out of the composer with `composer_draft.take` and returns it on refusal; `session_navigation.open_fork` opens the accepted fork's tab under the child's id and focuses it only while the issuing view is still selected. `layout.rename_buffer` binds a placeholder-named view to its session without leaving the former name behind: Neovim keeps a renamed buffer's former name on a new unlisted buffer, which otherwise remained in `:ls!` for every `/new` and startup view. A tab whose session a switch is moving into another tab keeps the session's label until it closes, because `tabline` also resolves a tab by the transcript buffer a visible window in it shows. `:ForgeHarness` focuses its existing panes or opens them in a new tab. `/clear` replaces the session in the current Harness panes after creation succeeds. A fork first persists a child with `provider_fork_state = preparing`, the source's last completed provider turn, and a snapshot of the source's visible history. Provider preparation then runs outside the parent's lock, so a slow fork cannot stall the parent. A prompt sent early waits only on that child's fork gate. While the child reads `preparing`, `SessionPhase::preparing_fork` replaces its idle phase with `PreparingFork`, so the status split names the copy that the waiting prompt's `[submitting]` entry depends on; a retry that reopens a failed fork and the outcome of every attempt redraw that status through `HarnessBroker::provider_fork_status_events`, because they change only the session record and no exchange publication follows them. The host registers the gate before it opens the child and starts the fork task before it sends the response or `session_created`, so a failed delivery cannot leave the gate pending; the task holds its outcome event until that announcement finishes, which keeps the outcome after it. A `preparing` child with no gate belongs to a fork that a previous host quit or that failed before its task started, so resolving it records the fork as failed. The child inherits history for display only, without tasks, questions, or live agents.

A provider copies a live conversation only while it is idle, so a fork of a session whose turn is running cannot copy that conversation: the native fork fails with `ExecutionActive`, and a child that had already copied the source's timeline would show the unfinished exchange frozen forever. `prepare_provider_fork` therefore selects a `ForkBoundary` before it writes anything, from `ForkOptions::source_is_executing`, which `start_session_fork` answers from the source's execution permit. It asks while it holds the history writer: a turn that starts later cannot commit its exchange until the writer returns, so the boundary and the history the fork copies describe the same moment. `start_session_fork` also reads the permit before preparation and keeps an executing answer, because a turn that ends while the fork waits for the writer may not have saved its finished exchange. `Current`, for an idle source, copies the whole conversation through the source's binding. `Settled`, for an executing source, stops at the last finished exchange: the child's timeline omits the unfinished exchange, its `forked` event records `unfinished_exchange_omitted`, and the native fork reads the provider checkpoint that exchange recorded, which stays readable while the source runs. A source that neither ran nor inherited a provider turn has no native history at either boundary, because a provider writes a conversation when its first turn runs: the Claude CLI and the Codex app-server both reject a native fork of a session that ran none. Its child therefore starts `ready` on a fresh provider conversation with no provider work, whether the source is idle before its first prompt or executing its first turn. `prepare_provider_fork` reads inherited turns from the source's own inherited timeline entries, since a fork's exchange list never shows the turns its native conversation copied. Two cases have no safe boundary and reject before any session exists: the last finished exchange recorded no checkpoint, or the source is a fork that inherited provider turns and is inside its first turn, whose inherited history lives only in a conversation that is busy.

The native fork runs after preparation returns the writer, so a source can still start a turn between a `Current` decision and the provider's copy. The fork task then retries once against the checkpoint recorded in the child's fork point, which names the same history the child inherited. The fork marker's text puts an omitted exchange first, "Forked before the unfinished exchange of", because a session ID and name fill most of a transcript row and a wrapped event folds every row after its first. A fork that still fails leaves the child `failed`, and that state is not terminal: `SessionControllerRegistry::await_provider_fork` starts a new native attempt, under a new operation identity, for the next provider-bound request that finds the child `failed`, and concurrent requests share that attempt through the fork gate. A request that waited on an attempt reports that attempt's failure and leaves the retry to the next request.

A native fork of an idle source whose binding is not open yet opens that binding only as a fork source, and no owner reads its event stream until the source runs a turn. `ProviderBridge::retire_owner` drops a stream that no owner took before it waits for the stream's published events to be consumed; otherwise closing that session, and every close queued behind it, would wait forever.

Reconnect responses carry admitted events and a state snapshot with independent lifetimes. `forge.client` replays a retained publication page before invoking its response consumer, so rejecting an invalidated snapshot cannot discard an acknowledged retraction, approval, or command completion. `HarnessSnapshot.receive_publication` retains the page receipt even when the controller rejects the state snapshot; only the matching owner confirmation advances the reconnect cursor. Live and replayed copies share the transport's publication deduplication. A cursorless attachment accepts the host's admitted-prefix anchor only when the matching page confirmation arrives; later pages must extend its confirmed cursor.

### Aside sessions

`/btw <question>` answers a question about a session without interrupting it. It sends `session.fork` with `aside: true`, which creates an ordinary fork whose `HarnessSession::aside` names the origin session; a fork of an aside keeps the same origin. The marker changes three things for the aside's primary agent, and nothing else about the session. `ProviderRequest::standing_sections` adds an `<aside>` section that names the origin and states the aside's role, delivered once per binding and again after compaction like every standing section, so the provider's cached system prompt is unchanged. `session_tools_enabled` keeps the `harness_session_*` tools on regardless of `/config`, because inspecting the origin is the aside's purpose, and `harness_session_exchange` reports an unfinished exchange's commentary so the aside can read a turn that is still running. The registry offers `origin_message`, the aside's only write to its origin.

`origin_message` delivers through `SessionMessageRouter`, which `BrokerRuntime` owns and `SessionControllerRegistry` binds, because a broker owns one session and cannot reach another session's controller. `SessionControllerRegistry::deliver_session_message` resolves the origin, waits for its own fork, attaches its publishers to the editor connection retained from the latest request, and submits the message as a `TurnKind::SessionMessage` that names the sending aside. The queue shows the turn's label, and the origin's model receives a `<session_message>` data element whose fixed instructions let it act on the message only where it agrees with the origin user's requests, so an aside's words never arrive with the origin user's authority. `CommandRequest::from_host_input` attaches the typed turn after the editor's own decoding, because `CommandRequest::from_input` never accepts one from an editor request. `queue` delivery, the default, waits behind the origin's running turn and queued input and never resumes a queue the user suspended; `steer` delivery carries the queue's control revision and enters the running turn as the user's own steering would. The registry releases the retained connection once shutdown has quiesced every request, so the outbound channel still closes with the editor.

## Commands and operations

A mutation that times out leaves the client unsure whether it ran, so retrying it blindly can apply it twice. `forge.command` prevents this by giving each mutation an immutable identity bound to the session, host epoch, method, and arguments. Rust records the response before delivering it, so a duplicate request returns the recorded response, and a client that lost an acknowledgement can ask `session.command.status.get`.

`session.command.apply` persists an operation ID before dispatch, and a compare-and-set claim lets each intent run once. `session.command.operation.get` can report an uncertain outcome but never replays it, and a restarted host never authorizes replay. A request rejected locally carries `not_admitted`, so the UI never reports an unknown outcome for a request that never left Neovim.

Settings, permission, model, resource, compaction, and cancellation commands enter the exchange owner's FIFO in admission order. It stops conflicting execution, collects the provider attempt, finishes checkpoint finalization, applies the latest intent, and resumes the same exchange if its task is still active. The turn that runs again receives the stopped turn's own input: `HarnessBroker::restarted_turn_input` reads it back from the submission journal by the exchange's `input_message_id` and adds a `Notice::TurnRestarted` that says why the turn runs again, such as which permissions changed, so a plan revision keeps its review request, comments, and edits, a check turn keeps its check results, and every input keeps its notices and attachments. Only an exchange whose input the journal does not hold continues from its first prompt; a generic continuation built from that prompt alone once sent a revision stopped by `/compact` back to the model without the review. A later pause prevents an earlier change from restarting work. Permission toggles resolve against the preceding pending selection, so rapid commands compose. An approval-mode change alone stops nothing: `ConfigurationCandidate::effect` classifies it as local, and its commit calls `PermissionCoordinator::apply_approval_mode`, which updates the mode the root owner's bound callbacks read and decides that owner's pending mode-governed requests as new ones would be (Allow approves once, Deny rejects with the reject-all reason, Ask leaves them waiting). Proposal reviews are not mode-governed and keep waiting. The interrupted attempt of a configuration restart is not a model turn: it never records goal or execution evidence, so restarts neither spend the total-turn budget nor advance the no-progress count, and only the replayed turn that completes normally counts.

`Admission::evaluate` (`exchange/driver/admission.rs`) holds every rule for what the driver may start: commands, turns, turn effects, question and check tools, automatic and task checks, task delivery, deferred configuration retries, restarts, and shutdown. It is a pure function of an `AdmissionFacts` snapshot that each phase gathers fresh, so no phase applies its own copy of a rule, and a table test pins the dispatch race cases. Its `start_command` rule decides when the owner starts its next queued command, and the effect phase and the step-restart gate both read it. No command starts while a provider restart or a stop runs, while the session's observation stream is closed, or while the current turn's send was lost (`DispatchStage::Lost`), except in a failed owner, whose commands start only to be rejected. A failed observation stream reports its failure to every later reader until a restart replaces it, so a command started then would fail on evidence that belongs to the failed turn. Commands other than cancellation also wait while the turn's send is unsettled, from host admission until the provider reports the native start of the turn the adapter dispatched (`TurnTransaction::dispatch_stage`). Stopping a turn whose send is in flight leaves its delivery unknown. Stopping it before the journal records `Sending` prevents the send, after which both the restarted exchange and the input queue would deliver the prompt again. The adapter's dispatch confirmation alone does not settle the send: Copilot confirms when it hands the input to its runtime, which begins the turn a moment later, and a thinking-level change in that moment aborted the runtime before the turn it then ran anyway. The adapter had already settled the input as stopped, so its observer rejected the late turn as unexpected execution, the binding closed under the pending abort, the stop failed, and the change was lost with the exchange failed or left `Stopping`. A model or thinking change made at the start of a turn therefore waits, marked `*` in the winbar, until the provider has started the turn, then restarts the turn on the new setting. Cancellation stays exempt from that wait, because it prevents an unsent prompt and restores the draft, or waits inside the provider runtime for an in-flight send, and on Copilot for the native start of an accepted input, before stopping the turn, and it never restarts the exchange. A submission (`InputCommand::Submit`) is exempt as well: it only adds a prompt to the input queue, which neither stops nor replaces the send. Holding it left the editor's request unanswered until the provider confirmed the send, so a prompt meant to steer a turn whose start the provider was slow to accept read as an unconfirmed submission for that whole time. The queued prompt still steers only once the send is confirmed, because steering needs the provider's running turn. Cancellation that arrives after a failing turn has closed its engine pins no invocation.

`forge.replica` keeps confirmed state, optimistic intents, and editor drafts apart. A reply removes only its matching intent and rebuilds the view over the newest confirmed state. Snapshots are scoped to their conversation, host generation, runtime epoch, and revision, so an older snapshot cannot replace newer state. A revision gap keeps the previous view until replacement state arrives. Failed state reads stay visible and retry after one, two, and four seconds (`controller.state_sync_retry_delays_ms`); a later successful read clears the failure and resets the sequence. A view keeps one `session.state.get` in flight per session and host generation, so an in-place session switch issues its own read, and a reply for a session the view no longer shows triggers a read of the current one. A `document_changed` patch does not discard an in-flight read, because the read's `timeline_revision` already orders it against the patch; a patch stamped with another runtime epoch or host generation is ignored.

## Tool execution deadlines

`ToolWatchdog` consumes typed item lifecycle observations from the ordered native stream and captures
each invocation's deadline once. The root broker and `AgentRuntime` stop provider
execution when the earliest unfinished tool expires and retain the timeout as a
failure. Output, title changes, and replayed start events cannot extend a deadline.
The root broker's `handle_foreground_timeout` also appends a `ToolTimeoutRecord` (item, title,
configured duration) to `Exchange::tool_timeout`. Providers report a call their interrupt stopped
only as interrupted, so the record is what marks that tool row failed with
`Failed: timed out after 10m; execution stopped.` and what keeps one
``Stopped: `title` exceeded its 10m tool timeout.`` row beside the exchange's turn errors after the
exchange's single failure notice is gone; the broker publishes no separate timeout diagnostic. The
exchange still fails, and no continuation turn follows. The watchdog names the call by the title
from the item's start, even when an approval or execution report armed the deadline first under
the item identifier.

A pending approval suspends its tool's deadline. Codex announces a command as running before it
asks to run it, so the deadline starts before the approval opens; with both timeouts at their
ten-minute defaults the tool deadline always fired first, interrupted the turn, cancelled the
approval as `TurnInterrupted`, and failed the exchange. The watchdog now observes
`PermissionApproval` events scoped to `ApprovalScope::Item`. A request moves the matching
invocation's deadline to `AwaitingApproval` with its remaining time, and the deadline restarts
from that remainder once every approval for the item resolves or is cancelled. An approval for an
item the watchdog has not yet admitted holds a full-duration entry, so the later start cannot arm
a deadline beneath the wait. Approvals without a tool subject leave every running deadline in
force. The approval's own timeout therefore decides the wait. Its rejection continues the work
through a permission-timeout turn only when the turn that asked was interrupted or failed, or had
already settled when the approval expired; see [permissions.md](permissions.md).

The approval-timeout watcher in `SessionController::attach_timeout` follows the current
invocation's `TurnCancellationSignal`. `TurnCancellation::arm` installs a fresh signal for every
turn and closes the previous one, so a closed signal means a new turn began, not that the session
ended: the watcher resubscribes to the current signal. Exiting on that closure would end the
watcher at the session's first turn and silently drop every later permission-timeout continuation.

While a foreground attempt runs, `ForegroundWait` holds a `ForegroundToolOwner` on its
watchdog, and the foreground is the sole collector of a timed-out turn. The inbox tool
monitor only signals expiry and waits for that owner to release before it collects
background work; two collectors racing for one native turn previously let either win, so
the exchange settled nondeterministically as failed or stranded in finalization. Foreground
timeout cleanup stops only the timed-out exchange through `cancel_exchange`, as owner
cancellation does, instead of closing the engine. Closing the engine dropped the interrupted
turn's terminal event and recorded the turn as a disconnected failure rather than
`Interrupted`. Because scoped collection leaves the stopped invocation registered with its
execution owner, failure settlement commits that invocation's settlement ticket after every
failure checkpoint and publication drains; an uncommitted ticket would reject the next prompt
with "execution owner is unavailable or already active". A cleanly collected timeout then finishes as a
settled `tool_timeout` response, as collected cancellation finishes as `turn_cancelled`.
A deadline found elapsed only after a cancel or restart already began collecting the turn
does not convert it into a timeout: the collected outcome settles the exchange, so a cancelled
prompt is still restored, and the foreground claims the timeout report so the inbox monitor
cannot later publish it against the settled invocation.

`SessionObservationInbox` routes tool observations to watchdogs by owner and exchange, not by
invocation. A steering message, child result, or check repair continues the exchange under a
successor invocation, and its events reach the inbox before the foreground adopts that scope;
a registry keyed by invocation never delivered them, so a hung tool in any continuation had no
deadline. Registering a new foreground's watchdog retires the previous one, which keeps its
admitted background deadlines and then lets its monitor end instead of parking for the
session's lifetime.

A steer is accepted under the invocation it was dispatched to. The parent's input receiver,
`ActiveSteering`, binds its event sink to the exchange's first invocation for the exchange's
whole life, so a steer into a successor invocation, such as the continuation that reports the
parent's children, once published its acceptance under the first invocation. The execution
owner and `HarnessBroker::apply_foreground_observation` both refuse an acceptance outside its
dispatched invocation ("acceptance receipt crosses foreground invocation"), so the exchange
failed, the parent's report stopped, and the steered prompt was lost on every provider.
`SteerCommand::deliver_to` rebinds the command's sink to the dispatched scope before the
`UserSteering` job steers it, so the acknowledged input waits for its consumption report on the
invocation whose turn will report it. A steer the provider refused is resent by
`SteerCommand::complete_with` as the prompt of a new invocation that only the execution owner
names, and its receipt still travels under the first invocation's sink, so the foreground
accepts an acceptance from any invocation the owner admitted for its own exchange; such a prompt
is recorded consumed on acceptance and needs no report.

A failure that leaves provider state unknown restarts the provider instead of stranding the
session. A turn that fails, a stop that cannot prove the provider idle, a collection task that
ends without its result, and an observation stream that closes each make the owner request a
restart on its own (`ExchangeDriver::restart_after_failure` and `restart_advance`), without
waiting for the next prompt. The owner holds every command and turn until the restart finishes.
The failed turn stays retained in `failed_work` until the restart replaces it, and the restart
starts only once no input delivery is active, so the failed turn must not hold any delivery.
`HarnessBroker::fail_foreground` therefore retires the turn's steering lane as soon as the
failure is classified, and `finish_foreground_failure` releases any steering still buffered in
it. Steering whose preparation finishes after the failure finds the lane closed, and a buffered
command is dropped unread; either way its delivery observes the retired lane with a `Prepared`
submission and returns the message to the queue. Only a command the native turn never read is
released this way, and the adapter records `Sending` before it dispatches one, so a message the
provider received is reconciled instead and never sent again. The session's observation
listener (`attach_provider_events`) ends once a restart replaces its inbox: a failed
generation's inbox reports its failure as pending for good, and the owner drains only the
replacement, so serving the old inbox after a failed initialization woke the owner without end.
The listener also stays off the inbox while a foreground consumes it. A foreground drains the
inbox into its own queue and applies one event per publication acknowledgment, so a listener
draining beside it once applied a native child's later events while the foreground still held
the earlier ones, and the child's record refused each earlier event as a sequence regression.
`ForegroundTransaction::inbox_claim` holds a `SessionInboxClaim` for the transaction's life:
`has_unclaimed_pending` and `unclaimed_notified` keep the listener waiting, and
`drain_session_events` drains nothing, until the claim drops and wakes the listener for any
remainder. A foreground whose inbox closed or failed releases its claim early.
Success reopens execution, lifts the collection fence, and traces `exchange.restart.finished`. Failure closes execution for the
session's lifetime and publishes a `provider_restart_failed` error. Its text becomes the owner's
failure reason, so every command queued behind the restart and every later one fails at once:
`Admission::evaluate` starts commands of a failed owner even while its observation stream is
closed, and `command_start` rejects each one, cancellation with `provider_failed` and every
other command with `session_unavailable` carrying that reason. A new prompt's observation
recovery (`OwnerEvent::RecoverObservation`) in a failed owner answers with the same cause
instead of requesting another restart. A failed owner with no remaining work reports its turn
status as idle, so session shutdown still finishes; its observation listener then reports the
stream failure that no restart replaced. A failed owner never executes again, so `session.resume`
reopens it (`SessionControllerRegistry::resolve_reopening`): when the resolved controller's
activity is `Unavailable`, `SessionController::stop_failed_owner` collects its owner and tasks,
retires its binding with `SessionExecutionRegistry::forget`, and releases its lease, and the
registry evicts it and resolves a fresh controller from storage. `forget` also removes the
owner's registry slot, because retirement leaves the slot's closed observer in place and a fresh
controller would adopt it. The transcript and the saved queue survive, and the loaded queue
starts suspended as after a host restart. A queue resume, retry, or new submission recovers a
closed or uncertain provider generation before delivery, as a prompt does, so a resumed queue in
a session loaded with an uncertain configuration does not wait for a later submission. A resume
of a healthy owner returns it unchanged.
The reopen rebuilds only this session's binding: a provider runtime that the host shares and
that cannot start again stays failed until `/provider` restarts the host. A failed owner
never executes again, so the reopen skips its shutdown domain commit: `stop_failed_owner`
aborts the exchange task, which drops the broker lock and the owner's retained resources,
and storage keeps what was last committed. It then retries the binding's retirement twice,
each attempt bounded by `FAILED_OWNER_STOP_BOUND` (10 s, the shortest cleanup boundary the
provider API defines), and when neither succeeds it calls `Provider::thread_terminate`, which
ends the binding's native process or connection without awaiting settlement. Only a binding
that can be neither retired nor terminated fails the reopen, because releasing it would let
two live writers share one native conversation. A lease the old broker cannot release is
taken over by the replacement, which runs under the same client, once the old broker drops
its runtime lock.

A cancellation whose native collection is still pending `STOP_COLLECTION_BACKSTOP` (20 s,
Claude's interrupt settlement grace and the longest any adapter allows) after the 30-second
stop deadline force-terminates the root binding through the same operation. Successful termination
supplies collection evidence. The host can settle a cancelled exchange from its collected outcome,
or recover the provider when the native terminal outcome is unavailable. Antigravity, Claude, and
Codex terminate by killing a process the binding owns alone. Antigravity releases its native
history reservation after collection.
Unacknowledged inputs retain their uncertain delivery state. Copilot's CLI serves every binding, so
it revokes the binding's callbacks and events and disconnects its session; when the disconnect
does not finish within five seconds it fails the shared client generation, which force-stops
the CLI and moves sibling bindings through ordinary generation recovery. Owner storage failures
stay terminal without a restart,
because a new provider generation cannot repair the database. Only failures sourced from SQLite,
file I/O, or the owner's journal count as storage failures (`exchange::failure::storage_failure`);
a domain rule that refuses a command, such as `/goal continue` on a paused task, answers that
command with a typed failure and leaves the session usable. A cancellation whose target pinning
fails for any other reason is answered as a failed stop and collected like one. Shutdown that
cancels a requested but unstarted restart fails execution instead of leaving the owner
`Restarting`, so its turn status reaches idle and shutdown finishes.

A stop's retained transition outlives the stop as evidence, so once its host jobs join, the driver
releases both its control permit and its child quiescence; a held quiescence parked every later
root turn at completion. Child collection treats a child whose cleanup failed as settled with an
error, which makes the stop uncertain and restarts the provider, because that child keeps its
execution slot and the active count never reaches zero. A cancellation settlement that fails, or
whose command loses its state commit, releases the host-settlement fence of the exchange it was
finalizing (`abort_prior_finalization`); the exchange stays finalizing with the recorded error for
the next admission to retry.

An explicit cancellation's response deadline ends caller observation while the same active
operation continues collection and foreground settlement. The owner retains the execution fence
until that operation finishes; it neither starts a second collection nor requires another cancel
to make progress. The historical timeout result remains terminal even when cleanup succeeds later.
Late automatic-check results cannot schedule refresh, execution, repair, or retry work during
collection. A compaction start publication acknowledged after cancellation retires its reserved
attempt without invoking the provider, then publishes that retirement before the final response.

Equivalent cancellation requests join the active operation only while no intervening command is queued and their input-restoration policies match. Every request retains its own durable receipt and replay result. The join table maps a follow-up input's `after_control` identity to the original operation; recovery copies an already committed operation outcome into unfinished joined receipts without executing either request again.

`ForegroundJob::disposition` distinguishes settlement work, reserved work that needs retirement, and new invocation work. Discarded jobs return a completion signal to their reducer. Late clarification, check-repair, stale-continuation, and compaction publications advance cancellation instead of reopening native execution or leaving a phase waiting for a discarded job.

`owner_cancellation` stores the latest operation projection in the same transaction as its `owner_core_log` record. It retains operation and exchange identities, revision, phase, response timeout, timestamps, and safe blocker facts: foreground jobs, staged effect names, publications, checks, children, input delivery, and recovery work. It contains no prompt or tool output. Snapshots project the record through native collection, host drain, settlement, and provider recovery; a response timeout remains separate from those phases. Restart recovery marks an interrupted operation failed and never replays it. The new owner restores that revision before admitting prompts, so its first progress update remains newer than reconnect state. Storage failure fences execution rather than certifying uncommitted progress. A cancel that finds nothing to stop still runs, because it pauses the queue and retracts an unclaimed prompt, but `cancellation_publish` stores no projection for it: an operation with no exchange, no expired response, and no blocker counted by `CancellationBlockers::owns_work` has no progress to report, and recording it made every observer show a stop on an idle session. An operation recorded once keeps reporting until it settles.

`CollectionStarted` pauses the exchange clock. Cancellation keeps the UI stopping until the operation settles, including after native collection, under the single `Stopping` label. Reconfiguration retains its existing `Cleanup timed out - provider state uncertain` status. The Lua controller keeps one cancellation request in flight per runtime epoch and ignores stale replies and older progress revisions. Input retirement sees an idle foreground once its work ends even while execution admission remains fenced; otherwise input retirement and provider recovery would wait on each other.

The `tool_timeout` setting defaults to ten minutes and applies to shell commands as
well as tool calls. `SessionEventInbox` retains watchdogs for confirmed background
commands after foreground completion and routes their later terminal events to the
original watchdog. `CheckSupervisor` applies the same setting to each subprocess,
collects the terminated process tree, and stops the run on timeout. The `/config`
timeout endpoint saves this policy without interrupting the current provider turn.

## Durable storage

Harness separates persistent settings from disposable execution state beneath `stdpath("data")/forge/harness/`. `storage::state::VERSION` selects `state/vN/` for history, submission journals, captured objects, plans, checkpoints, traces, check artifacts, and private provider runtimes. An incompatible contract increments that version; new hosts start with fresh state without opening or migrating older sessions.

Disposable state version 63 separates grouped check results and partial-failure identities into a host-owned inbox. Its admission receipt commits with the pending delivery; no check result enters the user input journal or its editor publication. The exchange loop schedules those deliveries independently of user-queue controls, while reusing the provider submission journal to preserve acceptance and uncertain-send evidence across restart. Persistent settings remain outside this version boundary. See [Project checks](project-checks.md) for collection, routing, and diagnostic events.

`settings.db` owns global and workspace choices, provider tuning and selection, model pins, resource selections, logging preferences, and receipts that prevent replay of persistent mutations. Session overrides and settings-application snapshots live in the versioned history database. The settings store validates its exact schema. An unsupported record or corrupt canonical schema reports its cause.

Startup validates `layout.json` before opening providers or storage owners. A positively recognized retired layout stops startup with an error requiring `:ForgeHistoryClear`. Under the layout gate, the command checks old leases, database owners, and repository process evidence before moving or deleting files. It keeps a compatible `settings.db`, permission rules, and subagent profiles at their existing paths. It moves incompatible settings databases and their SQLite sidecars, old provider selection, and logging files to `retired-settings/` for manual recovery. Archive conflicts stop cleanup before any setting file moves. The interrupted-reset record lives outside the root and persists until cleanup publishes the canonical layout. Missing markers alone do not authorize deletion. Root aliases remain invalid, and cleanup removes generated junctions without entering their targets.

The reset leaves `reset-notice.txt` at the root because the editor that ran the command has stopped its host and discards the command's standard error on success. `storage::layout::take_reset_notice` removes the notice under the layout gate, and `HarnessService::initialize` returns its text as `storage_notice` after registering the next Harness session. Services-only initialization leaves the notice pending. A host that stops between reading and removing the file leaves it for the next start, and a failed take is logged without failing startup.

`storage::state` owns ordinary version cleanup. State users retain `locks/vN.lock` through their final dependent operation; cleanup also checks retired `state-locks/vN.lock` files. `:ForgeHistoryClear` collects its editor's host and attempts every version, preserving an entire version whenever ownership or repository process collection remains unresolved. It preserves canonical settings and shared repository lock files, reports individual failures, and can remove stale versions while another version remains live. Filesystem deletion failures can leave a partial version and remain visible.

History and the independent provider-submission journal retain SQLite WAL mode with FULL synchronization. A configuration transaction captures its preference update with the session's recovery intent; completion applies that preference in the persistent store before acknowledging the intent. A persistent receipt makes replay idempotent if the process exits between those commits. Mutating transactions take write admission before reading baselines, while history readers can retain snapshots without blocking commits. If the five-second busy timeout expires, the operation fails visibly without replaying provider work.

`HistoryWriter` (`storage/writer.rs`) owns one named thread per state root and commits on behalf of its callers, because a `FULL` commit waits on the disk and a caller that commits inline paces every task behind it by that disk. The thread drains its queue, runs each queued command in its own savepoint inside one transaction, and commits once, so a burst of writes shares one sync. An awaited command returns after its batch commits and receives its own error. A write-behind command returns a ticket at once. Streamed message, reasoning, and tool-output text is write-behind: the broker shows the text first and queues the save, and a newer whole-exchange save replaces one still waiting at the tail of the queue. A crash or a shutdown that outruns its deadline therefore loses the queued tail of streamed text; the saved text stays a prefix of what was shown. A write-behind command that fails fences its session scope: the writer skips that scope's later commands, the next exchange save on the broker's handle returns `WriteBehindFailure`, and the driver's per-step check (`history_failure_apply`) marks owner storage unavailable. A lock timeout at `BEGIN` fails the awaited commands of that batch and leaves the write-behind commands queued for the next attempt; at 256 queued write-behind commands `enqueue` waits for the writer, so nothing is dropped. The broker's own connection (`OrderedConnection`) waits for the work it queued before its next direct statement, which keeps its reads and writes ordered after the queued saves. The broker keeps that connection by design. A WAL reader on its own connection never waits for another session's commit, and the broker's wait covers only the saves its own session queued. A broker that borrowed the writer's store for each read would queue every session's reads behind every other session's disk sync, and would move the per-session lock and exchange cache that its store holds onto a store shared by the whole root.

Every other history owner borrows the writer's store instead of opening a handle. `HistoryWriter::lease` hands the store to the calling thread in queue order and the writer thread waits until the lease returns, so the holder's statements are ordered after everything queued before it; the command journal, the input journal, the question controller, and the publication outbox each take a lease per operation, and `HistoryWriter::lease_for` serves one-off writes. A lease stays on its thread and cannot cross an `await`, and a thread holds at most one, so code that runs another owner inside its own transaction (session deletion) keeps a connection of its own. `CommandJournal::append_core` uses `HistoryWriter::commit`, which joins the next batch and returns after that batch commits. `HistoryReader::current` (`storage/reader.rs`) waits for the write-behind queue and then lends a standing read-only handle from the root's pool, which closes with the last writer handle. Four direct opens remain, each marked with the reason at its `#[expect(clippy::disallowed_methods)]`: the broker's session-long store, Background preparation, session deletion, and history clearing.

The reducer step runs off the runtime workers. `ForegroundRuntime::apply_update`, `finish_foreground`, and the reconnect capture take the broker with `lock_owned` and run inside `spawn_blocking`, so the step's remaining synchronous commits and its projection work never hold a worker that the transport and other sessions queue behind. `off_worker` gives the same protection to a lease or an awaited commit taken on a multi-thread runtime worker.

Each live session owner holds an operating-system file lock for the controller's lifetime. The operating system releases the lock when the process exits, so recovery needs no heartbeat. Owner-checked saves stop a stale broker from overwriting its replacement. A lock collision returns structured lease metadata, and Neovim then offers Retry and Start New Session, plus Fork Session when the backend supports it. Deleting a session takes the lock and commits an intent before filesystem cleanup, and interrupted cleanup resumes at startup.

Sessions and preferences decode at the current format, defined by `SESSION_FORMAT_VERSION` and `PREFERENCE_FORMAT_VERSION` in `storage/mod.rs`. The version-directory boundary excludes incompatible history before domain decoding. Record-version checks reject malformed or mismatched session records in an otherwise current database. Tool output is stored as ordered `tool_output_chunk` rows keyed by exchange, turn, call, and byte offset. Streamed chunks are saved after they are shown: the writer appends each one only where it continues the saved byte offset, so saved output is always a prefix of shown output. Observer connections are read-only, so renames, exchange comments, declaration reads, and rollback previews work during a provider turn.

## Input delivery

Harness file completion leaves candidate filtering and insertion with Blink.
`completion/file_rank.lua` creates a query-scoped comparator for `@` searches in
the composer, ranking full workspace-relative paths before Blink's generic score.
It caches each candidate's rank for that sorting pass. Accepted file selections
are recorded per workspace for the editor lifetime. Shortened labels remain a
separate presentation concern, and other buffers retain Blink's default sorting.

Accepted input must survive a closed window or a crash without ever being sent twice. `SessionCoordinator` owns accepted messages through `SessionInputQueue`, and the `session.input.*` methods work without the provider execution lock. Ctrl-S sends input that steers an active turn as soon as the provider allows, and Ctrl-Q queues an explicit follow-up. Each group stays in FIFO order. Steering never bypasses uncertain delivery, pending configuration, or a pause.

An interrupt pauses the queue, and only a submission that follows the pause resumes it. Each `session.input.apply` carries the queue `control_revision` the editor had seen and, as `after_control`, the newest interrupt it had requested; `SessionInputQueue::apply_action` resumes a paused queue for an automatic submission only when one of them names the pause, so a submission the host orders after a stop but the user made before it lands in the paused queue. The editor captures both values when the key is pressed. `composer_draft.after_pending_paste` runs a composer send one main-loop turn after its key, so a paste still arriving joins the draft, while `Ctrl-C` cancels at once; stamped at send time, `Ctrl-S Ctrl-C` produced a submission that claimed to follow the interrupt, and the host ran it by itself once the stop settled. `input_state.control_fence` records the control at the key, and `input_state.under_fence` applies it to the submissions the deferred action makes. A submission that resumes a paused queue runs first: `apply_action` turns every held automatic prompt, including a steer that a stop returned to the queue, into an ordinary follow-up before it places the new prompt ahead of them, so none of them runs first or joins the new prompt's turn as steering. A new automatic prompt also enters ahead of a failed message, which keeps waiting for its explicit retry, so a prompt sent after a failed exchange runs as the next exchange instead of waiting unsent behind the failure. `controller.paused_queue_hint` gives the queue heading `· paused` in every frame in which nothing sends the queue's messages: from the stop until the queue resumes, also while the stop settles, a submission sent as it landed still reads `[submitting]`, or a compaction or rollback runs, and while a failed message holds follow-ups behind it. The hint names the retry key with `retry` when the queue holds a message that key sends again, and with `resume` otherwise.

An active `SteeringLane` accepts consecutive steering messages in FIFO order
without waiting for earlier provider acknowledgments. The input worker holds an
ordering permit through attachment preparation and queue handoff, then releases
it while retaining each message's independent delivery receipt. The number of
workers is bounded by the steering lane capacity. Adapters without a queue
handoff signal retain the permit until their steering call completes.
`SteeringFlight` distinguishes these live workers from abandoned `Sending`
records: overlapping live sends are permitted, but an unacknowledged send whose
worker has ended continues to block further dispatch and cannot be replayed.

Ctrl-Q retains `/model` arguments as configuration on the queued entry, including
configuration-only entries with empty prompt text. Lua reconstructs the command
for queue display and editing. Rust applies the configuration only when that entry
is eligible for delivery and consumes an empty prompt without starting a turn.
Ctrl-S settings-only model commands use the immediate configuration coordinator.

Lua refuses edits of pending submissions: their immutable command is already in
flight, but their local display entry cannot yet acquire a host reservation. Once
acknowledged, edits follow the host reservation path. A commit that removes an entry blocks reopening that
entry until its result settles, even while the confirmed queue still displays it.
The block clears on success or failure. Delivery can still win before
a reservation is granted. Submitting or navigating an edit whose target has left
the queue releases editor ownership and preserves nonempty composer text as a
normal draft without resending it. Transport events update queue state immediately;
their presentation work is coalesced into one scheduled render per event-loop burst.

The queue commits accepted state and idempotency receipts to its SQLite journal before acknowledging a mutation. Recovery releases abandoned edit reservations and restores retained input suspended. It reconciles linked submission evidence: accepted input leaves the queue, uncertain sends stay blocked, and proven unsent work requires explicit resumption or retry. An empty recovered queue preserves readiness instead of creating a pause. Lua reserves a queued message for editing at the revision its last committed edit published: a reservation requested while that commit awaits its host result waits for the result, because the displayed revision is stale until then and the host rejects it as `RevisionChanged`. Saving an edit ends it in the editor before the host answers the commit, so `queue_editor.finish` records each saved draft through `input_state.hold_saved_edit`, and `render` draws that text in place of the host's copy until the host publishes a revision past the one the commit edited; a rejected commit drops it through `input_state.release_saved_edit`, and the row shows the message the host holds.

Provider acceptance and queue acknowledgement are separate facts. `SubmissionStore` persists a `Prepared â†’ Sending â†’ Accepted` journal, and restart recovery never treats `Sending` as permission to replay. A turn that ends before dispatch keeps the message for the next eligible interaction: settlement retires undispatched steering to `Cancelled`, and unless the user cancelled the turn the input worker returns that message to the queue rather than retracting it. A failed message stays visible and blocks the follow-ups behind it until the user retries or removes it, while a newer automatic prompt enters ahead of it, including across a host restart, and a retry resumes a queue that recovery or an interrupt paused, because it is an explicit request to send the message, because recovery reads a `Failed` queue entry whose record settlement retired as a failure rather than a retraction. A retracted user prompt takes the same durable form. `SessionInputQueue::retract` retires the retracted identity and, in the same journal commit, appends the prompt's content as a `Failed` follow-up without a submission, under a new identity of the form `retracted:<uuid>`. Restoring the composer is the editor's work, and an editor that exits between the retraction and that restore once left the prompt in neither the transcript nor the queue; the commit keeps it in the queue, where recovery retains it and suspends delivery like any other failed entry. The new identity is required, not cosmetic: `SubmissionStore` answers a later preparation of an identity it has seen with that identity's record, and a retracted prompt's record can already be `Accepted`, so a retry under the old identity would never be sent. The copy is a follow-up at the back of the queue whatever the prompt's intent was, so a retry waits its turn and neither queued follow-ups nor a newer prompt wait behind it. Harness-produced input, such as a task entry or a question continuation, leaves no copy, because its task or question keeps the authority to produce it again. Uncertain (`Unknown`) delivery blocks the queue until reconciliation proves an outcome or the user removes the message; `session.input` removal then retires its record to the terminal `Discarded` state, which is never replayed and no longer blocks later dispatch. `SessionAdmission` keeps a compact task, operation, question, and exchange projection in memory, republished after every committed mutation, so submission never reopens SQLite.

Lua owns the unsent draft, and typing sends nothing to Rust. Ctrl-S captures the draft and sends one `session.prompt.submit` with its text, typed attachments, and a monotonically increasing token. `composer_draft.take` clears the captured draft at submission, for prompts and for task commands such as `/plan` and `/goal`, because `session.command.apply` replies only after the task starts its provider turn. A rejection restores the draft only into an untouched or empty composer, so newer typing always survives. The cleared prompt has no home on screen until the host answers, and an owner holding commands answers late, so `input_state` shows a submission still unsettled after 500 ms as a `[submitting]` row in the status split; the timeline chapter describes the placement rules. Rust publishes a durable running exchange before provider preparation. Editing a queued prompt reserves its entry, so the queue drains only up to that entry.

Pasted file paths import through `session.attachment.import` into the object store. The composer keeps attachments separate from the text, so text never carries a hidden attachment URL.

### Steering consumption

A provider acknowledges steering when it owns the message, which can precede the model call that reads it by the remainder of the current call. A row drawn at acknowledgement therefore claimed the model was steered before output it produced without the message. `ExchangeInput::consumption` records what Harness actually holds: `Consumed` (the provider reported the input inside its turn, or the input never needed a report, such as plan feedback and question answers), `AwaitingConsumption { invocation }` (the provider acknowledged receipt under that invocation), or `Unconfirmed` (the exchange settled, or recovery closed the invocation, without a report). Consumption means positive provider evidence that the input joined processing; neither acceptance nor a turn's covered inputs establishes it, because adapters build coverage from accepted attempts and a terminal result can describe interruption or failure.

`Exchange` owns every transition, so the broker cannot draw a row the record disagrees with. `append_acknowledged_input` creates journaled steering as `AwaitingConsumption` and leaves the provider's current message open. The consumption report is a native user item that carries the input's submission ID. `Exchange::consume_input` accepts it only from a turn of the acknowledging invocation, marks the input `Consumed`, moves it to the current tail, and closes the turn's current message so later output follows the row. A report that precedes acknowledgement leaves its user item as a hidden `TurnContent` anchor at the tail, and acknowledgement replaces that anchor with a consumed row at the anchor's position, even after the turn has finished. Repeated reports and repeated acknowledgements change nothing. `Exchange::observe_provider_evidence` returns the input a report first made visible, and the broker publishes `TimelineUpdate::Node { prompt: Some(..) }` exactly once, on the report or on the acknowledgement that adopts an earlier report; acknowledgement of a waiting input publishes `prompt: None`. The `agent_wait` blocker still ends at acknowledgement, because that wait ends when the input reaches the provider. A steer the provider refused before dispatch is not steering by the time it is accepted: `SteerCommand::complete_with` resends it as the prompt of a new invocation and marks its presentation `AcceptedInputDelivery::TurnPrompt`. The model reads a turn's prompt when the turn starts, and no adapter echoes one, so `append_dispatched_input` records that input `Consumed` on acceptance. The receipt names the new invocation, so Forge places its prompt before that turn's first recorded content even if output arrives first. The continuation's open response keeps streaming under its original message identity.

A native user item confirms steering only when its submission identity belongs to the reporting invocation. Unattributed input can still appear in the transcript. Harness-authored input has a distinct presentation rule. Its messages open with a `<forge>` block that user text escapes, or echo the prompt of a task exchange Harness already opened, so they do not add a second row. Codex often puts the text in a delta after the item starts. `Exchange::admit_read_native_input` waits for that text before deciding whether to draw an unattributed item. This rendering decision does not settle a submission or permit replay.

`Exchange::finish` settles every remaining `AwaitingConsumption` input as `Unconfirmed`. Recovery cannot rely on `finish`, because `storage/recovery.rs` retains `Finalizing` for an exchange that was finalizing and skips finalizing or parked exchanges without a running turn. It therefore calls `Exchange::close_input_consumption` for every open exchange, which settles waiting input and records each invocation in `closed_input_consumption`; a late durable acknowledgement under a closed invocation creates an `Unconfirmed` row at once rather than a status entry nothing would clear. `pause_for_restart` closes consumption the same way. The submission journal keeps such input `Accepted`, so settlement never authorizes replay, and the row keeps the user's text instead of restoring it to a composer that may hold another draft. Closing a window does not settle consumption: the provider remains live, and the reopened presentation lists the waiting input again.

## Exchanges and cancellation

`ExchangeNode` preserves the order of turn content, delegations, clarifications, steering, plan resolution, and artifact changes. The shared session execution engine owns each admitted invocation and retains native submission and collection independently of foreground result waiters. The shared native runner retains terminal evidence and completes provider collection before the authoritative `Turn.Completed` event. Harness then applies its host commit ticket. An RPC acceptance, a message completion, or an interruption acknowledgement cannot replace that event. A native command can have a longer lifetime than the foreground invocation that started it.

The adapter marks a known running command with `ToolItemEvent::Backgrounded` before reporting normal foreground completion. `ToolStore` persists that lifetime on the original invocation and keeps the command running until its native completion arrives. Unmarked unfinished tools still settle as interrupted when the foreground turn ends. A turn ending in cancellation, interruption, or failure settles its running tools even when they were marked as background work, and a later completion cannot reopen a terminal result.

`thread_open` returns the binding's sole ordered observation stream atomically with its identity and effective capabilities. That stream also carries background-command output and provider-initiated compaction after foreground settlement. The binding registry resolves normalized thread, turn, and item identities to their original execution owner before forwarding them. The session collector queues events without waiting for the broker lock, so foreground work cannot block intake; the active broker drains invocation events before session events so lifetime admission precedes late completion. Delivery resolves the original stored tool and permits completion only while that exact background execution is still running. Output chunks are queued for the history writer when they are published, historical updates preserve the current foreground view, and a failed subscription is reported rather than treated as an empty stream.

Managed children consume that same session-event contract alongside their invocation stream. `AgentRuntime` consumes identity observations and open results from the same retained owner, continues forwarding during shutdown, and drains final events before reporting child completion. No active-session identity polling roundtrip runs alongside that owner. Every forwarded invocation must belong to the current child and task; a foreign observation fails the task without bypassing cleanup. This ordering prevents a stopped child command from remaining marked as running after its child has completed.

A correlated `Turn.Error` received after collection remains append-only diagnostic history on its original turn. Harness deduplicates that observation and persists it without reopening execution or replacing the immutable `CompletedTurn`, native outcome, or retry decision. A valid diagnostic alone does not fence a healthy binding.

A completed turn whose actual model remains unknown can accept its first positively correlated `ModelResolved` observation. That refinement belongs only to the original turn and survives reload; it does not confirm a successor's model or replace configured defaults. A completed turn with a known actual model rejects a conflicting late change.

The winbar displays `Session.resolved_model` when the provider has reported one and the configured model otherwise, because the user's selection is the model the provider runs. It names that model by its catalog label, and until the catalog loads it uses `Session.model_label`, the label recorded when the model was selected and kept in the provider preference's `ModelSetting.label`. An ACP catalog appears only after a binding opens, so without the saved label a new session would show the raw alias `opus` instead of "Opus 5.5". The label is presentation only: `HarnessSession::select_model` replaces it with every model change, and configuration with a catalog refreshes it because an alias can later name a newer model. A provider-reported model takes precedence only because it can name what an alias such as `default` selected, or a substitution the provider made. A started turn has no model evidence until its own `ModelResolved` arrives, so the broker keeps the previous resolved model when a turn starts and replaces it only with the new turn's resolved model; configuration that selects a different model clears it.

The winbar's thinking and speed values, and its waiting `*`, come from the editor, because the session snapshot carries only applied settings. `selected_settings` in `views/harness/controller.lua` layers the changes the host has not applied over the applied session: first each `session.configure` request in the order sent, then each unsettled queued input that carries `config`, which applies at its hand-off. A model change without a thinking level takes the model's catalog default, as `HarnessBroker::build_configuration_candidate` does. A request records whether it waits: one sent while a turn runs or hands off (`activity.turn_pending`) is answered only after the stopped turn restarts on the change, and every request sent after a waiting one waits behind it. A request sent while idle does not wait, although the host takes a second or two to answer it, because `SettingsRun` fetches the provider's model list to validate the change and the owner's activity reads `working` meanwhile; the winbar shows its value at once, so a second effort key press also steps from it. The marker shows while a waiting change or queued `config` is pending and a selected value differs from the applied one. A request leaves the list when the host answers, applied or rejected, and a request from another session or an earlier host generation never counts. The thinking value names the level the provider runs: `default` sends no level (`ReasoningSelection::Default`), so `model_options.thinking` resolves it to the catalog's `default_reasoning` when that is one of the model's levels and keeps `default` otherwise, and the model picker offers and preselects the same value through `model_options.reasoning_choices`. Before this rule the picker preselected the first listed level, which no provider had been asked to use.

`session.turn.cancel` enters the same command queue as configuration and other mutations. A stop can pass the head when that command is blocked on the stop target’s dispatch or native start. The owner revalidates the foreground identity before issuing the interrupt and leaves the deferred commands in queue order. The owner signals the exact invocation while retaining asynchronous settlement and host finalization; it does not wait for the original result request to finish before processing cancellation. A newly submitted prompt stays retractable until the provider produces a message, reasoning, tool activity, task update, or workspace change. The exchange that a task command started (`ExchangeOpening::TaskStarted`) is never retractable: `RetractionEligibility::for_opening` marks it consumed, because its task outlives the interrupt as a paused task and the transcript must keep the row that started it. Retracting a prompt the provider accepted also requires the `native_turn_rollback` capability, which Claude Code and Antigravity do not declare; there only a prompt proven unsent is restored, and an accepted output-free turn stays in history as cancelled. Reasoning counts as visible model work because the user can read it. The provider's echo of the submitted prompt does not count: Codex reports the prompt as a native user-message item before any assistant output, so `RetractionEligibility` records each user-message item identity at its start and ignores that item's later deltas and completion. Owner-collected cancellation and foreground failure settlement both decide restoration through `cancellation_restores_prompt`, which requires output-free history and the `RestoreIfUnconsumed` input policy; a clean cancellation that restores its prompt enters failure settlement rather than ordinary finalization, and settlement waits until the owner's collection completes before deleting the exchange. A collection that fails ends that wait as well: the stop's finish handler sends the turn `ForegroundSignal::CollectionFailed`, which `ForegroundAdmission::fail_owner_collection` records, and settlement then keeps the exchange without restoring the prompt, because nothing proved the provider left it unconsumed. Without that signal the failed turn waited forever for a `CollectionCompleted` that a failed collection never sends; the provider restart that the failed stop requested starts only once no foreground turn remains, so it never ran, and every later command, including each repeated cancel, queued behind it unanswered. An admission the owner was collecting ends the same way and collects its native owner itself. A running turn that has no failure of its own ends there as well: `step_foreground_inner` fails it with `CommandFailure::StopFailed`, unless a cleanup already in flight will record its failure. A finalizing turn is left alone, because it already holds its native result. A prompt cancelled while `before_send` still held it has no dispatched native turn, so no terminal result would ever fail that turn, and the restart waited on it exactly as it once waited on the missing signal. Its cleanup closes the engine, and the prompt returns to the queue as failed, neither restored nor resent, for the user to retry. Retraction is available both before the checkpoint baseline and after a committed baseline; after the baseline, a retained retraction result continues to the ordinary failure checkpoint. After settlement, the owner authorizes `input_retract` for the exact cancelled submission, delivery attempt, and checked history boundary. Only proven nonconsumption or confirmed history retraction permits removing the provisional interaction and restoring the exact draft. Retraction reverses provisional prompt-owned writes whose current values still match what admission wrote. It preserves configuration, task and plan revisions owned by later actions, and the live binding’s conversation identity, capabilities, and usage. Usage from before history truncation remains visible but cannot authorize automatic compaction. Copilot can supply a positive withdrawal receipt for an exact accepted submission and attempt at stop settlement. The host applies the same output-free eligibility and collection gates to that receipt. An unknown retraction result retains the draft boundary for reconciliation and never authorizes blind rollback; tool effects are never undone by history retraction. A confirmed retraction answers the cancel command with `CancellationOutcome::Retracted`, answers the prompt request with `turn_retracted`, and publishes the input update with `retracted` set, including for a submission the provider had already accepted. That update removes the retracted identity and upserts its unsent copy, described under [Input delivery](#input-delivery). `input_state.receive` checks whether the composer can receive the draft, then asks the host to remove the durable queue copy. It restores the composer after the host confirms removal. Newer typing during removal leaves the retracted text in an editor recovery row. An unconfirmed removal keeps an editor recovery copy behind any matching host row until observations establish which copy remains. Every retraction path reaches the queue through `SessionInputQueue::retract`: a submission cancelled before any owner claimed it (`retract_unclaimed_submission`), a claimed input interrupted before its provider submission exists (`InputDeliveryRun::finish_interrupted`), and a journaled submission that settles or is abandoned as cancelled or retracted (`InputReceipts::apply`). After visible activity, cancellation persists the partial exchange as cancelled.

Collecting an exchange's native work installs an exchange fence in its `SessionExecution` (`collect_exchange`): the host stops scheduling attempts for that exchange, and a configuration replacement removes the fence only through `resume_exchange`, which proves the collection it names. A cancel can collect an exchange whose turn already completed natively, as `Ctrl-C` does when it reaches a turn that is still finalizing; natural completion then wins, the exchange stays complete, and a check result its turn started later continues it as a new foreground admission. The fence once outlived that collection, so the continuation's start retired its prepared submission and the turn failed as `provider_cancelled` with no cancellation in flight, which the editor reported as "provider execution cancelled". A prepared foreground reservation (`Driver::reserve_input` with `ReservationOrigin::PreparedForeground`) is the owner's admission of new work after the collected work settled, so it removes the fence once no attempt, reservation, or unfinished invocation of the exchange remains; while one does, the collection is still in progress and the fence refuses the new admission as well.

An execution control fingerprints the execution record it decided on without the scan-owned `progress` (`control_fence_digest` in `broker/execution.rs`), because the foreground rescans progress every five seconds: a `plan_phase_done` request that waited for its turn to end was otherwise refused as "execution control changed before commit", which failed the turn and paused the task. The commit keeps the stored progress unless the control computed progress of its own. Collection also stops plan-execution progress scans. A scan is ordinary foreground work, and a collecting command keeps the effect gate closed until it ends, so a scan requested after collection began stayed staged while finalization waited for its result; Ctrl-C with a pending approval then waited for the 30-second collection deadline. `ForegroundTransaction::next` therefore yields no `PlanScan` while `collection` is set, and the step ignores a tick that was already selected. A plan question staged by a finalizing planning turn is settlement work, like a plan submission, so `ForegroundJob::disposition` classifies it as `Settlement` so it runs behind a closed effect gate instead of waiting out the command's deadline. When the reducer settles a turn while an observation or scan read during the settlement commit has started work, the driver drops effects that never started and joins the running ones, publishing any output they forward, before it reports the turn finished.

Failure finalization settles every turn still `Running` as the exchange outcome after native cleanup joins (`Exchange::settle_running_turns`), because a terminal event that cleanup dropped will not arrive later; without that step the failure checkpoint rejected the exchange and left it finalizing. A Codex interrupt registered before `turn/start` is acknowledged waits for the acknowledgment, then interrupts the acknowledged turn.

Typed provider cancellation enters the same collection path for root and managed-child requests. A native interruption remains `TurnOutcome::Interrupted` after a settings change; finishing host cleanup cannot turn it into normal completion. `Completed { stop_reason: Normal }` alone permits automatic continuation. Token limits, request limits, and refusals retain their exact stop reason and stop automatic retry or task/agent continuation until the user authorizes more work. It stops retries and cancels unsent child submissions while retaining evidence for uncertain or accepted sends. Provider error text does not determine cancellation, and a child cleanup failure remains a failure that requires collection.

Changing workflow mode interrupts the provider and pauses the exchange, which keeps its request, plan, goal, and initial checkpoint. Task controls collect running work through the same parking. The next admission closes a parked exchange, so a control that leaves no current task, such as Clear, closes it before releasing control. Collection whose provider turn already completed instead leaves the exchange finalizing, with its final checkpoint deferred to that next admission. When the control leaves no current task, the task command therefore runs a follow-up cancellation settlement (`TaskStage::SettlingFinalization`) that captures the checkpoint and finishes the exchange before the control reports completion; otherwise the transcript showed **Saving exchange** until unrelated input arrived. A configuration change or task control that fails after its collection parked the exchange schedules no continuation, so the exchange once kept the collection's `Stopping` label with nothing running until the next Ctrl-C. Its failure path records the command in `ExchangeDriver::failed_parking_command`, and once no turn, queued turn, command, or retained stop remains, `ExchangeDriver::failed_parking_release` has `HarnessBroker::owner_fail_parked_exchange` close the exchange as failed, stating that the change that stopped the turn failed. A closed exchange that never started a provider turn is cancelled rather than reported as completed work. A parked continuation in which the model produced nothing, such as one `/goal pause` stopped before its provider answered, is deleted rather than closed: `Exchange::is_output_free_continuation` admits only an `ExchangeOpening::TaskContinuation` with no nodes, tool calls, check runs, checklist, or host edits, and `HarnessBroker::close_parked_exchange` removes it, so the next prompt draws no continuation notice above an empty `Thought 0s` heading. An exchange that a user prompt or a task start (`/goal …`, `/plan …`) opened always stays, with its start row. A cleanup or checkpoint failure leaves the exchange finalizing and blocks new admission, and Ctrl-C, new prompts, and goal resume retry finalization first. Every finalization path, including that retry, first calls `SqliteStore::require_settled_descendants`, which fails with a typed `DescendantUnsettled` naming the unsettled child exchange, its owner, its delegating parent, its state, and the missing obligation; the caller adds its operation, such as checkpoint save or rollback. Child admission and stop handling keep that guard satisfiable: no admitted task can wait behind a stopped child's authorization gate. Each finalization path also settles its children before asking for the checkpoint: normal completion parks while children run, cancellation collects them through its control transition, and failure settlement interrupts the failed exchange's children and services their completions. Startup recovery interrupts unfinished children without replay, so prior finalization then succeeds. Recovery cannot capture a checkpoint inside its storage transaction, so `SqliteStore::interrupt_detached_execution` leaves a running primary exchange that holds a baseline finalizing instead of finishing it; child exchanges and exchanges without a baseline still finish there. The outcome is cancelled when a cancellation had begun collecting the exchange, which the foreground records as `Exchange::cancellation_requested` together with the collection's `Stopping` label, and interrupted otherwise. `Exchange::start_turn` clears the flag when it adds a turn, because a stop describes only the turn it stopped: a check result delivered after a cancel continues the same exchange, and an exit during that later turn interrupts it. The host's shutdown stop on an editor exit is such a cancellation, so an exchange that the exit was stopping reopens cancelled even when the host ended before the stop settled; recovery once read only the label, which a reconfiguration's restart leaves as well, and interrupted it. `SessionController::new` then calls `HarnessBroker::settle_recovered_finalization` before its first snapshot, which runs the same finalization retry for every exchange recovery left finalizing. Without that step an exchange interrupted by host loss kept no closing checkpoint, and a recovered finalizing exchange showed **Saving exchange** until the next prompt. A capture that fails there stays on the exchange as its finalization error and does not fail session start. The per-exchange settlement is `storage::interrupt_detached_exchange`; `HarnessBroker::preview_session` applies it in memory with `DetachedSettlement::Outcome` when `SqliteStore::session_owner_live` finds no process holding the session's owner lock, so the Resume Session preview of a killed session shows the interrupted exchange that resuming shows rather than a clock measured to the preview instant. The terminal checkpoint and the exchange outcome commit together. When the host exits, Lua shows a reconnect error over the retained transcript, and only reopening Harness reconnects.

## Tasks and recovery

`Task` owns a private `TaskLifecycle`: Active, Suspended, or Finished. `WorkflowState` contains a planning, execution, or goal state, and each workflow defines its own phase enum. Plan has Draft and Review, Execute has Implement, Check, Resolve, and Verify, and Goal has only Work. Suspension preserves that phase, and read requests never settle tasks or clear waits.

The controller validates candidate updates before replacing the task and committing its dependent artifacts. Artifact snapshots remain available for the plan, timeline, and transport adapters, but consumers cannot obtain a mutable borrow of the live task. Loading a task also validates its workflow against the serialized phase and lifecycle summary.

Gate phases contain an `ExecutionContract` whose private construction requires an accepted revision and a workspace baseline. Verify additionally requires accepted manual actions and passing automated evidence for that revision. `SuspensionReason` distinguishes user pause, no progress, total turn exhaustion, provider limits, and reported failures while retaining the workflow variant.

Goal completion and blocking tools acknowledge a pending request in the invocation's retained host-effect batch. They do not change the task during live publication. The collected-result path requires normal native completion and current task authority before applying Goal evidence; explicit stop or non-normal completion cannot authorize a terminal Goal transition. The observation receipt deduplicates the finishing turn and retains the reported explanation. Disposable state version 21 separates this meaning from older live Goal receipts.

Control mutations require the exact `TaskPermit` revision. Completed-turn accounting uses a separate observation fence that survives legal phase handoffs and changes on user control or explicit recovery. This lets a turn consume its allowance after advancing the phase while preventing its late callback from affecting a resumed task. `TaskTurnId` deduplicates observations, and terminal outcomes retain the stable task identity.

`TaskNextAction` derives provider work, local checks, or a wait from the current lifecycle and phase. Durable continuations use a `TaskWork` enum: Provider carries an instruction, and Checks carries no synthetic prompt. A continuation identifies its exact completed source exchange, so a newer chat exchange cannot strand it. Resuming Check reserves local work instead of starting a provider turn.

Workflow changes never enable writing or widen filesystem scope. When an access change restarts and resumes work, Harness tells the model the previous and current approval modes and asks it to inspect interrupted operations before retrying.

Restart recovery keeps committed phases and completion evidence, suspends pending entries and continuations, and never starts a provider automatically. Explicit resume reactivates the retained task; a proven pending entry keeps its provider-input identity. Uncertain provider delivery remains governed by the submission journal rather than by the task's phase. Failure, disconnect, and unknown outcomes stop automatic queue draining.

New conversations start in Ask; current conversations retain their explicit approval mode, including across Plan â†’ Execute. The plan-review answer to "How should execution handle tool approval?" is such an explicit choice. Entry admission commits it to the session through the same permission authority as `/allow` and publishes the configuration, so Implement continuations, Verify, and resumed phases run under it, the winbar shows it, and a later `/ask` replaces it. Only the executor model stays a per-invocation `TaskInvocationConfiguration` override. When approval was also an override of the entry turn alone, continuations reverted to the pre-acceptance mode and raised review popups the user had already declined. Database replacement discards obsolete task state rather than reconstructing it. The current task decoder validates phase payloads instead of guessing transitions from an older representation.

After exclusive runtime ownership is acquired, recovery also settles detached background tools inside already-completed exchanges. It preserves the foreground outcome, output, and last observed duration. On a fresh Copilot binding, native history is checked for unmatched tool calls; only a verified incomplete suffix can be truncated, and the retained prefix is checked again before new input is sent. Copilot never records a completion for a call that an abort interrupted, such as an interrupted shell command, although the abort closes that call's turn and the conversation continues after it. Such a call is settled history rather than a suffix: counting it once rejected every later resume of the session, because the conversation after it could not be truncated. The repaired session's provider prompt cautions that prior actions may have completed and must be inspected before repeating writes. Successful recovery does not emit an editor warning; ambiguous history blocks admission rather than discarding completed work.

## Plan generation

The broker owns plan generation as one bounded continuation loop for every backend. Each turn applies plan edits to the canonical document and either submits the plan or reserves another bounded turn. Every question a planning turn asks is required: `question_ask` waits for its answers in Plan mode whatever its `wait` argument, and the tool watchdog gives that wait no deadline. An asynchronous question let the planner end its turn with the question unanswered, and continuation turns with nothing to plan from then ran the loop into its no-progress limit. A required question stops execution while preserving the continuation, and the stop does not count as a failed progress attempt, even when the user answers before the turn finishes settling. A typed prompt after the loop has stopped at a limit runs as a conversation turn, so the model reads it, and `/plan retry` resumes planning with it in the conversation. A prompt that admission still refuses, such as a bare permission command or a typed answer while a question needs its explicit source, raises `PromptRefused` from `normalize_foreground_interaction`; `admit_prepared_foreground` answers it as a rejected command with the `prompt_refused` code, so no turn starts, fails, or restarts the provider, and `InputExecutionResult::Refused` leaves the queue entry failed with the refusal's reason instead of `Provider did not confirm message acceptance`. The refusal does not pause the task. An interrupt or host stop ends a waiting question with its turn, because the provider keeps no pending tool call across either; `HarnessBroker::retire_stopped_questions` retires it and adds a `Question lost` transcript row that names the question and says to type the answer and run `/task resume`. It adds the row only for a question whose task is still current: a control that clears the task, such as `/plan cancel`, ends the question with the task, and advice to resume would name a task that no longer exists. `ContinuationBudget` uses a default total allowance of 20 model turns and stops after five consecutive turns without observable progress. Plan acceptance carries consumed allowance into Execute; review revisions do not replenish the total allowance. Explicit resume or retry resets the continuation allowance while retaining task history.

Execution compares saved workspace checkpoints and plan document versions when observing progress. Phase changes, reads, failed edits, and repeated findings do not reset its no-progress count; new completed verification evidence can advance a manual verification attempt. Local check operations and human waits do not consume model turns. The native task summary supplies workflow, phase, and status to the winbar, so Lua does not reconstruct lifecycle state from artifact records.

`PlanStateMachine` validates plan transitions. `PlanQuestionLedger` records answers, skips, and withdrawals by both provider ID and content digest, so a resolved decision cannot reopen when a provider retries with a different ID. Automatic retries and goal continuations admit new exchanges without synthetic user prompts, so each attempt keeps its own metrics.

## Context and compaction

Provider usage normalizes into durable `ContextUsage`. `AutoCompaction` is a per-session policy with an enabled flag and a token threshold. It is off for ordinary sessions, and Background sessions enable it at 128,000 tokens. It runs after completed provider work and never estimates tokens from bytes. The threshold compares with `ContextUsage.used`, the latest request's context occupancy, not the summed input of every request in a turn, so a tool-using turn can report more input than the context holds without becoming due. `AutoCompaction::validate` rejects a threshold at or above the reported capacity, and `compaction_threshold.lua` offers only presets below that capacity so cycling past the smallest preset cannot wrap to an invalid one.

`Compaction` is a separate lifecycle with an operation identity, observed start and completion, and an outcome. Its after-compaction token count is accepted only once the provider confirms completion, and a turn that ends first records an unconfirmed outcome. `native_compact` gates manual `/compact`, which uses Codex `thread/compact/start` or Copilot `session.history.compact` and creates no user exchange. The sole stream returned by `thread_open` remains attached across turns for provider-initiated compaction. Manual `thread_compact` requires settled foreground work and correlated completion evidence; its result carries an observation watermark. `HarnessBroker::commit_owned_compaction` starts from the attempt's row as notifications left it, so a result that omits token figures keeps the ones the notifications reported, and the result's own fields win where both exist. A provider that declines the request returns a failed compaction whose `CompactionResult::provider_explanation` holds its sanitized words, such as Copilot's "Nothing to compact." or Claude Code's "Not enough messages to compact."; the command then fails with `ContextCompactionFailure::Declined` (`compaction_declined`), and both the row and the notice show those words instead of a normalized `Transport` category. A provider's terminal answer that is not a confirmed compaction, whether declined, failed, unconfirmed, or overtaken by an authority change, leaves `ContextCompactionRun` in its `Unsuccessful` stage with the failure and reports `CompactionProgress::Unsuccessful`. `NativeCommandRun` completes that exactly as it completes `Committed`, through `prepare_completion` and the replacement turn of the exchange the collection stopped, and only then finishes the command with `NativeCommandProgress::CompactionUnsuccessful`, which the owner reports as `CommandFailure::Compaction`. Failing the command at the provider's answer left the stopped turn paused with nothing to resume it; only a deadline or lost worker observation, where the native side may still be compacting, still fails the command before any turn is handed back. A queued `/compact` input (`InputDelivery`) still fails its input on an unsuccessful answer, because it reports through the input rather than through a command outcome.

`/compact` during a turn follows the configuration restart described under [Commands and operations](#commands-and-operations): the owner collects the turn, compacts, and resumes the same exchange. `ContextCompactionRun::update` passes the exchange the collection stopped to `HarnessBroker::prepare_owned_compaction`, which records the attempt as an `ExchangeNode::Compaction` inside that still-running exchange instead of as a session event, and clears its `ExchangeCollection` label because the collection has finished. The heading therefore reads `Compacting`, since `Exchange::activity` follows a Running compaction node, rather than `Stopping` for the length of the compaction. `heading_compaction` in the projection gives the heading the compaction's own interval, from its start to now or to its end, which is what the status row counts; the stopped turn's clock is paused and would hold the heading at the second the turn stopped. The heading advances between host events the way a running turn's does: the editor synchronizes again after each `activity_due_in_ms`, and `SessionPresentation::sync` redraws the headings of the timeline's ticking entries. `heading_clock_runs` decides which headings count, the execution clock or a Running compaction, for the timeline's `ticking` set, `timing_blocks`, and `timing_label_due` alike; reading only the execution clock left the heading at `Compacting 0s` while the status row counted, because a fresh projection gave the right figure but no refresh ever drew it. `SessionPhase::Compacting::turn_waiting` says whether an unfinished exchange's turn waits for the compaction; the editor's `activity.turn_awaited` reads it, so a compaction between turns, such as one while a plan waits in review, keeps the winbar at `plan · review` instead of the draft label a pending planning turn gets. It also keeps a completed manual compaction on the heading while the exchange waits, paused, for its replay, until a turn starts after the compaction began, so the heading never reads `Paused` between the compaction and the restart; the row sits above the output the resumed turn appends; and the projection appends `turn ran again` to a completed manual compaction that a later turn of the same exchange followed. A session-wide row placed the replayed output above the compaction, and an attempt that failed left the collection label, so the heading read `Stopping` until the next prompt.

Codex runs `thread/compact/start` as an ordinary turn on the compacted thread. While its normalizer is bound to the compaction's `SessionOperation`, that turn belongs to the operation: it admits no host invocation, its turn and item notifications contribute only thread-level facts, and an error on it settles the attempt as failed. Admitting it as an invocation would publish activity under a scope Harness never created, which `validate_native_event` rejects as an ownership conflict. The native `contextCompaction` item also takes the host operation ID as its compaction ID, so the host attempt and native progress settle one record. Every adapter keeps this rule: Claude names its `/compact` attempt after the operation ID rather than after the input frame's uuid, and Copilot's `CompactionMonitor` maps the native start notification onto the operation ID, so a second identity would draw a second row for one compaction. A manual compaction releases the binding afterward, so later provider-initiated compaction keeps its native identity. Because `SessionPhase::Compacting` follows any Running compaction record, an attempt that ends without completion evidence, through a failed result, unconfirmed evidence, or lost worker observation, marks every Running root-thread compaction Unconfirmed. The `provider.observation_failed` trace records the failing stage as `error_code` and the normalized `ObservationFailure` as `kind`, because the trace policy drops free-form error text.

## Rollback

The `/undo` picker names the last exchange to keep. The controller sends the next current exchange as the host's first removal, so that exchange supplies the rollback availability, the file checkpoint, and the prompt to return. **Before first exchange** supplies the first current exchange as the removal boundary. Both rollback scopes use the latest exchange identity from the list to reject a selection whose history has advanced.

`/undo` offers conversation-only rollback, or rollback with file restoration when a checkpoint exists. The interaction list opens during a running turn as well, and lists every current exchange, the running one and a paused goal's parked exchange included. Every request the picker sends before a rollback is confirmed is served without the execution permit: `session.exchange.list`, `session.exchange.rollback.preview`, and the status read of `session.exchange.recovery` are `BrokerObserver::query` reads, and preparation, application, and the recovery actions are owner commands. A status read that reached `HarnessBroker::dispatch_stream` instead was refused by `acquire_request_broker` with "This operation requires a settled session" whenever a turn ran, which made `/undo` fail before its list opened. Every rollback command except undoing a file restore collects active execution before it reads history (`RollbackCommand::requires_collection`), which includes preparing a files preview: the preview compares the workspace with the retained history's closing checkpoint, and a running or paused exchange has written none. Preparation once skipped that collection, so a paused goal's open exchange made every files rollback fail with "rollback authority changed; prepare again". Choosing **Conversation and files** therefore stops a running turn before the preview appears, and the scope's description says so; the preview's Cancel then says that the turn already stopped and that nothing was rolled back. **Conversation only** has no preview, so the turn stops only when the user chooses it. Rollback then rewinds the provider conversation natively and restores the reverted prompt to the composer when the user wrote it.

The task survives a rollback that keeps its start. `rollback_keeps_task` compares the task's creation time with the retained exchanges: a retained exchange created at or after the task means its start stays, so `SessionTaskController::commit_rollback` keeps the task, and pauses it only when its status is `Running`, that is, when it would otherwise continue by itself; a task waiting for the user, such as a plan in review, stays exactly as it was. Otherwise the rollback removed the start and clears the task without recording a finish row. The same rule applied to each plan's creation time decides which plans the rollback removed: `commit_rollback` records every such plan as cancelled, so the snapshot's artifact list and the winbar count drop an accepted plan whose execution is the current task, or whose execution already completed, as they drop a plan cleared in review. Rows the session recorded during the rolled-back interactions, such as `Goal completed`, `Goal cleared`, a configuration failure, or a compaction, are session-owned events that rollback cannot match to an exchange by ownership, so `SqliteStore::prepare_rollback` re-owns every such event created since the first rolled-back exchange began to that exchange, and the timeline hides them with it. Renames and fork origins describe the session itself and stay.

Harness never rebuilds a conversation by replaying retained exchange records into a fresh provider session, because those records include full tool output and a long session exceeds the model's context limit in a single prompt. Rollback therefore keeps the provider session and calls `ThreadRewind`, which discards every native turn after one checkpoint. Providers that support rewind report native checkpoints in finished turn results, including cancelled, interrupted, and failed turns where the runtime provides a checkpoint; completion settlement also copies it into the exchange's `provider_checkpoint_id`. `Exchange::native_checkpoint` reads the newest turn result first, because an interaction that ended by cancellation, an interrupt, `/task clear`, or a failure never reaches completion settlement, and reading only the settled field refused every rollback to the interaction after it. `rewind_target` in `exchange/rollback.rs` selects the checkpoint of the last retained exchange through `NativeBoundary::after`, the rule forking uses too. A retained exchange with provider turns but no checkpoint has no safe boundary, so rollback rejects it. The same function names every refusal before anything changes: `session.exchange.list` carries it as `rollback_unavailable` on each exchange it applies to, the `/undo` picker shows it on the destination immediately before that exchange and offers no scope for it, and preparing a files preview rejects it before the user confirms a restore. Codex maps the rewind to `thread/revert` before the turn after the checkpoint, and Copilot to `history.truncate` at the first primary `user.message` after it. Claude Code sends `rewind_conversation` to its idle process when its binding knows the first discarded prompt. When it cannot locate that prompt, it resumes at the checkpoint with `--resume-session-at`. Claude Code has no transcript entry before the first interaction, so its capability declares `conversation_rewind_requires_checkpoint`, and the first interaction is listed as unavailable instead of failing after confirmation with an interrupted restore. Claude also declares `conversation_rewind_stops_at_compaction`: a compaction boundary starts a new transcript chain, and the CLI resumes only at an entry of the chain it loads, so `rewind_target` refuses a checkpoint recorded before a compaction that may have replaced it. The compaction is either a row of an exchange or a session row, and it counts when it started at or after the end of the kept exchange's checkpointed turn; a compaction that stopped a turn which then ran again precedes that exchange's checkpoint and leaves it resumable. Antigravity's ACP integration lacks the `NativeConversationRewind` capability: the editor reports rollback as unsupported and the host rejects it before changing anything.

The rewind is idempotent, because an absent successor turn makes it a successful no-op, so a failed or uncertain attempt leaves history uncommitted and undo repeats the same request. File restoration stays with Harness checkpoints: `RollbackEffect::run` restores files under their journal first and rewinds afterward. A rewind failure after restoration leaves the journal incomplete, and restore recovery repeats both steps. That failure is `RollbackFailure::ConversationNotRewound`, whose message says that the files were restored and the conversation was not, and names **Continue interrupted restore** and **Restore pre-restore files** as the ways out; continuing the restore reports the same message when the rewind fails again. The journal reads incomplete for the whole restore, from the first file write until `commit_rollback_effect` marks it complete after the rewind, and a Claude Code rewind that resumes at a checkpoint can take seconds. An incomplete journal alone therefore cannot distinguish a running restore from an interrupted one, so `prepare_rollback_effect` takes a `RunningRestoreClaim` before the worker starts, the effect result carries it, and the commit releases it only after it completes or abandons the journal. `RestoreJournal::interrupted`, which feeds the snapshot's `restore_recovery`, and the recovery status's `pending` both exclude a claimed journal; a session's owner lives in one process, so a claim is process-local. While a rollback runs, the editor shows its own progress notice from the confirmation until the host answers, and a paused queue keeps its heading. When no current exchange remains, the commit also returns a session named automatically after its first prompt to unnamed, as a retraction of that prompt does. The rolled-back exchanges keep their records, so `stage_interaction_for_turn` names an unnamed session from a prompt that no current exchange precedes, not only from the session's first exchange ever; otherwise the session stayed unnamed after the returned prompt ran again. Neither step undoes command, network, or other tool side effects. A task start or continuation carries Harness-authored instructions, so the transcript and the `/undo` picker show only its notice, such as `Execution started: <title>` or `The task was resumed`. Rolling back a goal or plan start returns the command that started it to the composer: `/goal <objective>`, since the objective is the goal's title, or `/plan <request>`. A plan's title holds only the request's first line, so `session.exchange.list` names the command as `task_command` on each task start (`ExchangeRollbackReview`), reading the request from the newest plan created at or before the exchange. Execution starts and continuations leave the composer untouched. The `harness_session_*` model tools read the same history: `harness_session_exchange_list` omits rolled-back exchanges, a direct read or search result from one carries `history: rolled_back`, and a task opening appears under the `harness` role, so a model asked how many messages the user sent does not count Harness notices or discarded turns. A failed rollback is reported as a notice and kept in `:messages`. Rolled-back exchanges leave the timeline but keep their records. Sessions outside Git cannot be restored, so enabling writes there requires confirmation.

## Out of scope

Harness adds providers only through the typed `Backend` contract and never scrapes terminals. The broker runs per Neovim process, so controlling a session from another editor would need a shared daemon with stronger lease coordination. Provider-local hooks and command policies can still reject a tool under Harness Allow, because backend-native policy stays authoritative outside the Harness protocol.


## Question ownership

`QuestionController` stores each session's questions, resolution, discussion,
operation receipts, and pending outbox in `session_question_state` in
`harness.sqlite3`. Creation and answer/outbox persistence occur before publication,
without the broker's execution lock. Independent SQLite connections serialize
mutations with immediate transactions.

The question picker owns unsubmitted answer drafts by session, question identity,
and content revision. Confirming an intermediate answer advances locally; confirming
the last unanswered question submits `session.question.answer_batch`. The owner
validates and applies the complete set in one transaction, retaining one exact retry
receipt and publishing one question snapshot. A stale or invalid entry rolls back
the entire set. Clarification and historical corrections retain their separate paths.

Batch commits group message-delivered replies by task attribution. Each group enters
the input journal once and renders all its question identities and answers in a
single provider turn. Database bootstrap creates and validates the question table
before starting owners; opening a question controller never repairs missing schema.
Waiting tools observe the committed set through their existing
answer destination and do not also receive message delivery. Disposable state version
49 separates the grouped outbox and input payload from older executables.

The input worker transfers each outbox entry into the existing input journal using
a stable operation ID, then acknowledges that transfer. Provider acknowledgment
remains owned by the submission journal. A crash before transfer repeats admission;
a crash after admission reuses its receipt. Unknown provider delivery requires
reconciliation and never authorizes blind replay.

The question tools own their usage guidance; general prompts do not duplicate it.
`question_ask` defaults to returning Harness-generated question IDs immediately,
while answers arrive through normal user-input delivery; in a planning turn it always
waits, as with `wait: true`. With `wait: true`, it
keeps the tool call pending until every requested question is answered or withdrawn.
These questions appear as required, but do not trigger provider cleanup or a second
chat continuation. The tool returns their resolved records, without also sending
the answers through the input journal. Its live registration ends on completion or
cancellation; a later answer without a waiting tool uses ordinary message delivery.
The transcript draws each question row from the question store, not from the exchange
record: `crate::question::project` places it after the call that asked it. A live update
projects the store into the exchange it draws (`HarnessBroker::live_question_rows`), and the
owner redraws the unfinished exchange as soon as it commits a question change, before it
acknowledges the change (`exchange::question_input::present_question_change`, which takes no broker lock because a caller may hold the broker while it awaits the acknowledgement), because a waiting
`question_ask` hands the answer to the provider without any provider event to redraw it. An
answer accepted while the asking turn still runs therefore reads as answered at once; live
updates once carried the previous frame's rows forward, and `Questions · 0/1 answered`
stood beside a turn that was already using the answer until the next full snapshot.
When a wait ends without returning its answers, because the tool was cancelled, including
after it reported them, or because the owner closed, the owner moves every unreturned
answer to the outbox. A committed question change requests outbox admission, so a live
owner admits those answers at once; a closing owner leaves them for the next owner, which
admits the outbox at startup.
The model supplies neither question IDs nor mutation operation IDs. Existing IDs
and revisions select questions for replies, revisions, and withdrawals.

Legacy required questions stop active provider work through the shared cleanup
boundary and block automatic input and checks. Answers and clarification can run
discussion-only turns with writes disabled; task continuation waits for required
resolution and outstanding answer delivery.
Exchange completion retains questions. Task cancellation/replacement retires its
pending questions, and late answers cannot target the replacement task.

A legacy required question in plain chat retains one continuation for its original
exchange. Once required decisions resolve, the input worker admits user responses
first and then queues that continuation through the same journal. It cannot steer
into a read-only discussion turn or replay after acknowledgment. An optional
answer never creates a continuation for completed work. Each idle question delivery
admits a new discussion exchange instead of reopening the completed source exchange.
Cancellation revokes unfinished chat continuations and retires their required
questions. Optional chat questions remain answerable after cancellation or normal
completion; late answers enter discussion without resuming the original work.

### UI observation subscriptions

Terminal inventories arrive through normalized provider events. Check catalog views subscribe to `checks_changed`, emitted after committed check updates, so ordinary streamed text does not reload the catalog. Resource toggles subscribe before command admission, match completion by operation identity, and perform one durable read after the receipt to cover attachment races. They do not repeatedly query settings. Host exits and failed requests provide connection diagnostics; the UI does not send health heartbeat queries. Local animation clocks, operation deadlines, and delayed retries after an actual failed request remain separate from state observation.

Picker `on_dispose` releases owned subscriptions on every close, including confirmation and silent replacement. `on_close(resume, reason)` remains the optional user-workflow callback; `reason` is `"user"` only for the user's own close key and `"programmatic"` for every other close, including replacement by `Picker.open`, so an owner can tell a dismissal from a displacement. `Picker.when_idle` runs a callback once no picker is open.

LSP requests observe cancellation, scope lease release, and tool-selection revisions through watch notifications. Structural analysis also observes the pending request lifetime, so dropping an editor request cancels its analysis without a periodic map lookup. Check workers consume the owner's cancellation stream and publish output only after new bytes arrive; the existing output coalescing delay does not wake or rewrite idle progress.
