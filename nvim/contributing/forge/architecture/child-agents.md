# Harness child agents and inspection

Delegated work must not outlive its parent's authority or replay after a crash, and an agent reading session history must not gain that session's permissions. This chapter covers both: child conversations that run under a root session, and the read-only tools an agent uses to inspect sessions.

## Child ownership

`AgentCoordinator` owns child conversations per root session: unique `/root/<name>` paths, durable `AgentTask` records, inboxes, follow-up queues, and cancellation. Admission reserves one of eight active slots, then commits the agent, the parent `Delegation`, the queued child `Exchange`, and the task in one transaction, so a crash cannot leave a child without its parent record. Each child runs one task at a time, with up to 32 pending follow-ups, and starts with fresh provider history in the shared workspace.

Provider tool callbacks reach the coordinator through a 64-entry channel instead of the broker lock, and tool authority ends with the root turn. Children never receive delegation or root planning tools.

A child never receives its parent's words as user text, because a model gives a user message the user's authority and the parent is another model. `HarnessBroker::begin_managed_agent` builds each task as `TurnKind::AgentTask`, which renders an `<agent_message type="new_task" from="/root">` and fixed instructions to carry the task out within the child's permissions. Messages that `agent_send` queued while the child was idle follow the task as `type="message"` elements, and the broker marks them attached to that task. `AgentProviderFactory::request` also sets `ProviderRequest::child_agent`, the standing `<agent>` section that names the child's path and parent and carries its profile instructions, so the profile survives compaction as every standing section does. The child's final response returns to the parent as a `final_answer` `<agent_message>`, which `agent::report::is_child_report_echo` recognizes when a provider echoes it.

`agent_send` to a running child first tries to steer the message into the running turn, but `ProviderBridge` admits a steer only with a journaled submission or a child result, and an agent message has neither. The steer is therefore rejected, the broker records `agent.message_queued`, and the message waits in the inbox until the child's next task.

Two drains read that channel: the active root turn and the idle controller task. The idle task takes the broker lock for one command at a time through `drain_next_agent_command`, so a slow command, such as a child cleanup retry, does not also hold back the session requests and root events waiting behind the rest of the queue. The idle drain still applies child events and completions while a root turn runs, but it has no parent exchange to authenticate a model request against. It therefore hands any model request whose authority is still live to the turn through `AgentCoordinator::defer_to_foreground`, which the turn reads first. `AgentForegroundClaim`, held by each `ForegroundTransaction`, marks that a turn owns those requests. When the claim drops, the idle drain receives the leftovers and rejects them as unauthenticated. Before this hand-off, the idle drain could win the race and reject every `agent_spawn` with "agent request has no active authenticated root authority".

The idle drain settles each command independently. A child event or completion that fails is published as an error notice among the batch's events, and a completion is applied even when publishing its approval cancellations fails, because an unapplied completion leaves an execution with no runtime. `drain_next_agent_command` settles one command at a time so a caller can release the broker lock between commands. Once the lane is empty and no root turn holds the foreground claim, the drain launches every queued child that capacity now admits; the active root turn was previously the only poller, so an admitted child waited for the next root prompt. Every unfinished task that `has_active_task` and `has_unresolved_task` count can still reach a durable outcome, because no admitted task can wait behind a stopped child's authorization gate (see below). Those predicates once excluded such queued tasks so a parent would not park on them; the parent then finalized with an unsettled descendant, checkpoint settlement rejected it, and every later prompt failed on the same descendant.

The transcript records each delegation as one spawn event and summarizes finished children under the parent exchange's Agents root, while running children appear only in the status area; "Exchange content" and "Status" in [timeline.md](timeline.md) describe that presentation. Every view of a child reads one clock and one tally, those of its latest task's exchange: the status row, the summary row, and the child's heading render `Exchange::elapsed` and its `ToolCounter`, and `agent_summaries` gives the agents picker that exchange's accumulated `elapsed_ms`, the `running_since_ms` instant from which a running clock keeps counting, and the status row's own `tool_label`. The picker once measured the agent record from admission to its last update, which added startup and settlement time, so one child read `Ran 10s` in its row and `Completed in 14s` in the picker. The presentation draws a running child's clock from its last snapshot and the current time on every refresh, so `apply_managed_agent_completion` measures the child's settle instant under the presentation lock and keeps that lock until `SessionPresentation::settle_owned_exchange` has replaced the running child with the settled one inside its parent's entry; the full reconcile follows after the lock is released, because building its snapshot takes the same lock. A refresh between the settle instant and the reconcile once drew the running child past its settled duration, so its heading ticked to `11s` and then settled at `Cancelled 10s`. `AgentSnapshot` carries the snapshot `revision` and `runtime_epoch` of the read that produced it, because the editor receives child lists in `agent_updated` events and in session snapshots and a list read earlier can arrive later; `agent_catalog.replace` keeps the newest list of one host run. Applying a stale list once showed a finished child as running again, and `Ctrl-X` in the picker then interrupted a child that had already completed. Managed children use the same retained native runner and `Turn.Completed` collection boundary as roots. Provider-observed children use `AgentEvent` summaries without acquiring managed execution authority. `Started` and `Updated` carry an `AgentActiveState`; `Finished` carries an `AgentOutcome`, so a finished observation cannot carry a running state. A summary alone does not certify child resource collection or invent child transcript items.

A managed child's native outcome also controls automatic continuation. A collected stop that requires authorization ends the current task without starting permission-timeout feedback turns. The reusable `Agent` retains `AgentContinuationPolicy::RequiresAuthorization` pointing to that original task; its native result and any host observation failure remain in the original exchange. `apply_managed_agent_completion` cancels every follow-up already queued behind the stopped task in the same `complete_agent_tasks` transaction that records the stop, marks each reported with an error naming the stopped task, and only then lets `AgentCoordinator::settled` release the execution, which refuses to release one with an unfinished follow-up. Admission rejects new work against a stopped policy with the typed `ContinuationRequired` error, which the model receives as a tool error naming the child and stopped task: `AgentCoordinator::reserve_followup` rejects it before reserving anything, and `agent_policy::admit` rejects it again inside the admission transaction, so a stop that lands after reservation cannot be bypassed. Informational `agent_send` messages and unrelated user input never authorize a stopped child. Explicit user admission, or an accepted original user input that carried that stopped child report, can acknowledge the exact stopped task. Report acknowledgement atomically marks the captured task reported and clears only its still-matching policy; it preserves the original failure and rejects a newer stop. Admission compares the captured authorization with the latest persisted policy inside the same transaction that admits the next task, so a stale reservation cannot clear a newer stop. Live admission rejects a policy that names a missing task or a task owned by another session or agent. Startup instead restores through `AgentCoordinator::restore`, which loads every task before it validates any policy, because an agent's policy can name a task listed after that agent's earlier tasks. Restore resets a policy whose task is missing or foreign to `Ready`, persists the repaired agent, and continues startup; the policy is derived continuation state, and a stale one previously made the session unopenable.

A child cancelled through Harness, by the user or by its parent's model, is not such a stop. The cancel was its requester's decision about that one child, so `continuation_blocked` blocks only on interrupted or failed reports, and the siblings' results continue the parent by themselves. `AgentCoordinator::interrupt` records which source asked, and `AgentSource::cancellation_reason` gives the cancelled report its error, so the parent reads `Cancelled by the user before it finished.` rather than the provider error that the interrupted runtime returned. `acknowledge_agent_result` marks a cancelled report reported once a turn receives it; a lone cancelled report, with no sibling result to accompany it, does not start a continuation and travels with the next user input. Every stopped child once suppressed continuation, so after the user cancelled one child the parent settled without its sibling's completed result, which reached the model only with the next prompt.

A model-delegated child reports only to the turn that delegated it. `HarnessBroker::deliverable_child_results` drops an unreported result whose delegating exchange ended cancelled, failed, or interrupted, both when a new exchange starts and when a parent continues, because that exchange never resumes. Such a result once reached the next prompt's turn, whose model then reported on the earlier turn's children instead of its own work.

A user's cancel that arrives while the parent waits for its children ends the exchange `Cancelled`. The cancel marks the turn collecting as soon as it is admitted, before its acquisition has interrupted the children, so it wakes the result the parent had parked for them while they still run. `native_ready_awaits_children` keeps that result parked until the interrupted children settle, and the finalization outcome maps a completed result under a cancel collection to `Cancelled`. The parked result previously finalized at once and failed on the descendant guard, or, once the children had settled, recorded the completed result, so the interrupted exchange read as an ordinary response. The host's shutdown stop on an editor exit is the same cancellation, so such an exchange reopens `Cancelled`. Because the cancel announces its collection only after its acquisition has interrupted the children, the children's completions can let finalization settle the exchange first; `record_foreground_collection` and the collection's completion therefore never label a finished exchange. A late label once outlived the stop, and the heading of the settled exchange read `Stopping` from then on.

`ObservedAgent` persists each native child under the composite original `BindingId` and public `AgentId`. Its public agent identity can differ from the positively learned `ThreadOwner` identity, which Harness resolves from the child thread the adapter derived with `ThreadId::child`. The bridge supplies a registry-created `ObservedAgentAssociation`; neither storage nor the broker constructs a child owner from an ID or selects the newest turn. `observed_agent_record` stores validated native ancestry, typed host observations, and independent `Exchange::observed` histories without any managed `AgentTask` row. Those exchanges retain their own received `CompletedTurn`; a root or child lifecycle summary cannot supply one.

For positively observed native processing, the adapter retains a separate child driver with its original reader and callback collection. Parent-turn completion does not wait for that independent child or close its callback authority. A successor root turn can start while late child content continues into the original child history. Only that child's own native terminal evidence and collection can publish its completion.

`ObservedAgentAvailability` records loss of host observation separately from the last native lifecycle. Binding failure or exclusive startup recovery marks observation unavailable and freezes the host display clock at its last native publication boundary. A native child's start and finish come from the delegating turn while its own items carry the child's scope, so the session execution runtime sends a root `Agent` lifecycle through the session inbox with the child's content rather than the foreground stream; on separate paths the broker once applied a child's first item before its start and failed the delegating turn. Evidence the broker still cannot place, other than a storage failure, marks only that child unavailable through `HarnessBroker::reject_observed_child` and leaves the turn and its siblings running. When a session's observation fails, the intake still publishes the closed binding's retirement, so a child left active by the failed turn stops its live clock instead of running on in the status area. It does not invent a native interruption, completion timestamp, or cleanup certificate. The binding fence also prevents late host-only effects from recreating an available record for a retired generation. A user's cancel of the delegating exchange is the one host-originated end: `HarnessBroker::cancel_observed_children_of` runs when the cancel reaches the foreground, either as the owner's cancel collection or as a `TurnCancelled` failure. A collection of the whole tree stops the same native turn, so `ExchangeStop` runs it as that collection starts: `/plan cancel`, which the editor sends as the task action `clear`, a task pause, a plan decision, and a tree-wide configuration change all reach the foreground as a restart collection, which once left the fence unset and let a stopped subagent's queued output settle its row as `completed`. A root-only reconfiguration such as compaction or a model change keeps native children observed. It finishes every live child of that exchange as `Interrupted`, which the transcript shows as `cancelled`, ends the child's open turns interrupted, and fences the exchange so the broker discards every later native observation of its children, tracing each as `agent.native_discarded`. The provider can deliver such observations after the cancel because the broker places child observations one publication at a time: on Copilot a subagent that finished a second before the stop reached the CLI still had its tool calls, raw final answer, and completed finish queued, and they streamed into the stopped turn and settled the row as `completed`. Committed host effects and host policy events still apply. A new turn of the same exchange lifts the fence. Native child history and nested ancestry render read-only, without managed send, follow-up, or interrupt controls.

Each child has its own checked `AgentId` and, when resolved, its own `ThreadId`. `AgentDescription` may receive parent, delegation, and thread metadata independently. A delegation names the existing parent thread, turn, and optional item; missing metadata never permits attaching late child output to the parent's current turn. `ConversationResolved` associates the child with its original conversation, and host ownership checks reject conflicting relationships.

## Tools

The portable `subagent_tools` setting is off by default, and `/agents on` and `/agents off` change it. The change commits at once, and every agent tool call reads the committed flag, so `agent_spawn` is refused as soon as the toggle turns the tools off. A provider receives the root's tool set when a turn starts, so a toggle during a turn ordinarily restarts that turn to replace it. While child work is running or queued, `ConfigurationCandidate::effect` classifies a toolset toggle (`/agents`, the LSP tools, or the session tools) as local instead: the running turn keeps its tool set, the children finish and report as usual, and the next turn start, which follows their settlement, receives the new set. The restart once finalized the parent that was waiting for its children over the unsettled delegation tree, which failed the exchange on the descendant guard and left the editor showing `Stopping`. Enabling it exposes `agent_spawn`, `agent_send`, `agent_followup`, `agent_interrupt`, `agent_list`, `agent_activity`, and `agent_tool_output`. There is no wait tool. When a root turn ends with unfinished children, the exchange stays open, and Harness starts one continuation with their reports once they settle. New user input resumes the exchange immediately. The waiting root parks its deferred native result, as it does while child quiescence holds launches; only a coordinator revision (child activity or quiescence release), user input, or collection re-examines it. Before parking, the reducer re-read that result on every loop iteration, which spun the host while children or quiescence persisted. A stopped child no longer marks the parent exchange interrupted; only the parent's own stopped turn does. A stopped child that requires authorization suppresses that automatic continuation but not the wait: the exchange still stays open until its running siblings settle, because finalization captures a checkpoint that requires a settled descendant tree. The unreported sibling reports then travel with the next user input.

`agent_activity` returns at most 20 recent entries, five by default, without tool output. `agent_tool_output` reads at most 32,000 characters per call through references that validate ownership.

## Profiles

`AgentProfileStore` owns the global `stdpath("config")/forge/subagents.json`. A profile holds a purpose, instructions, enabled state, provider, model, thinking level, speed, permission mode, and write access. `inherit` copies the root's choice at admission, and `default` selects the provider default. `write_access: "off"` removes the child's write scope; it is the only value besides `inherit`, because a profile can narrow the root but never widen it. Forge never infers write access from a profile's name or instructions, so a profile that only says "Do not modify files" still holds the root's write scope. Saves are revision-checked atomic replacements.

Each child persists its resolved profile, so editing a profile never changes existing children. `AgentProviderFactory::request` computes each dispatch's access through `agent::effective_access`: the current root's policy, with write scope narrowed to the selection's if the selection is stricter. A root narrowed after admission therefore still narrows the child, and a write-off child stays write-off when the root later gains write scope. Approval mode narrows the same way; read scope, directory grants, and sandboxing follow the current root.

## Repository reservations

A child's effective write scope, not its profile wording, selects its repository reservation. `AgentRuntime::run` passes `agent::repository_access` of the dispatched policy to `AgentCommandSender::repository_admit`: write-off children take the shared `RepositoryAccess::Read` reservation and run concurrently, while any write scope takes the exclusive `Write` reservation and waits for readers and writers. The provider's startup process authorizes at the reservation's own level, so a provider starts under a shared reservation, while an LSP mutation that borrows `Write` is refused there with `repository_read_only`. The reservation lasts until the task's durable publication; a shared reservation never upgrades in place, so broadening a child's permissions takes effect on its next dispatch, which reacquires the reservation. A shared reservation only admits concurrency. Write denial comes from the permission policy, which authorizes reported operations rather than sandboxing every provider, so a provider without an enforced read-only sandbox can still write through unreported means. The Codex adapter, for example, maps write-off to its native read-only sandbox only while sandboxing is on.

The reservation follows the policy after provider capability resolution, because `agent::repository_access` reads the dispatched request's access rather than the profile. An adapter that cannot honor write-off therefore resolves to a writer and takes the exclusive reservation instead of running beside readers. Every repository consumer borrows the level its work needs from the child's reservation, and `ReservationState::authorize` refuses a `Write` borrow under a `Read` owner: LSP edits and Prepare checks fail with `repository_read_only` under a shared reservation, Verify checks borrow `Read` and run, and repository tools authorize each reported write through the permission policy, which already denies it.

## Interruption

Child approvals cancel only that child's requests on interruption, and the `approval_cancelled` events name exactly the requests that cancellation removed rather than an earlier snapshot of the pending list. Interrupting several children flags every target before any cleanup retry runs, then retries each retained process cleanup independently and reports every failure together; stopping at the first failed retry left later children editing the workspace under a cancel that had already reported failure. `/fork` rejects a root whose children still execute before it creates the forked session, because the native fork refuses an active thread and the copy would otherwise inherit live child rows that no runtime settles. Root cancellation and access changes collect child execution first, with a 30-second cleanup bound. A root turn that fails for another reason collects its own children before its terminal checkpoint: failure settlement sends the same interrupt for every child with an unfinished task delegated by that exchange, keeps servicing child completions, and prepares the checkpoint once none remain. It previously stopped servicing children and went straight to the checkpoint, whose descendant guard rejected the unfinished child, so the parent stayed finalizing. If the interrupt itself fails, settlement records that failure and lets the guard report the remaining child. Collection counts queued launches as well as running executions, so a transition whose child policy is Collect interrupts and durably cancels admitted work even when no execution slot is occupied; it skips only when no child work is admitted at all. A task cancelled before repository admission completes once as cancelled with nothing to collect. Once admission succeeds, `AgentRuntime::run` runs provider shutdown and collection after every failure, and the spawn fallback in `begin_managed_agent` never reports a cleanup failure, because the runtime fails only before acquiring resources or when its completion cannot be delivered. A child interrupted while its provider thread was still opening is an ordinary cancel. `ProviderBridge::shutdown` retires each owner before and after native shutdown, and the first pass can read the interrupted open's provisional interruption before the provider has joined it; it keeps that failure only when the owner is still unretired after native shutdown, because the second pass then reads the authoritative result. The provisional failure once became the child's cleanup error, which left the child `Closing`, failed the parent's stop as uncertain, and restarted the provider. A cleanup failure is recorded as the exchange's `finalization_error`, separate from the task's own error and state, and `release_child_cleanup` clears only that obligation when a retry succeeds, keeping the original failure and the continuation policy bound to it. On reopen, unfinished child tasks become interrupted and never replay.

## Session inspection

The root interaction exposes `harness_config` and seven `harness_session_*` tools through `tools/session/` and `tools/config.rs`, and the `harness-sessions` skill documents them. The portable `session_tools` setting is on by default, and turning it off removes the history tools but keeps `harness_config`. An aside session keeps the history tools regardless of that setting and additionally receives `origin_message` from `tools/origin.rs`; "Aside sessions" in [harness.md](harness.md) describes both.

Inspection uses read-only SQLite connections without migrations or leases. Reading another session requires authorization against its workspace, and that session's saved permissions never authorize the caller. Results go to a private temporary snapshot with opaque continuations, and page budgets bound each delivery, not the total size. Log inspection exposes only allowlisted diagnostic metadata, never prompts, credentials, or private reasoning.

The log reader captures each retained segment's byte length and keeps its open file
handle. It reads backwards from the current file into older rotations. Each request
decodes at most `limit` entries, defaulting to 1,000; continuations consume the next
older batch without scanning the full log first. Each log batch is returned complete,
including large Unicode records, independently of other inspection tools' byte budget.
Completed batches retain their boundaries so replaying a cursor returns the same page.
Concurrent appends stay outside the captured extent, and rotation renames files so
readers retain their original segments. Cancellation is checked between records;
live settings and read authority are rechecked before publication. Truncation or a
decode failure invalidates the cursor and fails explicitly instead of skipping entries.
