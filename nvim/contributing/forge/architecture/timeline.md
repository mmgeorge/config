# Harness timeline and presentation

A transcript that Lua assembles from provider events can disagree with durable history, and a large tool output can freeze the editor. Rust therefore projects the session into one ordered timeline and publishes changes as revisioned operations, and Lua renders only what it receives. Provider lifecycle events never change transcript records in Lua.

## Timeline stream

Each session controller owns one `TimelineStream`. It compares stable entry identities and emits ordered `insert`, `replace`, `remove`, `tool_output`, and `message` operations under a monotonic revision. Initial load, reconciliation, resume, and preview carry full snapshots, and streaming carries only changed items. Prompt submission creates no Lua-owned interaction: broker admission emits the first patch, with the durable interaction and a `Working` status. Provider deltas for one owner coalesce on the leading edge: the first delta after a quiet period passes at once, and later deltas merge until 16 ms after the previous emission or 64 KiB. Deltas that queue behind a publication in flight merge again in the session inbox and in the foreground collector, so a slow publication yields fewer, larger updates instead of a backlog. `owner_core_log` records no output deltas.

`TimelineProjector` combines interactions, plan lifecycle records, and executions into one ordered presentation, placing plan events by their `ExchangeAnchor`. `ExchangeLayout` keeps provider activity inside the activity fold and renders artifacts, plan submissions, verification results, and checkpoint changes before the final response of the turn that produced them, including a plan submission recorded after that response. Once a later turn of the same exchange begins, as in a continued plan revision or a resumed interruption, its results stay in source order after the earlier response, so a revision never appears above the answer that preceded it. Check runs and session events get a `TimelineOwner` at creation, either the session or an exchange position, and that owner never changes.

## Exchange content

An exchange owns an ordered `ExchangeEntry` list of commentary, steering, responses, and typed event references. Commentary owns its tool records, reported file changes, and completed check runs. Steering and events stay siblings of commentary, so collapsing commentary never hides steering. A tool keeps its original commentary owner after later commentary arrives, and a tool with no active commentary creates a synthetic "Considering initial steps" commentary.

While an exchange runs, active commentary stays expanded so its trailing tool group can show its count, the latest tool heading, and up to that tool's last four output rows. Previews use their actual row count without blank padding, and tools with no output reserve no preview rows. This includes the synthetic "Considering initial steps" commentary. A completed tool keeps its preview until a successor or commentary boundary replaces it. Commentary settles and folds when its activity is no longer live, and live expansion overrides clear at that transition. Full output stays available for expansion. After the exchange completes, the activity node collapses, and the final response stays outside the fold. Liveness requires a running execution clock, not merely an unfinished exchange: `Exchange::content` settles the newest group once the exchange parks, finalizes, or pauses for restart, so a paused goal or collected cancel reads "Ran N tools" rather than a stale "Running N tools".

File writes in one activity section share a `Changed N files` node that composes reported hunks into an original-to-final diff, without reading the workspace. Failed and interrupted edits keep their diagnostic but never count as changes. Commands, formatters, and generators stay ordinary tools, because their filesystem effects come only from checkpoint comparison.

## Node state and paging

`NodeMap` owns the expansion choices, node incarnations, and output sources for one open presentation. `NodeState` travels inside block metadata, so one publication changes text, node state, and visible ranges together. Lua sends `set_expansion`, `load_more`, and `retry_loading` actions with a view sequence and node generation, and every window showing the presentation shares the choice.

The timeline has no aggregate byte, row, or block limit. Only individual deliveries are bounded: tool output arrives in 16 KiB source chunks with an initial 64 KiB formatted prefix, and expanded bodies load two window heights at a time in 64 KiB pages, with at most eight section requests per viewport pass. A failed section reports once and waits for an explicit retry.

`ToolOutputView` keeps the ANSI parser across deltas, and `ToolOutputSnapshot` shares output storage with separate output windows without copying or reparsing. `BufferText` shares immutable packed rows through `Arc`. Fenced code is published first and highlighted later by `TranscriptSyntax` jobs, each with a 10-second deadline, so highlighting cannot delay text.

Each native item keeps its checked identity and original thread/turn ownership through reload. `ItemStart` fixes the item family. `ReasoningKind::Full` and `Summary` stay distinct in durable history and never become commentary. Assistant prose preserves explicit unclassified, commentary, or response interpretation. An open transcript updates the block of unclassified prose on every delta exactly as it does for classified prose, because an adapter such as Claude Code or ACP classifies a message only when a later event or the end of the turn settles its role. Reasoning has no transcript block, so a reasoning delta changes the transcript only through the status row's own `Replace` operation and never re-projects the session. A `MessageCompletion` replaces accumulated deltas; an interrupted snapshot remains visibly interrupted rather than becoming a final answer. Positive native user-message items retain their sender treatment and any matched submission association, so attachment references stay in the existing registry rather than copied into event payloads.

A configuration change during a turn interrupts that turn and restarts the request as a new turn in the same exchange, so the partial answer and its replacement share one response. `ProjectionBuilder::content` renders a `◇ Resumed` row before the first part of a turn that follows a turn finished `Interrupted`, keeping the partial text from reading as the start of the restarted answer. A native echo of a Forge submission keeps its turn evidence but gets no transcript node, because the broker already rendered the admitted prompt, and the internal resume, rollback, and continuation submissions never appear as user rows. Task starts and task continuations render through `ProjectionBuilder::task_notice` as one notice block whose Harness-authored provider input sits in a closed fold, because the user's own words are the start title or continuation reason and the instruction text only explains what the provider received. A continuation once rendered its input as a separate unfolded block, which filled the transcript with plan JSON and resume instructions on every phase hand-off. Providers that echo such input without a submission identity are recognized by the exchange prompt the echo repeats, so the echo adds no second copy. A committed conversation rollback publishes `interaction_rolled_back` together with the `document_changed` patch that removes the rolled-back exchanges; the event alone only refreshes session state.

Tool descriptor refinements update the same item without changing its family. Final descriptor and output snapshots replace prior content only when supplied. Output appends and replacements remain distinct, and repeated final snapshots must agree. Display identities use structured turn/item addresses; late output and verification links cannot be rebound through a concatenated key or the newest turn.

`TimelineEntry::ObservedAgent` renders native child summaries, their independently owned exchanges, and nested native children. It retains explicit public native parent IDs separately from host execution-owner IDs. Unknown ancestry remains unresolved rather than being assigned to the current parent. An unavailable observation shows its last native state and retained history without a running timer or a fabricated successful end. Native child entries have no managed-agent control action.

Harness retains each provider's checklist on its exchange, but nothing displayed it, so the progress it records stayed hidden. `ProjectionBuilder::provider_checklist` renders the canonical `Exchange.checklist` snapshot as **Provider-reported checklist** after activity and before host file changes. The label separates it from Plan/Execute/Goal lifecycle and from verified check results, and checking off every entry completes no Harness task or gate. The heading reports completed entries out of current entries, the provider's checklist name, and the superseded count. Each current entry shows `[ ]` pending, `[>]` in progress, `[x]` completed, or `[-]` superseded, without inferring state from tool success or message text. Block identities derive from the exchange ID and the tracker's stable entry IDs, so refreshes and reopened sessions rebuild the same blocks from persisted state without querying the provider. Superseded history stays in the snapshot and appears only as a count. The fold closes when the exchange finishes, an absent or empty checklist adds no section, and an interrupted turn leaves remaining entries in their reported state.

Each committed host callback's file diff appears as **Host file changes** after activity and before results. Its identity includes the original scope's exchange and a digest of that scope and exact host call ID. The view remains independent from native file-change snapshots, including when the host effect arrives before the matching native transcript item.

## Check results

An active check is status, not history. `TimelineStream::update_checks` replaces only the status during a run, and it removes the status atomically when it inserts the final result. Completed results form one Checks root that groups runs by Formatting, Lint, Validation, Tests, and Builds, then by source file or target. The root counts each check's latest outcome, so an earlier failure stops counting after a successful retry, while Run rows keep every attempt. The supervisor reads an optional generic JSON report from callbacks and never parses runner output itself.

`CheckSupervisor` holds admission and records under one lock, and the active run owns the source-work permit until its processes are collected. Process cancellation runs in an independent task, so blocked output cannot delay termination. `CheckPublication` coalesces intermediate snapshots in a separate persistence worker and flushes the terminal snapshot before the result returns. Automatic repair reopens the owning exchange through a dedicated transition that keeps its prompt, usage, and checkpoint.

## Status

`SessionPhase` projects exactly one visible phase, and `buffer/status.rs` combines it with optional `CheckActivity`. The primary label takes its own row, followed by check progress, then the latest reasoning preview when the `status_thoughts` preference is on. Rust derives elapsed time from its own start timestamp, and Lua supplies only the one-second sync cadence.

`WorkflowActivity` builds lifecycle text from `LifecycleAction`. Started enters a task or phase, Continued starts another automatic exchange, and Resumed restarts paused or interrupted work. The status row's `BlockMetadata.status` carries its row, animation flag, and hint context, and Lua reads these from committed metadata, never from label text. One timer per transcript updates only the spinner extmark, targeting 15 frames per second with a 67 ms timer and selecting frames from elapsed time. While the status is animated, that timer also requests one presentation sync per second, because Rust renders elapsed labels and refreshes them only inside a sync. A silent tool or held provider response emits no host events, so without these requests every elapsed label would freeze. Rust's ticking gate in `SessionPresentation::sync` decides whether any text changes, and a sync with nothing due returns an empty patch.

## Usage and durations

Each `Turn` retains identified `TurnUsageReport` observations with independently available input, cached-input, reasoning, and output counts. `UsageReportId` deduplicates replay; an optional `ModelCallId` correlates a call across token and timing reports. Complementary measurements merge atomically, and conflicting evidence fails. `ExchangeMetrics` reconciles cumulative snapshots against their original turn instead of charging a repeated snapshot as another call. `Thread.ContextUsage` updates context occupancy separately from token expenditure.

The outer display duration covers active execution and freezes during user-input and permission waits. Tool time is the union of overlapping calls on that host clock. Native model time instead uses reported call duration or complete positively observed native call endpoints. The ledger does not replace missing call timing with host elapsed time, tool subtraction, or provider collection latency; missing timing keeps native throughput unavailable. A `TurnUsageReport` with endpoints preserves them without synthesizing its `reported_duration_ms` field. Each `ToolCall` retains its first observed execution start and terminal timestamps, and a call first seen at completion shows `—`. It also records `Exchange::tool_instant` readings at those two points. That clock is the exchange's active clock while the exchange runs, so a tool waiting for approval or input pauses with the Working timer; Codex reports a command's execution start before it requests approval, and wall-clock tool time therefore counted the whole wait. After settlement the reading continues in wall time from the frozen duration, so a background command keeps counting. Host-generated tools and records without active readings use wall time.

Tool-group headings also show the union of their calls' execution intervals, excluding idle gaps and counting overlap once. The group uses active-clock readings when every call has them, otherwise wall-clock readings for the whole group so its intervals share one clock. Missing execution endpoints leave the group duration unavailable. Individual rows still show each call's own duration.

The exchange metrics header shows input summed across every request in the exchange, followed by the cached share of that input as `(N% cached)`. The input total is token expenditure, not context occupancy, and the winbar reports occupancy.

## Transcript window and pickers

The Harness controller binds a native transcript document, a native status document, and a Lua-owned composer buffer, all owned by `OpenPresentation`. The status document has its own revision, so status-only updates leave transcript rows unchanged. `HarnessStatusView` owns the split above the composer and a separate display buffer, so local notices never modify the native replica. Lua fills unused transcript space with virtual rows, so the live tail ends at the bottom without changing native text.

Switching a saved session into the current tab releases both window-bound presentations before transferring the panes. Their buffers, drafts, and queued input remain session-owned. The receiving session then binds fresh presentation, composer-height, and scroll observers to its new windows; closing only the old tab does not release those subscriptions.

`views/harness/workspace.lua` locks the transcript and composer panes. It pins both windows with `winfixbuf` and blocks commands that would close or unload them. Neovim's `:windo`, `:bufdo`, and related list commands split a pinned window whose previous window is also pinned, and they leave that unowned split focused. Netrw runs `:windo` from a non-nested VimEnter handler, which suppresses WinNew, so opening Harness from a startup command otherwise leaves a second composer window as the current window. Approval and input routing then target the wrong window. The lock therefore sweeps the Harness tab at SafeState, after every command and handler has returned. It closes any unowned split that still displays a Harness buffer and returns focus to the owned pane. `:new` and `:split {file}` have replaced their copied buffer by then, so they keep their windows.

Composer height follows wrapped rows within the configured bounds, and `smoothscroll` lets tall drafts scroll within one physical line. If the whole draft fits, the viewport starts at the first line, which stops Insert-mode scrolling from hiding the top of a short draft.

The status split has a fixed viewport at row one. Its owner resets vertical and horizontal scroll offsets after layout and scroll events without moving focus or the transcript. Status sizing remains content-driven, bounded by available window space, and the separate status-details view retains normal scrolling for overflow.

`HarnessResponseReveal` observes the latest top-level exchange's committed node lifecycle.
After transcript, status, local status layout, and Markdown decoration publication, a new transcript
revision in a live exchange follows the tail when the owning composer window is
focused, including tool activity before any response text. A permission review or
other floating popup whose previous window is the composer counts as composer focus,
because the user who was following the stream did not move to the transcript; a
popup entered from the transcript leaves the reader's position alone. Focus is checked at
publication, and unchanged revisions do not replay navigation. The Markdown adapter
settles navigation from the renderer's completion callback, after wrapped tables
have installed their replacement rows. A newer transcript revision or timeline
invalidates an older callback; no cursor or viewport snapshot crosses that wait.
Focused transcripts
retain the shared cursor and selection preservation contract.
A PlanReview acceptance or revision request is an explicit submission, so on success
it returns focus to the composer and positions the transcript at its tail, exactly as a
composer submission does. Closing PlanReview without a decision restores the previous
window and position.
A newly settled exchange reveals its response only when focus is outside the transcript. Each visible window measures from the exchange's prompt through the tail in screen rows, including wrapping and the winbar. An exchange that fits aligns to the bottom. A taller exchange places its prompt at the top, exposing the beginning rather than the end of the response. When steering was consumed mid-exchange, the newest steering row replaces the original prompt as that anchor, so the reveal starts at the reply to the steering instead of the earlier answer. Folded responses retain their positions. Initial adoption and timeline switches establish a baseline without replaying navigation, and skipped reveals are consumed rather than deferred.

Math rendering is an optional integration. `forge.integrations.markdown_math` loads the editor's `markdown_math` module through `pcall(require)`. When the module is present, its handlers convert display and inline math, and `markdown_text.lua` normalizes math delimiters. When it is absent, render-markdown's built-in handlers render math unconverted. A `markdown` or `latex` handler configured in render-markdown's `custom_handlers` takes precedence over both, and `:checkhealth forge` reports which path is active.

The transcript is read, not edited, so Harness disables `render-markdown`'s anti-conceal: the cursor row stays rendered, and an equation or emphasis span never reverts to its source when the cursor enters it. `render-markdown` separately reveals a row it replaced with virtual lines, such as a wrapped table row, because a hidden row has no cell to edit. `render/harness/markdown.lua` overrides that rule too, because the reveal changes the row's height: each cursor move through a wide table shifted the text below it and moved the scroll boundary. The cost is that the cursor on a wrapped table row sits on a hidden buffer row, so Neovim draws it on a neighbouring row.

Row heights must not change under a resting window. A rendered row differs in height from its source, and both layers render only near a window: `markdown.viewport` selects the messages within one window height above and below the visible rows, and `render/harness/markdown.lua` widens the span `render-markdown` renders from ten rows beyond a window to one window height, rendering again once a window comes within half a window height of that span's edge. A page or half-page scroll therefore reaches rows that are already rendered. A jump farther than that, such as from the first row to the last, still lands on source rows and settles when the render completes.

Two events change heights or the rendered span without a Markdown pass. A scroll that moves no cursor and keeps the same messages near the window skips the pass, so `render_markdown` calls `markdown.follow_view`, which has `render-markdown` render the approaching rows. A render changes heights without scrolling, so `render_markdown` applies `layout.clamp_scroll` to each transcript window when the render settles, which removes the empty rows a shrinking tail would otherwise leave below the final row until the next scroll.

The Markdown pass runs only when it has something to change. `render_markdown` skips it while the visible messages, their versions, and their rows equal those of the last pass, even though the buffer changed elsewhere, as it does for streamed tool output and status ticks. The exception is rows inserted exactly at a message's end, which stretch Tree-sitter's included region over them; `markdown.current` compares the parser's live regions with the message ranges and forces a pass when they differ, or when the previous render has not settled. The handler copies a mark only when it clips, shifts, or pads it.

Harness Markdown handlers clip decorations to the current message ranges before `render-markdown` caches them, because incremental parser trees can otherwise restore deleted list bullets onto a separator. `render-markdown` numbers each list item by walking all of its preceding siblings, which makes one render quadratic in the list length and never terminates on a sibling chain that revisits a node; either blocked the editor thread while the transcript re-rendered. `render/harness/markdown.lua` therefore replaces `Node:sibling_count` with a walk that memoizes positions for the current parse and stops at a revisited node.

Transcript windows soft-wrap raw Markdown rather than hard-wrapping it in Rust. `views/harness/layout.lua` owns the shared `transcript_wrapping` options, whose `breakindentopt` `list:-1` indents each continuation by the width of the buffer's `formatlistpat` match, so a wrapped bullet or numbered item hangs under its text at every nesting level. `forge.decorations` applies the same match when it extends full-width backgrounds across continuation rows. `render-markdown` replaces each wrapped table row with virtual lines anchored above the next visible row, and a table that ends the buffer has no such row; the window cannot scroll to lines anchored past the final line, so a window following the response end loses the table's body rows and bottom border. `render/harness/markdown.lua` therefore re-anchors those groups below the last visible row. Within a selected Markdown message, a rendered table includes all its rows rather than only rows intersecting the previous viewport. This keeps column widths and replacement height independent of tail positioning; newly streamed rows can still change both.

A tab label stores no session name. `views/harness/tabline.lua` resolves each tab at render time to the Harness view whose transcript window lies in that tab and shows that view's transcript buffer, then prints that view's session name, truncated to 30 characters. `/sessions` can move a view's windows to another tab, a background view can receive a rename, and a session can be deleted. A copied label went stale after each of these events, so the derived label changes at the next redraw instead. `controller.refresh_winbar`, session deletion, and history clearing call `tabline.refresh`. A tab without a Harness transcript falls back to its buffer name. The user's tabline returns once no tab displays a Harness view.

Only the transcript window owns the winbar. A trailing `*` marks a model, thinking, or speed change waiting for current work to stop. Configured defaults and requested overrides remain separate from a turn's confirmed model. The turn starts with no confirmed identity and updates it only on `Turn.ModelResolved`; absent native confirmation stays unavailable. The host translates that original turn's metadata into editor notifications without exposing native provider events to Lua.

`views/picker/` owns every compact Harness decision surface: one state and layout model, a renderer, and a float anchored to the bottom of the transcript and composer. Structured rows use stable field IDs. The picker hides the terminal cursor through a paired global `guicursor` transition and restores it afterward. Window-local highlighting cannot hide a focused terminal cursor, so keep this transition.

`/sessions` previews sessions in the transcript window without taking a lease. Each visited session has its own transcript buffer, and `session_navigation.lua` resumes the session on `BufEnter`.

`session_navigation.lua` keeps a closed or displaced view's buffers in `state_by_session_id` so a later resume restores its transcript and draft. **Open: Current Tab** therefore moves a retained session's buffers into the current view's windows; reopening it through `layout.open` would put it in a new last tab while the source tab closed. A session already displayed elsewhere keeps its tab, and the source tab closes. Deleting a session calls `session_navigation.session_deleted`, which finds every view of that session through both registries and the buffer map, stops its event subscription and presentation, closes its tab, and wipes its buffers. The host reports a deleted session's document reads as `session_not_found`, which `presentation.lua` treats as terminal, so a view left open stops reading and shows that the session no longer exists.
