# Harness timeline and presentation

A transcript that Lua assembles from provider events can disagree with durable history, and a large tool output can freeze the editor. Rust therefore projects the session into one ordered timeline and publishes changes as revisioned operations, and Lua renders only what it receives. Provider lifecycle events never change transcript records in Lua.

## Timeline stream

Each session controller owns one `TimelineStream`. It compares stable entry identities and emits ordered `insert`, `replace`, `remove`, `tool_output`, and `message` operations under a monotonic revision. Initial load, reconciliation, resume, and preview carry full snapshots, and streaming carries only changed items. Prompt submission creates no Lua-owned interaction: broker admission emits the first patch, with the durable interaction and a `Working` status. Provider deltas for one owner coalesce on the leading edge: the first delta after a quiet period passes at once, and later deltas merge until 16 ms after the previous emission or 64 KiB. Deltas that queue behind a publication in flight merge again in the session inbox and in the foreground collector, so a slow publication yields fewer, larger updates instead of a backlog. `owner_core_log` records no output deltas.

`TimelineProjector` combines interactions, plan lifecycle records, and executions into one ordered presentation, placing plan events by their `ExchangeAnchor`. An anchor counts only stored nodes: `ExchangeNode::is_derived` excludes plan events, timeline events, and the question rows `question::project` inserts, so a projected question never shifts a plan event. The live path rebuilds an exchange through `plan::event::replacement_exchange`, which carries the projected questions of the current exchange after the node each followed before it inserts plan events, so a live update and a snapshot order the same rows identically; before both rules held, a revision's `Plan submitted` row moved above its artifact on every live update and back on the next snapshot. A plan lifecycle record lives beside its exchange and only a rebuilt timeline attaches it, so `complete_live_plan_submission` reconciles the timeline when `plan_submit` succeeds; the live transcript otherwise showed `Plan submitted` only once the turn settled, while a reopened one showed it at once. `ExchangeLayout` keeps provider activity inside the activity fold and renders artifacts, plan submissions, verification results, and checkpoint changes before the final response of the turn that produced them, including a plan submission recorded after that response. Once a later turn of the same exchange begins, as in a continued plan revision or a resumed interruption, its results stay in source order after the earlier response, so a revision never appears above the answer that preceded it. An execution transition or resolution recorded after the response's turn ended, such as a plan revision the user accepted between two turns, is no result of that turn: `ExchangePlanEvent::occurred_at_ms`, copied from the durable record, tells it apart from a submission at the same source boundary, and it stays after the response. A check run has one owner in the transcript. The runs that commentary of the first response's turn owns are drawn once beneath the activity fold, as the exchange's results, and `ExchangeContentView::take_checks` removes them from that commentary, so an expanded live Thought shows no second `Checks` row; a later turn's commentary draws its own runs where they ran, before that turn's response. Check runs and session events get a `TimelineOwner` at creation, either the session or an exchange position, and that owner never changes.

Transcript and tool-output requests share `forge.infra.request_completion`, which settles each request once across response, timeout, and late response. It retires the timer before consumer callbacks and always runs the ownership finalizer, even when a callback or its error reporter throws. The transcript dispatcher releases its active slot in that finalizer; transient retries retain their queued request behind a separate retry gate. Neovim closes a `vim.defer_fn` timer before invoking its callback, so timeout settlement never closes that handle again.

## Exchange content

An exchange owns an ordered `ExchangeEntry` list of commentary, steering, responses, and typed event references. Commentary owns its tool records, reported file changes, and completed check runs. Steering and events stay siblings of commentary, so collapsing commentary never hides steering. A settled exchange also folds its activity under its heading, and a steer that preceded the response sits in that activity; when a stop or an abandoned draft leaves no visible response, nothing follows the fold at all. `ExchangeLayout::new` (`buffer/layout.rs`) therefore moves the user's steering out of the activity once the exchange settles, and `TimelineRenderer::interaction` draws it directly below the heading, consumed or `Steering (not confirmed read)`, so the fold never hides the user's own message. A tool keeps its original commentary owner after later commentary arrives, and a tool with no active commentary creates a synthetic "Considering initial steps" commentary. Consumed steering ends the commentary before it: `Exchange::tool_store_mut` gives a tool that starts after the steering message a synthetic commentary below that message, so the work that followed the new instruction is drawn after it.

The transcript omits assistant responses whose message state is `Interrupted`, while durable history retains their text and outcome. `Exchange::displays_node` applies this rule to live rendering and reopened documents. Completed responses remain visible even when later steering produces another response in the same exchange. Codex abandons a draft it was streaming when a steer arrives and never records it in the conversation, so that draft ends `Interrupted` and leaves the transcript when the steer is delivered, not when the turn settles: Codex reports the steer as a new `userMessage` item and stops streaming the draft without completing it, so `CodexNormalization::abandon_streaming_drafts` finishes every open agent message of that turn as `Interrupted` on the steer's `item/started` and ignores late deltas for those items; Claude Code finishes the draft before it reads the steer, so the draft stays as commentary. The rule reads the role the adapter assigned, so every adapter must have settled it when the turn ends: Codex and Copilot carry the phase from the item's start, and Claude Code and ACP, which classify late, mark the last pending prose as the response at every turn end, interrupted or not ([Messages](providers.md#messages)). Interrupted commentary and reasoning stay in the transcript.

While an exchange runs, active commentary stays expanded and its tool group stays folded until explicitly opened. The group heading reads `Tools · successful/total`, followed by a parenthesized denied count when nonzero, then elapsed time. Only successfully completed calls enter the numerator; running, denied, cancelled, interrupted, and failed calls remain in the total. Opening the group shows individual tool headings; opening a tool reveals its output. This includes the synthetic "Considering initial steps" commentary. Commentary settles and folds when its activity is no longer live, and live expansion overrides clear at that transition. A Tools group is folded whether live or settled, so `NodeMap::register` keeps a reader's choice to open it when it settles; clearing it refolded a group opened just before its calls finished. The Thought heading's `successful/total tools · (N denied) · duration` and the group heading share `tool_tally_label` and count through `ToolCounter::of`, so they cannot disagree. Each tool row's duration column shows milliseconds below one second (`92ms`), as the headings do, and seconds above it; a call that never executed, including every denied call, shows `—` on every provider, and its group and heading durations leave it out, because a provider that announces a call before its approval would otherwise report the wait as execution. A tool row that did not succeed shows one outcome line, preferring the host's own decision: `Failed: timed out after …` for a tool deadline, the approval's actor and reason for a denial (`Denied by Harness policy: …`, `Rejected by user: …`), `Cancelled by you; the turn stopped.` for a call whose approval the user cancelled, and `Interrupted before it finished.` for a call stopped mid-run. `ToolOutputView` carries that line and the row's marker state, so opening a tool after it ended renders them without re-projecting the entry. In an Edits group, a change refused by policy counts as denied, not unsuccessful. After the exchange completes, the activity node collapses, and the final response stays outside the fold. Liveness requires a running execution clock, not merely an unfinished exchange: `Exchange::content` settles the newest group once the exchange parks, finalizes, or pauses for restart. A stop is the exception: its collection pauses the clock as well, but the newest group stays live while `Exchange::collection` is set, because the stop changes the rows in place and the exchange settles moments later; folding the group at the stop's first frame moved every row below it. Lifecycle metadata remains independent of the heading text.

Tool groups omit an explicit failed count; the successful/total ratio and optional denied count summarize outcomes. Their duration is the union of execution intervals on a shared clock. An announced tool contributes to the count but not to elapsed execution until its start is observed, so it cannot temporarily erase the group's existing duration. `Edits` headings count reported edit operations, and folded `Checks` headings retain latest result counts, total runs, and durations. Each tool row's marker comes from the call's typed `ToolState`, which `ToolHeading::of` carries from the retained call to `decorate_tool_heading`: green for a completed or running call, red for a failed one, orange for a denied one, and gray (`ForgeHarnessToolInterrupted`) for a cancelled or interrupted one. The heading once carried only failed and denied flags, so a call stopped by an interruption or a restart rendered as a success beneath a heading that counted it as unsuccessful. Denied calls, including approval timeouts, use orange markers without changing their retained `Denied` lifecycle. Expanding a denied tool shows its host approval reason instead of output, falling back to the provider diagnostic when no matching host decision exists.

An exchange heading's `N files changed` counts the workspace files its successful edits changed. `exchange_metrics_summary` leaves out every path that `plan::is_authoring_path` places in a plan authoring tree under the Harness state directory, because a planner writes its design and proposed files there: counting them made a plan draft read `3 files changed` while the workspace had no change.

A managed child never renders inside its parent's activity, because a live child section turned the parent's Thought fold into a dashboard that buried the parent's own reasoning. `ProjectionBuilder::content_nodes` renders each `ExchangeNode::AgentReference` as one static `◇ Spawned label · provider · model` event carrying `TranscriptAction::Agent`, which opens the child's own transcript through `select_agent`. `SessionPresentation::validate_input` accepts that activation from an older transcript revision, as it does a tool row's, while the captured block still carries the target, because running children revise the transcript several times a second and the strict revision check refused the row with "transcript input revision changed". Because a successful `agent_spawn` tool is hidden once its delegation exists, this row is the only trace of the call. `ProjectionBuilder::agent_results` adds an **Agents** root after host file changes and before the Checks root once at least one delegated child exchange is finished. Until an exchange the user stopped settles (`Exchange::cancellation_requested` is set, or the exchange is finalizing as `Cancelled`), the root leaves out the children that ended `Cancelled` at or after the start of the exchange's latest turn, the turn the stop collects: the stop cancels the running children while the status area still lists them, and the status split closes only when the exchange settles. A child that finished before that turn started, including one a restart for a configuration change cancelled, keeps its row, and so does every child that ended any other way. A restart collects the turn and its children too (`Exchange::collection` is set), but the exchange runs on, so the root draws the children it cancelled at once. Withholding every cancelled child during any collection blanked the root while a restart collected and brought it back afterwards, and a stop after a restart removed the rows of the children the restart had cancelled and shortened the heading's span; within one exchange the root only gains rows. Drawing each child as it settled made the root appear with one child and grow while the status split shrank; drawing them once all had settled still inserted the root a frame before the split closed, so the rows above moved twice. The cancelled children now join the root in the publication that settles the exchange and closes the status. Its heading counts completed children against every resolved delegation, reports the wall-clock span from the first finished child's creation to the last one's settlement (children run concurrently, so summing durations would overstate it), and sums their tool counts, tool time, and token usage. Each finished child is a leaf marked `✓` for Complete or `✗` for Failed, Cancelled, or Interrupted; it carries the child exchange's metrics summary and the same agent action, and it never expands inline. A finished child's own finished children nest beneath its leaf. The root stays open while its exchange runs and closes with it. Running children appear only in the status area, so `timing_blocks` refreshes no agent row.

Skill-read and instruction-read events remain siblings of commentary. `TranscriptRenderer::heading_marker` places their `≡` icon in the shared marker column, so their rows align with commentary while tool groups remain nested beneath their owning commentary. Instruction rows display paths relative to the working directory when possible, home-relative paths with `~` next, and absolute paths otherwise; the file-navigation action retains the full source path. Lua opens absolute source paths directly and resolves workspace-relative source actions against the session workspace. Enter opens the instruction file in a tab, and `,` in that file returns to the timeline path captured when it opened. Their persisted `ExchangeNode::InstructionRead` identity includes the original turn and full path, so files with equal names remain distinct and repeated observations of one path in a turn render once. Wrapped labels use the same event-fold handling as other timeline notices. Disposable state version 64 adds the normalized instruction-read event and timeline node; persistent settings remain outside the version namespace.

Live check headings keep the configured check title separate from explicit test selection. A single selected test appears using only its name; multiple IDs show a selected-test count. The complete IDs remain unchanged in execution and check details. `append_checks` renders one row per selected command and appends the selection, live progress, and the latest failure output to that row, separated by ` · `. A run selects its commands when it starts, so the check tree reaches its height in one step and each row changes its text in place as its command starts, reports progress, and finishes. Detail rows under each command once appeared when it started and disappeared when it passed, and the status split changed height several times within a second of checks starting, scrolling the transcript beside it. A row wider than the window still wraps, so no detail is dropped.

File writes in one activity section share a `Changed N files` node that composes reported hunks into an original-to-final diff, without reading the workspace. Expanding a diff node replaces its body with saved diff rows that carry no transcript nesting, so `replace_tree` in `buffer/session/diff_view.rs` places them one level under the heading they belong to, wherever that heading sits. Copilot reports a created file with one added row per newline-separated segment of its content, so `copilot/file_change.rs` drops the empty final row that follows the content's last newline; without that the node counts one line more than the checkpoint comparison does. Failed and interrupted edits keep their diagnostic but never count as changes. Commands, formatters, and generators stay ordinary tools, because their filesystem effects come only from checkpoint comparison.

## Node state and paging

`NodeMap` owns the expansion choices, node incarnations, and output sources for one open presentation. `NodeState` travels inside block metadata, so one publication changes text, node state, and visible ranges together. Lua sends `set_expansion`, `load_more`, and `retry_loading` actions with a view sequence and node generation, and every window showing the presentation shares the choice. A newer action supersedes an older one in flight, and a superseded answer does not synchronize the replica, so `set_section` sends nothing when the same transition is already in flight for that node generation. An editor that repeated the expansion before each answer arrived once kept the section collapsed although the host had opened it, until an unrelated session read happened to synchronize the transcript.

The timeline has no aggregate byte, row, or block limit. Only individual deliveries are bounded: tool output arrives in 16 KiB source chunks with an initial 64 KiB formatted prefix, and expanded bodies load two window heights at a time in 64 KiB pages, with at most eight section requests per viewport pass. A failed section reports once and waits for an explicit retry.

`ToolOutputView` keeps the ANSI parser across deltas, and `ToolOutputSnapshot` shares output storage with separate output windows without copying or reparsing. `BufferText` shares immutable packed rows through `Arc`. Fenced code is published first and highlighted later by `TranscriptSyntax` jobs, each with a 10-second deadline, so highlighting cannot delay text.

Each native item keeps its checked identity and original thread/turn ownership through reload. `ItemStart` fixes the item family. `ReasoningKind::Full` and `Summary` stay distinct in durable history and never become commentary. Assistant prose preserves explicit unclassified, commentary, or response interpretation. An open transcript updates the block of unclassified prose on every delta exactly as it does for classified prose, because an adapter such as Claude Code or ACP classifies a message only when a later event or the end of the turn settles its role. Reasoning has no transcript block, so a reasoning delta changes the transcript only through the status row's own `Replace` operation and never re-projects the session. A `MessageCompletion` replaces accumulated deltas; an interrupted snapshot keeps its `Interrupted` state in durable history and never becomes a final answer, and an interrupted response leaves the transcript under the rule in [Exchange content](#exchange-content). Positive native user-message items retain their sender treatment and any matched submission association, so attachment references stay in the existing registry rather than copied into event payloads.

A configuration change during a turn interrupts that turn and restarts the request as a new turn in the same exchange. The interrupted turn's partial response leaves the transcript like any interrupted response, while its commentary and tool activity stay. `ProjectionBuilder::content` renders a `◇ Resumed` row before the first part of a turn that follows a turn finished `Interrupted`, and only when a part of that interrupted turn is still displayed, so the surviving activity does not read as the start of the restarted answer. A native echo of a Forge submission keeps its turn evidence but gets no transcript node, because the broker already rendered the admitted prompt, and the internal resume, rollback, and continuation submissions never appear as user rows. Task starts and task continuations render through `ProjectionBuilder::task_notice` as one notice block whose Harness-authored provider input sits in a closed fold, because the user's own words are the start title or continuation reason and the instruction text only explains what the provider received. A continuation once rendered its input as a separate unfolded block, which filled the transcript with plan JSON and resume instructions on every phase hand-off. Providers that echo such input without a submission identity are recognized by the exchange prompt the echo repeats, so the echo adds no second copy.

Approval-timeout continuations keep their original request reason, target details, complete command sources, and associated tool arguments in the notice body. The coordinator retains every expired request until consumption; admission persists this human-facing body separately from the provider's unchanged continuation guidance, including task continuations.

A committed conversation rollback publishes `interaction_rolled_back` together with the `document_changed` patch that removes the rolled-back exchanges; the event alone only refreshes session state. The patch removes the session rows recorded during those exchanges too: a task finish, configuration failure, or compaction row is a session-owned event, so the rollback commit re-owns each one created since the first rolled-back exchange began to that exchange, and `TimelineEntry::build` drops events whose owner is retired. Without that step a rolled-back goal left its `Goal completed` row behind. The rollback itself records no `Goal cleared` row when it removes a goal whose start it rolled back.

Tool descriptor refinements update the same item without changing its family. Final descriptor and output snapshots replace prior content only when supplied. Output appends and replacements remain distinct, and repeated final snapshots must agree. Display identities use structured turn/item addresses; late output and verification links cannot be rebound through a concatenated key or the newest turn.

`TimelineEntry::ObservedAgent` renders native child summaries, their independently owned exchanges, and nested native children. `TimelineProjector::with_observed_agents` attaches a native child whose delegating exchange has a top-level entry to that entry's `agent_by_id`, and the exchange draws it at the end of its Thought section, so the row stays where the child ran, before the answer, while the turn runs and after it settles. A child whose delegating exchange has no top-level entry remains a top-level entry ordered by its creation time. A rollback keeps the exchanges it removes as rolled-back history that the timeline does not draw, so `with_observed_agents` also receives the session's exchanges and drops a native child, with its nested children, whose delegating exchange is no longer current; without that check a rolled-back subagent stayed behind as a top-level row after the last kept exchange. It retains explicit public native parent IDs separately from host execution-owner IDs. Unknown ancestry remains unresolved rather than being assigned to the current parent. An unavailable observation shows its last native state and retained history without a running timer or a fabricated successful end. Native child entries have no managed-agent control action.

Harness retains each provider's checklist on its exchange, but nothing displayed it, so the progress it records stayed hidden. `ProjectionBuilder::provider_checklist` renders the canonical `Exchange.checklist` snapshot as **Provider-reported checklist** after activity and before host file changes. The label separates it from Plan/Execute/Goal lifecycle and from verified check results, and checking off every entry completes no Harness task or gate. The heading reports completed entries out of current entries, the provider's checklist name, and the superseded count. Each current entry shows `[ ]` pending, `[>]` in progress, `[x]` completed, or `[-]` superseded, without inferring state from tool success or message text. Block identities derive from the exchange ID and the tracker's stable entry IDs, so refreshes and reopened sessions rebuild the same blocks from persisted state without querying the provider. Superseded history stays in the snapshot and appears only as a count. The fold closes when the exchange finishes, an absent or empty checklist adds no section, and an interrupted turn leaves remaining entries in their reported state.

Each committed host callback's file diff appears as **Host file changes** after activity and before results. Its identity includes the original scope's exchange and a digest of that scope and exact host call ID. The view remains independent from native file-change snapshots, including when the host effect arrives before the matching native transcript item.

## Check results

Internal check-result deliveries retain receipt and replay evidence but have no standalone transcript row or status section. The Checks categories show their outcomes. Rust schedules delivery directly from its internal inbox; Lua does not schedule delivery.

A response followed by an internal check-result input remains inside the exchange's Thought fold, rendered as commentary alongside the resumed work. The latest response stays outside the fold. The layout derives this boundary from retained inputs without changing provider message roles; user replies and question answers preserve their existing response boundaries.

An active check is status, not history. `TimelineStream::update_checks` replaces only the status during a run, and it removes the status atomically when it inserts the final result. Completed results form one Checks root that groups runs by Formatting, Lint, Type checking, Tests, Builds, and Custom, then by source file or target. The root and category summaries count distinct definition IDs using each definition's latest executed command state, independently of selection paths and test-result rows. Test totals use the latest outcome for each definition-and-case identity; rerunning a case replaces its outcome without increasing the total. Runs count every executed command, including prerequisites and failed executions, while pending and skipped commands count as no execution. Summary rows show passed ratios, optional test ratios, total runs, and duration without separate failed or attempt counts. Expanded Run rows preserve every original outcome. The supervisor reads an optional generic JSON report from callbacks and never parses runner output itself.

`CheckSupervisor` holds admission and records under one lock, and the active run owns the source-work permit until its processes are collected. Process cancellation runs in an independent task, so blocked output cannot delay termination. `CheckPublication` coalesces intermediate snapshots in a separate persistence worker and flushes the terminal snapshot before the result returns. Automatic repair reopens the owning exchange through a dedicated transition that keeps its prompt, usage, and checkpoint.

## Status

`SessionPhase` projects exactly one visible phase, and `buffer/status.rs` combines it with optional `CheckActivity`. Rust publishes the complete normalized reasoning preview with its commentary decoration when `status_thoughts` is on. The active turn selects its newest nonempty summary, retaining the preceding readable summary while a new section is empty or whitespace-only. A new turn never inherits the previous turn's preview. Lua places it after the primary label and command hints, separated by `│`, and clips only the displayed thought to the remaining window columns. The controls keep their space, and a row with no remaining space omits the thought. Rust derives elapsed time from its own start timestamp, and Lua supplies only the one-second sync cadence.

`CheckActivity` captures every selected command in execution order, including queued and terminal states, from the existing run records. This activity is reconstructed for presentation and is not a persisted state format. The check tree expands each running command into its structured progress and latest output, collapses successful commands to their result, and retains unsuccessful commands' reported causes. Completed timestamps freeze command durations. During preparation between commands, the timeline retains the preceding tree for the same run until its successor starts. Checks form a root while the model is idle or a branch beneath its active phase; Lua appends pending questions as sibling branches and preserves the connecting stems.

`TimelineEntry::Status.agents` lists every unfinished managed child exchange as a `StatusAgent`. `timeline::running_agents` builds the list from the timeline's `AgentLifecycle` entries in delegation order, once per child exchange. It runs at the observation snapshot and after every `TimelineStream::update_live` replacement, and `update_message` reruns it when a child message arrives, so a child's reasoning reaches its own row without touching the root preview. Each snapshot keeps the child exchange's clock and tool metrics, so elapsed time and tool time advance with the status's one-second tick, which a non-empty agent list enables. `append_agents` renders one row per child: a `⠋` spinner, elapsed seconds, the label and selection, the shared `successful/total tools · time` label, and the newest reasoning summary when `status_thoughts` is on. It never substitutes commentary and leaves the column empty when the provider reports no summary. The rows stay unwrapped so the spinner and thought columns are exact. The thought carries `ForgeHarnessAgentThought` rather than `ForgeHarnessCommentary`, because `status_hint.lua` merges every commentary row into the root preview; Lua instead clips each agent row's thought to the window and drops it when no room remains. An idle root shows `Agents · N running` as its primary row, and a root waiting for agents or stopping lists the rows directly beneath its primary row: a branch heading added by the interrupt made the status one row taller just before the cancelled children left it. Otherwise the rows nest under an `Agents · N running` branch after the checks branch, whose heading then becomes `├─` so the stem stays open.

Test progress keeps the current phase message on the same row as its phase, such as `Building · Built forge-diff`. A known test inventory does not replace the Building label before execution starts. The adapter clears the build message when the phase changes to Run, and the status then displays finished and failed test counts.

Formatting progress appears only when the adapter reports a known file total or at least one file outcome. Without that evidence, the running check's row keeps its title and elapsed time without a zero-count detail.

Check status and `check_status` share the latest-message selector. It removes terminal escapes and skips diagnostic borders, source gutters, and annotation rows, so a closing error frame cannot replace the preceding message. Complete output remains unchanged in the retained log.

`WorkflowActivity` builds lifecycle text from `LifecycleAction`. Started enters a task or phase, Continued starts another automatic exchange, and Resumed restarts paused or interrupted work. The status row's `BlockMetadata.status` carries its row, animation flag, hint context, and a `handoff` flag, and Lua reads these from committed metadata, never from label text. `handoff` is set while the phase is the predicted hand-off (`WorkflowActivity::HandingOff`, rendered as `Working`), and `Reveal:publish` adopts a settlement that arrives with it as seen instead of revealing it, because the queued successor replaces that exchange at the tail a few owner steps later. Rust marks each running check's icon with a `ForgeTimelineStatusSpinner` decoration after wrapping. Lua maps those byte positions through its indentation and question branches, then uses one timer per transcript to update every spinner extmark at 67 ms intervals. Check-tree markers use the shared `◐`, `◓`, `◑`, `◒` sequence at 120 ms per frame, also used by the `/mcp` loading indicator; the main phase retains its Braille spinner. The timer leaves buffer text unchanged, clears retired markers on publication, and stops when the status window closes or is suspended. Rust renders elapsed labels and refreshes them only inside a sync, and a silent tool or held provider response emits no host events. Each clock that a running label formats starts at its own instant, so `SessionPresentation::sync` measures `LabelDue`, the earliest instant at which any label shows its next whole second, refreshes the labels once that instant has passed, and returns the remaining delay as `activity_due_in_ms` (also on open). `StatusView:schedule_refresh` keeps one timer for that delay and requests a sync when it fires. Two independent one-second gates, the host's and a poll on the spinner tick, once sampled the clock every 1.04 to 1.08 seconds and skipped a displayed second whenever the drift crossed a boundary; the measured deadline changes each label within a timer tick of its boundary and never skips one. A sync with nothing due returns an empty patch. Neovim draws no window while Command-line mode reads a line, so a status, transcript, or picker countdown changed by a timer or a host event stayed frozen while the user sat at a `:` prompt. `forge.infra.command_line_redraw.request` flushes the pending screen updates once per main-loop turn while the editor is in Command-line mode; `forge.buffer.apply_async` calls it after each applied publication, `StatusView` after each render and spinner frame, and the picker after each countdown tick.

The exchange owner reconciles the native timeline and status document from the same committed cancellation snapshot before publishing its state notification and document wake. Settlement must update that document even after retraction removes the provisional exchange; otherwise Lua can report an idle session while the native status document still renders cancellation in progress.

A finished exchange alone resolves to `SessionPhase::Idle`, and the owner claims the next queued message a few steps later. Publishing that idle phase closed the status split and reopened it at every hand-off, so `BrokerObserver::hand_off_phase` substitutes `Working` with no running clock, which `buffer/status.rs::primary_text` renders as `Working` without a duration because the successor publishes the first clock (a `Working · 0s` row followed the finished turn's clock, then jumped to the successor's), while `task_successor_pending` or `successor_turn_pending` (`exchange/input_readiness.rs`) holds. A task reserves its next turn in task state when the finished turn's evidence is applied, and that continuation becomes queued input only after the finished input settles, while an Execute task's verification checks never become queued input; `task_successor_pending` reports such reserved work from the committed task: a running task whose entry or continuation is still pending, whose next action matches the work, whose source exchange completed, and which no required question, undelivered answer, queued user message, suspended queue, pending approval, or collecting check run holds back, which are the conditions `task_input::reconcile` and `OwnedTaskCheckRun::eligible` apply before starting it. A reserved turn reads as the hand-off. Reserved checks read as `WorkflowActivity::ChecksStarting`, whose row is the finished turn's `Working`, because no exchange replaces the finished one and the rows the run will show exist only once `HarnessBroker::begin_owned_task_checks` prepares its first record, after the owner admits the check work and after this phase was published; that substitute applies only over an idle phase, since a recorded run already gives the execution a `Checking` phase of its own. Run progress reaches the presentation only through `TimelineStream::update_checks`, which turns a `ChecksStarting` phase into `Checking` in the same publication that attaches the run's rows, so entering Check changes the status height once instead of first showing a one-row `Checking` heading, and which sets a `Checking` phase's clock from the run it reports, so the heading counts with the run instead of staying at `0s`. The presentation is otherwise reconciled only by a dispatched request, a foreground turn, or check progress, and settled task verification is none of these, so `OwnedTaskCheckRun` reconciles it when the verification finishes and publishes the resulting `document_changed` with its `session_changed`: a passing final run draws the implementation report and completion rows and closes the status split without waiting for the next prompt. `successor_turn_pending` is true for a user message already claimed for its own turn, or for the message `select_pending_input` would offer next when `TurnOfferGates::admit` passes; the owner's `InputOffer` handler applies the same gates, so the prediction and the offer cannot disagree. The same substitute replaces `AwaitingPlanReview` when the acceptance of the revision in review is already decided, either recorded on the plan (`SessionCommand::recorded_acceptance`) or waiting as a `plan_acceptance:` terminal request of the current task: an automatic acceptance with a saved comment first sends the comment back for revision, and the revision it then accepts reaches review only for the instant before execution starts, which showed `plan · review` and a review status between the revision and the execution. The editor's winbar keeps `plan · draft` through a hand-off (`activity.turn_awaited`, which counts a compaction only when its `turn_waiting` says a turn follows it). Both status resolvers, `HarnessBroker::live_interaction_status` and `BrokerObserver::build`, apply the substitution last, after the cancellation and pause overrides. A suspended queue, a reserved or failed message, a running check, a pending approval, an owner whose activity is `Unavailable`, and unreadable admission state each leave the phase idle, because the owner would start no turn and the row would never clear. A local directive is excluded for the same reason. A `/compact` the owner has accepted but whose attempt has not started also reads as the hand-off, because the work it waits for settles to idle first: a compaction requested while a task's check run holds session control waits for that control, and the idle phase between the checks' status and its own `Compacting` phase closed the status split for a frame. `ExchangeDriver::compaction_wait_publish` records that wait on `BrokerObserver::compaction_waiting` after it starts a command and after every wake, counting the active compaction until its attempt starts and any compaction still queued, and re-projects the status through `owner_refresh_idle_status` whenever the record changes, so the hand-off also ends when the command fails before its attempt. A committed input command can add or withdraw the predicted message without any exchange event, as an edit reservation that lands between a settled turn and the next claim does, so the owner's `finish_input` re-projects the status through `HarnessBroker::owner_refresh_idle_status` before it completes the command. An interrupt between a finished turn and its reserved work withdraws the prediction the same way: it pauses the task with no exchange to stop, and nothing else republishes the status, so `owner_cancel_local` re-projects it through `owner_refresh_idle_status` once the pause commits. Without that, a pause between an Implement turn and its check run left the spinning `Working · 0s` of `ChecksStarting` beside `exec · check · paused` until `/task resume`.

## Usage and durations

Completion stops the exchange clock before finalization and publishes the stopped clock before host effects and the final checkpoint run. The presentation renders running elapsed labels from its last snapshot and the broker's clock so a pause that stayed unpublished until the exchange settled let the heading count on through the checkpoint and settle lower, as `Thinking 5s` followed by `Thought 4s`. `HarnessBroker::present_clock_stop` measures the pause and installs the paused snapshot under the presentation lock, so every label refresh comes either before the pause instant or after the paused snapshot, and `complete_foreground_native` delivers that snapshot as an observation publication that host effects wait to drain. The label refresh follows the clock, not redraws: `presentation.lua`'s `owner.sync` adopts the status and schedules the next refresh from `activity_due_in_ms` as soon as a sync result arrives, before the transcript patch applies. Chained behind the patch, the refresh waited on every resize, which keeps the transcript re-rendering, and the timer stood still until the resizing stopped.

Interruption cleanup pauses the exchange clock rather than extending displayed model work. A restart collection, which task controls and reconfiguration use, leaves the exchange labelled `Settling` like a cancellation does: an unlabelled exchange whose turn was interrupted reads as `Paused`, so `/task clear` and `/plan cancel` showed `Stopping → Paused → Stopping` before the cleared exchange closed. `Exchange::resume` and settlement clear the label, and a committed task control that keeps its task releases it on the parked exchange through `HarnessBroker::owner_close_orphaned_parked_exchange`. Cancellation snapshots retain a stopping phase through native collection, host drain, settlement, and recovery. `ExchangeCollection::label` reads `Stopping` for both `Pending` and `Settling`, and the row stays animated through both, so the status row and the exchange heading keep one text for the whole stop; only `TimedOut` changes it. The owner commits the cancelled exchange inside a command step but records the operation's settled phase only when `cancellation_publish` runs at the next step's start, so a publication between the two would read a `Cancelled` heading beside a `Stopping` status. `BrokerObserver::build` therefore lets an acquiring, collecting, draining, or settling operation stop the session only while its target exchange is unfinished (an exchange the cancellation withdrew, as it does an output-free prompt, counts as settled), and the status reads the same committed exchange record as the heading; a `Recovering` operation still stops the session, because the provider restart outlives the exchange it settled. The operation's response timeout is a separate flag and cannot certify settlement. A stop that settles promptly adds no notice. `cleanup_progress.apply` stores every committed revision but sets the notice only when the response has timed out or the owner has reported the stop as still pending, and the notice then names the open phase; a notice per phase replaced the row's text several times within a second. `status_hint.compose` places that notice directly after the block that carries the phase row, ahead of staged input, so queued rows cannot move it. The notice survives reconnects through the durable cancellation projection; older revisions and callbacks from another runtime epoch cannot replace it. A cancel that finds nothing to stop records no operation at all: `cancellation_publish` skips an operation that has no exchange, no blocker for which `CancellationBlockers::owns_work` holds, and no expired response, because every observer otherwise showed `Stopping` on an idle session. Queued and active publications do not count as owned work. Reconfiguration keeps its separate nonanimated uncertainty status until collection or authorized resumption.

Each `Turn` retains identified `TurnUsageReport` observations with independently available input, cached-input, reasoning, and output counts. `UsageReportId` deduplicates replay; an optional `ModelCallId` correlates a call across token and timing reports. Complementary measurements merge atomically, and conflicting evidence fails. `ExchangeMetrics` reconciles cumulative snapshots against their original turn instead of charging a repeated snapshot as another call. The same rule spans exchanges. Codex opens a turn on a resumed thread by repeating the thread's last usage notification, the previous call's breakdown under an unchanged cumulative total, and an exchange cancelled before any model call once showed the earlier exchange's tokens in its heading. `HarnessBroker::stage_interaction_for_turn` therefore creates a root exchange's metrics with `ExchangeMetrics::following`, which stores each thread's latest cumulative total as that exchange's `usage_baseline`. A report whose total equals the baseline charges nothing, and an exchange that reports no newer total passes the baseline on. The baseline is persisted with the exchange because the repeat also follows a host restart; the Codex adapter's own record of the last total lives only as long as its process. A baseline only identifies a repeat: a changed total keeps the provider's per-call breakdown, because the native thread behind a Harness thread can be replaced between exchanges. Stored metrics without the field read as an empty baseline, so the addition needs no state version change. The heading's output figure and speed come from `ExchangeMetrics::reported_output_tokens` and `reported_response_ms`, which cover every turn while each reported its output count. A turn whose output is unknown, such as one a compaction or a configuration change stopped mid-answer before running it again, leaves the exchange total unknown, so both figures then cover only the turns after the newest such turn, the runs that produced the answer, and the input figure keeps the whole exchange; summing across the stopped turn once dropped the rerun's output and speed from the heading. A speed is shown only over a known duration of the same turns. `Thread.ContextUsage` updates context occupancy separately from token expenditure.

The outer display duration covers active execution and freezes during user-input and permission waits. `Exchange::observe_blocker` treats a `question:<id>` blocker as it treats an `approval:<id>` one: the first such wait pauses the clock and the last to end resumes it if it was running. `HarnessBroker::handle_foreground_question_change` records one for every pending question of the exchange that a waiting tool or the turn's stop depends on, so the model's turn, still open while `question_ask` waits, no longer counts the user's answer time, and the status reads `Waiting for your answer`. `SessionPhase::resolve_status` derives that phase from `ExchangeActivity::AwaitingInput` even though the paused clock and the question controller leave the exchange's own question fields empty; before it did, the phase fell through every working branch to idle, so the status split showed only the question list. Tool time is the union of overlapping calls on that host clock. Native model time instead uses reported call duration or complete positively observed native call endpoints. The ledger does not replace missing call timing with host elapsed time, tool subtraction, or provider collection latency; missing timing keeps native throughput unavailable. A report counts as a model call only when it carries a call identity, a duration, both endpoints, or a changed token total. A lone endpoint with none of these cannot be attributed, as with Copilot's call-end event; counting it as an untimed call erased the duration of the call it ends and removed the throughput figure from the heading. A `TurnUsageReport` with endpoints preserves them without synthesizing its `reported_duration_ms` field. Each `ToolCall` retains its first observed execution start and terminal timestamps, and a call first seen at completion shows `—`. It also records `Exchange::tool_instant` readings at those two points. That clock is the exchange's active clock while the exchange runs, so a tool waiting for approval or input pauses with the Working timer; Codex reports a command's execution start before it requests approval, and wall-clock tool time therefore counted the whole wait. After settlement the reading continues in wall time from the frozen duration, so a background command keeps counting. Host-generated tools and records without active readings use wall time.

An exchange interrupted by host loss reports a lower bound on that duration. `ExchangeMetrics::observed_elapsed_ms` holds the active-clock reading at the last recorded exchange event, and `SqliteStore::interrupt_detached_execution` settles the clock at that reading, because recovery cannot tell execution after the event from the interval in which no host ran. A turn that was silent, or paused at an approval, when the host stopped therefore shows less than its wall-clock time, and the offline interval is never added.

Tool-group headings also show the union of their calls' execution intervals, excluding idle gaps and counting overlap once. The group uses active-clock readings when every call has them, otherwise wall-clock readings for the whole group so its intervals share one clock. Missing execution endpoints leave the group duration unavailable. Individual rows still show each call's own duration.

The exchange metrics header shows input summed across every request in the exchange, followed by the cached share of that input as `(N% cached)`. The input total is token expenditure, not context occupancy, and the winbar reports occupancy.

## Transcript window and pickers

`ExchangeOpening::User` and `InputIntent::User` carry `UserInputContent`.
The broker resolves each structured reply against its submitted question revision
before persisting it, retaining the original wording, choices, selected or freeform
value, and reply identity. A user opening renders before the Thought fold; a reply
delivered during existing work keeps its chronological position. Admission selects
that position independently of provider delivery, so a required-question continuation
keeps its original exchange even when the provider starts another turn.

Rust owns transcript rendering; Lua uses `exchange_opening.notice` only to identify
task notices for composer actions. Task notices and plan execution rows (`Plan complete`, `Plan failed`, and phase rows) are drawn through `TranscriptProjection::event_row`, whose heading keeps the whole title visible when its fold is closed. A task notice whose exchange settled `Complete` or `Cancelled` with no output and no error draws only its notice row (`ExchangeRecord::is_settled_output_free_task_notice`): a goal paused before its first turn and later resumed otherwise left an empty `Thought` heading beneath `Goal started`. One shared question-group renderer produces the blue **Answered N questions** fold. `question::project` places each controller question's row after the `question_ask` call that asked it, which `Exchange::question_call_positions` finds: the n-th question operation of an exchange belongs to its n-th successful `question_ask` call, and a row whose call is not found goes to the end. The row once always went to the end, after the response the answer led to.
`QuestionHistory` merges consecutive answered groups under the same parent regardless
of submission batching or delivery through a waiting tool. Intervening visible activity,
pending questions, withdrawals, and exchange boundaries end the run. Each branch retains
its original question action. Canonical question projection checks question and reply
message identities before adding an occurrence, so an admitted answer has one transcript
owner and a later correction remains distinct.

Provider acceptance carries the typed turn into the broker; delivery through steering
never changes the content category. Answers render on acceptance while consumption
tracking remains independent. Lua staging sends an explicit content discriminator; the host resolves it into
`UserInputContent` before retaining staging. Malformed structured replies fail decoding rather than becoming text. Pending or failed
question replies use their own status section, and admission removes the staged copy by
input identity. Disposable state version 57 stores the opening and reply snapshots;
persistent settings remain outside that namespace.

The Harness controller binds a native transcript document, a native status document, and a Lua-owned composer buffer, all owned by `OpenPresentation`. The status document has its own revision, so status-only updates leave transcript rows unchanged. `HarnessStatusView` owns the split above the composer and a separate display buffer, so local notices never modify the native replica. Lua fills unused transcript space with virtual rows, so the live tail ends at the bottom without changing native text.

Switching a saved session into the current tab releases both window-bound presentations before transferring the panes. Their buffers, drafts, and queued input remain session-owned. The receiving session then binds fresh presentation, composer-height, and scroll observers to its new windows; closing only the old tab does not release those subscriptions.

`views/harness/workspace.lua` locks the transcript and composer panes. It pins both windows with `winfixbuf` and blocks commands that would close or unload them. Neovim's `:windo`, `:bufdo`, and related list commands split a pinned window whose previous window is also pinned, and they leave that unowned split focused. Netrw runs `:windo` from a non-nested VimEnter handler, which suppresses WinNew, so opening Harness from a startup command otherwise leaves a second composer window as the current window. Approval and input routing then target the wrong window. The lock therefore sweeps the Harness tab at SafeState, after every command and handler has returned. It closes any unowned split that still displays a Harness buffer and returns focus to the owned pane. `:new` and `:split {file}` have replaced their copied buffer by then, so they keep their windows.

Composer height follows wrapped rows within the configured bounds, and `smoothscroll` lets tall drafts scroll within one physical line. If the whole draft fits, the viewport starts at the first line, which stops Insert-mode scrolling from hiding the top of a short draft.

The status split pins its viewport at row one and preserves the transcript's position when resizing. `StatusView:resize` measures the composed text in screen rows and uses the smaller of its height, the available window space, and 12 rows. The same rule applies during cancellation, so the split shrinks as child rows disappear. The separate status-details view retains the complete content and supports normal scrolling.

A submitted message likewise moves only forward through the status split. `input_state.render` places every unsettled message in one of four lists. Only the host knows whether an automatic submission starts a turn, steers the active one, or waits, so an unclaimed message that has not demonstrably waited stays in `pending_submit`, which no view stages, until the owner claims it into `pending_steer` or a turn. Guessing from the editor's view of the session drew prompts submitted just after a cancellation, and every steer, as queued follow-ups for the moment before the claim. `queue` holds only a message the user queued, one that failed or is reserved for an edit, any message while the queue is paused, a message another view submitted, and an automatic submission still unclaimed after the notice delay. Input the host produces for a task, such as its planning or continuation input, counts as an automatic submission: an idle owner claims it at once, so it too waits out the delay before it is drawn. A message the editor is removing, an emptied edit or a retracted prompt the composer can take back, is drawn in no list while `input.removing` holds its id, so the row never reappears while the host confirms the removal. A message that waits is staged from `queue` under "Queued follow-up inputs", and once shown it stays shown: when the owner claims it for a turn it moves to `pending_handoff`, which the controller stages ahead of `queue`, until the host accepts it. The exchange that carries its prompt lands first, and `history_input_ids` drops the staged copy in that same publication, so the row hands over to the transcript without a gap. A submission still unsettled after `submission_notice_delay_ms` (500 ms) joins `queue`, labelled `[submitting]` while its request is unanswered: an owner holding commands through a stop or a provider restart answers late, and the composer was already cleared. A submission claimed within the delay never renders a pending row. A locally unconfirmed submission remains in the staged queue, where it cannot be edited into a new submission. An automatic submission still unclaimed after the delay while a provider turn runs (`activity.turn_running`) is a steer the host holds until the provider reports that turn, as it does while the provider is still starting it, so `notice_overdue` enters it in `waiting_steer` instead and `render` lists it in `pending_steer`, labelled `[waiting]`, rather than under the queue. It joins `queue` only when the owner holds input: the queue is paused, the entry failed or is reserved, or the status reads `awaiting_approval`, `waiting_for_agent`, or `stopping`, which `status_changed` re-evaluates when the status changes. Compaction between turns has no steering target, so a prompt held during it waits with the queue. A turn that ended before the steer reached it starts the message as its own turn, and the row stays through `pending_handoff`.

A steering message has exactly one visible place in each publication, and the transcript holds it only once its provider reports consumption. `update_staging_block` in `buffer/session.rs` builds the "Steering active turn" section from two sources in this order: steering that `Exchange::awaiting_inputs` lists for the open top-level exchanges, then the messages Lua staged. Acknowledgement creates the durable node under the staged message's ID, and `history_input_ids` already filters a staged copy whose node exists, so the row stays in the section without moving; the section is built even when Lua has staged nothing, which is what a reopened presentation shows. `presentation.set_staging` publishes staged steering immediately; an earlier 100 ms reveal delay hid the section for almost the whole interval it was meant to cover. `Exchange::displays_node` excludes an `AwaitingConsumption` input and a consumption anchor from the exchange layout and from `Exchange::content`, so neither renders nor marks where a response begins. Consumption moves the message from the section to its transcript row in one publication. Consumed steering displays the message text with its prompt styling and no `Steering:` prefix. An `Unconfirmed` row renders as `Steering (not confirmed read)`.

A failed staged input may still require recovery after the transcript displays its text. The status keeps its recovery notice and the transcript keeps the prompt. The retry key opens recovery choices for unconfirmed input and can discard the queue entry without repeating the message.

`HarnessResponseReveal` observes the latest top-level exchange's committed node lifecycle.
After transcript, status, local status layout, and Markdown decoration publication, a new transcript
revision in a live exchange follows the tail when the owning composer window is
focused, including tool activity before any response text. A permission review or
other floating popup whose previous window is the composer counts as composer focus,
because the user who was following the stream did not move to the transcript; a
popup entered from the transcript leaves the reader's position alone. Focus is checked at
publication, and unchanged revisions do not replay navigation. The Markdown adapter
settles navigation from the renderer's completion callback, after wrapped tables
have installed their replacement rows. A newer transcript revision or timeline
invalidates an older callback; no cursor or viewport snapshot crosses that wait.
Focused transcripts
retain the shared cursor and selection preservation contract.
A PlanReview acceptance or revision request is an explicit submission, so on success
it returns focus to the composer and positions the transcript at its tail, exactly as a
composer submission does. Closing PlanReview without a decision restores the previous
window and position.
A newly settled exchange reveals its response only when focus is outside the transcript. Each visible window measures from the exchange's prompt through the tail in screen rows, including wrapping and the winbar. An exchange that fits aligns to the bottom. A taller exchange places its prompt at the top, exposing the beginning rather than the end of the response. When steering was consumed mid-exchange, the newest steering row replaces the original prompt as that anchor, so the reveal starts at the reply to the steering instead of the earlier answer. `HarnessResponseReveal` recognizes such rows by their `ForgeHarnessPrompt` marker. An unconfirmed steering row keeps prompt styling through its decoration, but `TranscriptRenderer::unconfirmed_prompt` gives its marker the `ForgeHarnessUnconfirmedPrompt` capture, which links to the prompt highlight, so no reply is presented as answering input the provider never reported reading. Folded responses retain their positions. Initial adoption and timeline switches establish a baseline without replaying navigation, and skipped reveals are consumed rather than deferred. The one exception is an exchange that settles while no window of the current tab page shows the transcript: a hidden tab still synchronizes, so `HarnessResponseReveal` records the exchange as `deferred`, and `owner.hasten_displayed_refresh`, which runs on `TabEnter`, publishes it again once the transcript is displayed, under the same focus rule.

Math rendering is an optional integration. `forge.integrations.markdown_math` loads the editor's `markdown_math` module through `pcall(require)`. When the module is present, its handlers convert display and inline math, and `markdown_text.lua` normalizes math delimiters. When it is absent, render-markdown's built-in handlers render math unconverted. A `markdown` or `latex` handler configured in render-markdown's `custom_handlers` takes precedence over both, and `:checkhealth forge` reports which path is active.

The transcript is read, not edited, so Harness disables `render-markdown`'s anti-conceal: the cursor row stays rendered, and an equation or emphasis span never reverts to its source when the cursor enters it. `render-markdown` separately reveals a row it replaced with virtual lines, such as a wrapped table row, because a hidden row has no cell to edit. `render/harness/markdown.lua` overrides that rule too, because the reveal changes the row's height: each cursor move through a wide table shifted the text below it and moved the scroll boundary. The cost is that the cursor on a wrapped table row sits on a hidden buffer row, so Neovim draws it on a neighbouring row.

Row heights must not change under a resting window. A rendered row differs in height from its source, and both layers render only near a window: `markdown.viewport` selects the messages within one window height above and below the visible rows, and `render/harness/markdown.lua` widens the span `render-markdown` renders from ten rows beyond a window to one window height, rendering again once a window comes within half a window height of that span's edge. A page or half-page scroll therefore reaches rows that are already rendered. A jump farther than that, such as from the first row to the last, still lands on source rows and settles when the render completes.

Two events change heights or the rendered span without a Markdown pass. A scroll that moves no cursor and keeps the same messages near the window skips the pass, so `render_markdown` calls `markdown.follow_view`, which has `render-markdown` render the approaching rows. A render changes heights without scrolling, so `render_markdown` applies `layout.clamp_scroll` to each transcript window when the render settles, which removes the empty rows a shrinking tail would otherwise leave below the final row until the next scroll.

The Markdown pass runs only when it has something to change. `render_markdown` skips it while the visible messages, their versions, and their rows equal those of the last pass, even though the buffer changed elsewhere, as it does for streamed tool output and status ticks. The exception is rows inserted exactly at a message's end, which stretch Tree-sitter's included region over them; `markdown.current` compares the parser's live regions with the message ranges and forces a pass when they differ, or when the previous render has not settled. The handler copies a mark only when it clips, shifts, or pads it.

Harness Markdown handlers clip decorations to the current message ranges before `render-markdown` caches them, because incremental parser trees can otherwise restore deleted list bullets onto a separator. `render-markdown` numbers each list item by walking all of its preceding siblings, which makes one render quadratic in the list length and never terminates on a sibling chain that revisits a node; either blocked the editor thread while the transcript re-rendered. `render/harness/markdown.lua` therefore replaces `Node:sibling_count` with a walk that memoizes positions for the current parse and stops at a revisited node.

Transcript windows soft-wrap raw Markdown rather than hard-wrapping it in Rust. `views/harness/layout.lua` owns the shared `transcript_wrapping` options, whose `breakindentopt` `list:-1` indents each continuation by the width of the buffer's `formatlistpat` match, so a wrapped bullet or numbered item hangs under its text at every nesting level. `forge.decorations` applies the same match when it extends full-width backgrounds across continuation rows. `render-markdown` replaces each wrapped table row with virtual lines anchored above the next visible row, and a table that ends the buffer has no such row; the window cannot scroll to lines anchored past the final line, so a window following the response end loses the table's body rows and bottom border. `render/harness/markdown.lua` therefore re-anchors those groups below the last visible row. Within a selected Markdown message, a rendered table includes all its rows rather than only rows intersecting the previous viewport. This keeps column widths and replacement height independent of tail positioning; newly streamed rows can still change both.

A tab label stores no session name. `views/harness/tabline.lua` resolves each tab at render time to the Harness view whose transcript window lies in that tab and shows that view's transcript buffer, then prints that view's session name, truncated to 30 characters. `/sessions` can move a view's windows to another tab, a background view can receive a rename, and a session can be deleted. A copied label went stale after each of these events, so the derived label changes at the next redraw instead. `controller.refresh_winbar`, session deletion, and history clearing call `tabline.refresh`. A tab without a Harness transcript falls back to its buffer name. The user's tabline returns once no tab displays a Harness view.

Only the transcript window owns the winbar. A trailing `*` marks a model, thinking, or speed change waiting for current work to stop. Configured defaults and requested overrides remain separate from a turn's confirmed model. The turn starts with no confirmed identity and updates it only on `Turn.ModelResolved`; absent native confirmation stays unavailable. The host translates that original turn's metadata into editor notifications without exposing native provider events to Lua.

`views/picker/` owns every compact Harness decision surface: one state and layout model, a renderer, and a float anchored to the bottom of the transcript and composer. Structured rows use stable field IDs. The picker hides the terminal cursor through a paired global `guicursor` transition and restores it afterward. Window-local highlighting cannot hide a focused terminal cursor, so keep this transition. Because `guicursor` and Insert mode are both global, the picker shows the cursor again when the user leaves its tab, and when its tab is entered with the picker focused it leaves Insert mode and hides the cursor: otherwise returning from a composer that was typing put the picker into Insert mode, and its hotkeys edited the unmodifiable list and raised E21.

`/sessions` previews sessions in the transcript window without taking a lease. Each visited session has its own transcript buffer, and `session_navigation.lua` resumes the session on `BufEnter`.

The picker float covers the lower rows of the transcript window, so a preview that rested its final row on the window's last row would hide the latest exchange behind the picker. The picker reports the rows it leaves uncovered as `preview_height` with every selection change. `session_picker.lua` passes that count to `SessionPreview.render`, and `layout.position_tail` rests the preview's final row on the last uncovered row. The preview's scroll boundary reads the same count through `layout.attach_scroll_boundary`; a boundary measured against the whole window would pull the tail back behind the picker on the next scroll event. `SessionPreview.open` clears the window's `scrolloff` for the preview's lifetime so the cursor margin cannot move the tail, and `SessionPreview.close` restores it. The host builds a preview from the session's last 20 timeline entries and keeps their final 200 rows (`preview_lines`), so the preview always ends where the session ends and a long session loses its earliest rows instead.

The `/undo` picker lists exchanges in transcript order and uses the shared picker's initial selection and viewport to open at the newest exchange. Navigation stops at the ends of the list, so Up moves toward earlier exchanges in both the picker and the Main transcript. The presentation resolves the opening by block identity, marks its first row, and uses the picker's uncovered height when scrolling and clamping the window. It opens folded top-level responses in that exchange through the normal section expansion request, so the host supplies the full text and retains the expansion for the presentation. The picker retains focus, and closing it clears the mark and restores the prior transcript position.

`session_navigation.lua` keeps a closed or displaced view's buffers in `state_by_session_id` so a later resume restores its transcript and draft.

Choosing another session in the current tab (`/sessions`) must draw the target once. Swapping buffers into the visible panes and opening the target's presentation there drew each intermediate state: the session being left without its decorations once its presentation closed, the target's raw Markdown from its first row, then from its last, and finally the rendered view. `switch_in_place` instead opens the target, a retained view or a new one with its own buffers, in a hidden float over the transcript window (`layout.open_hidden_transcript`), bound to no composer. The source keeps its panes, presentation, and selection while the target's presentation opens, renders its Markdown, and positions itself there. `HarnessPresentation.when_rendered` then calls `complete_switch`, which in one callback releases the source's presentation, gives the composer window the target's composer buffer, converts the float into the transcript split and closes the source's transcript window (`layout.place_transcript`), binds the target's presentation to the composer (`bind_composer`), and closes the session picker through `on_settled`. The picker and its preview therefore stay on screen until the target replaces them. A switch can finish while the user works in another tab, as a provider switch started in one tab does when the user moves on before the host answers. Placing a buffer in any window runs that buffer's `BufEnter` autocommands even when focus never reaches the window, and each view's activation autocommand selects its session, so `place_in_background` suppresses that selection whenever `complete_switch`, or `activate` without focus, places buffers into a tab the user is not in. Without it every later submit and `:ForgeHarness` in the user's tab acted on the other tab's session: a submit read that session's empty composer and did nothing, and `:ForgeHarness` focused the other tab. Whether the user is in the source's tab comes from `session.selected_harness()`, the view the user last selected, never from `session.harness`: `forge.client` delivers every reply to a session request with that session's view active, and the target's transcript usually opens, and so completes the switch, inside such a reply. Reading `session.harness` there treated the target as the user's selection, placed it behind the tab the user was looking at, and left the source selected, so the first submit typed into the new composer went to the session being left and, on a provider switch, switched the host back to that session's provider in another tab. For the same reason `controller.with_state` and the client's reply scope keep a selection made inside their scope instead of restoring the view that was active before it. The session left behind stays retained with its buffers and draft. A target that a newer switch supersedes, or whose view is deleted first, is abandoned with its float; a target whose transcript fails to open is still shown, with the failure its presentation reports. A session displayed in another tab moves into the current tab the same way, and its former tab closes. A hidden transcript window belongs to no tab, so `valid_view` and the tabline ignore it. Deleting a session calls `session_navigation.session_deleted`, which finds every view of that session through both registries and the buffer map, stops its event subscription and presentation, closes its tab, and wipes its buffers. The host reports a deleted session's document reads as `session_not_found`, which `presentation.lua` treats as terminal, so a view left open stops reading and shows that the session no longer exists.
